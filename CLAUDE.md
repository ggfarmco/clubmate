- Every change that adds, removes or rebinds a keyboard shortcut also updates `docs/shortcuts.md` in the same commit.
- Every change to a view in `client/Clubmate`, `client/Companion` or to the UI a plugin renders follows the `clubmate-ui` skill (`.claude/skills/clubmate-ui`) and its design language (`design/language/`, `design/companion/`); it is done only after `make app` builds and the result was looked at, or the report says "visually unverified".
- A feature or fix lands in `main` as one squashed commit (`git merge --squash <branch>`, then one conventional-commit message); no merge commits and no intermediate WIP/fixup commits on `main`.
- Follow "Working in Clubmate" from the Clubmate MCP instructions (`internal/mcp/clubmate.md`): independent parts of a task run in parallel as child Clubmate sessions (`mcp__clubmate__agents_new` with a branch, loaded via ToolSearch) so they show in the Agents tree, never the built-in `Agent`/Task tool for work that edits files (a broad read-only search may go to the built-in `Explore` subagent, which returns only its conclusion); repeated or delayed checks go to `cron_add`, not a polling loop.
- A plan names, for each task, the files and functions it touches, so the builder starts editing instead of searching; a child's prompt carries that list.
- Tasks of a slice with an integration branch branch off that branch, not `main`: the session that starts them works in the integration branch's worktree and lets `agents_new` with `branch` make each task branch (no `git branch` by hand), so the task branch's base is the integration branch and the child calls `git_land` without `into`; the `base` (parent's branch) land gate reviews that landing.
- A conversation with the designer (Claude Design through Chrome, Artifact rounds) runs in its own child, which hands back only the ruling and the paths of the boards it saved; the orchestrator never drives the designer chat itself.
- Size a child's task to between about 40 and 150 tool calls: a smaller piece goes to a child already working nearby or stays with the caller, since each child pays its start, its review and the orchestrator's turns; split anything bigger into children that run one after another, and a visual check of UI (`make app`, test-app shots, the Claude Design boards) runs as its own child after the code is committed, not inside the builder. Every child prompt asks it to send independent reads, greps and `git` queries together in one message instead of one per turn, since each turn re-reads the whole context.
- Every child is started with `kind` (feature|fix|refactor|docs|test|ui-check|review|spike) and `size` (your estimate: S ≤60 tool calls, M 60–150, L >150) in `agents_new`, and with `model: "auto"` when the choice of model doesn't matter for the task (Clubmate then picks one at random for the model experiment), an explicit model when it does (`opus` for a review, a plan check, a spike or hard multi-file work; `fable` only when the user asks for it); no `[exp …]` line in the prompt.
- A behaviour that the Mac and the Companion both show (grouping, headers, collapse, counts, the echo of a sent message, transcript folding) is the same on the Mac, the iPhone and the iPad; a fix on one client lands on the others in the same commit or goes to the backlog. Transcript folding is written in `docs/agents.md` § Transcript folding.
- What a session, task or notification means to the user (needs you, waiting, asking, counts, grouping) is decided once in the Go plugin and sent to clients as a field (e.g. `needsYou` in `agents.sessions`); the Mac UI and the phone render that field and never re-derive the rule, and a rule change updates the plugin, its tests and the matching section in `docs/` (e.g. `docs/agents.md` § Needs you) in the same commit.
- Anything left for later goes into the backlog (`backlog_add`, status `todo`) before the task is reported done: deferred review findings, "Not done" items, things visually unverified, follow-ups a ruling postponed. Group related leftovers into a few tasks, each with the commit, files and enough context to act on it without the conversation; a final report names the task ids instead of only listing the leftovers.
- Every landing (a squash into `main`, or a child merging into its parent's branch) is reviewed by the repo's land gates, which `git_land` starts itself (`agents_gates`: "Landing into main" and a `base` gate, both on the `opus-review` graph); nothing is started by hand. Fix the confirmed findings and rerun the tests before landing again; deferred ones go to the backlog. A landing no gate covers gets no hand-started review.
- Tests follow `docs/testing.md`: wait on conditions through `internal/testutil` (scaled deadlines, `WaitEvents`, `Never`), never sleep or read state once after a wait; `make lint-tests` (in `make test` and CI) enforces it, and CI's advisory `stress` job reruns new or edited tests under load.
- Stop a build or test run you started by its pid (from `$!` or a pid file), never with `pkill` or `killall` and a command pattern: other sessions and the nightly graph's steps run the same `xcodebuild` and `make` command lines.
- Plugin state that a user or an agent relies on (queues, holds, verdicts, prompts sent, op ids, review state) survives a plugin and a core restart: it is stored, not kept only in memory, and a test restarts the plugin and checks it.
- A change to what an agent-visible command does, returns or refuses updates its `description` and argument texts in `plugin.json` and the matching `docs/*.md` section in the same commit.
- Every entry point that acts for a caller (cm subcommands, ui events, command run, plugin-to-plugin calls) passes `CLUBMATE_AGENT_SESSION` as the caller, and a user-only check refuses a call from an agent session.
