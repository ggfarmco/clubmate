Clubmate · Startup skeleton, round 1. Hi. This is a new question for this canvas: what a Clubmate Mac window shows while the app starts, before the Go core is up. Page `today` has board `Today` with real screenshots of today (each shot named); page `language` has the language boards (`Principles`, `Tokens`, `Components`, `Patterns`) and three target screens (`Agents-Mate-1280`, `Code-1280-Mate`, `Backlog-1280-Mate`). Draw on top of them.

1. Today. When the Mac app starts, it starts the Go core and connects to it. Until the core answers, every window shows only the centred muted text "Starting core…" on the window background (drawn on `Today`: the test app cannot capture this state, because its snapshot goes through the core). No rail, no sidebar, no status bar. In a workspace window whose store is not connected yet the text is "Connecting…". On failure the window shows the error text in the danger ink, centred, and a Retry button. After a core restart the client is in `.reconnecting(attempt:)`: the last real content stays and the status bar says "core reconnecting (attempt n)" in the warning ink. In the test app, launch to a ready workspace took 3.6 s; a slow disk or many plugins make it longer. Users read the bare text as "unfinished".

2. The direction the user chose: a skeleton of the real window. The window opens at once with its real layout (title bar, section rail, sidebar, main pane, the chat column if it was shown). The panes show static placeholder shapes in the style of SwiftUI `.redacted(reason: .placeholder)`: no shimmer, no text. When the core is ready, the real content fades in. Text appears only when start-up is slow (about 3 s or more, for example "Still starting…") and on failure (the error + Retry, as today). Apple HIG points: no splash screen; show placeholder content in the shape of the real content; no blank screen; a progress indicator only for long waits.

3. What the client knows before the core is up (this limits the skeleton). Known locally: the windows and the workspaces open in each window (`WindowLayout`, UserDefaults), the user's section order (`AppSettings.sectionOrder`, ids only), the sidebar side, the interface font sizes, the theme. Not known: the section list with its icons and titles (it comes from the plugins through the core), the selected section, whether the sidebar is hidden, whether the chat column is shown and its width, the workspace names. Showing any of these in the skeleton means the client caches it from the last run (cost: a small client cache, tag (a)). Extra windows from the last run open only after the core lists the workspaces; today only the first window opens at launch.

4. Questions for you.
(1) A workspace window in this state: the rail with the cached section icons (last run's list), or neutral rail shapes? The sidebar and main pane placeholders: per section type (list rows for Agents/Backlog/Cron, a terminal block for Code, an editor block), or one generic shape for all?
(2) The Welcome window (a window with no workspace) in this state: Today it shows "Clubmate", Open folder… ⌘O, New terminal ⇧⌘N and Recent (`mac-welcome` on `Today`). Which parts are real at once (the title and the two actions do not need the core; Recent does), which are placeholders?
(3) The hand-over: a fade, how long, and does each pane cross-fade on its own when its content arrives, or the whole window at once when the core is ready? What if one pane is still empty when the others are ready?
(4) Slow start (≥ 3 s) and the failure state: the exact words, where they go (status bar, centre of the main pane, a small line under the skeleton), and whether a progress indicator shows and from when.
(5) Reconnect after a core restart (`.reconnecting`): keep the last real content dimmed or not dimmed, or go back to the skeleton? Can the user still read and scroll it?

5. Constraints. Keep the design language (`Principles`, `Patterns`, `Components`; colour roles, not hex; the Mac font is the terminal font, monospaced; compact, keyboard first; sentence case). No splash, no logo screen, no shimmer, no spinner in the first 3 s. Placeholders use surface and border roles (for example `surface2` bars on `surface1`), never the accent. Reduced motion: no fade, a plain switch. Nothing here may need a new SDUI node: the skeleton is client SwiftUI before any SDUI arrives.

6. Deliverables. Put this round on page `r1`, at most 6 boards, 1280 Mate dark + 640 Mate light. Give 2–3 directions (A, B, C) with one line each for the pitch, and your pick with the reason. Suggested boards: one board per direction with the workspace window skeleton (1280 dark, and 640 light where it differs) and the Welcome window; one board with the timeline (0 s skeleton → ready fade, ≥3 s slow text, failure, reconnect) for your pick; a rules board with the states, timings in ms, every text, and each change tagged (a) client SwiftUI, (b) SDUI node or prop, (c) plugin content, (d) new plugin or core logic. Prefer (a).
