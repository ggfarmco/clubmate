Checkout retries

Payments · updated 08:41 by agent

How the charge step retries a provider timeout without losing the cart. Follows the payments overview and the cart store.

Why

The charge step fails about 0.4% of the time on a provider timeout. Today the cart is released and the user starts over, which costs about 30 orders a day.

How it works

  1. The checkout holds the reservation for 10 minutes.
  2. A timeout retries the same idempotency key up to 3 times with backoff 1 s, 4 s, 9 s.
  3. After the last try the cart goes back to the user with the message “Payment didn't go through”.
for try := range 3 { err := charge(ctx, key) if !isTimeout(err) { return err } } booking.roots2:30:17: error: Booking needs room: only optional fields can be left out

Decisions

Retries reuse the idempotency key, so the provider never charges twice. See the payments overview.

We keep the reservation for the whole retry window rather than re-reserving, because stock can move in 9 seconds.
