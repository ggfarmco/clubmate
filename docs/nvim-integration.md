# nvim integration

Neovim is the `editor-nvim` plugin and its Neovim section; VS Code is a separate plugin with its own section, off by default (see [VS Code integration](vscode-integration.md)). Either can be turned off in Settings; with both on, Settings → General → Default editor picks which one `editor.open` uses. `editor.open` takes an optional `focus: true` that also shows the Neovim section.

Clubmate always starts its bundled Neovim with its own distribution: lazy.nvim, snacks (picker, input, notifications), which-key, blink.cmp, treesitter, gitsigns, neo-tree, lualine, LSP configs, dap/neotest and the `0xnorimori/diffview.nvim` fork with `nrev`. It never reads or writes `~/.config/nvim` or `~/.local/share/nvim`; the only access is an existence check for the import offer.

## Neovim binary

Clubmate runs the Neovim shipped at `Clubmate.app/Contents/Resources/nvim/bin/nvim` as `nvim -u <Resources>/nvim-distro/init.lua`. Without the bundled copy (for example when the core runs outside the app), it falls back to the `nvim` in `PATH`; with neither, the editor shows `nvim not found in PATH`. Clubmate removes any inherited `VIM` and `VIMRUNTIME` and sets `NVIM_APPNAME` to `clubmate` (release) or `clubmate-dev` (every other build), so `stdpath("config")`, `data`, `state` and `cache` are Clubmate's own (`~/.config/clubmate`, `~/.local/share/clubmate`, …). nvim also gets `COLORTERM=truecolor` and, when the app's bundled terminfo is present, `TERM=xterm-ghostty` with `TERMINFO` pointing at it: nvim knows Ghostty's truecolor, undercurl and cursor shapes without asking the terminal, and programs nvim starts find the entry. nvim usually starts before a terminal attaches; its remaining startup queries are answered when one does (see `ARCHITECTURE.md`, `clubmate-session`). Its server (`nvim --embed`) already answers RPC on `--listen` while it waits for that terminal, but sources `init.lua` only once the terminal's UI attaches, so editor-nvim waits for `v:vim_did_enter` (up to 15 s) before it hooks into a new nvim or calls the distribution, the review fork included.

The app's bundled tools dir (`Contents/Resources/tools`, with `rg` and `nrev`) is appended to the end of `PATH` for nvim, terminals and agent sessions, so your own tools still win. The binary is chosen each time nvim starts; after an app update, restart Neovim (palette "Restart Neovim") so running editors pick up the new binary and distribution.

## The distribution

`Contents/Resources/nvim-distro/` is read-only and replaced by every app update:

| Path | What |
|---|---|
| `init.lua` | entry: lazy.nvim pointed at the bundled plugin dirs, then the user layer |
| `lua/clubmate/` | options, keymaps (leader `,`, see `docs/shortcuts.md`), autocmds, theme, LSP, health check, import offer; `plugins/*.lua` are the default lazy specs |
| `lua/clubmate/manifest.lua` | generated: every plugin's URL and commit, the parser list and the lock file's sha256 |
| `plugins/<name>/` | each plugin's unmodified source tree at its pinned commit, with generated `doc/tags`; `blink.cmp/target/release/libblink_cmp_fuzzy.dylib` is blink's prebuilt fuzzy library |
| `site/{parser,queries,parser-info}/` | treesitter parsers compiled at bundle time |
| `colors/`, `lsp/` | the `clubmate` and `lightowl` colorschemes, LSP server configs |
| `skill/SKILL.md` | the guide agents follow to change the user layer |

Nothing is cloned, downloaded or compiled when nvim starts, and nothing writes inside the app. lazy.nvim's checker and change detection are off and its module cache is disabled, so a long install path (a dev build in DerivedData) cannot break `vim.loader`.

## User layer

Your changes live in `stdpath("config")` (`~/.config/clubmate`, or `~/.config/clubmate-dev`) and survive app updates: `lua/user/options.lua` (before plugins), `lua/user/plugins/*.lua` (lazy specs merged over the defaults: `opts`, `enabled = false`, `keys`, extra plugins), `lua/user/keymaps.lua` and `lua/user/autocmds.lua` (after the defaults), `snippets/` for blink. Each file is optional; an error in one shows as a notification and the rest still loads. A root `init.lua` or `lua/plugins/` there (an old copied config) is ignored. Plugins you add are installed by lazy.nvim into `stdpath("data")/lazy`; that is the only download, and only for plugins you chose.

## Theme

The app publishes its Ghostty theme — Clubmate / Clubmate Light unless Clubmate's own `ghostty.conf` sets `theme =` — (name, dark flag, background, foreground, 16-colour palette) on the bus as `theme.changed` at launch and on every change, including light/dark switches. editor-nvim writes it to `plugin-data/editor-nvim/theme.json`, passes that file to new nvims as `CLUBMATE_THEME_FILE`, and calls `require("clubmate.theme").apply(t)` in every running one. It remembers the last event it handled, so a theme published while the core or plugin restarts is still picked up. Known themes (Kanagawa Wave/Dragon/Lotus, Light Owl) take their syntax from the bundled colorscheme; any other theme gets a generated scheme from the palette. Chrome groups (floats, picker, which-key, blink, gitsigns, diffview, neo-tree, lualine, notifications) follow the app's tokens. Clubmate and Clubmate Light (`client/ghostty-themes/`, staged into the bundle by `scripts/build-ghostty.sh`) are the exception: `lua/clubmate/mate.lua` sets every group, chrome and lualine included, from the design board `T-Nvim-Clubmate`, so nothing is derived from ANSI slots. If you pick another colorscheme in your layer, theme changes leave it alone.

## LSP and mason

The distribution ships `lsp/*.lua` for gopls, rust_analyzer, ts_ls, tailwindcss, sqls and solidity_ls_nomicfoundation and enables them; a server found in `PATH` or in mason's dir just works. Servers are never installed automatically. The first time you open a file whose server is missing, a notification names the `:MasonInstall …` command to run.

## Health check

`:checkhealth clubmate` lists the distribution root and lock, every bundled plugin and parser, the fuzzy matcher, the theme, your user layer files, missing LSP servers with their `:MasonInstall` lines, and the bundled tools.

## Import my nvim config

Palette "Import my nvim config" (offered once when `~/.config/nvim` exists) starts an agent session that moves your own settings into the user layer; see `docs/agents.md`.

## Bumping a plugin

1. Edit its line in `scripts/nvim-distro.lock` (`plugin <name> <commit> <sha256> <url>`; the sha256 is of `<url>/archive/<commit>.tar.gz`). A parser bump follows nvim-treesitter's `parsers.lua`; blink's `blink-lib` line must name the same commit as the `blink.cmp` plugin line.
2. Refresh `scripts/licenses/nvim-distro/<name>/` (licence files and `COMMIT`).
3. `make nvim-test`: vendors into `build/resources` and runs the distro tests against the bundled nvim.
4. `scripts/licenses.sh` to regenerate `THIRD_PARTY_LICENSES.md` (it also lists the Rust crates in blink's fuzzy library from blink's `Cargo.lock`); `go test ./nvim-distro/` fails while the licences name an older commit.
5. `make app` runs the same smoke tests against the built `Clubmate.app` and fails the build on any error.

## Review changes

Reviews open through the bundled diffview fork's host API and show in the Code section, all of it inside nvim: the two diff panes and, on the right of the review tab, the fork's review panel, 38 columns wide (a pinned header with progress and filters, the file tree as the only part that scrolls, a pinned footer with the comments, keys, Send and Copy; `:h diffview-review-panel`). The header and the footer are their own windows but never keep focus: entering one from the keyboard (`<C-w>h` from the diff at any row) lands in the file tree, `<C-w>w`/`<C-w>W` from the tree goes on past them, and a click on a checkbox or a footer action acts and returns to the window it came from. Only the Send sheet is native ([SDUI protocol](sdui-protocol.md) has the slot `editor-nvim.review`). In the Agents section, "Review changes" in a session's header and "Full diff" on an edit card open a review of the worktree against the checkpoint Clubmate took before the turn (the first turn's for Review changes): `editor-nvim.diffview {cwd, rev, session?, turn?}` switches the folder to that worktree, opens the review in its nvim with the left side labelled `Before turn N`, makes the session its opener and shows the Code section with nvim focused. The right side is the editable worktree, uncommitted and untracked files included.

Agents open reviews for the user with `editor-nvim.review {base?, head?, cwd?}` (agent tool; returns `{id, worktree, base, head}`). `base` defaults to `main`; a branch base is compared from its merge-base with head (the left winbar then reads `main merge-base ‹sha›`), a commit as is. `head` omitted is the working tree of the worktree containing `cwd` when it is passed, else of the caller's worktree (from `agents.sessions`), else of the worktree the editor shows. A branch checked out in a worktree of the repo is that worktree's working tree: editable, opened in that worktree's nvim, its nrev comments and `review.db` marks. A branch or commit checked out nowhere is its tip, read-only, compared `base...head` in the caller's worktree. The call moves the editor at once (Code section, that worktree, the review tab current), because the user asked the agent for it. There is one review per (worktree, base, head): asking again reuses the open one, makes its tab current and makes the new caller the opener. It belongs to one workspace at a time: asked for from another workspace, it moves there (the old workspace's tab closes and its Review list drops it, the Agents card follows). A review stays open until the user closes it in nvim (`q`, `,dq`); its opener, recipient and comments sent are kept in the plugin's storage by that key and come back when the same review is opened again; a review whose nvim exits is gone. When editor-nvim restarts while Neovim keeps running, it reconnects and adopts the review tabs still open there (the fork's `reviews()` hands back the `{id, worktree, base, head}` editor-nvim passed to `open`), so the next request for the same review makes that tab current instead of opening a second one. A review that another workspace's nvim already adopted keeps that owner: the same tab found in a second nvim is closed there (comments and reviewed marks live in `review.db` and come back wherever the review opens next). The open-comment count behind Send comes from editor-nvim running the bundled `nrev list --json --status all` in the review's worktree, not from the fork's `comments(tab)` (which answers an empty list when `nrev` fails); it is re-read when `review.db` changes, when the app opens the workspace again, when the review is asked for again and when Send is pressed, and a read that fails or takes over 2 s keeps the last list. Several reviews can be open at once, across worktrees, each in its own nvim tab with its own panel; "Open review" in Agents makes a review's tab current (and switches the folder to its worktree when needed).

editor-nvim talks to the panel only through the host API (version 4): on open and whenever they change it calls `set_meta(tab, {subtitle, base, changes, recipient, sent})`, so the panel's header names the opener (`Claude · ‹session title›`, else nothing after `Review`), then on lines of their own what is compared: `base` the left side (its label, plus the short sha when the label is not one: `Before turn 1 · 97a29b4`, `main`) and `changes` the right side (`‹branch› · working tree`, a detached worktree `(detached ‹sha›) · working tree`, else the head's label), its done line the default recipient of Send (the opener while it is open in the worktree, else the newest open session there, else `a new session`; worked out on open, on reuse, when a restarted editor-nvim adopts the tab and when the Send sheet opens) and after Send `M/M · N comments sent`. Send in the panel (`gS`, or a click on the button) sends the `send` event and the app opens the Send sheet; ⌘↩ does the same from the app while a review tab is current (a status bar button "Send review"; ⌘↩ is the app's, so it never reaches nvim), as long as the review has open comments. `,b` toggles the panel. editor-nvim reads `filters(tab)` (code, tests, generated, reviewed: shown and count) on every host API event of the tab, so the progress it publishes counts what the panel shows; it never reaches into the fork's internals. The fork watches the worktree's `review.db` itself: an agent's `nrev add` or `nrev resolve` outside nvim updates the panel's counts, its comment list and the comment lines in the diff, and fires `User NrevCommentsChanged`; editor-nvim only re-reads the comments for what it publishes. It also watches the worktree, so a reviewed file an agent edits turns `●` and its diff reloads without waiting for focus or a write (recursive on macOS; on Linux only the top folder). When the editor is narrower than 900pt the client asks for the inline layout and every open review (and every later one) switches to one pane: the panel closes, a one-line strip in the tabline reads `N/M · K open · ‹ file n of m › ☰`, and `,b` (or ☰) opens the panel as a drawer floating over the diff's left edge (`Esc` closes it); wide again, back to split with the panel. While a review tab is current the status hint reads `,b files · ⌘B chat`. editor-nvim publishes each review's progress on the bus topic `editor-nvim.review` for the Agents section.

The file panel starts with a review header: a progress bar and `reviewed/total`, the `+/−` totals and open comment count, and checkboxes for the code, test and generated files it holds (the distribution sets `file_panel.checkbox` to the Nerd Font boxes `󰄲`/`󰄱`, which the app's terminal font carries; the fork's default is `☑`/`☐`). Test files (`*_test.go`, `*Tests.swift`, `*_spec.lua`, `test/`, …) and generated files (lock files such as `go.sum` and `*-lock.json`, dependency directories such as `vendor/`, `node_modules/` and `Pods/`, files starting with `// Code generated … DO NOT EDIT.`) are hidden by default; `zt` and `zg` show them, `zr` hides files already reviewed. The tree shows one folder per parent directory; `t` switches to the nested folders and back, for the rest of the nvim session. The progress counts the files the test and generated filters let through. Add patterns in your layer with `file_panel.filters.tests.extend` / `file_panel.filters.generated.extend`, or per repository in `.gitattributes` with `linguist-generated` and `diffview-test`. `r` marks a file reviewed (`✓`) for its current content: the mark survives new agent turns and a different left side while the file stays the same, and turns into `●` once the file changes. Marks live in `review.db` in the worktree's git dir, so they go away with the worktree. nrev keeps `review.db` in SQLite's rollback journal, so reading comments or marks touches no file and only a write wakes the watchers on the git dir (with WAL every read created and removed `review.db-wal`, and an open review re-ran nrev and rehashed its files in a loop).

A new file keeps both panes: the left one is `╱` filler that reads "New file — nothing before ‹left side›" and every line on the right is in the added fill; a deleted file mirrors it ("Deleted in ‹right side›") and opens with the cursor on the old side; its old text keeps its syntax colours on the removed fill. Review comments are virtual lines that wrap at the pane width with a rule in their tone (an issue amber), `,rx resolve · ,rd delete` on their first line; a resolved one collapses to one faint line, and the other pane gets as many `╱` filler lines so both sides stay in line.

Reviews opened through the fork's host API (`require("diffview.clubmate")`, version 4; editor-nvim refuses an older fork with `diffview host API v4 is not available`) keep the panel open, take a `head` besides `base` (a rev compares `base...head`, both sides read-only) and side labels, and use a review profile: no tabline while the review tab is current, absolute line numbers with only the cursor line's accented, and winbars that read label, tag (`checkpoint ‹sha›`, `merge-base ‹sha›`, `editable`, `read-only`, `new file · N lines`, `did not exist`, `deleted`), path, where only the path truncates. `set_layout("inline")` switches a review to one pane with the removed lines above the added ones (their fill reaches the right edge, tabs expanded to the buffer's tabstop); it follows edits and width changes, and comments on the old side show under their removed line (read-only there: resolve them from the split layout or the panel). Its entries carry `stale`, `category`, `kind` and `old_path`, `comments` lists the worktree's nrev comments, and every event names its tab.

## Large and binary files

Opening a file larger than 5 MiB, or one whose first 8000 bytes contain a NUL byte, uses light mode: `noautocmd noswapfile edit`, so no filetype detection, treesitter, LSP or swap file, plus `syntax=off` and `b:clubmate_light = true`. The status bar shows a "light" badge for such a buffer. Other files open normally. Opening is asynchronous, so a slow open never times out the command; if nvim then refuses the open (for example E37 with `nohidden` and a modified buffer), the status bar shows an "open failed" badge until the next buffer is entered.

## Opening at a line and column

`editor.open` takes an optional 1-based `line` and `col`. `col` is a byte column, as ripgrep reports it; it is clamped to the line length and ignored without `line`.

## Quickfix

`editor.quickfix {title, items:[{path, line, col?, text?}]}` replaces nvim's quickfix list with a new one (`setqflist({}, ' ', {title})`, so `:colder` brings back the previous one) and focuses the Neovim section. It takes 1 to 10 000 items with at most 2 MiB of paths and text in all, and a `title` of at most 512 characters; each `path` is absolute (at most 4096 bytes), `line` at least 1, `col` a 1-based byte column (0 or absent for none) and `text` at most 512 characters; line breaks and NUL are rejected, and so are unknown fields. nvim creates a buffer for every distinct file in the list, which is slow, so only items in the first 1000 distinct files are kept and the title then ends in " (first 1000 files)". The command returns once the request is validated. nvim then appends the items in batches of about 40 ms each, so it stays responsive. It opens the quickfix window with `copen` after the first batch and returns the cursor with `wincmd p`. A newer quickfix request stops an older one that is still filling. A failure shows as an "open failed: quickfix: ..." badge.
