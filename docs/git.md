# Git

The git plugin owns worktrees, branches and landings for the workspace's git folders. Worktree hooks (`.clubmate/setup.sh`, `teardown.sh`) are in [worktree hooks](worktree-hooks.md).

## git.land

`git.land {path, message, into?, mode?}` lands a change as one commit. It is the landing path agents are told to use (finish texts in [agents](agents.md)); it is an MCP tool (`git_land`).

- `mode: branch` (default) squashes the branch checked out at `path` into `into` (default the branch's base when it is usable, else the repo's default branch, see below), in the worktree that has `into` checked out: `git merge --squash` and `git commit -m <message>`, so the repo's own commit hooks run. Before that it computes the result with `git merge-tree --write-tree` and fails on a conflict, naming the files; it fails when the target worktree has staged changes or the target branch moved meanwhile, and puts the index back (`git reset --merge`) when the squash or the commit fails. A commit hook that changes the committed tree (lint-staged, a formatter re-staging files) fails the landing and names the paths it changed: the branch goes back to the old tip only when the commit's parent is that tip and the branch still points at the commit; in branch mode exactly the paths the squash changed go back to the old tip in index and working tree (paths it added are removed) and the index goes back to the old tip, in index mode the index goes back to the staged change; the working tree is not touched otherwise, so unrelated uncommitted files in the target stay as they were. Then it removes the worktree at `path` (never the main checkout, never one on the default branch, and not while a terminal runs in it) with plain `git worktree remove`, no removal handlers, so the session that landed stays open, and force-deletes the branch; when the branch moved after the landing (a new commit on it), or an editor (a session of a plugin that handles `git.worktree.removing`, such as editor-nvim) is rooted inside the worktree, the worktree and branch both stay with a `note` (the editor is not asked; the landing agent leaves the worktree and the user removes it from the app, which stops the editor first), and a removal git refuses (uncommitted files) leaves a `note`. A branch that adds nothing (already landed) lands nothing and is cleaned up the same way.
- The commit message: when the land gate approved the change by a reviewer who gave a `summary`, `git.land` adds the summary, wrapped at 100 columns, as its own paragraph after `message`, before its trailer block when it ends with one (`Co-Authored-By:`, `Signed-off-by:`, as `git interpret-trailers --parse` finds them), so the trailers stay trailers; a landing with no gate, a docs-only approval or a Land anyway has none to add. When that commit fails and the repo's `commit-msg` hook (`git hook run commit-msg`) refuses the message with the summary, `git.land` commits `message` alone once more and says so in `note` ("The commit-msg hook refused the message with the gate's summary (‹first line of the error›); landed without the summary."); any other failure, or one after the call's time ran out, returns the first commit's error. CRLF line ends in the message become LF.
- A branch's base: `git.worktree-new {from}` that makes a new branch from a worktree on a branch other than the default one (and without `base: "default"`) records that branch as the new one's base in the git plugin's own storage, once for the branch (`worktree-base/<main checkout's real path>/<branch>`) and once for the new worktree (`worktree-base-tree/<worktree's real path>`); a new branch made any other way drops any record that branch name and that worktree had, a worktree made for a branch that already exists keeps that branch's record and drops the worktree's, removing the worktree through Clubmate drops the worktree's record, and a branch deletion through Clubmate (`git.branch-delete`, the cleanup after `git.land`) that leaves the branch gone drops the branch's record. A branch with no record of its own takes the record of the worktree it is checked out in, so `git branch -m` or `git switch -c` in a worktree keeps its base. It also writes `git config branch.<new>.clubmate-base <from's branch>` (or unsets it) for people reading the repo, but nothing ever reads that line for a decision: an agent can write git config, so it can't move or drop its own base. The first start of a git plugin with this storage copies, once, every `branch.<b>.clubmate-base` of the repos of your workspaces that has no record yet and then marks the import done (`worktree-base/imported`; a repo that can't be read is left out and the rest are imported; `imported` stays unset, that repo is tried again on each read of its own bases, which fail until it imports, and every minute on any read; a folder that is gone or not a repo is skipped); a base an agent rewrote before that upgrade is trusted that one time. The base is usable when some worktree of the repo whose folder still exists has it checked out. `git.land` in branch mode without `into` lands into a usable base. When the recorded base branch still exists but no worktree has it checked out (its worktree was removed or its folder deleted), it fails with `the branch's base <b> is checked out in no worktree: check <b> out in a worktree, or pass into to land somewhere else`, so the branch, which may hold the base's unlanded commits, never lands on the default branch by surprise; when the base branch is gone it lands into the default branch and `note` says `Base <b> is gone, landed into <default>.` (a branch that adds nothing to the default branch says only that nothing landed); a git error while checking whether the base branch exists fails the landing instead of taking it for gone. A storage error while reading the record fails the landing. The agents plugin reads the record through `git.worktree-base {path, branch?}` → `{base, live}` (hidden, refused to any caller but the agents plugin). The [land gate](agents.md#gates)'s hook protects a session's recorded base like the default branch.
- `mode: index` commits what is staged in `path`, which must have `into` checked out: for sessions working on the default branch itself (cron jobs, nightly runs, graph steps).
- In a repo with a [land gate](agents.md#gates) a call from an agent, into any branch, needs an approved verdict for exactly this landing (the target's tip and the resulting tree): with none it starts the review and fails with `review pending: <session>`, with `changes` it fails with the findings, and past the gate's rounds it waits for the user. A call from the user (the app, `cm` without `--agent`) is never gated.

Returns `{commit, into, source, removed, note}`.

## git.gate-tree

`git.gate-tree {repo, gate, key, old, tree, remove?}` is for the agents plugin only (anyone else, an agent included, gets an error; not an MCP tool). It keeps one landing's worktree for a [land gate](agents.md#gates) at `<main checkout>/.worktrees/.gate-<gate>-<key>` (`key` is the landing's, so two landings through one gate never share a tree), detached at `git commit-tree <tree> -p <old>` (the tree that would land, on the target's commit; when the worktree's commit already has that tree and parent it is kept, not made again), and returns `{path, commit, setup?}`. The first call for a key makes it with `git worktree add --detach`, copies the main checkout's files that its `.clubmate/worktree-include` names (as `git.worktree-new` does) and runs `.clubmate/setup.sh` only when you already trust it (it never asks, so a landing never waits on an approval); when the tree has a `setup.sh` you don't trust it skips it and returns `setup: "untrusted"`. Later calls `git checkout -f --detach` the commit and `git clean -fd`, so tracked edits and untracked files from the last round go and ignored ones (build caches) stay. A worktree dir deleted by hand is pruned from `git worktree list` and made again. Its git commands run without the repo's hooks and filters. `remove` removes the key's worktree with `--force`, or with no `key` every worktree of the gate (the agents plugin's gate delete), and then deletes any `.worktrees/.gate-<gate>-<key>` (or every `.gate-<gate>`, `.gate-<gate>-*`) dir that `git worktree list` no longer shows or whose removal failed; it runs `git worktree prune` only when one of those trees was registered and its dir is gone. When the plugin first opens a workspace it sweeps each repo's `.worktrees` the same way: it deletes `.gate-*` dirs git doesn't list and the un-keyed `.gate-<gate>` trees of older versions, and keeps every keyed tree git lists (a gate run may still use it). The git plugin's worktree commands (`git.worktrees`, `git.worktree-index`, removal, landing) and the Agents folder sheets leave gate worktrees out, so nothing offers to switch to, archive or clean one up.

## The agent git hook

Agent sessions in a gated repo run git with an injected `core.hooksPath` that proxies every hook to the repo's own and refuses moving the protected branches with plain git; sessions in other repos get nothing. See [agents § Gates](agents.md#gates).
