# SDUI protocol

Plugins render trees of nodes into slots; clients draw them and send events back. Every tree is validated by `internal/sdui` (max 5000 nodes, depth 32). Violations fail with `ErrInvalidTree`.

## Node

```json
{"type": "button", "id": "new", "props": {"label": "New"}, "children": []}
```

- `type`: one of the types below.
- `id`: required for interactive types, unique within a tree.
- `props`: only the listed props are accepted; unknown props are rejected. `*` marks required props.
- `children`: count limited per type.

Interactive types (`tabs list tree table button textField folderField toggle select form toolCard permissionCard composer graph flow lanes runstrip`) require an `id`. All but `toolCard`, `composer`, `graph`, `flow`, `lanes` and `runstrip` accept an optional `action` prop: a string of 1-64 chars matching `^[a-z][a-zA-Z0-9.-]*$` (camelCase allowed, e.g. `showEarlier`). It overrides the default action name sent in `ui.event`. Action names inside props (`menu`, card `actions`) follow the same rule.

## Item shapes

`items` and `options` accept `null` as an empty list.

- item (`tabs`, `list`): `{id*, label*, detail, icon, badge, tone, menu, truncate, shortcut}`, strings except `menu`, ids unique and non-empty. `shortcut` (a key combo, on a `tabs` item) picks that tab while the tabs are on screen. `menu` is a list of menu entries (`list` and `tree` show them as the row's context menu). `truncate` is where `list` and `tree` cut a long label: `tail` (default), `middle` (branches, paths; keeps the prefix and the end) or `head`; the full label is the row's tooltip. `tabs` ignore it. `tone` (`neutral`, `accent`, `success`, `warning` or `danger`) colours a `list` row's icon and tints a whole `tabs` chip (tone background, label and badge in the tone's ink); use it for attention only, e.g. a "needs you" count above 0.
- `tabs` draw a row of filter chips: label then `badge` (a count), the selected chip outlined in accent; a click marks its chip at once and every new tree resets the mark to `selected`, so a chip the plugin does not keep selected (a "show N more" toggle) never stays marked. More than three chips wrap onto further rows. Up to three: when the row does not fit its width, chips with an `icon` show the icon instead of the label (the label becomes the tooltip); when it still does not fit, the row scrolls sideways and keeps the selected chip in view.
- menu entry (item `menu`): `{action*, label*, confirm, key}`: choosing it sends `action` with the item id as value; with `confirm` the client asks first. `key` is one lowercase letter or digit: in a focused `tree` that key sends the entry for the row under the keyboard cursor (else the selected row), like choosing it, and the context menu prints it.
- tree item (`tree`): item fields (`tone` colours the icon and the detail) plus `labelIcon` (string: a second glyph in the muted ink between the icon and the label, e.g. the folder of a repo row), `pinned` (bool: the row stays shown under a folded parent; a parent that sends children with `expanded` false shows only those), `detailTone` (`neutral`, `accent`, `success`, `warning` or `danger`: colours only the detail, over `tone`, e.g. a group's count while something in it needs you), `detailFaint` (bool: the detail in the faint ink, for a hint that is not the point), `muted` (bool), `faint` (bool: the label in the faint ink, for rows that are there but not the point, e.g. a detached worktree), `action` (bool: the row is something to do, not something to look at, e.g. a group header or a "Show more" row: a click or ↩ still sends `select`, but the selection highlight stays on the row that had it and only the keyboard cursor moves there; when the next render moves or drops that row, the cursor goes to the row now at its old place, e.g. the first row a "Show more" added; a cursor on any row that goes away (deleted, its group folded) does the same, or takes the last row when the tree got shorter), `hasChildren` (bool), `expanded` (bool), `children` (tree items), `badges` (`[{text*, tone, outline}]`: small chips after the label, each in its tone, e.g. `new` in success or an open-comment count in warning; `outline` draws a ring instead of the fill) and `changes` (`{added*, removed*}`, ints ≥ 0: drawn last in the row as `+added −removed` in the success and danger inks, tabular figures; never hidden for space, unlike `detail`).
- option (`select`): `{value*, label*}`.
- choice option (`choice` `options`): `{value*, label*, description, shortcut, hint, on}`: `shortcut` a key combo as on `button`, `hint` a key printed on the row that binds nothing (a `keys` scope handles it), `on` picked at first.
- choice other (`choice` `other`): `{id*, label*, placeholder, shortcut, hint, on, value, focus}`: `id` the form field its text is collected under, `on` and `value` its row and text from the plugin (an autosaving form that keeps its answers), `focus` a counter: a higher value opens the row and moves focus into the field.
- column (`table`): `{id*, title*, align, width, truncate, priority}`: `align` is `left` (default) or `right` (numbers; every table cell uses tabular figures), `width` is a fixed width in points at the 12pt interface font, which the Mac scales with the interface font (`0` or absent = flexible, sharing the remaining space), `truncate` is where a long cell text is cut: `tail` (default), `middle` (paths, commands) or `head`; the full text is the cell's tooltip. `priority` is an integer 0-32: `0` or absent never drops; while the flexible columns would get less than 200pt each, the column with the highest priority drops (header and cells), then the next. Ids unique and non-empty.
- row (`table`): `{id*, depth, hasChildren, expanded, muted, group, cells*}`: `depth` is an integer 0-32 (indent 12pt per level, chevron when `hasChildren`), `muted` dims the row's text. `group: true` makes the row a group heading: the first cell's text spans the whole row in the muted small font after the chevron, the other cells are not drawn, and clicking the row expands or collapses it instead of selecting it. Ids unique and non-empty. `cells` must have exactly one cell per column.
- cell (`table`): `{text, bar, tone, spark, since, action, label}`: `bar` is a number 0…1 drawn as a filled capsule behind the text, `tone` is `""`\|`ok`\|`warn`\|`danger` (colours the bar and sparkline, or the text when there is no bar), `spark` is a spark. `since` is a time in Unix seconds (`0` or absent = none): the client shows the time elapsed since then as `h:mm:ss` after the text and counts it up every second itself, so a plugin does not re-render a row only to advance a clock. `action` with `label` draws `label` as a link at the cell's trailing edge (a link on the phone at the row's end); a click on it, or ↩ on the selected row, sends `action` with the row id (`action` follows the action-name rule; the first cell with one wins for ↩).
- spark (`table` cell): `{values*, max*}`: at most 900 numbers, `max` > 0. Values are clamped to 0…`max` and drawn as a 60×16pt line. The Go helpers `sdui.Sparkline`, `sdui.SparklineSized` and `sdui.NewSpark` clamp them before sending.
- attachment (`message`, `composer`): `{id, kind*, path*, startLine, endLine}`: `kind` is `file` or `selection` (with the 1-based line range); `path` is shown as given (relative to the worktree when inside it); `id` names a composer attachment for `detach` (non-empty and unique within the list when set).
- plan entry (`plan`): `{content*, status*}`, `status` `pending`\|`in_progress`\|`completed`.
- tool body (`toolCard` `body`): `{format*, text*}`: `format` `diff` (unified diff, drawn like `diff`), `text` (plain) or `terminal` (monospaced command and output).
- card action (`toolCard` `actions`): `{action*, label*, icon, value}`: `value` is a string, number, bool or an object of those.
- repos segment (`repos` `summary`): `{text*, tone}`, the header's words, joined with ` · `.
- impact row (`impact` `rows`): `{id*, icon*, tone, title*, count}`: `icon` in `tone`'s ink, `title` strong with a muted `· count` after it.
- repos row (`repos` `rows`): `{id*, order*, name*, path, session, foldKey, landsBy*, landsIcon, source, state*, tone, icon, opens, open, cursor, tail, note, actions}`: `order` the number in the ring, `landsBy` and `source` how it lands and who said so, `state` the word in the tone `tone`, `opens` whether a click opens the row, `open` whether it is open, `cursor` the row the keys act on, `tail` a monospaced box, `note` a muted line, `actions` the id of the child `stack` of its buttons.
- permission option (`permissionCard`): `{id*, label*, kind}`, ids unique, `kind` `allow_once`\|`allow_always`\|`reject_once`\|`reject_always` (tints the button; absent = neutral).
- command (`composer` `commands`): `{name*, description, hint}`: the agent's slash commands; `hint` describes the expected input.
- picker (`composer` `pickers`): `{id*, title, help, value*, options* (option[]), toggle}`: a session option menu; its label is the current option's label, prefixed by `title: ` when `title` is set; `help` is the tooltip. With `toggle: true` it is one checkable item named `title` instead of a submenu, on while `value` is `"true"`, sending `"true"`/`"false"`, and its `title` joins the options summary while on (except `afk`, which the header shows); `options` (On/Off) are the fallback for clients without toggles.
- graph node (`graph` `nodes`): `{id*, label*, state*, tone, icon, attention, pending, start, tooltip, kind, command, since, timeout, tag, outs*}`: `label` is the role, `state` the state word under it (`waiting for you`, `idle · 3 turns`, `closed · 4 turns`, `not started`; empty: the card draws no state glyph and no state line, the head keeps its height), `tone` (`neutral`\|`accent`\|`success`\|`warning`\|`danger`) colours the `icon` glyph and the state word, `attention: true` draws the waiting card (warning border and tint, soft pulse on the glyph), `pending: true` the not-started card (dashed border, muted role), `start: true` joins the start marker to the node's input, `tooltip` is the card's tooltip (the session title). `kind` (`agent`\|`check`\|`action`) is the small word at the card's right; `check` and `action` draw a step: a square card (radius 3) with a 2pt left rule in the state's tone (accent running, warning waiting, danger error, else `borderStrong`) and `command` on a mono `$ …` strip under the head (middle-truncated, the full command as its tooltip); an `agent` card keeps the round card. `since` (RFC 3339) is when the running or waiting state began: the client appends the elapsed time to `state` (`running · 1:12`) and ticks it each second, and with `timeout` (seconds) draws a progress bar under the state line that fills over the timeout. `tag` replaces the kind word with a warning chip (`changed` on a definition whose step changed since it was trusted). Ids unique and non-empty; at most 16 nodes.
- graph out (`graph` node `outs`): `{id*, label*, count, state*, end}`: one row with a port on the card's right edge; `id` names the out within its node (edges and moves refer to it), `count` (int ≥ 0) is drawn as `×N`, `state` is `taken`\|`last`\|`never`\|`plain`, `end: true` leads the port to the end marker instead of an edge.
- graph edge (`graph` `edges`): `{from*, out*, to*, state*, ref, tooltip, label}`: from node `from`'s out `out` to node `to`'s input; `state` `taken` (solid muted line, filled port), `last` (accent line and port) `never` (dashed faint line, empty port), `plain` (a graph's definition, not a run: solid muted line, filled muted port, like `taken`) or `held` (a firing held at its round cap: dashed warning line and port), drawn in that order never → taken/plain → last → held. `label` is a chip on the edge's middle (`×1/2`, `at most 3`, `×2/2 · waits for you`), in the edge's ink, warning-tinted on a `held` edge. `tooltip` shows while the pointer is on the edge or Tab has selected it; `ref` (non-empty) makes it clickable: a click, or ↩ on the selected edge, sends `openEdge` with `ref`. At most 32 edges.
- graph move (`graph` `moves`): `{node*, cause*, label, tooltip*, out, current, user, last, end, bar, tone, round, pending}`: one History move, in run order. `cause` is the index of the move whose edge started it (`-1` for start and user moves), `out` the id of the out on that move's node whose edge it was (absent for start and user moves), so the hop links to edge (`moves[cause].node`, `out`); `label` names the hop when it is not an out (`you` for user moves); `tooltip` is `move N · Role · HH:MM`; `current` draws the node's live glyph (the move is still open), `last` the hop in accent, `user` a move the user started in the session, `end` the id of the `end` out this move ended the run through (only on that move of a stopped run; History draws a hop from it to the end marker). At most 1000 moves. `bar` (a step's move) draws the move as a bar from its start to the next move (open-ended to the lane's end while `current`, dashed) labelled under it with `bar` (`pass · 2:10`, `running`, `error · timed out`) in `tone`'s ink, and the hop out of it starts at the bar's end without a label; `round` (≥ 1) groups moves into rounds: consecutive moves with the same round get a `round N` bracket above the lanes (the graphs plugin numbers them from the first node that runs a second time, so a loop reads as a loop). A move without `bar` is a dot: `tone: danger` draws it as a danger ✕ (the turn ended in an error), `pending: true` as a faint dashed circle (a move a stopped run left open that never reported anything and whose session isn't running or waiting it; one that is gets `current` and the live glyph), else a success dot.
- flow card (`flow` `cards`): `{id*, label*, state, tone, icon, attention, pending, ghost, tooltip, outs*}`: a graph node's card without `start` (a flow draws its start as a marker); `state` may be absent; `ghost: true` draws the empty-state card (dashed faint border, no fill, muted role, faint state and outs: the shape of what you can make). Ids unique and non-empty; at most 8 cards.
- flow out (`flow` card `outs`): `{id*, label*, count, state*}`: as a graph out without `end`; `state` is a flow edge state.
- flow marker (`flow` `markers`): `{id*, kind*, label, reached}`: a cause or destination that is not a card, laid out in the layers like a card. `kind` `start` (ring, `start` under it), `end` (double ring, `end` over it, its inner circle filled when `reached`), `schedule` (a clock in a circle with `label` under it, e.g. `every 2 min`), `inbox` (a chip with the inbox glyph and `label`, default `Inbox`) or `session` (a chip with the session glyph and `label`, the session title) or `runs` (a clock glyph and `label`, default `Runs, below`, no chip: where results stay when nothing receives them). A layer that holds only markers sits 36pt from its neighbours instead of a card gap; a `schedule` marker's label widens only the gap after the first column (where the marker sits) so the label stays whole, and the gaps further right stay 36pt. Ids unique among the markers; a marker whose id repeats a card's is not drawn; at most 8 markers.
- flow edge (`flow` `edges`): `{from*, out, to*, state*, ref, tooltip, label}`: `from`/`to` are a card or marker id; `out` is the out id when `from` is a card (an edge from a card without a matching `out`, or to an unknown id, is not drawn), absent from a marker. `state` `taken`, `last`, `never`, `plain` as in a graph, plus `selected` (accent, like `last`: the edge a screen is about), `dim` (faint solid line, faint port: paused, or a graph's other triggers) and `ghost` (dashed faint, empty port, on a ghost card); drawn never/ghost → dim → taken/plain → last/selected. `ref` and `tooltip` as on a graph edge. `label` is a chip on the edge's middle as on a graph edge, e.g. `this trigger · fired ×2` or `paused`; the gap the edge crosses widens to fit it. At most 32 edges.
- lane actor (`lanes` `actors`): `{id*, label*, icon, tone}`: one lane, its glyph (`icon`, default a circle) in `tone`. Ids unique; at most 8 actors.
- lane move (`lanes` `moves`): `{actor*, cause*, label, tooltip*, current, last, user, tone, ref, time}`: one dot on `actor`'s lane, in order; `cause` is the index of the move that led to it (`-1` for none; an index that is not earlier counts as `-1`), drawn as a curve labelled `label` (a move without a cause shows `label` over its dot); `current` draws the actor's glyph instead of a dot, `last` the hop in accent, `tone` the dot's colour (default success; `danger` draws ⊗ instead of a dot), `user` a move the user made. `ref` makes the dot clickable: a click, or ↩ on the selected dot, sends `openMove` with `ref`; without `ref` no click. `time` is a label drawn on a time axis under the lanes, centred under the move's dot (the plugin writes it: `Nov 2 14:10` on the first move and on a new day, `16:02` otherwise); the axis shows only when a move has one. At most 1000 moves.
- strip run (`runstrip` `runs`): `{at*, status*, tooltip, ref}`: `at` an RFC 3339 time; `status` `ok` (teal dot), `failed` (danger ✕ in a ring), `missed` (warning ring), `running` (accent play glyph) or `ignored` (small faint dot); `tooltip` on hover (default the status); `ref` makes it clickable (`select` with `ref`). At most 200 runs.
- paused span (`runstrip` `paused`): `{from*, to}`: RFC 3339 times; drawn hatched over the axis with `paused` over it; without `to` it lasts until `now` (still paused). At most 200 spans.
- sort (`table`): `{column*, desc}`: the active sort column (arrow in its header) and direction. `column` must be one of the table's column ids.

A window shows at most one `surface` node at a time in v1. The client keeps every terminal it has shown mounted until the session's attach exits or the window closes, so switching between sessions is instant. A second `surface` visible in the same window at once renders a placeholder.

A `webview` shows a loopback page (`http`, host `127.0.0.1`, a port; anything else is rejected). The client keeps one web view per `key` alive until the window closes, also while its slot is hidden, so switching sections and back neither reloads it nor loses its state. A new `url` for the same key navigates; the same `url` with a new `rev` reloads; otherwise a re-render does nothing. The page stays on the origin of `url`: a main-frame navigation elsewhere is cancelled, and a clicked http or https link to another origin, or one that opens a new window, opens in the default browser instead. While the page has focus, ⌘W, ⌘N, ⌘O, ⌘P and ⇧⌘P go to it and the other app menu keys stay with the app ([shortcuts](shortcuts.md#vs-code-vs-code-section)).

`spacer` takes the free room along its `stack`'s direction, so in a horizontal `stack` the children after it sit at the trailing edge (Cron's Missed banner puts Run it now at the far right). A phone row that wraps ignores it.

`list` and `tree` rows render lazily. Outside a `scroll` a `list` or `tree` scrolls itself and fills the height left by its siblings, so a long one never grows the window; a changed `selected` from the plugin scrolls to that row.

`table` rows render lazily; wrap the table in a `scroll` to scroll them under a pinned header. Each row counts toward the 5000-node limit; cells are bounded by the row and column caps (at most 1000 × 32), and spark values (cell sparks and `sparkline` nodes) are capped at 100000 per tree. The client does not page or truncate: a plugin with more rows renders the first 1000 or fewer and adds a final muted `… N more` row itself. `selected` works like `tree`'s: a changed value from the plugin sets, moves or clears the highlight (and scrolls to it); clicking a row highlights it locally and sends `select`. `sparkline` draws `values` as a 60×16pt line (e.g. in a header); with `height` it fills the available width at that height in points (e.g. a detail chart).

`document` shows `html` (an HTML fragment from `pkg/docrender`) in a web view with the shared document template. `size: fill` takes the space it is given and scrolls itself; `size: fit` is as tall as its content, does not scroll and sits in a `scroll` or `stack` next to other nodes. A new `rev` for the same `path` replaces the body in place and keeps the scroll position; another `path` loads fresh at the top, or at the element whose id is `anchor` when it exists. A new `anchor` for the same `path` and `rev` scrolls to it; a new `rev` keeps the scroll position, not the anchor. Clicking a `clubmate-doc:` link sends `openDoc`, a `clubmate-file:` link `openFile` (see § ui.event contract); `http(s)` links open outside the app, other links do nothing. With `kind: artifact`, `html` is a whole HTML page that runs with JS in a sandbox, a `path` must be absolute, and a new `rev` reloads it (see [docs viewer](docs-viewer.md#artifacts)). Neither the core nor its JSON-RPC transport limits the size of a tree or a message: a `document` with 10 MiB of `html` goes through `ui.render` and `ui.get` unchanged.

`graph` draws a graph run as cards with ports (the `graphs` section): one card per node (state glyph, role, state word, one row per out with its port), the edges between ports in their state's look, a start marker before each `start` node and an end marker (a double ring, its inner circle filled when `reached`) after every `end` out. Under it, when `moves` is not empty, a collapsed `History · N moves` row opens the moves as swimlanes, one lane per node, consecutive moves joined by `cause`. Clicking a card sends `open`, clicking a move `openMove`; with `static: true` (a definition, nothing to open) cards have no hover tint, a click or ↩ sends nothing and the status bar drops `↩ open`, while j/k and edge tooltips stay. The phone does not draw it (see below).

`flow` draws cards with ports, edges and markers with the same renderer as `graph` (Cron's Does, a trigger's chain, an empty list's ghost): layers left to right by the edges (back edges over the cards, edges that skip a layer under them), at 100% and scrolling sideways when wider than the pane, cropped to what it draws (no empty band above or below the cards; cards are 20 characters wide, 84pt apart, so a marker and two cards fit a 640pt pane); no zoom bar, no History. Clicking a card (or ↩ on the focused one; j/k move focus) sends `open` with the card id; Tab / ⇧Tab select the next / previous edge that has a `ref` or `tooltip` and show its tooltip, ↩ on it sends `openEdge`. When a pane (slot) holds several of `table`, `graph`, `flow`, `lanes` and `runstrip`, the first one in tree order takes the keyboard when the pane gets focus (a `flow` of only ghost cards takes none); the others take it on a click.

`lanes` draws a graph's History generalised: one lane per actor, each move a dot joined to its cause. With `title` it sits under a foldable `‹title› · N moves` row (`h`), `‹title› · ‹count›` when `count` is set (e.g. runs rather than moves), open unless `collapsed` (the client keeps the user's fold per node id until the app quits); without `title` it is always open. The lanes open scrolled to the latest move; ←/→ select the previous / next move with a `ref`, ↩ opens it.

`impact` lists what an action changes, one row per thing between hairlines: an icon, a key column and the row's body, the child `stack` whose `id` is the row's `id`. The body gets no gutter of its own and clips at its column, so a control that won't wrap can't widen a sheet. The phone doesn't draw it.

`runstrip` draws runs on a time axis the width of the pane: from the first run to the later of `now` and `next` (labels at both ends and at `now`, `HH:mm`, with the date when the axis spans more than 20 h). `now` is a vertical line, `next` a dashed accent ring, `selected` an accent ring around that run. Clicking a run with a `ref` sends `select` with it; ←/→ select the previous / next run with a `ref` (the newest when none is selected). With `title` a foldable row sits above the axis like a titled `lanes`: `<title> · <count>` (`count` defaults to the number of runs) and, at its right, a legend the client counts from `runs` (`● ok 19 · × failed 1 · ○ missed 1 · ▶ running 1 · skipped N` for `ignored`, each with its glyph); a click on the row or `h` folds the axis (kept per node id until the app quits). The phone draws none of `flow`, `lanes` and `runstrip` (see below).

Agent chat nodes (the `agents` section):

- `transcript` is the chat column: a vertically scrolling list of its children (messages, plans, cards, `text`, a "Show earlier" `button`), anchored to the bottom while the user is at the bottom. Its `id` identifies the session, so the client keeps a scroll position per id. Adjacent `toolCard` children collapse into one summary row (`8 actions: read 3 files, 2 searches, …`, a spinner and the running card's title while one runs) that expands to one line per card; a lone card is shown as that line, and a line expands to the card's `body` and `actions`. Edit lines show the file name when the `title` holds a path (the path as a tooltip) and the `diff` body's `+added −removed`. Expanding the last item scrolls to the bottom. With `center: true` items shorter than the column sit in its vertical middle instead of at the bottom (the Code chat's new-chat and graph-step screens); taller ones scroll as usual. When the pair (`anchor`, a child node id; `anchorRev`) differs from the last pair the client scrolled to for this transcript id, on appear or on change, the client scrolls that child to the top and stops following the bottom; the same pair sent again does not scroll again, so a sender that wants a second jump to the same child bumps `anchorRev`. `failed` cards and `permissionCard`s stay full-size and split the run; a `standalone` card (the agents plugin's compaction card) is never folded into a run and is shown as its own line. Expansion is kept per card id until the app quits, so a group stays expanded as cards stream in or the run splits.
- `message` renders `text` as markdown (headings, lists, quotes, tables (GFM, column alignment kept; on the Mac the columns wrap to the width, on the phone a wide table scrolls sideways), code blocks with copy, inline code, links). `user` messages are right-aligned bubbles with their `attachments` as chips (`@ path`, `path · lines 12–40`) and an optional muted `from` line ("from <from>") for prompts that another agent session sent; a `user` message with `heard` is a voice prompt: a right-aligned capsule "🎙 <heard>" (one line, tail-cut) with a chevron that opens `text`, the prompt JSON, pretty-printed with sorted keys in a scroll box at most 480 pt tall; closed by default; `agent` messages are plain, and a link target or inline code span that is a key of `docLinks` (exactly as written) is drawn as a link whose click sends `openDoc` with the key's value (an absolute path, maybe with `#anchor`) on the message node, and each `docCards` entry with `presented` is a card under the text (kind icon, `title`, "Document · <rel>" / "Diagram · <rel>" / "Artifact · <rel>", an open glyph) whose click sends `openDoc` with its `path`, the others fold into one muted plate after them ("N docs mentioned", or the file name for one, and a chevron) that opens into the same cards; a link target or inline code span that is a key of `imageLinks` is drawn as a link too, and it and each `images` thumbnail under the text open that image in the client's viewer (nothing is sent); `thought` is collapsed behind "Thinking" and expands on click; once the agent moved on, `seconds` is how long it thought (to the next transcript entry, at least 1) and the row reads "Thought for 4 s" ("Thought for 2 min" from 60 s); without it the thought is still going.
- `plan` is a card captioned `Plan · <completed> of <entries>`: `completed` a check and muted text (no strikethrough), `in_progress` an accent icon and semibold text, `pending` an empty circle and secondary text. In `agents.main` an agent message that is only a plan (an optional `Plan` heading and list items) directly followed by the turn's `plan` is left out, so the plan shows once, as the card.
- `toolCard` shows an icon for `kind`, the `title` and `status` (spinner while `pending`/`in_progress`, red for `failed`, muted for `cancelled`). `read` and `search` cards are one line. A `body` is shown under the title (`diff` and `terminal` in a monospaced box). A `diff` body is drawn per file from its unified diff: a file bar (the path from `+++ b/`, `+added −removed`) that also holds the card's `openLocation` and `review` actions, then the hunk headers and lines with line numbers (old for removed, new for added and context); the `---`/`+++` lines are not shown. ⌘D runs `review` of the transcript's last card that has it. `truncated` adds a muted "Output truncated" note; the plugin then also offers a `showAll` action. Each `actions` entry is a small button.
- `text` with `style: "block"` is mono text in a sunken box (the page background with a border, the width of its parent, selectable): command output such as a graph step's tail.
- `card` groups its children in a card (things that ask or change, per the design language): a `tone` card has the tone's 15% fill and border (the permission card's look), without one the raised surface and border; `icon` is drawn in the tone's ink before the children, on the first text line; it is inset by two gutters on both sides. It is not interactive: put it inside a `form` to collect fields.
- `sheet` asks the user something modal over the slot (id required): `title` (required) is the sheet's heading, `icon` is drawn before it in `tone`'s ink, `cancel` (required) names the `action` of one of the sheet's buttons. `note` is a small line at the left of the action row, in `noteTone`'s ink, muted without one; it gives way to the buttons. Its children are the body, drawn like a `stack` (a `card` inside it is inset by one gutter, not two); a last child that is a horizontal `stack` of only buttons is the action row, right-aligned at the bottom. A sheet must be a direct child of the slot's root node; the Mac takes it out of the slot's tree and presents it as a window sheet (560pt wide, the body scrolls past 520pt) while the node is there, and dismisses it when the next render drops it. The `cancel` button is the default: it has the focus ring and prints ⎋, and Esc, ↩ or Enter (↩ and Enter not while a text field has focus) press it, sending that button's event; Esc is the app's key, so the plugin never declares it. The other buttons keep their `shortcut`s, which work only while the sheet is up; the page's own buttons wait under it. Graphs uses it for Trust… ([agent graphs](agent-graphs.md#steps)).
- `permissionCard` shows `text` and one button per option. With `title` it shows `title` instead of `text` ("Run a command?"), `command` in a monospaced box under it and `caption` ("Claude says: …") as a muted line; `text` stays for clients that don't know them. A permission option is `{id*, label*, kind, shortcut, menu, rule, scope, workspace}`: `shortcut` is its key (`opt+1`…`opt+3`, printed on the button), `menu: true` puts it in the card's ••• menu instead of the button row (Always reject), and `rule` with `scope` (on `allow_always`) is what the client shows in the confirm before it sends the option ("Bash(go test:*)", "in shop on this Mac"), and `workspace` is the workspace name in that scope, for clients that set it apart ("shop"); nothing is sent until the user confirms. Without `rule` the confirm shows the option's `label`. See [Agents § Permission card](agents.md#permission-card). With `outcome` set the card is answered: the chosen option (`outcome` = its id) is shown as chosen, `cancelled` as "Cancelled", and the buttons are disabled.
- `request.connectRepo` is the permission-family card that asks to connect repos (see [Agents § Connect requests](agents.md)). A connect repo is `{key*, name*, path, remote, state, warn, clone, reason, landsBy, source, brings, trust, folded}`: `key` is what the answer names, `state` the branch and clean line (`warn` draws it in the warning ink, for a dirty clone or one behind origin), `clone` a repo not on disk, `folded` a row behind `more` ("2 more repos"). One repo draws the large form with `effects` (`{text*, note}`, what a yes does); several draw ticked rows with `effect`, the `hint` and Connect counting the ticks. `declined` is what Don't connect means. `effect`, `effects` and `reason` take `` `code` `` and `**bold**`, no links. Answering sends the named action `connectAnswer` with `{request, answers: [{path, action, otherPath?}]}`. The ticks, the focused row and the other folders live in the client, per node id.
- `request.land` is the `Land ‹repo›?` card: `detail` takes `` `code` ``, `options` are the buttons with their keys, a `reject_once` option stands at the far end and asks `confirm` first. A press sends the named action `landAnswer` with `{request, action}`.
- `composer` is the prompt editor: a multi-line field (`placeholder`: "Message Claude…" when idle, "Queue a message" while a turn runs, "Answer Claude…" when Claude asked you), `hint` on the hint row under it ("/ for commands, @ for files"), the `attachments` as removable chips, an attach menu with the kinds in `attach`, the `agent` label, a mode picker over `modes` (current `mode`), one menu per `pickers` entry, and Send (labelled Queue while `running` unless `steers`, set when the agent takes prompts into a running turn). The composer has no Stop: Stop is the session header's button (with its ⎋ hint), one per surface. ↩ (or ⌘↩) sends (the plugin steers or queues it while a turn runs), ⇧↩ or ⌥↩ inserts a newline, Esc stops while `running`, `@` opens the client's fuzzy file picker (`search.files`) in attach mode, and `/` at the start lists `commands` filtered by the typed prefix; choosing one inserts `/name `. The field is uncontrolled; the plugin clears it after a send by rendering the composer with a new `id`. With `docked` a card above the composer (a pending permission or question) holds the pane's primary action, so Send/Queue is drawn without the accent fill. With `disabled` the composer is shown but off: the field takes no focus or text, `placeholder` says why ("Reviewer runs as part of Review loop"), the agent and mode read as one muted line without menus, and Send is greyed out.

`button.confirm`: when set, the client asks the user to confirm with that text before sending the event.

`choice` is a radio or check list inside a form: one row per option, a round or square mark, the label, the description (on the label's line, or under it in a form at most 560 pt wide), the key on the right, the row filled while it is on. `text` is the question over the rows, `title` a chip before it, `number` a numbered circle that turns green once answered; a choice without `text` is rows alone. `quote` is one context line under the question, behind a rule; `note` a muted word after the question; `summary` replaces the question on the folded row. `other` adds a last row that opens a text field only while it is on; the field gets focus and scrolls into view, ↩ in it submits the form. Radio: Other is one more row of the group, so picking an option closes the field and drops its text, and re-picking Other brings the text back; check: Other is ticked on its own. In a form at most 560 pt wide choices with `text` are an accordion (the width of the form, not of the window: a form is the window less 290 pt of rail and sidebar, so that is a window at its 800 pt minimum, 510 pt wide, and not one of 900, 610 pt wide; a narrow Code chat panel folds too, and an 800 pt window with its sidebar hidden does not): the current one is open (first the one with `open`, then the last one touched or clicked; picking a radio row moves on to the next question below it that has no answer yet), the others are one line with their answer ("not answered", "none ticked"). `number` also marks the current one with an accent bar. A row's `shortcut` presses it like a button's. With `openAction` the plugin owns the cursor: `open` alone says which choice is current, a click on a folded row sends that action with the choice's id instead of opening it, a pick doesn't move it on the client, its rows take no Tab stop, and `cursor` (an option value) draws the keyboard ring on that row while the enclosing `keys` scope has focus. The phone doesn't draw `choice`: its question card is native.

`keys` is a focus scope around one child: it takes keyboard focus like a `table` (a click anywhere in it, a click on a row, a `ui.focus` naming it, or with `pane: true` the pane's focus), and only while it has it, a key in `keys` (combos in the `button.shortcut` form, here bare `return` too) sends `props.action` with the combo as `value`, nothing else; what the key does is the plugin's. So a bare `l` can't steal a key from the sidebar or the composer, unlike a `button` `shortcut`, which works while the button is on screen. Buttons and rows inside print their key with `hint` and bind nothing. Esc or ↩ in a `choice`'s Other field gives focus back to the scope. The status bar shows the open items' hints while a scope has focus. Only the agents section sends it, and the phone's agents screens are native, so the phone has no renderer for it.

`repos` is the live Repos card of a task ([agents](agents.md#repos-card)); the plugin decides every word, tone and which row is open, the client draws them. The header toggles the card with `action`; a row with `opens` sends `rowAction` with the row's `id`. Below about 520 pt the Lands by column drops out and the buttons wrap. A `button` with `pill: true` inside a session `header` isn't in the button row: it is drawn on the title line, before the badges, as a bordered pill "icon label · detail ▾" with `detail` in `detailTone`, and as "detail ▾" alone when that doesn't fit. `footerAction` is the id of the child `stack` drawn at the end of the footer line. `keys` `hints` is what the status bar shows while the scope has focus (without it, the open items hints).

`card` with `rows: true` draws its children as rows divided by a rule, on the card's fill with no icon or tone: a `choice` row runs to the card's edge so its accent bar touches it, other children get the card's padding. Inside a `transcript` the card lines up with the messages. `form` `accordion: true` folds its choices at any width. `text` `short` is what shows when `text` doesn't fit on one line, nothing when that doesn't fit either, and such a text gives way to its neighbours in a row; `strong` is the bold body size on one line. `badge` `outline` draws a ring instead of the fill. `header` `inline: true` keeps the title, `meta` and buttons on one row while they fit, as a header with a filter does.

`scroll.fit: true` hugs its content and scrolls only what doesn't fit the height it gets. `form.dock: true` gives the form the pane's height before its flexible siblings: a question docked above the composer takes the room the transcript doesn't need, its Send stays on screen because the questions are in a `fit` scroll. A button's `shortcut` inside such a form outranks other buttons with that key and a focused `composer` with no text, loses to a composer with text, and does nothing while a terminal has focus (also for ⌘↩): the question's Send takes ⌘↩ from an empty composer, Send review keeps it in Neovim.

`button.variant`: `primary` (accent fill; at most one per pane), `secondary` (raised, bordered), `ghost` (text only, fill on hover; toolbars and headers) or `danger` (danger outline; destructive actions). Without it the button looks like `ghost` in the body text colour. `disabled: true` greys it out and drops clicks and its shortcut. `shortcut` is a key combo in `cm ui key` form (`cmd+r`, `opt+1`, `shift+p`, `p`): the client prints it inside the button (`⌘R`) and presses the button on that key while the button is on screen in the key window; a combo without `cmd`, `ctrl` or `opt` does nothing while a text field has focus, a combo an app menu item uses goes to the menu, and `esc`, `return` and `tab` without `cmd`, `ctrl` or `opt` are rejected. A plugin keeps its shortcuts unique per pane (two buttons that do the same thing may print the same key; the first one on screen takes it), declares them in its manifest (`contributes.shortcuts`, see [Shortcuts](#shortcuts)) and lists them in `docs/shortcuts.md`. `loading` is the progress verb (`Saving…`): a non-empty one replaces the label, the button keeps the width of its label (a longer verb widens it, so keep verbs short) and drops clicks and its shortcut like `disabled`. Buttons take keyboard focus like macOS buttons (Tab, with Keyboard navigation on; a click does not focus them) and draw the focus ring while focused; Space or Return presses the focused button. `hint` prints a key without binding it, for a key a `keys` scope handles. `iconOnly: true` with an `icon` draws only the icon in a control-height square; the `label` and the key become its tooltip. `withForm: true` on a button with its own `action` inside a `form` sends the form's collected values with its event (see [Forms](#forms)).

`button.overflow: true` puts a `header` button in the header's "…" menu even when the bar has room (a rare or destructive action, e.g. Delete of a trigger a graph run owns, with its warning as `confirm`); its shortcut keeps working. Outside a `header` it has no effect.

`text.lines` clamps the text to that many lines; when it is cut, the client draws a "Show all" / "Show less" link under it and the full text is the tooltip, so the plugin sends the whole text (a prompt in a card). `lines: 1` cuts the text to one line with "…" and no link (the full text is the tooltip on the Mac), and in a row it gives way to its neighbours like a `short` text: the comment text of a review card row. `divider` is a hairline in the border colour across its parent, inset like text: the rules between the comments of the Send review sheet. `text.tone` and `icon.tone` draw the text or glyph in the tone's ink (`neutral` = the normal colour): a status glyph, or a line that needs attention ("Missed" in warning ink) without a badge.

`button.copy`: the client puts that text on the clipboard instead of sending the event (after `confirm`, when set); the shortcut does the same.

A `button` with a `form` child is a popover button: a click (or its `shortcut`) opens an anchored popover holding that form instead of sending the button's event; clients without popovers (the phone) send the event as before, so the plugin keeps the defaults behind it. In the popover the form works as everywhere else and a submit also closes it; ↩ submits it (⌘↩ too, and a plain ↩ only when no text field has focus: a single-line field submits by itself), ⎋ or a click outside closes it without sending anything, and so does a button whose `action` is `dismiss`, which sends no event. Submit buttons (no `action`) print ↩, `dismiss` ones ⎋; a horizontal `stack` of only buttons is the popover's footer, aligned to the trailing edge. Events from the popover's other buttons and fields (an Edit that re-renders the form) keep it open; the plugin keeps the form's `id` stable so the chosen values survive the re-render. Backlog's Start agent is the first user.

`textField.drop: true` makes the field a drop zone, drawn with a dashed border and a paperclip: dropped files send `drop` with the string[] of their absolute paths (the plugin decides which it takes, e.g. only files inside the workspace folder once symlinks are resolved), a dropped `http(s)` link is put into the field as text, and `@` typed into the empty field opens the workspace's file picker (the composer's `@`) and sends the picked file the same way. The phone ignores it.

`form.needsAny` lists field ids and holds the form back until one of them has a value: a string with text in it, an array with an item, any other value. Until then a button that sends the form (no `action`, or `withForm`) is disabled and nothing else sends it either, ↩ in a field included; a button with its own `action` stays live. Its `shortcut` still takes the key and does nothing, so a docked form keeps ⌘↩ from falling through. A client's picks are form state the plugin doesn't see, so the plugin names the fields and the client checks the values.

`textField.live: true` (outside a `form`) also sends the field's submit event 250 ms after the last keystroke, besides on Return; while the field has focus, a changed `value` from the plugin does not replace the text, so a render that lags behind the typing cannot undo it. Filter fields use it.

`textField.error` and `select.error` (one short sentence, `Title is empty`) draw the field with a danger border and the text as one caption line under it. Unlike `value` it is not an initial value: the field shows whatever the latest render says, so the plugin drops the prop once the input is valid.

`header` heads a detail pane: the `icon`, the `title` (heading size, two lines at most, then cut with a tooltip), the `badges` (toned like `badge`; leave the normal state untoned), an optional muted `meta` line and its children as the action bar on one row: a `textField` child (a filter) comes first, at most 220pt wide, and never moves into the menu, then the `button`s. When they don't fit, or the header is under 480pt wide, the first three non-`danger` buttons stay and the rest (`danger` ones included) move into a "…" menu at the right end; their shortcuts keep working, and the menu shows them after the label. A header with a `textField` child (a list header: title, filter, tools) puts everything on one row while it fits: the title on one line, `meta` in muted ink after it, then at the right end the filter (220pt) and the buttons in the plugin's order; when that row doesn't fit it falls back to the layout above. It draws a rule under itself. An agent session's header (the `agents` section) also sets `status` (one of `running`, `waiting`, `asks`, `done`, `idle`, `error`, `closed`, `childrenRunning`, `childrenWaiting`; glyph, word and tone per [Agents § Status](agents.md#status)), `agent`, `branch` and `mode`: the client draws the status glyph (`icon`) in the status's tone before the title and "Claude · docs/design-brief · Ask before edits" (agent · branch · mode, muted, cut in the middle) after it, the badges ("waiting for you" in warning while the session needs you) at the trailing end and the `stop` button (the child with action `stop`) last on that row with its ⎋ hint, out of the action bar. Under 640pt the agent · branch · mode line goes under the title and Stop is icon-only. `meta` follows on its own line.

`header.field` makes the title editable in place inside a `form`: the title is that form field (keyed by `field`, value the `title` text without a prefix). A click on the title, or ⏎ while it has focus, turns it into a text field; ⏎ or leaving the field commits, ⎋ cancels. A committed change submits an `autosave` form at once; in a form without `autosave` ⏎ submits it and leaving the field only keeps the value for the next submit. Until the plugin sends a new `title` the header shows the committed text. `header.error` (one short sentence) is drawn as a danger caption under the title, and the edit field gets a danger border; drop it once the title is valid. Outside a `form` both are ignored. Buttons in such a header are inside the form, so give each its own `action`, or it submits the form.

Inside a `form`, a horizontal `stack` whose first child is a muted `text` is a property row: that text is the key column (120pt, 88pt when the form is narrower than 480pt) and the rest is the value. An empty muted text continues the row above.

`empty` fills its pane, top-left in the content column: an optional `icon` and `title`, the `text` (one sentence), an optional `hint` in monospace (a path or command) and its children in order: a `button`, the action that fills the pane, a `form` (the field that fills it, e.g. Backlog's New task row), a `flow` of ghost cards, the shape of what the section holds (Triggers), and a `stack` of further rows (Backlog's lifecycle: disabled status chips Idea → Todo → In progress → Done). A flow whose cards are all ghosts does not take the pane's focus. With `center: true` it is a column at most 560pt wide, centred, text centred, placed a little below the top (a section with nothing in it, as Backlog's).

Input fields are uncontrolled: `value`/`values` on `textField`, `folderField`, `toggle` and `select` are initial values. The client keeps what the user entered while the node keeps its identity. A changed `value` in a later render replaces it, but re-rendering an unchanged one does not. To reset a form (e.g. after a successful submit), the plugin renders it with a new node `id`. The client then discards the form's field state and starts again from the props. Actions are routed by `action`, not by `id`, so rotating ids (e.g. `create-<n>`) does not change event handling.

## Phone

The Companion (`client/Companion/SDUI`) draws the same trees with iOS controls and sends the same events (§ ui.event contract). Where it differs from the Mac:

- An event whose result is `{"open": {"session": "agt_…", "turn": N}}` opens that session in Agents. Plugins return it from links that reveal a session on the Mac with `agents.reveal` (a trigger run's Open session, a graph turn panel's Open ‹Role› and its header's open, a cron job's Show session), since the reveal only moves the Mac; the Mac ignores the result.
- A section's `sidebar` and `main` slots are watched while the navigation shows the section (`RootView`), not from the screen's appear and disappear, which a pushed detail breaks.
- `split`: panes stack vertically on compact width; a horizontal split is side by side on regular width (iPad).
- `toggle` with `style: "checkbox"` is a small checkbox followed by its `label` (a click on the label toggles too; `disabled` dims it, label in muted ink, and takes no click); a `switch` draws `label` before the switch. `progress` is a 4pt rounded bar that fills the width it is given (at least 40pt), `value`/`total` of it filled in `tone` (`total` 0 draws it empty).
- `stack` horizontal wraps its children when they don't fit on the phone; the Mac draws it as one row, so a plugin keeps such rows short (or splits them into rows) for narrow panes. A vertical `stack` or `form` outside a `scroll` that holds nothing scrolling (`scroll`, `split`, `list`, `tree`, `table`, `transcript`, a `fill` `document`) scrolls itself.
- `list`, `tree`, `table` outside a `scroll` are an inset grouped `List`; inside one, rows in a rounded group. In a `<section>.sidebar` slot a row tap sends `select`, then asks the screen to push `<section>.main`. Row menus are a context menu; the first two entries without `confirm` are also swipe actions (destructive entries are never swiped, per the phone design); an entry with `confirm` asks first. `tree`: the chevron sends `expand`/`collapse`, the row sends `select`.
- `table`: the first column is the row title, the other columns one line under it (`title value`, bars and sparks inline; stacked when they don't fit), `group` rows are section headers; `sort` is a menu above the rows. Column `priority` is ignored.
- `tabs`: horizontally scrolling chips; the selected chip is filled with the accent.
- `form`: consecutive fields and property rows are grouped like a Settings form. `header.field` is an always-editable title field.
- `header`: up to three buttons on a wrapping action bar, the rest (and `overflow` ones) in a "…" menu.
- `button.shortcut` is ignored; `confirm` is an alert. A `button`'s `form` child (a Mac popover) is not drawn: the button sends its own event. `textField.drop` is ignored.
- `folderField` shows its folders read-only with "Choose folders on the Mac".
- `sheet` is not presented: the phone shows "sheet isn't supported on the phone" in its place, like an unknown type.
- `surface` shows "Terminal — open it on the Mac"; `graph`, `flow`, `lanes` and `runstrip` one faint line "Drawn on the Mac" (a `flow` of only ghost cards nothing; a `runstrip` or `lanes` with a `title` puts its `<title> · <count>` above that line, a `runstrip` with its legend; a `graph` lists its nodes under that line, label and state in its tone, and a tap sends the same `open` with the node id as a click on the Mac card), followed by the node's children (a graph run's approval card and its step or turn panel); `webview` and any other unknown type shows "<type> isn't supported on the phone".
- `transcript`: adjacent `toolCard`s (except `failed` and `standalone`) fold into one "N actions" row. `message.from` shows as "From another agent". `composer` is a field and Send only: no modes, pickers, attach, `/` commands or `@` files.

## Slots

A slot is named `<section>.sidebar`, `<section>.main` or `<section>.status`, or `<section>.<name>` for a name the section declares in `slots`. A section is registered by a plugin, which owns all of its slots. Only the owning plugin may call `ui.render` for them. Slots are rendered per workspace, unless the section has `scope: "app"`. The client insets a `<section>.main` tree from the top edge, unless its root is a `surface` or a `webview`.

A manifest section may declare extra slots with `slots`: names matching `^[a-z][a-z0-9-]{0,31}$`, unique, and not `sidebar`, `main` or `status` (otherwise manifest load fails). `{"id": "alpha", "slots": ["extra"]}` adds the slot `alpha.extra`. Extra slots belong to the section like its own (owner, scope, `ui.event` routing); views cannot claim them, and the client decides where to show them. `ui.render` and `ui.event` on an undeclared `<section>.<name>` fail with invalid params. `ui.sections` lists them as `slots` (omitted when empty).

### Hosted sections

A manifest section may set `host` to another section's id; `ui.sections` returns it (omitted when empty). A `host` equal to the section's own id fails manifest load; a host that is not registered, is itself hosted or has another scope is dropped by the core, and the section stays a normal one. A hosted section has no rail icon, ⌘ number or palette "Go to …" entry, and the client shows none of its slots. Selecting it (a saved `section` in the UI state, `ui.focus` to it or any of its slots) selects the host. No bundled plugin sets `host`.

### Rail

A manifest section may set `rail: false`; `ui.sections` returns `rail: false` only then (omitted when absent or true). Such a section has no rail icon, ⌘ number or palette "Go to …" entry, but unlike a hosted section the client still shows its extra slots. `ui.focus` to it accepts only its `popup` slot.

### Popup slot

An extra slot named `popup` (`slots: ["popup"]`, giving `<section>.popup`) is shown by the Mac client as a floating panel over the workspace while its tree is not `empty`, and closed when the tree becomes `empty`. The user closing the panel sends `ui.event` with action `close`, nodeId `""` and value `null` on that slot; the plugin then renders `empty`.

### Scope

A manifest section has `scope`: `"workspace"` (default) or `"app"`; any other value fails manifest load. `ui.sections` returns it. Slots of an app-scope section are not tied to a workspace and are rendered, read, subscribed and sent events with `workspaceId: ""`:

- `ui.get` and `ui.subscribe` with `""` cover only app-scope slots; with a workspace id, only workspace-scope slots.
- `ui.render` and `ui.event` with `""` on a workspace-scope slot, or with a workspace id on an app-scope slot, fail with invalid params.
- `ui.subscribe` with `""` does not count toward presence and publishes no `ui.opened`/`ui.idle`.
- App-scope slots of a stopped or crashed plugin are cleared like workspace slots (the `empty` view is delivered to live subscribers).

### Auto new

A manifest section may set `autoNew: true` (default `false`); `ui.sections` returns it. When the user selects such a section and its main slot, once rendered, is an `empty` node (the section has nothing to show, e.g. no terminals; an exited terminal's view is not `empty`), the client runs the section's `<section>.new` command once for that selection (`CommandInvocation.shouldAutoNew`). Terminals sets it, so a terminal appears on entering the section.

The `.status` slot is a compact status line for the section; clients show it in the status area while the section is active.

### Views

A plugin may claim a slot of another plugin's section with `contributes.views`:

```json
{"contributes": {"views": [{"slot": "alpha.sidebar"}]}}
```

The claiming plugin becomes the owner of that slot instead of the section owner: only it may `ui.render` the slot and `ui.event` for it is routed to it. Slot syntax is validated at manifest load. A view on a section that no plugin registers is ignored and logged. When two plugins claim one slot, the later manifest in discovery order loses its claim and the conflict is logged.

A plugin may also declare its own settings slot `<plugin-id>.settings` (`{"slot": "voice.settings"}` in the voice manifest); a settings slot of another plugin's id fails manifest load, and a section can't declare an extra slot named `settings`. It needs no section, is always app scope (rendered, read, subscribed and sent events with `workspaceId: ""`; a workspace id fails with invalid params) and only the declaring plugin may render it. The Mac shows it on that plugin's Settings page. A manifest may set a top-level `icon` (an SF Symbol name, e.g. `"icon": "mic"`); Settings uses it for the plugin's page, else the icon of the plugin's first section. voice renders `voice.settings` (`enabled` toggle, `model` select; events go through `voice.settings-set`), agents renders `agents.settings` (`finish` select: the finish mode new sessions start with, the same value as `agents.finish-default`); both render again whenever the value changes, also from a command.

The agents plugin claims `editor-nvim.sidebar` for its chat panel: an agent session of the workspace's current worktree (the one picked there or with New, else the newest open one) with the same transcript and composer as the Agents section. Without a session the panel is an `empty` with New as its action. A session with no turns shows, instead of the transcript, `New chat in <branch>` with "It sees the file and selection you're on. ### Shortcuts

A plugin declares the keys its views use in `contributes.shortcuts`, so Settings → Shortcuts and the plugin's Settings page can list them:

```json
{"contributes": {"shortcuts": [{"keys": "cmd+r", "action": "Run the job now"}, {"keys": "opt+4", "action": "Pick the question's 4th option", "when": "a question is pending"}]}}
```

`keys` is a combo in the `button.shortcut` form (`cmd+shift+n`, `opt+2`, `p`; `esc`, `return` and `tab` need `cmd`, `ctrl` or `opt`), `action` says what it does in the user's words, `when` (optional) the context it works in. An invalid combo, an empty `action` or the same `keys` twice fails manifest load. One entry per key: a key that does two things (agents' ⌥1 answers a permission request or a question) says both in `action`. `plugin.list` returns them as `manifest.contributes.shortcuts` (`[]` when none). Each plugin's tests check that every `shortcut` its views carry (buttons, permission options) is declared, and a test checks every declared key appears in `docs/shortcuts.md`. Rebinding is not supported yet.

## Revisions

Every slot (per workspace) has a revision counter that starts at 1 and increases by 1 on each render. When a plugin stops or crashes, its slots are cleared: the counter increments and the tree becomes `empty` with empty text. The cleared slot is removed from the store: the `empty` view (rev + 1) is delivered only to live subscribers, and later `ui.get` or subscribe replays omit the slot. Clients render that view like any other update (an empty pane) and do not get the slot back from `ui.get` after a reconnect.

`workspace.delete` clears every slot of the deleted workspace the same way (the `empty` view at rev + 1 to live subscribers; `ui.get` for that workspace then returns `[]`). Before deleting, the core kills the workspace's session processes (groups registered with `process.register` whose root is still running are left to their owner plugin, which handles `workspace.deleted`; leftovers of an ended registered group are killed with the sessions; once a group left running ends, the core kills whatever it left behind on the next process scan), waits for each of its sessions to stop and removes them, publishing `session.removed` `{id}` for each; then it deletes the workspace and publishes `workspace.deleted` `{id}`. If a session does not stop within the kill grace, the delete fails and the workspace is kept. Clients take a workspace out of its window when its workspace disappears from `workspace.list` after having been listed.

Revisions are in-memory and reset when the core restarts; clients must reset their rev map on reconnect.

Clients keep the highest `rev` per `(workspaceId, slot)` and ignore views with a lower or equal `rev`.

A manifest command id is `<plugin id>.<noun>` or `<plugin id>.<noun>.<verb>`, each part lowercase kebab-case (`git.worktree-new`, `remote.set-port`; core primitives follow it too, e.g. `workspace.worktree.set`); any other id fails manifest load with `command id "<id>" must be <plugin id>.<noun>[.<verb>] in kebab-case`. Its MCP tool name replaces `.` and `-` with `_`.

A command with `"hidden": true` in its manifest entry is still listed and runnable; clients leave it out of the command palette.

A command with a non-empty `"confirm"` string in its manifest entry is listed with that text (`""` when absent); the client asks for confirmation with it before running the command.

A manifest command entry may also declare, all optional and listed as declared:
- `description` (`""` when absent): what the command does, for agents and `command describe`;
- `args` and `result`: schemas for the command's args and its result (absent: any args, nothing declared);
- `agent` (default `false`): the command is meant for agents;
- `remote` (default `false`): paired companion devices may run it through the `remote` plugin (see [remote](remote.md));
- `scope` (`workspace`, the default, or `app`): an `app` command needs no workspace, so `command.run` skips the `workspaceId` check and passes whatever `workspaceId` it got (possibly `""`);
- `destructive` (default `false`): the command destroys state (closes, kills, discards);
- `provides`: generic capability names the command implements;
- `handles`: topics of `command.broadcast` the command answers (see below);
- `timeout` (1 to 600 seconds; listed only when set): how long the core waits for the plugin's `command.run` reply, instead of the 5 s every other plugin call gets (`routeTimeout`). For commands that block on purpose, such as `agents.wait`. Callers apply no shorter limit: `clubmate mcp`, `clubmate command run` and `clubmate agent` set no timeout on `command.run`.

A schema is a small JSON Schema subset: an object `{properties: {name: prop}, required: [name]}`, where a prop is `{type, items, enum, description, default}`, `type` is `string`, `integer`, `number`, `boolean` or `array`, and an `array` has scalar `items` or object `items`. Object items go one level deep: `{type: "object", properties, required}` whose properties are scalars or arrays of scalars (no further object items), and a value is validated item by item, so a bad field names its path (`args.items[0].line: want integer`). Only an `array` has `items`, only object items have `properties` and `required`, and only a scalar has `enum`; `enum` values and `default` must match the type (a `default` also the `enum`), and every `required` name must be a property; anything else fails manifest load. `default` is documentation only: the plugin applies it, the core never fills it in.

`command.run` validates `args` against the command's `args` schema before routing, so the plugin is never called with bad args. Absent or `null` args count as `{}`; properties not in the schema are allowed; a `null` property counts as absent. Errors are invalid params naming the field: `args: want object`, `args.path: required`, `args.line: want integer`, `args.side: want one of ["left","right"]`, `args.paths[1]: want string`. `integer` rejects fractions and exponents. A command without an `args` schema accepts any args.

`session.send` types `text` into a running session (a data frame on the session host's socket, chunked under the frame limit); with `enter: true` it sends `\r` as a separate frame 50 ms later, so a TUI sees a keypress rather than a paste. Its writes have a deadline: the call's own, else 10 s; when it passes, or the call is cancelled, before all input is written, the call fails with `session busy: its program is not reading input; part of the text may have been typed` (or the context error, with the same note). It then half-closes its connection and drains what the host sends until the host closes (2 s at most), so every input frame is consumed even when the host is still replaying a large ring to the new connection. When the host has not closed after those 2 s (its program is not reading its terminal, so the host is still blocked typing the input), the call returns `{queued: true}`: the host has all the input and types it once the program reads; the core keeps draining that connection for up to a minute so the host is not cut off. Sending it again would type it twice. Hosts are unchanged by this. `session.read` returns the last `bytes` (default 16384, 0 means default, more than 262144 is invalid params) of the session's output ring, cut from the raw bytes before processing. Without `raw` it renders the text the way a terminal shows each line: it drops OSC, DCS, SOS, PM and APC strings (up to BEL or `ESC \\`) and other escape sequences, but keeps a cursor on the current line: `\r` returns to column 0, `\b` and `CSI n D` move left, `CSI n C` moves right, `CSI n G` sets the column, `CSI K` (0, 1, 2) erases, and printable characters overwrite at the cursor (so a redraw by a line editor or zsh-syntax-highlighting reads back as the final line, and output ending in `50%\r` reads `50%`). Cursor moves stop at column 512 (an overflowing parameter counts as the maximum), lines are capped at 4096 characters, the rendered text is cut to its last `bytes` bytes, trailing spaces are trimmed, a control character right after `ESC` is kept, other control characters except tab and newline are dropped, and invalid UTF-8 is dropped (e.g. a character split by the cut); `raw: true` returns the tail as is. When the session's app is on the alternate screen it returns `altScreen: true` and no text. Both fail with not found (`-32004`) for a session that is not running. The core reads the ring with a new host frame: the client sends an empty `snapshot` frame (type 4), the host stops streaming to it and answers with one `snapshot` frame whose payload is `[1]` on the alternate screen, else `[0]` followed by the ring; data frames already queued may arrive first. The session protocol version is unchanged: hosts started by an older core ignore the frame, and `session.read` fails after 2 s with not found (`-32004`) `session host cannot be read; restart the session`.

Sessions get `PATH` with the core's own directory first (`Contents/Resources/bin` in the app, `bin/` in dev), so `clubmate` works in clubmate terminals. The core prepends it only when that directory has an executable `clubmate`, and not when it is already first. A login shell may reorder `PATH`: macOS `/etc/zprofile` runs `path_helper`, which puts the system directories first, so a `clubmate` installed in a system directory (e.g. a release symlink in `/usr/local/bin`) wins over the bundled one.

CLI over the registry:
- `clubmate command list [--agent]` (`--agent`: only agent commands), `clubmate command describe <id|capability>` (description, flags, `provides`, args and result schemas).
- `clubmate command run <id|capability> [key=value …] [--args JSON] [--workspace ID] [--agent]`: `--workspace` defaults to `$CLUBMATE_WORKSPACE_ID`; `key=value` pairs are coerced by the resolved command's schema (integer, number, boolean, string, array as comma-separated values) and an unknown key (or any key, for a command without an args schema) fails before calling the core, naming the key; pairs and `--args` are exclusive. The CLI never turns on `--agent` by itself, not even inside a clubmate session.
- `clubmate open <file>[:line]` runs `editor.open` with `{path (absolute, from the CLI's cwd), line}`; a trailing `:line` or `:line:column` is parsed (the column is dropped; line 0 means no line), and anything else stays part of the path (`a:b.go:3` is `a:b.go` line 3).
- `clubmate plugin list`, `clubmate plugin restart <id>`, `clubmate plugin enable <id>` and `clubmate plugin disable <id>` call `plugin.list` / `plugin.restart` / `plugin.set-enabled`.
- `clubmate session send <id> <text> [--enter]` and `clubmate session read <id> [--bytes N] [--raw]` run `session.send` / `session.read` through `command.run` (not as agent calls).
- `clubmate agent spawn [prompt] [--branch B] [--title T]`, `tell <session> <text>`, `wait <session>… [--timeout N]`, `output <session> [--from-turn N]`, `sessions`, `cancel <session>`, `blame <file|commit> [-L a,b]` run `agents.new` / `agents.prompt` / `agents.wait` / `agents.transcript` / `agents.sessions` / `agents.cancel` / `agents.blame` through `command.run`, always as agent calls with `caller` = `$CLUBMATE_AGENT_SESSION`; `--workspace` as for `command run`.
- `clubmate mcp` is a stdio MCP server (newline-delimited JSON-RPC 2.0, protocol `2025-06-18`; `initialize`, `ping`, `tools/list`, `tools/call`; other requests get `-32601`, notifications get no reply; stdout carries only protocol messages). `notifications/cancelled` `{requestId}` cancels that request: its core connection closes, so the core drops the call (an approval it waits for counts as refused even if the user approves later) and the request gets no reply. When stdin closes, every request still running is cancelled the same way and the server exits. Tools are the agent commands (core primitives included), named by id with `.` and `-` turned into `_`; a command that provides a capability is listed under the capability name instead. `inputSchema` is `{type: "object"}` with the command's args plus an optional `workspace`; annotations carry `destructiveHint` (the command's flag) and `readOnlyHint` (`workspace.list`, `session.list`, `session.read`, `process.tree`, `terminals.busy`). `tools/call` runs `command.run` with `agent: true` and `workspaceId` = `workspace`, else `$CLUBMATE_WORKSPACE_ID`, else the most recently opened workspace; with `$CLUBMATE_WORKSPACE_ID` set, a different non-empty `workspace` fails the call without reaching the core; the result is one text item with the JSON result, and failures (including approval refusals) are `isError: true` with the message. It never starts the core: without one, `tools/list` lists the core primitives and every call fails with `Clubmate isn't running`. Turning a plugin on or off changes the list without an event to the MCP server, so it re-checks the tool list every 5 s and sends `notifications/tools/list_changed` when it differs from the last list it served. See `docs/agents.md`.

`process.tree`'s `args` is the full argv (`[]` when it can't be read, e.g. for another user's process) and `startTime` is RFC 3339.

`process.register` makes a process the plugin started a root of its own group in `process.tree`, like a session: the root and its descendants get `sessionId` = the returned `id` (`prc_…`), and `sessionId` in `process.tree` and `process.kill` accepts that id. `owner` is the calling plugin. The pid must be a descendant of the plugin process (by parent chain), else invalid params; `label` is trimmed and 1..200 characters, and `workspaceId` must exist. Registering the same live process again keeps its `id`, `owner` and owning process and updates `workspaceId` and `label`; another plugin process registering it is refused. While a registration is active its processes are never orphans (`orphan: false`): their owner reaps them. It ends (`ended: true`) with `process.unregister` (by pid, the caller's own registrations only; another plugin's call does nothing), when the plugin's connection closes (later registers from that connection fail), or when the root process is gone: a root registered before a `process.tree` snapshot started that the snapshot misses is checked again by its start time, and only a dead or reused pid ends it, so a slow snapshot never drops a fresh registration; `process.roots` runs the same start-time check. An ended registration stays, labelled `<label> (exited)` once its root is gone, while any tracked process still carries its `id`: those leftovers stay in their workspace, are orphans when reparented to launchd, and `orphansOnly` kills (and the Processes section's auto-kill) reach them. It disappears from `process.roots` once no process carries it. The agents plugin registers each agent process it starts (`Claude · <worktree folder>`, in the background, best effort), and the Processes section lists registered groups next to sessions.

`process.kill` with `orphansOnly` kills only orphaned processes and needs `sessionId` or `workspaceId` (otherwise invalid params). With `workspaceId`, only that workspace's orphans are killed; with `sessionId`, only that session's. Without `orphansOnly`, `pids` must be tracked processes. Each target is signalled only if its start time still matches the tracked one, so a reused pid is skipped.

`workspace.show` fails with not found for an unknown workspace; otherwise it sends the `workspace.show` notification to every connection that registered `"workspace.show"` via `client.register`, except the caller, and returns how many were notified (`clients`). `clubmate workspace open --id <id>` calls it and, when `clients` is 0, runs `open -b com.clubmate.app --args --open-workspace <id>`.

A workspace is `{id, name, folders, createdAt, home, lastOpenedAt}`; `lastOpenedAt` is `null` until the first `workspace.touch`; subscribing to a workspace's UI does not set it. `folders` is `[{path, worktree?, missing?, addedBy?, addedAt, addedAfk?, seen}]` in the order they were added: `path` is the folder, `worktree` the directory selected for it with `workspace.worktree.set` (usually a git worktree of the folder; omitted when none), and `missing: true` marks a selection whose directory no longer exists (it stays stored). `addedBy` is the session title that added it (omitted for the user), `addedAt` when it was added (the workspace's creation time for its first folders and for folders older than these fields), `addedAfk: true` that it was added while the user was away, and `seen: false` that an agent added it and the user has not looked at it yet. A folder's root is its `worktree` when set and not missing, else its `path`. Sessions created without `cwd` start in the first folder's root. `workspace.list` orders by `lastOpenedAt` then `createdAt`, newest first.

`workspace.open` resolves each folder path (symlinks resolved, cleaned), drops duplicates and returns the workspace whose repos are exactly that set (order-insensitive, stored repos resolved the same way) with `created: false`; with a single folder and no exact match it returns the workspace that folder comes first in, most recently opened first, so `cm <folder>` still finds a workspace that grew; a folder that is not first never matches. Otherwise it creates a workspace with the resolved folders, named after the base name of the first one (`workspace.created`), with `created: true`. Folders must be absolute paths to existing directories (otherwise invalid params, as is an empty `folders`). `workspace.home` returns the single `home: true` workspace, named `~` and rooted at the user's home directory, creating it (`workspace.created`) on first use. Both then send the `workspace.show` notification exactly like `workspace.show` (not to the caller) and return how many were notified (`clients`); `clubmate workspace open <dir>…` and `clubmate workspace home` run the app like `open --id` when `clients` is 0. `workspace.touch` sets `lastOpenedAt` to now (not found for an unknown workspace); clients call it when they activate a workspace. `workspace.rename` fails with invalid params on a blank name and publishes `workspace.updated`.

`workspace.folder.add` `{id, path, addedBy?, addedAfk?}` appends a folder (absolute path to an existing directory, not already in the workspace) and publishes `workspace.updated`; it sets `seen` to false when `addedBy` is set. `workspace.folder.remove` `{id, path}` drops a folder from the workspace and clears its selected worktree. It never touches files, publishes `workspace.updated`, and `path` must equal a folder's `path` exactly; removing the last folder fails with invalid params `a workspace keeps at least one folder`. It does not look at sessions and has no CLI verb. `workspace.folder.seen` `{id, path}` sets `seen` and publishes `workspace.updated`. None of the three is a command. Plugins call them as `pluginsdk.Host.AddFolder` and `RemoveFolder`.

`workspace.worktree.set` `{id, repo, path}` selects the directory a workspace folder points at. `repo` must equal a folder's `path` exactly (otherwise invalid params `path is not a folder of this workspace`). An empty `path`, or one equal to `repo`, clears the selection; any other `path` must be an absolute path to an existing directory (otherwise invalid params `path is not a directory`). It stores the selection, publishes `workspace.updated` with the full workspace and returns the workspace. Selections are deleted with the workspace and with the folder. Plugins call it as `pluginsdk.Host.SetWorktree`. It is not an agent command (an agent `command.run` of it fails with not found): it accepts any existing directory, so agents switch worktrees through a plugin command that validates the target instead.

`workspace.worktree.check` `{id}` re-reads the workspace and, when `missing` is not empty, publishes `workspace.updated` with it; it changes nothing and returns the workspace. The git plugin calls it (`pluginsdk.Host.CheckWorktrees`) when a refresh finds a `missing` list it has not reported yet, so a worktree removed outside Clubmate moves every plugin and the app back to the folder without waiting for another event; the app then shows the one-time banner and clears the selection by switching the folder to its own checkout.

`client.register` marks the calling connection for the listed handles: `"workspace.show"` and `"ui.confirm"`; anything else is invalid params. The app registers both. Registration lasts for the connection. Plugin callers get invalid params.

`ui.focus` is open to any caller. It is invalid params when the workspace does not exist, the section is not registered or is app-scope, or `slot` is not `""`, `<section>.sidebar`, `<section>.main` or a slot the section declares in `slots` (a `rail: false` section accepts only `<section>.popup`), or `field` is true with a `slot` other than `<section>.sidebar`, or `node` is set without a `slot` or with `field`. It sends the `ui.focus` notification to every `ui.subscribe` subscription of that workspace (app-scope subscriptions never receive it) and returns their count as `delivered`. Plugins call it as `Host.Focus`, as `Host.FocusField` to focus the sidebar's text field, or as `Host.FocusNode` to name the node in the slot that should take focus.

### Focus

Where key focus goes in the Mac app, and when it moves (`SDUI/SDUIView.swift` `FocusRouter`, `WorkspaceView.swift`, `WorkspaceUIStore` `focusRequest`):

- **Focus moves for the user.** A key, a click, a command the user runs (app menu, palette, `cm`), or an agent tool whose job is to show the user something (`docs_open`, `editor_open`, a review the user asked for). Starting or selecting a session from an agent, cron, a trigger, voice or the phone never moves focus (agents.new from them selects the session at most), and new output, a session appearing or a notification never takes it.
- **A request names its target.** `ui.focus` shows the section at once and asks for a slot; with `node` it names the node in that slot, by id or by an id prefix before a `/` (agents asks for `<session>/composer`). Only that node takes it. The request waits up to 1.5 s for the node to be on screen, then any view of the slot may take it. The node's content may arrive after the request (a section's slots load when it is shown), so a request never goes to whatever the slot showed before.
- **Inside a slot.** `<section>.main` goes to the slot's composer when it shows one, else to its terminal or nvim surface, else to the pane; the pane does not take it before the slot has content. `<section>.sidebar` goes to the sidebar's tree or list, with `field` to its text field; `<section>.popup` to the popup.
- **Switching sections** without a request puts focus back where it was when you left that section (the composer, the tree, the terminal), unless that sidebar has been hidden since.
- **When the focused view goes away.** Hiding the sidebar moves focus to the main pane; closing or leaving the popup returns it to where it was before the popup; Esc or ⌃L/⌃H in a sidebar moves it to the main pane; showing or hiding Code's chat column moves it to the chat or to the editor. After sending, the composer keeps focus.

`ui.render` is invalid params for a workspace that has been deleted.

`ui.approve` shows the app's approval dialog for a plugin's own action and waits up to 60 s. `command` must start with `<plugin id>.`, `title` is 1 to 200 characters, `args` is at most 10 string fields of at most 200 characters each, shown as detail lines; `body` is optional text of at most 65536 characters (`approvalMaxBody`) shown in full in a scrollable monospaced box, e.g. a script. A body line starting with `──── ` (four U+2500 and a space) is drawn as a bold, highlighted header and every other line is plain, with wrapped lines indented, so no other line can pass for a header; a plugin that puts untrusted text in `body` escapes U+2500 in it. The core forwards it as `ui.confirm` with `plugin: true` and the `body`, and the dialog asks "<title>?" instead of "Allow agent to <title>?", since the core can't tell whether a person or an agent started the plugin's action. Denial, timeout, a busy dialog or no running app fail with the same denied errors as approvals of agent commands.

`command.run` routes a plugin command with `via` set to the calling connection's plugin id (`""` for the app and the CLI); the core overwrites any `via` the caller sent, so a plugin can trust it.

`command.run` resolves `id` to a command: a listed command id wins; otherwise `id` is taken as a capability name (see below). It fails with unknown command when neither matches; it is routed to the plugin that registered the resolved command, which receives the resolved command id (not the capability name) in `id`.

`editor.code-root {folder?}` (hidden, `editor-nvim.code-root`, `editor-vscode.code-root`) returns `{folder, root}`, the workspace folder Code shows, empty when the root is no folder's; with `folder`, a folder of the workspace (else `not a folder of the workspace`), it moves Code to that folder's selected worktree, also when no folder's selection changed. A move, however it came, publishes `<plugin>.root {workspace, folder}`, which the app follows like `git.changed`.

A capability is a generic name a command declares in `provides`, so callers need not know which plugin implements it. Only enabled plugins provide capabilities. A capability resolves to its default provider when one was chosen with `capability.set-default` and that plugin is enabled; otherwise to the first provider in plugin load (discovery) order whose plugin is running, else to the first provider (then `command.run` fails with plugin unavailable). When several commands provide one capability and no default was chosen, the core logs `capability X provided by A and B; using A` (command ids) once per distinct outcome. `command.capabilities` returns that resolution for every declared capability. `capability.providers` lists every plugin with a command that provides `name`, enabled or not, and `default` is the plugin the capability resolves to now (empty when none); Settings → General → Default editor shows the enabled providers of `editor.open` and sets it with `capability.set-default`, which fails with plugin unavailable for a disabled plugin and invalid params for one that does not provide it. The choice is kept in the core's storage and survives restarts. Bundled capabilities: `editor.open` (`editor-nvim.open`, `editor-vscode.open`), `editor.quickfix` (`editor-nvim.quickfix`), `editor.reveal` (`editor-nvim.reveal`), `terminal.new` (`terminals.new`) and `terminal.close` (`terminals.close`).

`command.broadcast {topic, workspaceId, args}` is an event with an ack: the core runs, in parallel, every plugin command whose `handles` lists `topic`, with the workspace `workspaceId` and the same `args` (each with its own `timeout`, `via` the calling plugin), and waits for all of them. It returns `{}` when every handler succeeded (or none exists); otherwise it fails with plugin error whose message is the handlers' error messages joined with `; `, without the `plugin <id> command.run:` prefix. A handler whose plugin is not running counts as a refusal (`plugin unavailable: <id>`). Any other error a plugin replies with reaches the caller as plugin error (`-32013`) with message `plugin <id> <method>: <message>` and `data` `{plugin, method, message}`, so a caller can show the plugin's own message without cutting the prefix; a broadcast refusal has no `data`. The publisher never names its handlers: the `git` plugin announces worktree changes this way (see the `git` plugin below), and `editor-nvim` and `agents` answer them.

`command.list` also lists the core primitives, with `plugin: "core"`, `agent: true` (except `workspace.worktree.set` and `diagnostics.collect`, which are `agent: false`) and `hidden: true` (so the palette leaves them out). `command.run` resolves a primitive id before plugin commands and capabilities, and runs it with the existing method's handler. Plugin ids `core`, `session`, `workspace`, `process`, `ui` and `diagnostics` are reserved (manifest load fails), and `command.capabilities` maps a capability named like a primitive to that primitive, as `command.run` does:

| Primitive | Method | Args | `workspaceId` |
|---|---|---|---|
| `workspace.list` | `workspace.list` | none | ignored |
| `workspace.open` | `workspace.open` | `{folders}` | ignored |
| `workspace.home` | `workspace.home` | none | ignored |
| `workspace.worktree.set` (not for agents) | `workspace.worktree.set` | `{id, repo, path}` | ignored |
| `diagnostics.collect` (not for agents) | `diagnostics.collect` | `{appVersion?, extra?}` | optional, the workspace whose UI is dumped |
| `session.list` | `session.list` (all workspaces; an agent call only its workspace's) | none | ignored; required for an agent call, which lists only that workspace |
| `session.create` | `session.create` (a login shell) | `{cwd?, title?}` | required, passed as the session's workspace |
| `session.kill` (destructive) | `session.kill` | `{id}` | an agent call is denied unless it is the session's workspace; the approval names that workspace |
| `session.send` (destructive) | `session.send` | `{id, text, enter?}` | an agent call is denied unless it is the session's workspace; the approval names that workspace |
| `session.read` | `session.read` | `{id, bytes?, raw?}` | an agent call is denied unless it is the session's workspace |

Plugin commands keep requiring a valid `workspaceId`. An agent `session.send` always needs approval, also into the agent's own session. Approval shows the full `text`, so the 200-character limit applies: agents send long input in chunks. An agent call accepts only the keys the resolved command's args schema declares, matched exactly (primitives and plugin commands alike; a command without a schema accepts no args, `{}` or none) (so `command`, `env` or a case variant like `Command` is invalid params: `args.Command: not allowed in agent calls`); keys inside object items are matched exactly too (`args.items[1].PATH: not allowed in agent calls`); the core rebuilds the args from those keys and dispatches that object.

An agent call is `command.run` with `agent: true` (the CLI's `command run --agent`; the MCP server always sets it). When it carries a `caller` that is an agent session (`agt_…`) and a non-empty `workspaceId`, the core checks that the session belongs to that workspace by asking the agents plugin (`agents.sessions {session}` in that workspace, at most 2 s; a positive answer is cached for the core's lifetime) and fails with denied (`-32014`) when it does not; when the agents plugin cannot answer, the call fails with that error (`cannot check the calling session …`), so it can be retried; without an installed agents plugin the check is skipped, and calls from plugins (graph steps) are not checked. This is a guardrail, not a boundary: `caller` is set by the client, so a call that leaves it out, or a call without `agent: true` (plain `cm command run`, which is user-level), is not tied to a workspace (#401). With no `$CLUBMATE_WORKSPACE_ID` (Claude outside Clubmate), `session_read`, `session_send` and `session_kill` need the session's own workspace in `workspace`, since the core denies an agent call on a session of another workspace. It resolves only core primitives and commands with `agent: true` (judged on the resolved command, never on the capability name); anything else fails with not found, as if unknown. Args are validated first. Then a `destructive` command needs the user's approval, and what the user approves is exactly what runs, so its args must be approvable or the call fails with invalid params before anyone is asked: an object (absent or `null` counts as `{}`); no args at all when the command declares no `args` schema; only keys its schema declares (`args.<key>: not declared`); at most 10 fields; each value at most 200 characters (a string's characters, otherwise its compact JSON); no number beyond ±2^53, anywhere in a value (`args.<key>: number outside ±2^53`), so the app shows it exactly. These limits live in the core (`approvalMaxFields`, `approvalMaxValue`, `approvalMaxInt`); the app checks the field and length limits itself and never truncates args. The core then sends the request `ui.confirm` `{title, workspaceName, command, args, timeoutMs, session?, from?}` (`ui.approve` adds `body?` and `plugin`) (`title` is the command's title, `workspaceName` the affected workspace's name or `""`, `command` the resolved id, `args` the args exactly as they will run, or `{}`; once approved, exactly these bytes are dispatched; `timeoutMs` is 60000; `session` is `{id, title, workspaceName}` of the targeted session, when the args name one: `id` for `session.send`/`session.kill`, `sessionId` for plugin commands such as `terminals.close`; `from` is `{id, title}` of the calling agent session, when the call carries a `caller`: `title` is the first line of its title from `agents.sessions` in the affected workspace, looked up for at most 2 s, and empty when that finds nothing) to one connection that registered `"ui.confirm"`: one that has a `ui.subscribe` subscription for the affected workspace if any, else the earliest connected. It waits up to 60 s for `{approved}`. The call fails with `-32014` (denied) and one of these messages, and the command does not run:
- `no app to approve`: no connection registered `"ui.confirm"`, or the request failed;
- `denied by user`: the answer was `approved: false` (when the answer carries a `reason`, that is the message instead);
- `approval timed out`: no answer within 60 s, or the app's own answer that it timed out;
- `approval busy`: that connection already has an approval pending (one per connection; the second is denied, not queued).

An approval outlives a dropped caller: if the caller disconnects while the alert is up, the request stays pending until it is answered or times out, and an approved command still runs. Non-agent calls (the app, plugins, the CLI without `--agent`) are unchanged: any listed command runs without approval. Agent mode is a cooperative guard, not a security boundary: any same-uid process can reach the core socket directly (and call without `agent`, or register `ui.confirm` itself).

The app answers `ui.confirm` with an alert "Allow agent to <title>?" whose text lists the workspace, the command, the targeted session (title, id and workspace), the calling session (`From: <title> (<id>)`, or `From: <id>` without a title) and each argument (shown in full; scalars of general category control, format, line separator or paragraph separator escaped as `\n`, `\r`, `\t` or `\u{…}`, so a value cannot fake extra lines or reorder text; the title, workspace and command are escaped the same way and cut at 200 characters with `…`). The alert has Allow and Deny (Deny is the default and holds focus; Allow never takes keyboard focus, so a space typed into the terminal as the alert appears can't approve; Esc denies). A `body` is shown below that text, long lines wrapped, with line breaks and tabs kept and every other such scalar escaped the same way; the box can't take focus, so it scrolls with the mouse or trackpad. If the args exceed the app's own limits (more than 10 fields, a value over 200 characters, or a body over 65536 characters) it shows no alert and answers `{approved: false, reason: "args too long to display"}`, so the alert never shows less than what runs. The alert closes itself 5 s before `timeoutMs` and the app answers `{approved: false, reason: "approval timed out"}`. It is a sheet on the key workspace window (else the first workspace window, else a modal alert) and asks for attention (dock bounce) until it closes.

editor-nvim keeps one nvim per workspace root, an entry of the workspace's `roots` (each folder's selected worktree, so every folder and every worktree of it has its own), else `$HOME`. Each runs in its root with its own socket (`<runtime>/<workspaceId>-<8 hex of sha256(root)>.sock`); a running session belongs to a root when its cwd is that root and it listens on that socket (or on the pre-worktree `<runtime>/<workspaceId>.sock`). The main and status slots show the nvim of the current root. The status slot's git branch is the one of the current buffer's repo (else the root's), read on `BufEnter`/`DirChanged` and again whenever the workspace's `fs.watch` reports a `HEAD` change (an in-place `git switch` in a checkout or a linked worktree) or an overflow. The current root starts as the first entry of `roots` that exists and stays until a path is routed to another folder (below) or exactly one folder's root changes (`workspace.updated` after a worktree switch of that folder), which makes that folder's root current; when the current root no longer exists or is no longer in `roots`, the first existing one is current again. When the current root changes, editor-nvim starts that root's nvim if needed and shows its surface, and the other nvims keep running. `editor-nvim.open` (absolute path), `quickfix` (first item's path) and `diffview` (`cwd`) first look, for each workspace folder, at that folder's own `git worktree list` (run in the folder's repo, never in the target path's repo): the worktree owning the path is the longest listed root containing it, compared with symlinks resolved. When the folder maps into that worktree (a folder at `<toplevel>/<rel>` maps to `<worktree>/<rel>`) and its current root differs, they call `workspace.worktree.set` for that folder with the worktree path as git prints it joined with `<rel>` (empty when it maps back to the folder itself), focus the editor and act on the new root's nvim. A path inside a folder that is already on the owning worktree, or inside a non-git folder's root (the longest such root), acts on that folder's nvim and makes it current; any other path acts on the current root's nvim.

`editor-nvim.restart` takes optional args `{force}` and restarts every running nvim of the workspace (and the current root's one if it is not running). Without `force: true` it first asks each of them for modified listed file buffers (`buftype` empty, `buflisted`; scratch buffers do not count) and fails with `unsaved buffers: <names>` (all of them, relative to the workspace repos and roots, `[No Name]` for unnamed buffers) if there are any; the sessions are left running. If an nvim does not answer within the RPC deadline it fails with `unsaved buffers: unknown (nvim not responding)`. If the session cannot be started its main slot shows the error and a Restart button, which restarts only the current root's nvim. `editor-nvim.stop-root` (hidden, not agent-visible; handles `git.worktree.removing`) takes args `{root, force}` (`root` absolute): it stops the nvim of that root with the same unsaved check and errors, and is a no-op when there is none; without `force` it first refuses with `unsaved buffers: <names>` when any nvim of the workspace (e.g. the main checkout's, with a file of a nested worktree open) has a modified buffer of a file inside `root`. A buffer counts for a root when no other nvim's root nested inside that root holds it. Every RPC to an nvim first asks for its mode: while nvim waits for input (a hit-enter prompt) the call is refused with `Neovim is waiting for input — press Enter in the editor` and never sent, so it can't run late; one that nvim started waiting on after it was sent fails after 2 s with `Neovim started waiting for input — press Enter in the editor; this request runs after that`. After it succeeds (even as a no-op), no nvim starts in that root (opening a file there fails with `the worktree is being removed`) until `editor-nvim.release-root {root}` (hidden, not agent-visible; handles `git.worktree.released`), which starts it again when the root is still the workspace's current root. `editor-nvim.unsaved {root}` (hidden, not agent-visible) returns the names of the modified file buffers of every running nvim of the workspace whose files are inside the root, except files another nvim holds inside its own root (a worktree nested in the root, such as `.worktrees/<branch>`) (same names and `unknown` error as restart), `[]` when there are none; it never starts or stops nvim. `editor-nvim.guard-switch {root}` (hidden, not agent-visible; handles `git.worktree.switching`) fails with `Save or discard unsaved changes first: <names>` (the names `unsaved` lists; `Save or discard unsaved changes first: unsaved buffers: unknown (nvim not responding)` when an nvim does not answer) and succeeds otherwise.

`editor-nvim.selection` (hidden, not agent-visible) takes no args and returns `{path, startLine, endLine, text}` for the current visual selection, else the last one (`'<` / `'>`), of the current root's running Neovim; `text` joins the selected lines with `\n`. It fails with `no selection` when there is none or Neovim is not running. `editor-nvim.checktime {root}` (hidden, not agent-visible; handles `git.worktree.switched`; `root` absolute, else an error) runs `:checktime` in every running Neovim of the workspace, so unmodified buffers changed on disk under that root reload whichever folder's Neovim holds them; it is a no-op when none runs.

`editor-nvim.diffview {cwd, rev}` (hidden, not agent-visible) takes an absolute worktree root `cwd` and a commit sha `rev` (7 to 40 lowercase hex digits; anything else is an error), routes to that worktree's nvim like `editor-nvim.open`, runs `DiffviewOpen -C<cwd> <rev> --untracked-scoped` there and focuses the Neovim section, so the working tree (uncommitted and untracked files included) is compared with `rev`. Clubmate never installs or configures diffview; when `DiffviewOpen` fails (for example without diffview.nvim) nvim's error shows as the "open failed" badge. The agents' "Review changes" and tool-card "Full diff" call it with the session's worktree and a turn's checkpoint sha.

`terminals.busy` (hidden) takes args `{sessionId}` and returns `{busy, process}`. `busy` is true when the session's process tree (`process.tree`) has a live descendant of the shell (the session's `childPid`); `process` is the `comm` of the newest such descendant (latest start time), `""` when not busy. Close the terminal?` before `terminals.close`; an exited one is not busy, so it closes without asking. The `search` plugin has one hidden, non-agent command, which the app's file picker (the agents composer's attach list) calls through `command.run`; results are never published. `search.files {query, limit?=50 (max 200)}` ranks workspace-relative paths (prefixed with the folder name when the workspace has several folders; a file inside a folder that is inside another folder is listed once, under the deepest one, so a repo added from its parent folder reads `api/main.go`, not `kufar/api/main.go`; a file reachable through two folders that are the same directory, under the first in order) from a per-workspace index of `git ls-files --cached --others --exclude-standard` (or a bounded walk outside git) capped at 200 000 paths, rebuilt in the background after `fs.changed`; it returns `{matches: [{path, absPath, positions, line?}], truncated, capped, indexing?}`, where `positions` are rune (Unicode scalar) indexes into `path`, a query ending in `:N` puts `line: N` on every match, and `indexing: true` (empty matches) means the first index is still building: retry. It refuses the home workspace with `search unavailable in the home workspace`. Walks never enter `~/Library` or another direct child of `~` when they start at `~` or above it; a workspace folder of `/` or a firmlink root such as `/System/Volumes/Data` is otherwise not guarded, since the user opened it.

The `git` plugin manages the worktrees of each git workspace folder through hidden commands; `repo` (optional) is a workspace folder's `path` and defaults to the first git folder. Worktrees always come from the folder's own `git worktree list`, compared with symlinks resolved, and map like editor-nvim's routing: a folder at `<checkout>/<rel>` maps to `<worktree as git prints it>/<rel>`, stored as empty when that is the folder itself. `git.worktrees {}` (agent) returns `[{repo, path, branch, head, committed, main, current}]` for every git folder, per folder the current worktree first, then newest `committed` first, ties in `git worktree list` order (`branch` empty when detached, `head` the short SHA, `committed` its committer date). `git.worktree-switch {repo?, path}` (agent) accepts only a listed worktree root (else `not a worktree of <repo>`) and calls `workspace.worktree.set`. `git.worktree-new {repo?, branch, from?, switch?, slug?, base?}` (agent) and `git.worktree-remove {repo?, path, force?, discard?}` (agent, destructive; `discard` removes a worktree with uncommitted changes and is refused unless the agents plugin calls it, for your tick on the Remove folder sheet) validate synchronously and return `{id}`, then run in the background behind a per-workspace busy gate (`another git operation is running` while one runs); `git.worktree-op-status {id}` (agent) waits up to 1 s and returns `{done, error?, path?, notice?, note?}`, `path` being the new worktree after a create or the clone after `git.clone`. When the call came from the app or the CLI (not an agent, not a plugin), the finished operation (new, remove, branch switch) also publishes `git.outcome {workspace, id, message?, confirm?}`: `message` is the error or else the notice for the banner; a remove refused with `unsaved buffers: …` without `force` carries instead `confirm {title, command: "git.worktree-remove", args: {repo, path, force: true}}`, which the app asks and then runs. `git.worktree-remove-prompt {repo?, path}` (not agent-visible) refuses like remove and returns that shape for the first question: `{title: "Remove worktree <name>? Its branch is kept.", detail?, command, args: {repo, path, seenSecrets?, seenOrphans?}}` (a detached worktree drops "Its branch is kept."); `detail` has one line each for `Terminals still in it: …`, `Deletes ignored <files>.` and `Loses <n> commits on no branch.`, and `args` carry those counts. When a folder's selected worktree goes missing the plugin itself switches the folder back to its own checkout (`workspace.worktree.set` to empty) and publishes `git.outcome {workspace, message: "Worktree <name> no longer exists — back on main"}`, once per disappearance. The app subscribes to `git.*`, takes `git.outcome` only with source `plugin:git`, shows `message`, asks `confirm` only when its command is `git.worktree-remove`, and reloads the list on `git.changed` and `git.outcome`; it never polls. New: the branch must pass `git check-ref-format --branch` unchanged, `<main>/.worktrees` and every existing component under it must not be a symlink (`worktrees folder must not be a symlink`), and `<main>/.worktrees/<branch>` must not exist; `slug` (same name rules as a branch, `'x' is not a valid worktree name`) replaces the branch in that folder name only; it runs `git worktree add <dir> <branch>` for an existing branch, else `git worktree add -b <branch> <dir> <sha>` from the HEAD of the worktree `from` (a listed worktree root, else `not a worktree of <repo>`; ignored when the branch exists) or, without it, of the current worktree. With `base: "default"` a new branch starts instead, inside the operation, from `origin/<default>` after `git fetch origin` (`from` then only picks the worktree `.clubmate/worktree-include` copies from); when the fetch fails or that ref is missing it starts from the local default branch (else the stale `origin/<default>`) and `note` says so. A repo with no `origin` remote has nothing to fetch: it starts from the local default branch with no `note`. A folder with `addedAfk` that isn't `seen` yet is not fetched at all and takes that same fallback, since the user hasn't looked at its config; once seen it fetches as usual. `<default>` is `origin/HEAD`, else `main`, else `master`; with none of them the operation fails. It then adds `.worktrees/` to `info/exclude` when the repo does not ignore it, then switches unless `switch` is `false` (`path` is returned either way). Remove refuses the main checkout (`cannot remove the main checkout`) and the checkout holding the folder itself (`cannot remove the checkout of the workspace folder`) synchronously; in the background it refuses a dirty worktree (`worktree has uncommitted changes`), re-reads the workspace and announces the removal with `command.broadcast`, never naming its handlers; every payload is `{path: <worktree>, root: <the folder's root in it>}`. First `git.worktree.removing` (plus `force`): a refusal is the operation's error and nothing else happens (editor-nvim's `stop-root` stops the root's nvim or refuses with `unsaved buffers: …`). Then `git.worktree.vacating` (best effort, failures are only logged: agents' `stop-root` closes the worktree's agent sessions, stops their processes and deletes their checkpoint refs), `git worktree remove <path>` (never `--force`, never deleting the branch) and, when the folder's stored selection then points at the removed worktree, `workspace.worktree.set` back to the folder; it always ends with `git.worktree.released` (editor-nvim's `release-root`), so a failed `git worktree remove` brings the current worktree's nvim back. `git.worktree-switch` also fails with `another git operation is running` while one runs. `git.repo-facts {path}` (not agent-visible, 20 s) describes a repo that need not be in the workspace and that nobody has approved yet, so it uses no network and runs nothing the repo's config names, from the checkout holding `path` (a repo, a worktree or a folder inside one; anything else: `invalid_params: not a git repo: <path>`): `{name, path, remote, branch, clean, dirty, behind, ahead, defaultBranch, fetched, brings: {graphs: [name], hooks: [name], instructions: [path], skills: [name]}, trusted: {hooks, graphs: [name]}}`. `name` is the folder in the main checkout, `path` the given path, `remote` the URL of `origin`, else of the first remote, with any login removed from an `http(s)` URL, `branch` empty when detached, `dirty` the number of `git status --porcelain` entries (`clean` when 0), `defaultBranch` empty when unknown. `behind` and `ahead` count against the branch's upstream, else `<remote>/<default>`, 0 with neither, from local refs only; `fetched` is always false: no fetch runs before a repo is connected, since `remote.<name>.uploadpack` and the like would run from its `.git/config`. For the same reason the status and rev-list behind these facts turn off every `filter.<name>` the repo's config sets and all lazy fetching, and leave submodules out. `brings.graphs` lists `.clubmate/graphs/<name>.json` with a valid graph name, `hooks` the regular files `setup.sh` and `teardown.sh` in `.clubmate/` of the checkout (`worktree-include` needs no trust and is not listed), `instructions` the relative paths of `CLAUDE.md`, `.claude/CLAUDE.md`, `AGENTS.md` and `CONTRIBUTING.md`, `skills` the folders of `.claude/skills/` holding a `SKILL.md`. `trusted.hooks` is true when every listed script is trusted with today's `.clubmate/` (so also with none), asking nobody; `trusted.graphs` comes from `graphs.trusted` and is `[]` when the graphs plugin does not answer within 2 s. `git.repos-in {path, dates?}` (not agent-visible, 20 s) finds the repos inside a folder that isn't one, the path need not be in the workspace: two levels down by `os.ReadDir`, skipping hidden directories, `node_modules` and symlinks, a directory holding `.git` (a directory or a worktree's file) being a repo it lists and doesn't enter; the walk stops after 3 s with `partial`. With `dates` each repo's last commit comes from `git log -1` through `gitrepo.Inert`, 8 at once for at most 10 s (`partial` again when that ran out), and repos come newest first, undated ones last by name; without, by name. It returns `{path, repo, repos: [{path, name, lastCommit?}], partial}`, `name` being the path below the folder (`kmessages/go-kmessages`), and `repo: true` with no repos when the path is itself a git repo or inside one. `git.clone {url, into}` (not agent-visible) refuses a relative `into` and one that holds anything, returns `{id}` and runs `git clone` outside the workspace's busy gate, so worktree work goes on meanwhile, with its own limit of 30 minutes and `GIT_TERMINAL_PROMPT=0`, so credentials are the user's git config and a missing one is the operation's error; a cancelled clone is sent SIGTERM so git removes what it wrote. In the home workspace `git.worktrees` returns `[]` and switch, new and remove fail with `worktrees unavailable in the home workspace`. `git.worktree-sessions {path}` (not agent-visible) returns `[{id, title}]` of the workspace's running sessions that started inside `path` or with a process whose working directory is inside it now, except those owned by a plugin with a `git.worktree.removing` handler (it stops them itself; editor-nvim's nvim). `git.branches {}` (not agent-visible) returns `[{repo, name, remote?}]` per git folder: local branches no worktree has checked out, then remote-tracking branches whose local name does not exist (the remote is the longest `git remote` name prefixing the ref, so remotes with `/` work), each newest commit first (one `git for-each-ref --sort=-committerdate`), at most 1500 local and 500 remote-tracking per folder. `git.branch-switch {repo?, branch}` (not agent-visible, destructive) validates the name (git's ref-name rules, then `check-ref-format --branch`) and that it is `refs/heads/<branch>` or `refs/remotes/<branch>`, returns `{id}` behind the same busy gate (refused at once in a folder AFK added that nobody has seen yet, see [agents](agents.md)) and runs in the folder's current worktree: a branch some worktree has checked out switches the folder to that worktree; else, after the `git.worktree.switching {root}` broadcast succeeded (a refusal fails at once with the handler's message, e.g. editor-nvim's `Save or discard unsaved changes first: <names>`; no handler means no check), `git switch --no-guess -- <local>` (a remote `origin/x` with a local `x`), or `git switch --track -- origin/x`; git's own refusal (local changes, conflicts) is the operation's error. When git warns that commits were left behind a detached `HEAD`, that warning is the status's `notice` (the app shows it in the banner). After a switch it broadcasts `git.worktree.switched {root}` for the folder's root (editor-nvim runs `checktime`; failures are only logged).

`git.worktree-index {}` (hidden, not agent-visible) lists every worktree of every git folder of the workspace for pickers that may hold hundreds: `[{repo, path, branch, head, committed, main, current, created?, lastOpened?, madeBy?, merged, remoteGone, locked?, lockWhy?}]`, the fields and order of `git.worktrees` plus seven. It uses no network and no `git status`, only one batch per folder (`worktree list`, `for-each-ref` with `%(upstream:track)` and with `--merged` against `origin/<default>` and the local default branch, `log --first-parent --merges` on those bases when a worktree's branch is merged into one, `show -s`), whose number of git processes does not grow with the worktrees. `created` is when a linked worktree was made, the time of its `.git` link, hand-made ones included. `lastOpened` is when the worktree last became or stopped being the selection, however that happened (the plugin compares the folder's root on `workspace.updated`; the root a folder has when first seen does not count), `madeBy` the plugin that called `git.worktree-new`, empty for the user and for agents calling it directly; both live in the plugin's storage per repo. `locked` and `lockWhy` say whether `git worktree lock` holds it and why. `merged` needs proof that the branch had commits of its own and they landed: its tip is a parent, other than the first, of a merge on the first-parent line of a default branch. An ancestor of main proves nothing, since a branch cut from main and left behind looks the same, so a branch fast-forwarded into main reads unmerged too; only the unsafe direction matters, because cleanup deletes on this. `merged` is always false for the main checkout, the default branch, a detached worktree and a branch at a default tip. A branch whose upstream is gone and that is no ancestor of a default branch gets the `gitrepo.LandedInert` check (an ancestor of the default branch, or else, when the branch changes something and the repo has no local merge attributes, a `git merge-tree --write-tree` of the branch onto the default branch whose tree is the default branch's own, written into a throwaway object directory with the repo's objects as an alternate, so no object, commit or ref lands in the repo) on its own goroutine, at most 4 at a time, remembered per tip and default tips in plugin storage (`landed/<repo>`, rewritten after each round with only the keys the repo's worktrees still use), so a plugin restart doesn't run it again and nothing waits for it; until it answers `merged` is false. Answers come from a per-folder cache, so a request runs no batch unless a folder has never been read. The cache refreshes in the background on `git.changed`, on `workspace.updated` and when a request finds it over a minute old, and before a git operation reports done, so `git.worktree-op-status` done means the index shows it.

`git.worktree-remove` takes `discard` and `left` from the agents plugin only: `discard` removes uncommitted changes, `left` says `repo` has just left the workspace and is opened directly, and with either the operation reads the worktree before anything closes and again after sessions closed, before teardown, and fails with the worktree kept if it holds a nested repo or has more changed files, secret files or orphaned commits than `seenDirty`, `seenSecrets`, `seenOrphans` (0 when absent); other ignored files don't count. What teardown writes doesn't count, and the removal is forced so those files can't strand the worktree. Without `discard` or `left`, `git.worktree-remove` and `git.worktree-remove-prompt` refuse a worktree of a folder AFK added that nobody has seen yet ([agents](agents.md)). Without them, `git.worktree-remove` also reads, before anything closes and again before teardown, the secret-looking ignored files (as on `git.worktree-state`) that no other worktree of the repo holds byte for byte (a copy made by `.clubmate/worktree-include` doesn't count) and the commits on no ref; more of either than `seenSecrets`/`seenOrphans` fails the operation with `removing it would lose ignored <files> and <n> commits on no branch; remove it from the app, which asks first`, keeping the worktree. Only the app may pass those counts there (anyone else: `only the app removes a worktree it would lose files or commits with`); the prompt above fills them in. So an agent's `git_worktree_remove` and the agents plugin's cleanup of a merged child worktree refuse such a worktree, and the cleanup shows that as its notice.

`git.worktree-unpushed` (hidden, not agent-visible) returns the paths of the linked worktrees whose tip is on no remote and not in the local default branch, from one `git rev-list` per folder.

`git.branch-delete {repo, branch, tip}` (hidden, the agents plugin's only) deletes a local branch with `git branch -d` rules: refused for the default branch, a tip that isn't the one seen and a branch with a remote-tracking ref of that name; `git branch -d` decides, and only the exact `git merge-tree` proof, read right before, goes past a branch it calls not fully merged, by deleting the ref only while it still points at the tip seen and dropping its `branch.<name>` config as `-D` would. Both run no hooks the repo names. No remote branch is touched.

`git.worktree-state {paths, proof?}` (hidden, not agent-visible) reads what removing worktrees could lose: `[{path, dirty, unpushed, ignored, secrets?, orphans, nested, tip, merged, landed, remote, locked?, lockWhy?, error?}]` in the order of `paths`, at most 8 worktrees at a time. `tip` and `merged` are read from git now, not from the cached index, by the rule above, and whatever deletes on the index re-reads them right before deleting; a squash check that hasn't answered reads as not merged. `remote` says a remote-tracking branch of that name exists, and `landed`, read only with `proof`, whether the change is in the default branch by ancestry or `git merge-tree --write-tree`, exact, with a net change from the fork and with no merge driver, attribute, merge setting or replace ref of the repo; `locked` and `lockWhy` say git holds it. A locked worktree can't be removed: `git.worktree-remove` refuses it before anything is stopped or vacated, as it does any worktree on the default branch. `dirty` counts changed and untracked files, each file of a new folder, whatever the repo sets `status.showUntrackedFiles` to; `ignored` the ignored files, which go with the worktree too and are taken as regenerable; `secrets` the paths, relative to the worktree, of the ignored files that look like secrets (`.env`, `.env.*`, `*.pem`, `*.key`, `.npmrc`, `.netrc`, `secretNames` in `plugins/git/index.go`), read with `git ls-files --others --ignored --exclude-standard --directory`, so a file inside an ignored folder (`node_modules/`) is not one: the sheets keep a worktree with a secret file unticked and name it, and count no other ignored file as lost; `unpushed` the commits on no remote and not in the local default branch, so a repo with no remote counts only the branch's own; `orphans` the commits on no branch, tag or remote, which only a detached worktree can have and which are lost with it; `nested` the initialised submodules and repos inside it, whose work these numbers can't see, so a worktree with any can't be removed through `discard` or `left`. A path that isn't a worktree of the workspace, or a git failure, gives `error` and no numbers: a sheet must not read that as clean.

Both run through `gitrepo.Inert`, like `git.repo-facts`: nothing the repo's config names runs (fsmonitor, filters, `log.showSignature` with `gpg.program`) and a partial clone fetches nothing.

The `backlog` plugin renders `backlog.sidebar` and `backlog.main` for every open workspace, again on `backlog.changed`, `agents.changed` and `agents.turn`. `backlog.sidebar`'s `tree` `tasks` groups the tasks under one `action` row per status (id `group:<status>`, label `<Status> · N`; `expand`/`collapse` fold it, `select` on it does nothing), each task a row with id its number. `backlog.main` is the selected task: the `header` `heading` (title as the `title` field; its buttons are the primary action the plugin picks from the owner — `start` "Start agent · ‹what it passes›" or `open` "Open ‹session or run›" (action `reveal`), both ⌘↩ — then `release`, `takeback`, `done`, `delete`), the autosaving `form` `edit` (action `save.<id>`) with the `lanes` `owners` under the description (title `Owners`; actors `you`, a session id or `run:<run id>`; a move's `ref` is that session id or `run:<run id>`, and `openMove` with it opens the session in Agents or the run in Graphs) and the Owner / Last owner rows (a session is a button `owner`, action `reveal`, or `lastOwner`, action `revealLast`), and under it the Links and Attachments blocks: a muted count row, a `list` `links` (item id the other task's number; `select` selects that task, menu `unlink`) or `attachments` (item id the index; menu `detach`), and a `textField` `linkText` (action `link`) or `attachText` (action `attach`) whose submitted text adds one, a bad one coming back as the field's `error`. While a plugin runs, the supervisor sends it `plugin.ping` every 15 s. Any reply counts, an error such as method not found included. After 3 pings in a row get no reply within 5 s, the plugin counts as crashed (`lastError` `plugin stopped answering plugin.ping`): its process group is killed and it restarts with the usual backoff. The SDK answers `plugin.ping` on a goroutine of its own, so a busy or deadlocked handler does not trip it; it catches a frozen process (stopped, or its whole runtime stuck) or one that no longer reads its stdin.

When a plugin enters the `running` state, and when a run or start attempt ends (after its new state — `backoff`, `failed`, `stopped`, `starting` for a restart — is set), the core publishes `plugin.changed` `{id, running, enabled}`; it also publishes it after `plugin.set-enabled` and `capability.set-default`.

`plugin.restart` `{id}` asks the supervisor to restart one plugin and returns at once; poll `plugin.list` for the outcome. A running plugin is stopped the way the core stops plugins (`plugin.shutdown`, then SIGTERM, then SIGKILL of its process group) and spawned again right away; a plugin in backoff is spawned now; a failed plugin is supervised again. A disabled plugin fails with plugin unavailable (`-32012`). A requested restart is not a crash: `restarts` does not grow, the crash window and backoff start over and `lastError` is cleared. As on a crash, the plugin's bus subscriptions, process roots and rendered slots go with the old connection, so the new process renders and subscribes again from `plugin.initialize`; the manifest (sections, commands) is the one read at core start. An unknown id fails with not found (`-32004`). Each plugin's page in Settings has a Restart button.

Any plugin can be turned off. A manifest with `"enabledByDefault": false` starts off until the user turns it on (the bundled `editor-vscode` does); the user's choice, set with `plugin.set-enabled` (Settings → the plugin's page, or `clubmate plugin enable|disable <id>`), is kept in the core's storage and wins over the manifest from then on. A disabled plugin has state `disabled`, `enabled: false` and pid 0 in `plugin.list`; it is not spawned, its sections are left out of `ui.sections` (`ui.focus` on one fails with plugin unavailable), its commands are left out of `command.list` (so MCP tools and the palette lose them, and `handles` no longer routes bus events to them) and it provides no capability. Turning one off stops it as on core shutdown and returns once it has stopped, so its rendered slots are cleared; turning it on starts it as at core start with a fresh crash count. Clients refetch `ui.sections` on `plugin.changed`. Upgrading from a core where the Code section chose VS Code with editor-nvim's `editor: "vscode"` setting turns `editor-vscode` on once and makes it the `editor.open` default, and carries the accepted VS Code Server License Terms and the server port over to it.

`clubmate diagnostics [-o file.zip]` calls it without `extra` (60 s deadline) and copies the archive to `-o` (default `./<archive name>`), printing the path. When the call fails (no core, a dial error, the deadline, or an error reply) it neither starts the core nor reads any database: it writes the zip itself with `info.json` (the CLI's own build, `macOS`, `arch`, `collectedAt`, `"core": "unreachable"` and `coreError`), the same log tails and a README noting `core unreachable: no workspace/session/plugin/UI state`.

The app's Help ▸ Collect Diagnostics… first shows a sheet listing the files and `Terminal output, environment variables and plugin storage are not included.`, with an unchecked box "Include a screenshot of the window (may show terminal and editor contents)" and Cancel (default) / Save…. On Save… it passes its own settings (keys containing `token`, `secret`, `password` or `key`, case-insensitive, read `<redacted>`), the key window's workspace and its version, and `window.png` (its own drawing of the key window, never a Screen Recording prompt) only when the user opts in; then it asks where to save (default `~/Downloads`), moves the archive there and reveals it in Finder. Without a core connection it points to `cm diagnostics`.

## Notifications

- `ui.updated` `{subscription, view}`: `view` is a `SlotView`. On subscribe, the current views of the workspace are replayed first. A subscriber is never dropped for falling behind: while the core waits to write to a slow connection, a newer render of a slot replaces the one still pending for that slot, so a slow client skips intermediate revs and gets the latest view of each slot. A plugin connection may subscribe too: it gets them as `Plugin.UIUpdated` (`pluginsdk.UIUpdate{Subscription, View}`), and uses `Host.UISubscribe` / `Host.UIUnsubscribe`, `Host.UIGet`, `Host.UISections` and `Host.UIEvent`.

### Delta frames

A subscriber that passed `delta: true` to `ui.subscribe` may get a view without `tree`: `{workspaceId, slot, owner, rev, base, delta}`. `base` is the rev of the last view of that slot the core sent on this subscription, and `delta` is the new tree in which any subtree that also occurs, byte for byte, in the tree of `base` can be replaced by `{"ref": [i, j, …]}`: the child indexes leading from the root of the `base` tree to that node (`{"ref": []}` is the whole `base` tree, an identical re-render). Only nodes are referenced (the root and elements of `children`), never props, so a ref may stand wherever a node may. The client resolves refs against its tree of rev `base` and keeps the resolved nodes as they are, so unchanged subtrees keep their decoded values.

- The first view of a slot on a subscription (the replay, or the first render after it) is always a full `tree`; so is a view whose delta would not be smaller than the tree.
- The core diffs against what it sent, not against rev − 1, so skipped revs (a slow client) still yield a delta.
- A client whose tree for the slot is not at rev `base` (or whose ref does not resolve) resubscribes: it calls `ui.subscribe` again, unsubscribes the old subscription and reloads with `ui.get`; the new subscription starts with full trees.
- Without `delta`, or from a core that predates it (it ignores the unknown param), every view carries the full `tree`; old clients never see `base` or `delta`. `ui.get` always returns full trees.

A subscriber that also passed `append: true` may get string values in a delta as `{"append": "<tail>"}`: the value is the string at the same prop in the counterpart node followed by `<tail>`. The counterpart of the delta root is the root of the `base` tree, and the counterpart of the child at index `i` of a delta node is the child at index `i` of that node's counterpart (none when out of range). The prop is found by the same keys from `props` down through nested objects (`props.body.text`), never through arrays. An object of exactly the shape `{"append": <string>}` is an append only where the counterpart's value at that place is a string; anywhere else it is a plain value. The core uses an append only when the tail is shorter than the whole value and never sends a delta in which a plain value of that shape stands over a string in the counterpart (it sends the full `tree` instead). Without `append`, or from a core that predates it, deltas carry whole strings.

A subscriber that also passed `keep: true` may get array elements in a delta as `{"keep": k}`: the element is element `k` of the array at the same prop in the counterpart node, found the same way as for an append (arrays are only looked into one level: an element is kept whole or sent whole). An object of exactly the shape `{"keep": <number>}` is a kept element only inside an array whose counterpart value is an array; anywhere else it is a plain value. The core keeps only elements of at least 16 bytes that occur byte for byte in the counterpart array, and never sends a delta in which a plain element of that shape stands in an array over an array (it sends the full `tree` instead). Without `keep`, or from a core that predates it, deltas carry whole arrays.

The app subscribes with `delta: true, append: true, keep: true`. While an agent streams into a ~620 KB `agents.main` tree, each frame is the new tail of the streaming message plus refs for every other node.
- `ui.focus` `{subscription, section, slot, field}`: the client should show `section`, and `slot` when non-empty, for that subscription's workspace. `field` is present (true) only when the caller passed it: the client puts keyboard focus into the first `textField` of that sidebar instead of its list or tree. A focus to a hidden sidebar shows it first.

### Render deltas

A plugin may render a slot as `{workspaceId, slot, base, delta}` instead of `{tree}`: `base` is the rev the core returned for that plugin's last render of the slot, and `delta` is the new tree in the delta frame format above against the tree of rev `base`, with refs, string appends and kept array elements all allowed (the core always reads `{"append": …}` and `{"keep": …}` as described there, so a plugin encodes with both on). The core resolves it byte for byte into the full tree, which then goes through the same strict decoding and validation as a `tree` and replaces the slot like any render; subscribers and `ui.get` never see the plugin's delta.

- `tree` together with `delta`, or `delta` without a `base` ≥ 1, is invalid params; a delta that does not resolve (a ref outside the base tree, trailing data) or resolves to more than twice the base tree plus the delta's own size is an invalid tree.
- A `base` that is not the slot's current rev (another render came in between, the slot was cleared, or the core restarted) fails with `-32016` ("delta base is not the slot's current rev") and leaves the slot as it is.
- `pluginsdk.Host.Render` / `RenderJSON` do this on their own: after a slot's first successful render they send the delta against the last tree the core accepted for it, and on any error from a delta render resend the full `tree` once. A tree whose delta would not be smaller goes as a full `tree`. The SDK remembers that tree for the 64 most recently rendered (workspace, slot) pairs; a slot it has forgotten (for example of a deleted workspace) goes as a full `tree` the next time.

While an agent streams into the ~726 KB `agents.main` tree, each plugin→core render is ~10 KB (the same size as the app's frame) instead of the whole tree.

## File watching

`fs.watch` starts one FSEvents stream over the workspace's repos and roots (the union, deduplicated) as they are at call time (repos added or worktrees selected later are not covered; call `fs.watch` again). It ends on `fs.unwatch` or when the connection closes. Repos that cannot be resolved (missing or deleted) are skipped and the rest are watched; a workspace with no resolvable repos gets a watch that never emits. When a repo is a linked git worktree (`.git` is a file with `gitdir: <path>`), the watch also covers that worktree's gitdir and the main repository's common dir (from `<gitdir>/commondir`), so commits, checkouts and ref updates made in the worktree emit paths under `<main>/.git/` (only `HEAD`, `index`, `refs/heads/**` and `worktrees/<name>/{HEAD,index}`, and nrev's `review.db` / `review.db-wal` in either git dir are reported from inside `.git`). Roots are symlink-resolved, so paths are real paths (`/private/var/...`, not `/var/...`).

- `fs.changed` `{watch, workspaceId, paths, overflow}`: sent to the watching connection with a 200ms coalescing window. `paths` is deduplicated. Under any `.git/`, and under a linked worktree's gitdir and the main repository's common dir, only `HEAD`, `index`, `refs/heads/**` and `worktrees/<name>/{HEAD,index}` are reported. A window with more than 1000 paths, or one in which FSEvents reports dropped or coalesced events (MustScanSubDirs, KernelDropped, UserDropped), is sent as `overflow: true` with `paths: []`; the receiver rescans.

Plugins receive it as `Plugin.FSChanged`, and use `Host.WatchFS` / `Host.UnwatchFS`.

Unavailable in the home workspace (`Agents aren't available in the home workspace`). - `agents.wait {sessions: [id], timeout?}` (`timeout` in seconds, default 120, at most 300; the manifest gives it a 310 s command timeout) waits for any of the listed sessions of the workspace (not only the caller's children) to stop `running`: it returns at once when one of them is not `running`, else on the first status change of any of them, else when any of them starts a new turn (its `turn` grows, e.g. queued prompts went out), else when the calling session has queued prompts from the user (not from agents), else when the timeout ends, and fails with `sessions is empty` or `unknown agent session: <id>`. It returns `{sessions, message?}`: `message` `{text, attachments?}` holds the caller's queued user prompts (texts joined with blank lines, attachments concatenated), taken off the queue so they are not sent again; `sessions` is, in the order given, `[{session, status, turn, stopReason?, error?, asks, permission?: {request, title, kind, options: [{optionId, name, kind}]}}]`: `turn` is the latest turn and `stopReason` its stop reason; `permission` is the oldest pending permission (`request` the permission entry's id for `agents.permission`, `title` and `kind` from its tool call). `asks` is true when the status is `done` and the session's last agent message ends with `?` once trailing whitespace, `*`, `_` and `` ` `` are trimmed: the agent is asking a question. It is computed when the status is set and stored in the record.

`review {id, worktree, base, head, reviewed, total, comments, note?}` when it came from `agents.send-review` (logged as `review` on the prompt); the log keeps `voice: true` on the prompt, so it survives a reload), `agent` / `thought` (`text`), `tool` (the merged ACP tool call fields under `tool`, without `rawOutput` and `_meta`, which stay only in the log; unfinished calls of a cancelled turn get status `cancelled`), `plan` (one per turn), `permission` (`toolCall`, `options`, `outcome` once answered), `elicitation` (`elicitation` the normalised request `{mode, message, url?, elicitationId?, toolCallId?, fields?}`, `response` `{action, content?}` once answered, `completed` after `elicitation/complete`), `notice` and `compaction` (one per `compactionId` of `compaction_update`; `compaction {status, error?}`, `text` the summary: the streamed `compaction_summary_chunk`s, replaced by the update's `summary` when it has one; `initialize` advertises `session.compaction`, an `in_progress` one shows `cancelled` once no turn runs; the client shows it as a collapsed `think` card "Context compacted" with the summary as its body). `usage` is the latest `usage_update` (`{used, size, cost?}`; a report without `cost` keeps the previous cost); the log keeps only the last of a run of usage updates. `last: true` keeps only the last turn (in `turns` and `entries`) and sets `modes`, `configOptions` and `commands` to null, so an orchestrator can read a child's latest turn cheaply; `compact: true` drops the images in tool calls' content and sets `commands` to null. `cursor` is opaque (`<plugin start>.<revision>`); every entry gets a new revision when it is added or changes (including an unfinished tool call shown `cancelled` once no turn runs, and back), and every entry of a transcript read back from its log, so a `since` after that returns them all. `since: <cursor>` returns only the entries with a later revision, in log order, with `delta: true`, and ignores `fromTurn`; the client replaces entries by `(kind, id)` and appends the new ones. A cursor from before the plugin restarted (or with `last`) is ignored: the result is the normal one without `delta`.

At each turn end (before `agents.turn`), the commits reachable from the worktree's `HEAD` but not from the checkpoint's parent nor from any other local or remote branch get a git note in `refs/notes/clubmate` (`Clubmate-Session`, `-Turn`, `-Agent`, `-Title`, `-Prompt` (first line, 80 characters), `-Checkpoint` lines, committed as `Clubmate <clubmate@localhost>`), unless they already have one; the turn's log then gets a `commits {turn, commits}` event. `path` (absolute, or relative to `cwd`, which defaults to the calling agent session's worktree) runs `git blame --porcelain` and returns the ranges of consecutive lines whose commit has a note; `commit` resolves any revision in `cwd` and returns its note, or no attributions.

Each turn also pins `refs/clubmate/cp/<session>/<turn>.end` when it ends, and both checkpoints get a `Clubmate-Worktree: <git toplevel>` trailer. For commit C with parent P (an empty tree for a root commit), the snapshots are the checkpoints whose parent is P and whose worktree is the one of C's note's checkpoint (else the cwd's, else the only one; old checkpoints without the trailer match by C's note's session), plus the note's checkpoint itself, ordered per session by turn and across sessions by commit time. Clubmate writes the throwaway chain P's tree → snapshots → C's tree with `commit-tree` (no refs) and runs `git blame --porcelain -L` over the new-side hunks of `git diff -U0 P C` on its tip: a line from the step into `<turn>.end` is `ai` with `url` `clubmate://session/<id>#turn=<n>`; the step into a start checkpoint is `human` when no turn is open, that turn when exactly one is open and has an end checkpoint, else `unknown`; the last step is C's noted turn, else as a start step (`unknown` when no snapshot matched). Lines blamed to P's tree are left out, and so are files without changed lines. `id` is a UUID from the SHA-1 of the commit; `timestamp` is the committer date.

## Bus topics

Every event is `{seq, topic, source, time, workspace?, payload}`; `workspace` repeats the payload's top-level `workspace` when it is a string, so a consumer can filter by workspace without decoding the payload. `source` is set by the core, never by the publisher: `plugin:<id>` for a plugin's `bus.publish`, `cli` for any other connection's (`clubmate bus publish`), `core` for the core's own events, `agent` for `notify.posted` from an agent. Anyone on the socket can publish any topic, so a consumer that acts on an event checks its source: the app takes `git.outcome` only from `plugin:git`, graphs counts `agents.turn` only from `plugin:agents`, and triggers fire only on events from their topic's owner ([Triggers § Sources](triggers.md#sources)).

Retention: the core prunes `bus.db` when it starts and every hour. An event is kept while it is less than 30 days old or among the newest 10 000 events, and the newest event is never pruned, so `bus.head` never goes back. A `bus.cursor.set` cursor also keeps every event from its seq on, for at most 90 days (cursors have no owner that could expire them; a forgotten one must not stop pruning). Pruned space is reused, the file does not shrink. `bus.read` and `bus.subscribe` with an `after` below the oldest kept event start at the oldest one without saying so: `bus.head` returns `{seq, oldest}` (`oldest` is 0 when the store is empty), so a consumer that resumes from a stored seq can tell it missed events. Reads of exact topics use the `(topic, seq)` index; a pattern with a `prefix.*` scans the seq range.

- `workspace.created` `{workspace, info}`, `workspace.updated` `{workspace, info}`, `workspace.deleted` `{workspace}`: published by the core; `workspace` is the id, `info` the full workspace. `workspace.updated` is published when a repo is added to a workspace (`workspace.folder.add`), it is renamed (`workspace.rename`) or a folder's worktree selection changes (`workspace.worktree.set`). Existing `fs.watch` streams do not follow; re-watch on this event.
- `agents.changed` `{workspace, session, kind, status?, request?, requestKind?}`: published by `agents` when a session is created, changes status or is deleted, coalesced per session and kind (`created`, `status`, `deleted`); and once per permission or elicitation request when it stops pending (answered on any device, by a parent agent, completed by the agent, or cancelled), kind `resolved` with the request id in `request` and `requestKind` `permission` or `elicitation`, never coalesced; kind `review` (coalesced) for the opener and recipient sessions when an `editor-nvim.review` payload of theirs arrives, so the phone re-reads `reviewProgress`. Streamed transcript updates are not published.
- `agents.turn` `{workspace, session, turn, status, asks, finished, reply, cronJob?, trigger?}`: published by `agents` at every turn end (`status` after it: `done`, `error`, `closed`, `waiting` when a permission is still pending, or `running` when queued prompts start the next turn), when a session's agent fails (`error`), when a running session is closed (`closed`, once: the turn end that follows publishes nothing) and when a permission request starts waiting (`waiting`). `turn` is the session's 1-based number of the turn the event is about (as in `agents.transcript`'s `turns`); `asks` is as in `agents.wait`; `reply` is the turn's last agent message, trimmed and cut at 4000 characters (`…` appended), or empty when the turn has none. `finished` is true when `status` is `done` and no descendant session is `running`, `waiting` or asking its parent (as `childStatus` counts them). `cronJob` / `trigger` name the cron job or trigger that started the session with `agents.new` (stored on the session, also in `agents.sessions`). Not coalesced: one event per occurrence.
- `notify.posted` `{id, workspace, session?, owner?, title?, message, kind, agent?, ts}`: published by `notify.post` (`cm notify`, the `notify_post` MCP tool). `agent` is true (and the event source `agent`) when an agent called it through `command.run` with `agent: true`. `kind` is `needs-input`, `permission`, `question`, `done`, `stuck` or `info`; `message` is at most 1000 characters and `title` 120 (longer ones are cut with `…`); `owner` is the owner of a `ses_` session (e.g. `terminals`); `ts` is RFC 3339 UTC. `notify.post` checks that the workspace exists and that a `ses_` session belongs to it (other session ids pass as they are when shaped like `agt_<16 hex>`), and allows 5 calls per 10 s per workspace and 20 in all (error code -32015, "too many notifications", beyond that), counted separately for plugin callers (not agent calls) and for everyone else.
- `git.changed` `{workspace}`: published by `git` (debounced 300 ms) when a `HEAD` file in a git dir of an open workspace's folder changes (an in-place `git switch` in a checkout or a linked worktree) or its `fs.watch` overflows; the app reloads `git.worktrees` for that workspace, so the titlebar pill follows the branch, and `agents` rereads the branch names of its sidebar groups.
- `editor-nvim.file` `{workspace, root, path}`: published by `editor-nvim` when a Neovim enters a buffer of another file (absolute `path`; buffers without a file are skipped); `agents` shows it in the Code chat panel when `root` is the panel's worktree.
- `processes.killed` `{workspace, pids}`: published by `processes` when auto-kill terminates orphans of a workspace; never published with empty `pids`. Auto-kill (every 10 s) covers every workspace whose stored `autokill/<id>` is on, read at plugin start for workspaces that still exist, not only those opened since.
- `remote.watching` `{workspace, sections}`: published by `remote` when the set of sections whose non-popup slots paired phones watch in a workspace changes (sorted, unique; `[]` once none); `remote` also publishes `[]` for every workspace when it starts. `processes` and `agents` render a watched section as if the Mac showed it and restore the set on start from the bus history (`pluginsdk.Host.WatchedSections`, which reads only this topic through the index). A watch lives as long as the phone's event stream, which reconnects and announces its sections again, so a `remote.watching` older than the 30-day retention is never the current one in practice. See [Remote § Plugin UI on the phone](remote.md#plugin-ui-on-the-phone).

## Core notifications

- `workspace.show` `{id}`: sent to every connection that registered `"workspace.show"` (not to plugins, not to the caller of `workspace.show`, `workspace.open` or `workspace.home`); the client shows that workspace.
- `core.stopping` (no params): sent to every connected client (not to plugins) after `core.shutdown` has replied and right before the core stops. A client that sees the connection end after `core.stopping` treats the stop as intentional and does not restart the core; a connection that ends without it is an unexpected loss.

A socket client that does not take a frame within 10 s (`clientWriteTimeout`) is disconnected, with its bus subscriptions and file watches; until then notifications to it queue behind the stuck write. The app reconnects.

## Presence

The core publishes `ui.opened` `{workspace}` on the durable bus when a workspace's UI subscriber count goes from 0 to 1, and `ui.idle` `{workspace}` when it goes from 1 to 0.

## Visible section

Clients keep per-workspace UI state with `ui.state.get` / `ui.state.set` `{workspaceId, state}` (client callers only). `ui.state.patch` `{workspaceId, key, value}` sets one top-level key atomically in the core, so concurrent writers to the same workspace do not drop each other's keys; a `null` value deletes the key. Its `section` field is the section the workspace's window shows: the app has one window per workspace and writes `section` when it opens the workspace and on every switch. When a `ui.state.set` or `ui.state.patch` changes `section`, the core publishes `ui.section` `{workspace, section}` on the durable bus. Plugins read the current value with `ui.state.section` (`pluginsdk.Host.SelectedSection`).

`processes` uses it to skip work nobody sees: its refresh samples every second while some present workspace shows the section and every 10 s while none does (each such sample fills the 10 s it covers in the history, so the charts keep their time scale), records history for every present workspace, reads a core process's argv once per pid and start time, and renders only workspaces whose section is `processes` or unknown (`""`), or that a phone watches (`remote.watching` lists `processes`, see [Remote § Plugin UI on the phone](remote.md#plugin-ui-on-the-phone)). On `ui.section` to `processes`, and when a phone starts watching it, it renders at once. `processes.sidebar` is sent again only when its sessions or selection changed; the core keeps the last tree for new subscribers.

`agents` renders only for present workspaces (it renders every workspace once at start-up). `agents.sidebar` is always rendered for a present workspace; `agents.main` only while the section is `agents` or unknown, and its `editor-nvim.sidebar` panel only while the section is `editor-nvim` or unknown; a section a phone watches (`remote.watching`) counts as shown. A hidden slot keeps its last tree in the store until the next render, which `ui.opened`, `ui.section` and `remote.watching` trigger. `agents` encodes each tree once and sends the bytes with `pluginsdk.Host.RenderJSON`, skipping the call when they equal the last sent tree. Composer command descriptions are clipped to 300 runes (`…`), as the client shows them on one line.

## Removed names

v0.0.19 removed the names the core accepted before the Project → Workspace rename and the command id rule: the `project.*` methods and bus topics, the `projectId` param and session meta key, `CLUBMATE_PROJECT_ID`, `--project` and `clubmate project …`, the camelCase command ids (`agents.afkDefault`, `agents.finishDefault`, `remote.setPort`, `remote.cancelPair`) and their MCP tool names, the manifest `scope` `"project"`, a workspace's `repos`, `roots` and `missing`, and `closed` in `agents.sessions`. Old method and command names fail as unknown, a `"project"` scope fails the manifest, and `projectId` is ignored. Only `remote`'s `workspaces` still returns `roots` (see `docs/remote.md`).

## Plugin runtime dir

The core creates `<runtime>/p/<pluginId>` (mode 0700) and passes its path to the plugin in `CLUBMATE_PLUGIN_RUNTIME_DIR` (`pluginsdk.RuntimeDir()`). It passes `<state>/plugin-data/<pluginId>` in `CLUBMATE_PLUGIN_STATE_DIR` (`pluginsdk.StateDir()`) for data that must survive restarts; the plugin creates it when needed. It also passes the build flavour in `CLUBMATE_FLAVOR` (`pluginsdk.Flavor()`): `release` for release builds, `dev` otherwise.

The core also passes the app's resources directory in `CLUBMATE_RESOURCES` (`pluginsdk.ResourcesDir()`), `Clubmate.app/Contents/Resources` when run from the app; bundled tools live under `tools/` and `nvim/` there.

A plugin's `session.create` (`pluginsdk.Host.CreateSession`) also takes `env`, entries added to the environment the session inherits, `unsetEnv`, names of variables removed from it first, and `pathAppend`, directories appended to the end of the session's `PATH` (entries already in it are skipped).

## Forms

A `form` collects the values of the `textField`, `folderField`, `toggle`, `select` and `choice` nodes (with a `choice`'s `other` field) and the title of a `header` with `field` among its descendants (nested forms collect their own fields), keyed by the field node `id`. The value is the field's current text, bool, option value (a `radio` `choice` with nothing picked has none) or string[] (`folderField`: chosen paths, `check` `choice`: picked option values); fields that disappear from the tree are dropped.

- A `button` without an `action` prop inside a form submits the form: the form sends `props.action ?? "submit"` with the collected object as `value` and the form's `id` as `nodeId`.
- Return in a `textField` without an `action` prop submits the form the same way.
- With `sheet: true` the Mac presents the form as a sheet over the window while the node is in the tree (it leaves the slot's layout) and dismisses it when the node goes; ⎋ and closing it send `cancel` with the form's `id` as `nodeId`. Inside it a horizontal `stack` of only buttons is the action row, right-aligned, and its button with action `cancel` prints ⎋ (as in a popover form). The phone draws it in place.
- Fields without an `action` prop inside a form are silent: they only update the collected values.
- A field or button with its own `action` prop sends its own event per the contract above (fields still update the collected values); it does not submit the form.
- A button with its own `action` and `withForm: true` sends its own event too, but with the form's collected object as `value` instead of `null` (nodeId and action stay the button's); it does not submit the form. A `choice` with its own `action` in a form sends that action on every pick with the form's collected object as `value`, the pick already in it. The agents plugin's question uses it, so a pick carries the note typed in Other.
- With `autosave: true` the form also submits itself when the user edits a field: 600 ms after the last keystroke in a `textField` or when it loses focus with unsent edits, at once on a `select`, `toggle` or `folderField` change, and when the form leaves the tree with unsent edits. A submit (button, Return) sends at once and drops the pending one. Values a render sets do not count as edits. While a `textField` in an autosave form has focus, a changed `value` from the plugin does not replace the text (the field is the source of truth while the user types; its next save carries its text). The plugin answers each submit like a normal one; a form without `autosave` behaves as before. From the first edit until the last submit is answered, the form's submit buttons (buttons without an `action` prop) draw `Saving…` like a `loading` verb but keep their clicks and shortcut, so an explicit save still goes through.
