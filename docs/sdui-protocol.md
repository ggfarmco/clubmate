# SDUI protocol

Plugins render trees of nodes into slots; clients draw them and send events back. Every tree is validated by `internal/sdui` (max 5000 nodes, depth 32). Violations fail with `ErrInvalidTree`.

## Node

```json
{"type": "button", "id": "new", "props": {"label": "New"}, "children": []}
```

- `type`: one of the types below.
- `id`: required for interactive types, unique within a tree.
- `props`: only the listed props are accepted; unknown props are rejected. `*` marks required props.
- `children`: count limited per type.

Interactive types (`tabs list tree table button textField folderField toggle select form toolCard permissionCard composer`) require an `id`. All but `toolCard` and `composer` accept an optional `action` prop: a string of 1-64 chars matching `^[a-z][a-zA-Z0-9.-]*$` (camelCase allowed, e.g. `showEarlier`). It overrides the default action name sent in `ui.event`. Action names inside props (`menu`, card `actions`) follow the same rule.

## Item shapes

`items` and `options` accept `null` as an empty list.

- item (`tabs`, `list`): `{id*, label*, detail, icon, badge, menu}`, strings except `menu`, ids unique and non-empty. `menu` is a list of menu entries (`list` and `tree` show them as the row's context menu).
- menu entry (item `menu`): `{action*, label*, confirm}`: choosing it sends `action` with the item id as value; with `confirm` the client asks first.
- tree item (`tree`): item fields plus `muted` (bool), `hasChildren` (bool), `expanded` (bool), `children` (tree items), and the review columns `additions`, `deletions`, `comments` (non-negative integers) and `reviewed` (bool).
- review header (`tree` `review` prop): `{base*, head*, baseRef, headRef, readOnly, mode, progress, warning, error, chips}`, all strings except `readOnly` (bool) and `chips`, a list of `{id*, label*, on}` (`on` bool).
- option (`select`): `{value*, label*}`.
- column (`table`): `{id*, title*, align, width}`: `align` is `left` (default) or `right`, `width` is a fixed width in points (`0` or absent = flexible, sharing the remaining space). Ids unique and non-empty.
- row (`table`): `{id*, depth, hasChildren, expanded, muted, cells*}`: `depth` is an integer 0-32 (indent 12pt per level, chevron when `hasChildren`), `muted` dims the row's text. Ids unique and non-empty. `cells` must have exactly one cell per column.
- cell (`table`): `{text, bar, tone, spark}`: `bar` is a number 0…1 drawn as a filled capsule behind the text, `tone` is `""`\|`ok`\|`warn`\|`danger` (colours the bar and sparkline, or the text when there is no bar), `spark` is a spark.
- spark (`table` cell): `{values*, max*}`: at most 900 numbers, `max` > 0. Values are clamped to 0…`max` and drawn as a 60×16pt line. The Go helpers `sdui.Sparkline`, `sdui.SparklineSized` and `sdui.NewSpark` clamp them before sending.
- attachment (`message`, `composer`): `{id, kind*, path*, startLine, endLine}`: `kind` is `file` or `selection` (with the 1-based line range); `path` is shown as given (relative to the worktree when inside it); `id` names a composer attachment for `detach` (non-empty and unique within the list when set).
- plan entry (`plan`): `{content*, status*}`, `status` `pending`\|`in_progress`\|`completed`.
- tool body (`toolCard` `body`): `{format*, text*}`: `format` `diff` (unified diff, drawn like `diff`), `text` (plain) or `terminal` (monospaced command and output).
- card action (`toolCard` `actions`): `{action*, label*, icon, value}`: `value` is a string, number, bool or an object of those.
- permission option (`permissionCard`): `{id*, label*, kind}`, ids unique, `kind` `allow_once`\|`allow_always`\|`reject_once`\|`reject_always` (tints the button; absent = neutral).
- command (`composer` `commands`): `{name*, description, hint}`: the agent's slash commands; `hint` describes the expected input.
- picker (`composer` `pickers`): `{id*, title, help, value*, options* (option[])}`: a session option menu; its label is the current option's label, prefixed by `title: ` when `title` is set; `help` is the tooltip.
- sort (`table`): `{column*, desc}`: the active sort column (arrow in its header) and direction. `column` must be one of the table's column ids.

A window shows at most one `surface` node at a time in v1. The client keeps every terminal it has shown mounted until the session's attach exits or the window closes, so switching between sessions is instant. A second `surface` visible in the same window at once renders a placeholder.

`table` rows render lazily; wrap the table in a `scroll` to scroll them under a pinned header. Each row counts toward the 5000-node limit; cells are bounded by the row and column caps (at most 1000 × 32), and spark values (cell sparks and `sparkline` nodes) are capped at 100000 per tree. The client does not page or truncate: a plugin with more rows renders the first 1000 or fewer and adds a final muted `… N more` row itself. `selected` works like `tree`'s: a changed value from the plugin sets, moves or clears the highlight (and scrolls to it); clicking a row highlights it locally and sends `select`. `sparkline` draws `values` as a 60×16pt line (e.g. in a header); with `height` it fills the available width at that height in points (e.g. a detail chart).

Agent chat nodes (the `agents` section):

- `transcript` is the chat column: a vertically scrolling list of its children (messages, plans, cards, `text`, a "Show earlier" `button`), anchored to the bottom while the user is at the bottom. Its `id` identifies the session, so the client keeps a scroll position per id. Adjacent `toolCard` children collapse into one summary row (`8 actions: read 3 files, 2 searches, …`, a spinner and the running card's title while one runs) that expands to one line per card; a lone card is shown as that line, and a line expands to the card's `body` and `actions`. Edit lines show the file name when the `title` holds a path (the path as a tooltip) and the `diff` body's `+added −removed`. Expanding the last item scrolls to the bottom. `failed` cards and `permissionCard`s stay full-size and split the run. Expansion is kept per card id until the app quits, so a group stays expanded as cards stream in or the run splits.
- `message` renders `text` as markdown (headings, lists, code blocks with copy, inline code, links). `user` messages are right-aligned bubbles with their `attachments` as chips (`@ path`, `path · lines 12–40`) and an optional muted `from` line ("from <from>") for prompts that another agent session sent; `agent` messages are plain; `thought` is collapsed behind "Thinking" and expands on click.
- `plan` is a checklist: `completed` checked, `in_progress` highlighted, `pending` empty.
- `toolCard` shows an icon for `kind`, the `title` and `status` (spinner while `pending`/`in_progress`, red for `failed`, muted for `cancelled`). `read` and `search` cards are one line. A `body` is shown under the title (`diff` and `terminal` in a monospaced box). `truncated` adds a muted "Output truncated" note; the plugin then also offers a `showAll` action. Each `actions` entry is a small button.
- `permissionCard` shows `text` and one button per option. With `outcome` set the card is answered: the chosen option (`outcome` = its id) is shown as chosen, `cancelled` as "Cancelled", and the buttons are disabled.
- `composer` is the prompt editor: a multi-line field (`placeholder`), the `attachments` as removable chips, an attach menu with the kinds in `attach`, the `agent` label, a mode picker over `modes` (current `mode`), one menu per `pickers` entry, and Send (labelled Queue, with Stop beside it, while `running`). ⌘↩ sends (the plugin queues it while a turn runs), Esc stops while `running`, `@` opens the client's fuzzy file picker (⌘P) in attach mode, and `/` at the start lists `commands` filtered by the typed prefix; choosing one inserts `/name `. The field is uncontrolled; the plugin clears it after a send by rendering the composer with a new `id`.

`button.confirm`: when set, the client asks the user to confirm with that text before sending the event.

Input fields are uncontrolled: `value`/`values` on `textField`, `folderField`, `toggle` and `select` are initial values. The client keeps what the user entered while the node keeps its identity. A changed `value` in a later render replaces it, but re-rendering an unchanged one does not. To reset a form (e.g. after a successful submit), the plugin renders it with a new node `id`. The client then discards the form's field state and starts again from the props. Actions are routed by `action`, not by `id`, so rotating ids (e.g. `create-<n>`) does not change event handling.

## Slots

A slot is named `<section>.sidebar`, `<section>.main` or `<section>.status`, or `<section>.<name>` for a name the section declares in `slots`. A section is registered by a plugin, which owns all of its slots. Only the owning plugin may call `ui.render` for them. Slots are rendered per project, unless the section has `scope: "app"`.

A manifest section may declare extra slots with `slots`: names matching `^[a-z][a-z0-9-]{0,31}$`, unique, and not `sidebar`, `main` or `status` (otherwise manifest load fails). `{"id": "git", "slots": ["review"]}` adds the slot `git.review`. Extra slots belong to the section like its own (owner, scope, `ui.event` routing); views cannot claim them, and the client decides where to show them. `ui.render` and `ui.event` on an undeclared `<section>.<name>` fail with invalid params. `ui.sections` lists them as `slots` (omitted when empty).

### Hosted sections

A manifest section may set `host` to another section's id; `ui.sections` returns it (omitted when empty). A hosted section has no rail icon or ⌘ number: the client shows its `.sidebar` slot as a tab of the host's sidebar, after the host's own sidebar, and never shows its `.main`. A `host` equal to the section's own id fails manifest load; a host that is not registered, is itself hosted or has another scope is dropped by the core, and the section stays a normal one. Selecting a hosted section (palette "Go to …", a saved `section` in the UI state, `ui.focus`) selects the host and that tab; a focus to `<hosted>.sidebar` or `<hosted>.main` goes to the host's `.sidebar` or `.main`. A focus to an extra slot of a hosted section (`git.review`) selects the host and the tab showing that slot. The client keeps the chosen tab per workspace and host, across hiding the sidebar and switching sections; `<` / `>` in a sidebar tree cycle the tabs. When `git` is not hosted (no editor-nvim), it renders `git.main` as an `empty` hint so its rail entry is not blank. `git` sets `"host": "editor-nvim"`, so the Code sidebar has Files | Git tabs (and Review while a review runs, see below).

### Scope

A manifest section has `scope`: `"project"` (default) or `"app"`; any other value fails manifest load. `ui.sections` returns it. Slots of an app-scope section are not tied to a project and are rendered, read, subscribed and sent events with `projectId: ""`:

- `ui.get` and `ui.subscribe` with `""` cover only app-scope slots; with a project id, only project-scope slots.
- `ui.render` and `ui.event` with `""` on a project-scope slot, or with a project id on an app-scope slot, fail with invalid params.
- `ui.subscribe` with `""` does not count toward presence and publishes no `ui.opened`/`ui.idle`.
- App-scope slots of a stopped or crashed plugin are cleared like project slots (the `empty` view is delivered to live subscribers).

### Auto new

A manifest section may set `autoNew: true` (default `false`); `ui.sections` returns it. When the user selects such a section and its main slot, once rendered, is an `empty` node (the section has nothing to show, e.g. no terminals; an exited terminal's view is not `empty`), the client runs the section's `<section>.new` command once for that selection (`CommandInvocation.shouldAutoNew`). Terminals sets it, so a terminal appears on entering the section.

The `.status` slot is a compact status line for the section; clients show it in the status area while the section is active.

### Views

A plugin may claim a slot of another plugin's section with `contributes.views`:

```json
{"contributes": {"views": [{"slot": "alpha.sidebar"}]}}
```

The claiming plugin becomes the owner of that slot instead of the section owner: only it may `ui.render` the slot and `ui.event` for it is routed to it. Slot syntax is validated at manifest load. A view on a section that no plugin registers is ignored and logged. When two plugins claim one slot, the later manifest in discovery order loses its claim and the conflict is logged.

## Revisions

Every slot (per project) has a revision counter that starts at 1 and increases by 1 on each render. When a plugin stops or crashes, its slots are cleared: the counter increments and the tree becomes `empty` with empty text. The cleared slot is removed from the store: the `empty` view (rev + 1) is delivered only to live subscribers, and later `ui.get` or subscribe replays omit the slot. Clients render that view like any other update (an empty pane) and do not get the slot back from `ui.get` after a reconnect.

`project.delete` clears every slot of the deleted project the same way (the `empty` view at rev + 1 to live subscribers; `ui.get` for that project then returns `[]`). Before deleting, the core kills the project's session processes (groups registered with `process.register` are left to their owner plugin, which handles `project.deleted`), waits for each of its sessions to stop and removes them, publishing `session.removed` `{id}` for each; then it deletes the project and publishes `project.deleted` `{id}`. If a session does not stop within the kill grace, the delete fails and the project is kept. Clients take a workspace out of its window when its project disappears from `project.list` after having been listed.

Revisions are in-memory and reset when the core restarts; clients must reset their rev map on reconnect.

Clients keep the highest `rev` per `(projectId, slot)` and ignore views with a lower or equal `rev`.

`SlotView` is `{projectId, slot, owner, rev, tree}`.

A command with `"hidden": true` in its manifest entry is still listed and runnable; clients leave it out of the command palette.

A command with a non-empty `"confirm"` string in its manifest entry is listed with that text (`""` when absent); the client asks for confirmation with it before running the command.

A manifest command entry may also declare, all optional and listed as declared:
- `description` (`""` when absent): what the command does, for agents and `command describe`;
- `args` and `result`: schemas for the command's args and its result (absent: any args, nothing declared);
- `agent` (default `false`): the command is meant for agents;
- `destructive` (default `false`): the command destroys state (closes, kills, discards);
- `provides`: generic capability names the command implements;
- `timeout` (1 to 600 seconds; listed only when set): how long the core waits for the plugin's `command.run` reply, instead of the 5 s every other plugin call gets (`routeTimeout`). For commands that block on purpose, such as `agents.wait`. Callers apply no shorter limit: `clubmate mcp` and `clubmate command run` set no timeout on `command.run`.

A schema is a small JSON Schema subset: an object `{properties: {name: prop}, required: [name]}`, where a prop is `{type, items, enum, description, default}`, `type` is `string`, `integer`, `number`, `boolean` or `array`, and an `array` has scalar `items` or object `items`. Object items go one level deep: `{type: "object", properties, required}` whose properties are scalars or arrays of scalars (no further object items), and a value is validated item by item, so a bad field names its path (`args.items[0].line: want integer`). Only an `array` has `items`, only object items have `properties` and `required`, and only a scalar has `enum`; `enum` values and `default` must match the type (a `default` also the `enum`), and every `required` name must be a property; anything else fails manifest load. `default` is documentation only: the plugin applies it, the core never fills it in.

`command.run` validates `args` against the command's `args` schema before routing, so the plugin is never called with bad args. Absent or `null` args count as `{}`; properties not in the schema are allowed; a `null` property counts as absent. Errors are invalid params naming the field: `args: want object`, `args.path: required`, `args.line: want integer`, `args.side: want one of ["left","right"]`, `args.paths[1]: want string`. `integer` rejects fractions and exponents. A command without an `args` schema accepts any args.

`session.send` types `text` into a running session (a data frame on the session host's socket, chunked under the frame limit); with `enter: true` it sends `\r` as a separate frame 50 ms later, so a TUI sees a keypress rather than a paste. It then half-closes its connection and drains what the host sends until the host closes (2 s at most), so every input frame is consumed even when the host is still replaying a large ring to the new connection. `session.read` returns the last `bytes` (default 16384, 0 means default, more than 262144 is invalid params) of the session's output ring, cut from the raw bytes before processing. Without `raw` it renders the text the way a terminal shows each line: it drops OSC, DCS, SOS, PM and APC strings (up to BEL or `ESC \\`) and other escape sequences, but keeps a cursor on the current line: `\r` returns to column 0, `\b` and `CSI n D` move left, `CSI n C` moves right, `CSI n G` sets the column, `CSI K` (0, 1, 2) erases, and printable characters overwrite at the cursor (so a redraw by a line editor or zsh-syntax-highlighting reads back as the final line, and output ending in `50%\r` reads `50%`). Cursor moves stop at column 512 (an overflowing parameter counts as the maximum), lines are capped at 4096 characters, the rendered text is cut to its last `bytes` bytes, trailing spaces are trimmed, a control character right after `ESC` is kept, other control characters except tab and newline are dropped, and invalid UTF-8 is dropped (e.g. a character split by the cut); `raw: true` returns the tail as is. When the session's app is on the alternate screen it returns `altScreen: true` and no text. Both fail with not found (`-32004`) for a session that is not running. The core reads the ring with a new host frame: the client sends an empty `snapshot` frame (type 4), the host stops streaming to it and answers with one `snapshot` frame whose payload is `[1]` on the alternate screen, else `[0]` followed by the ring; data frames already queued may arrive first. The session protocol version is unchanged: hosts started by an older core ignore the frame, and `session.read` fails after 2 s with not found (`-32004`) `session host cannot be read; restart the session`.

Sessions get `PATH` with the core's own directory first (`Contents/Resources/bin` in the app, `bin/` in dev), so `clubmate` works in clubmate terminals. The core prepends it only when that directory has an executable `clubmate`, and not when it is already first. A login shell may reorder `PATH`: macOS `/etc/zprofile` runs `path_helper`, which puts the system directories first, so a `clubmate` installed in a system directory (e.g. a release symlink in `/usr/local/bin`) wins over the bundled one.

CLI over the registry:
- `clubmate command list [--agent]` (`--agent`: only agent commands), `clubmate command describe <id|capability>` (description, flags, `provides`, args and result schemas).
- `clubmate command run <id|capability> [key=value …] [--args JSON] [--project ID] [--agent]`: `--project` defaults to `$CLUBMATE_PROJECT_ID`; `key=value` pairs are coerced by the resolved command's schema (integer, number, boolean, string, array as comma-separated values) and an unknown key (or any key, for a command without an args schema) fails before calling the core, naming the key; pairs and `--args` are exclusive. The CLI never turns on `--agent` by itself, not even inside a clubmate session.
- `clubmate open <file>[:line]` runs `editor.open` with `{path (absolute, from the CLI's cwd), line}`; a trailing `:line` or `:line:column` is parsed (the column is dropped; line 0 means no line), and anything else stays part of the path (`a:b.go:3` is `a:b.go` line 3).
- `clubmate session send <id> <text> [--enter]` and `clubmate session read <id> [--bytes N] [--raw]` run `session.send` / `session.read` through `command.run` (not as agent calls).
- `clubmate mcp` is a stdio MCP server (newline-delimited JSON-RPC 2.0, protocol `2025-06-18`; `initialize`, `ping`, `tools/list`, `tools/call`; other requests get `-32601`, notifications get no reply; stdout carries only protocol messages). Tools are the agent commands (core primitives included), named by id with `.` and `-` turned into `_`; a command that provides a capability is listed under the capability name instead. `inputSchema` is `{type: "object"}` with the command's args plus an optional `workspace`; annotations carry `destructiveHint` (the command's flag) and `readOnlyHint` (`workspace.list`, `session.list`, `session.read`, `process.tree`, `terminals.busy`). `tools/call` runs `command.run` with `agent: true` and `projectId` = `workspace`, else `$CLUBMATE_PROJECT_ID`, else the most recently opened workspace; the result is one text item with the JSON result, and failures (including approval refusals) are `isError: true` with the message. It never starts the core: without one, `tools/list` lists the core primitives and every call fails with `Clubmate isn't running`. There are no plugin-change events (manifests are read once per core start), so it re-checks the tool list every 5 s and sends `notifications/tools/list_changed` when it differs from the last list it served. See `docs/agents.md`.

`process.tree`'s `args` is the full argv (`[]` when it can't be read, e.g. for another user's process) and `startTime` is RFC 3339.

`process.register` makes a process the plugin started a root of its own group in `process.tree`, like a session: the root and its descendants get `sessionId` = the returned `id` (`prc_…`), and `sessionId` in `process.tree` and `process.kill` accepts that id. `owner` is the calling plugin. The pid must be a descendant of the plugin process (by parent chain), else invalid params; `label` is trimmed and 1..200 characters, and `projectId` must exist. Registering the same live process again keeps its `id`, `owner` and owning process and updates `projectId` and `label`; another plugin process registering it is refused. While a registration is active its processes are never orphans (`orphan: false`): their owner reaps them. It ends (`ended: true`) with `process.unregister` (by pid, the caller's own registrations only; another plugin's call does nothing), when the plugin's connection closes (later registers from that connection fail), or when the root process is gone: a root registered before a `process.tree` snapshot started that the snapshot misses is checked again by its start time, and only a dead or reused pid ends it, so a slow snapshot never drops a fresh registration; `process.roots` runs the same start-time check. An ended registration stays, labelled `<label> (exited)` once its root is gone, while any tracked process still carries its `id`: those leftovers stay in their project, are orphans when reparented to launchd, and `orphansOnly` kills (and the Processes section's auto-kill) reach them. It disappears from `process.roots` once no process carries it. The agents plugin registers each agent process it starts (`Claude · <worktree folder>`, in the background, best effort), and the Processes section lists registered groups next to sessions.

`process.kill` with `orphansOnly` kills only orphaned processes and needs `sessionId` or `projectId` (otherwise invalid params). With `projectId`, only that project's orphans are killed; with `sessionId`, only that session's. Without `orphansOnly`, `pids` must be tracked processes. Each target is signalled only if its start time still matches the tracked one, so a reused pid is skipped.

`project.open` fails with not found for an unknown project; otherwise it sends the `project.open` notification to every connection that registered `"project.open"` via `client.register`, except the caller, and returns how many were notified (`clients`). `clubmate workspace open --id <id>` calls it and, when `clients` is 0, runs `open -b com.clubmate.app --args --open-project <id>`.

Projects are shown to users as workspaces; `clubmate project …` is an alias of `clubmate workspace …`. A project is `{id, name, repos, roots, missing?, createdAt, home, lastOpenedAt}`; `lastOpenedAt` is `null` until the first `workspace.touch`; subscribing to a project's UI does not set it. `repos` are the workspace's folders. `roots` lists, in the same order, each folder's effective path: the directory selected for it with `workspace.worktree.set` (usually a git worktree of the folder), else the folder itself. A selection whose directory no longer exists falls back to the folder and is listed in `missing` (omitted when empty); it stays stored. Sessions created without `cwd` start in `roots[0]`. Clients that predate `roots` treat a missing one as `repos`. `project.list` orders by `lastOpenedAt` then `createdAt`, newest first.

`workspace.open` resolves each folder path (symlinks resolved, cleaned), drops duplicates and returns the project whose repos are exactly that set (order-insensitive, stored repos resolved the same way) with `created: false`; otherwise it creates a project with the resolved folders, named after the base name of the first one (`project.created`), with `created: true`. Folders must be absolute paths to existing directories (otherwise invalid params, as is an empty `folders`). `workspace.home` returns the single `home: true` project, named `~` and rooted at the user's home directory, creating it (`project.created`) on first use. Both then send the `project.open` notification exactly like `project.open` (not to the caller) and return how many were notified (`clients`); `clubmate workspace open <dir>…` and `clubmate workspace home` run the app like `open --id` when `clients` is 0. `workspace.touch` sets `lastOpenedAt` to now (not found for an unknown project); clients call it when they activate a workspace. `project.rename` fails with invalid params on a blank name and publishes `project.updated`.

`workspace.worktree.set` `{id, repo, path}` selects the directory a workspace folder points at. `repo` must equal an entry of `repos` exactly (otherwise invalid params `repo is not a folder of this workspace`). An empty `path`, or one equal to `repo`, clears the selection; any other `path` must be an absolute path to an existing directory (otherwise invalid params `path is not a directory`). It stores the selection, publishes `project.updated` with the full project and returns the project. Selections are deleted with the workspace and with the folder. Plugins call it as `pluginsdk.Host.SetWorktree`. It is not an agent command (an agent `command.run` of it fails with not found): it accepts any existing directory, so agents switch worktrees through a plugin command that validates the target instead.

`workspace.worktree.check` `{id}` re-reads the project and, when `missing` is not empty, publishes `project.updated` with it; it changes nothing and returns the project. The git plugin calls it (`pluginsdk.Host.CheckWorktrees`) when a refresh finds a `missing` list it has not reported yet, so a worktree removed outside Clubmate moves every plugin and the app back to the folder without waiting for another event; the app then shows the one-time banner and clears the selection by switching the folder to its own checkout.

`client.register` marks the calling connection for the listed handles: `"project.open"` and `"ui.confirm"`; anything else is invalid params. The app registers both. Registration lasts for the connection. Plugin callers get invalid params.

`ui.focus` is open to any caller. It is invalid params when the project does not exist, the section is not registered or is app-scope, or `slot` is not `""`, `<section>.sidebar` or `<section>.main`, or `edge` is not absent, `""`, `h`, `j`, `k` or `l`. It sends the `ui.focus` notification to every `ui.subscribe` subscription of that project (app-scope subscriptions never receive it) and returns their count as `delivered`. Plugins call it as `Host.Focus`, or as `Host.FocusEdge` to pass `edge`.

`ui.render` is invalid params for a project that has been deleted.

`command.run` resolves `id` to a command: a listed command id wins; otherwise `id` is taken as a capability name (see below). It fails with unknown command when neither matches; it is routed to the plugin that registered the resolved command, which receives the resolved command id (not the capability name) in `id`.

A capability is a generic name a command declares in `provides`, so callers need not know which plugin implements it. A capability resolves to the first provider in plugin load (discovery) order whose plugin is running, else to the first provider (then `command.run` fails with plugin unavailable). When several commands provide one capability the core logs `capability X provided by A and B; using A` (command ids) once per distinct outcome. `command.capabilities` returns that resolution for every declared capability. Bundled capabilities: `editor.open` (`editor-nvim.open`), `editor.quickfix` (`editor-nvim.quickfix`), `editor.reveal` (`editor-nvim.reveal`), `terminal.new` (`terminals.new`), `terminal.close` (`terminals.close`), `files.reveal` (`files.reveal`), `git.stage-all` (`git.stage-all`), `git.review` (`git.review`).

`command.list` also lists the core primitives, with `plugin: "core"`, `agent: true` (except `workspace.worktree.set` and `diagnostics.collect`, which are `agent: false`) and `hidden: true` (so the palette leaves them out). `command.run` resolves a primitive id before plugin commands and capabilities, and runs it with the existing method's handler. Plugin ids `core`, `session`, `workspace`, `process`, `ui` and `diagnostics` are reserved (manifest load fails), and `command.capabilities` maps a capability named like a primitive to that primitive, as `command.run` does:

Plugin commands keep requiring a valid `projectId`. An agent `session.send` always needs approval, also into the agent's own session. Approval shows the full `text`, so the 200-character limit applies: agents send long input in chunks. An agent call accepts only the keys the resolved command's args schema declares, matched exactly (primitives and plugin commands alike; a plugin command without a schema accepts any args unless it is destructive) (so `command`, `env` or a case variant like `Command` is invalid params: `args.Command: not allowed in agent calls`); keys inside object items are matched exactly too (`args.items[1].PATH: not allowed in agent calls`); the core rebuilds the args from those keys and dispatches that object.

An agent call is `command.run` with `agent: true` (the CLI's `command run --agent`; the MCP server always sets it). It resolves only core primitives and commands with `agent: true` (judged on the resolved command, never on the capability name); anything else fails with not found, as if unknown. Args are validated first. Then a `destructive` command needs the user's approval, and what the user approves is exactly what runs, so its args must be approvable or the call fails with invalid params before anyone is asked: an object (absent or `null` counts as `{}`); no args at all when the command declares no `args` schema; only keys its schema declares (`args.<key>: not declared`); at most 10 fields; each value at most 200 characters (a string's characters, otherwise its compact JSON); no number beyond ±2^53, anywhere in a value (`args.<key>: number outside ±2^53`), so the app shows it exactly. These limits live in the core (`approvalMaxFields`, `approvalMaxValue`, `approvalMaxInt`); the app checks the field and length limits itself and never truncates args. The core then sends the request `ui.confirm` `{title, workspace, command, args, timeoutMs, session?}` (`title` is the command's title, `workspace` the affected workspace's name or `""`, `command` the resolved id, `args` the args exactly as they will run, or `{}`; once approved, exactly these bytes are dispatched; `timeoutMs` is 60000; `session` is `{id, title, workspace}` of the targeted session, when the args name one: `id` for `session.send`/`session.kill`, `sessionId` for plugin commands such as `terminals.close`) to one connection that registered `"ui.confirm"`: one that has a `ui.subscribe` subscription for the affected workspace if any, else the earliest connected. It waits up to 60 s for `{approved}`. The call fails with `-32014` (denied) and one of these messages, and the command does not run:
- `no app to approve`: no connection registered `"ui.confirm"`, or the request failed;
- `denied by user`: the answer was `approved: false` (when the answer carries a `reason`, that is the message instead);
- `approval timed out`: no answer within 60 s, or the app's own answer that it timed out;
- `approval busy`: that connection already has an approval pending (one per connection; the second is denied, not queued).

An approval outlives a dropped caller: if the caller disconnects while the alert is up, the request stays pending until it is answered or times out, and an approved command still runs. Non-agent calls (the app, plugins, the CLI without `--agent`) are unchanged: any listed command runs without approval. Agent mode is a cooperative guard, not a security boundary: any same-uid process can reach the core socket directly (and call without `agent`, or register `ui.confirm` itself).

The app answers `ui.confirm` with an alert "Allow agent to <title>?" whose text lists the workspace, the command, the targeted session (title, id and workspace) and each argument (shown in full; scalars of general category control, format, line separator or paragraph separator escaped as `\n`, `\r`, `\t` or `\u{…}`, so a value cannot fake extra lines or reorder text; the title, workspace and command are escaped the same way and cut at 200 characters with `…`). The alert has Allow and Deny (Deny is the default and holds focus; Allow never takes keyboard focus, so a space typed into the terminal as the alert appears can't approve; Esc denies). If the args exceed the app's own limits (more than 10 fields, or a value over 200 characters) it shows no alert and answers `{approved: false, reason: "args too long to display"}`, so the alert never shows less than what runs. The alert closes itself 5 s before `timeoutMs` and the app answers `{approved: false, reason: "approval timed out"}`. It is a sheet on the key workspace window (else the first workspace window, else a modal alert) and asks for attention (dock bounce) until it closes.

`files.collapse-others` ("Collapse Others") takes no args. It keeps expanded only the repo roots and the ancestors of the selected file (the file last opened in or revealed from the editor), persists the expanded set and re-renders the tree. When the project's roots change, a selected file that is no longer under them, or that lies in another git worktree nested inside one, is deselected. In the files tree a directory whose only visible entry is one directory is merged with it into one row labelled `a / b / c` whose id is the deepest path; expand and collapse act on that path. File rows have no icon.

The files tree can be focused on one folder per workspace (neo-tree's `set_root`). The `focus` ui action (value: a path) focuses that folder (a file focuses its parent folder); `""` or a workspace root clears the focus. The path is canonicalised first (cleaned, symlinks resolved) and must exist; a path that is not inside the roots after that fails, so `..` and symlinks that escape the roots are refused. While focused the tree shows only the folder's children (other roots are hidden) and carries a `breadcrumb` of `{id, label}` items from the root down to the focused folder; the client draws it as a row above the scrolled tree and sends `focus` with a segment's id when it is clicked (the first segment clears). Focusing expands the folder and its ancestors. The focus is stored per workspace under `focus/<projectId>`, survives restarts, and is cleared when it is no longer a canonical directory under the roots (e.g. after a worktree switch, or a stored path that escapes them). Revealing a file outside it (`files.reveal`, `editor.buffer`) moves it up to the nearest ancestor containing the file, or clears it. `files.focus` ("Focus Folder") focuses the folder of the selected file (a no-op without one) and `files.unfocus` ("Clear Folder Focus") clears it; both take no args and are not agent commands.

editor-nvim keeps one nvim per project root: the first entry of the project's `roots` that exists, else `$HOME`. Each runs in its root with its own socket (`<runtime>/<projectId>-<8 hex of sha256(root)>.sock`); a running session belongs to a root when its cwd is that root and it listens on that socket (or on the pre-worktree `<runtime>/<projectId>.sock`). The main and status slots show the nvim of the current root; when `project.updated` changes it, editor-nvim starts that root's nvim if needed and shows its surface, and the other nvims keep running. `editor-nvim.open` (absolute path), `quickfix` (first item's path), `diff` (`path`) and `review` (`repo`) first look, for each project folder, at that folder's own `git worktree list` (run in the folder's repo, never in the target path's repo): the worktree owning the path is the longest listed root containing it, compared with symlinks resolved. When the folder maps into that worktree (a folder at `<toplevel>/<rel>` maps to `<worktree>/<rel>`) and its current root differs, they call `workspace.worktree.set` for that folder with the worktree path as git prints it joined with `<rel>` (empty when it maps back to the folder itself), focus the editor and act on the new root's nvim.

`editor-nvim.restart` takes optional args `{force}` and restarts every running nvim of the project (and the current root's one if it is not running). Without `force: true` it first asks each of them for modified listed file buffers (`buftype` empty, `buflisted`; scratch buffers do not count) and fails with `unsaved buffers: <names>` (all of them, relative to the project repos and roots, `[No Name]` for unnamed buffers) if there are any; the sessions are left running. If an nvim does not answer within the RPC deadline it fails with `unsaved buffers: unknown (nvim not responding)`. If the session cannot be started its main slot shows the error and a Restart button, which restarts only the current root's nvim. `editor-nvim.stop-root` (hidden, not agent-visible) takes args `{root, force}` (`root` absolute): it stops the nvim of that root with the same unsaved check and errors, and is a no-op when there is none. After it succeeds (even as a no-op), no nvim starts in that root (opening a file there fails with `the worktree is being removed`) until `editor-nvim.release-root {root}` (hidden, not agent-visible), which starts it again when the root is still the project's current root. `editor-nvim.unsaved {root}` (hidden, not agent-visible) returns the names of the modified file buffers of that root's running nvim whose files are inside the root (same names and `unknown` error as restart), `[]` when none runs there; it never starts or stops nvim.

`editor-nvim.selection` (hidden, not agent-visible) takes no args and returns `{path, startLine, endLine, text}` for the current visual selection, else the last one (`'<` / `'>`), of the current root's running Neovim; `text` joins the selected lines with `\n`. It fails with `no selection` when there is none or Neovim is not running. `editor-nvim.checktime {root}` (hidden, not agent-visible; `root` absolute, else an error) runs `:checktime` in the Neovim of that root so unmodified buffers changed on disk reload; it is a no-op when none runs there.

`editor-nvim.diff` takes args `{path, base, target}`: `path` must be absolute (otherwise an error), `base` is `head`, `index` or `rev:<sha>` (lowercase hex), `target` is `index`, `worktree` or `rev:<sha>` (lowercase hex), and they differ (`rev:` sides compared by their 7-char short sha). The repo is the nearest ancestor of `path` containing `.git`; `path` itself need not exist. editor-nvim reads `HEAD:<rel>` / `:<rel>` / `<sha>:<rel>` with `git show`; a path missing from `HEAD` (or an unborn `HEAD`), from the index or from `<sha>` is empty content, any other git failure (including an unknown `<sha>`) is an error. It opens a new nvim tab with a side-by-side diff: the left window is a read-only scratch buffer named `clubmate://<base>/<rel>` (`clubmate://<first 7 chars of sha>/<rel>` for `rev:<sha>`), the right window is the file itself for `worktree`, a scratch buffer `clubmate://index/<rel>` for `index`, or a scratch buffer `clubmate://<first 7 chars of sha>/<rel>` for `rev:<sha>` (scratch buffers are read-only). Any other tab showing a `clubmate://*/<rel>` scratch buffer is closed. When the worktree file has `fileformat=dos`, trailing `\r` is stripped from the scratch lines.

`editor-nvim.review` takes args `{repo, base, head, mergeBase}` and returns `{mode}`. `head` defaults to `HEAD` when empty. `repo` must be absolute and `base` and `head` non-empty refs not starting with `-` and without whitespace (otherwise an error); `mergeBase` is accepted but unused. It starts nvim if needed. If nvim has `:DiffviewOpen` (`exists(':DiffviewOpen') == 2`), it closes the review tab it opened last time if that tab is still valid (switches to it and runs `DiffviewClose`), runs `DiffviewOpen -C<fnameescape(repo)> <base>...<head>` and returns `mode: "diffview"`, or `mode: "builtin"` (recording no tab) when the command opened no new tab (diffview reports its own errors softly); without `:DiffviewOpen` it changes nothing and returns `mode: "builtin"`. When nvim has the diffview fork's module (`require("diffview.clubmate")` loads and its `version` is at least 1), it instead opens the review through the module's `open({cwd = repo, base = "<base>...<head>"})`, shows diffview's file panel (`set_panel(true, tab)`) and returns `mode: "diffview"` (`builtin` when that opens nothing). `editor-nvim.review-close` takes no args and closes that review tab the same way; it is a no-op when nvim is not running or the tab is gone.

The hidden, non-agent `editor-nvim.review-*` commands drive the review list. `review-open {cwd, base, excludes?}` needs an absolute `cwd` inside a git worktree (an error otherwise), a ref `base` (same rules as above) and `excludes` globs made only of letters, digits and `* ? [ ] { } , . _ - / !` (anything else, such as a backtick or `$`, is an error). It acts on the nvim of the worktree owning `cwd`, like `review`, closes the previous review tab (through the module's `close`, so that close is not reported as `closed`) and opens the worktree toplevel against `base`. With the module it calls `open({cwd, base, excludes})`, where each glob becomes a `:(exclude)` pathspec (the module `fnameescape`s the cwd and every glob, so nothing is expanded or run) and the working tree with untracked files is the right side, and returns `mode: "module"`. Without it, it runs `DiffviewOpen -C<toplevel> <base>` without the excludes and returns `mode: "diffview"`, and without diffview it returns `mode: "native"`; a module open that opens nothing is an error (the module's message, else `diffview opened no review`), so the caller retries, and a diffview open that opens nothing returns `native`. The other commands act on the module review in the current root's nvim: `review-entries` returns `[{path, status, additions, deletions, reviewed, comments}]` in diffview's order (`path` relative to the toplevel; `comments` counts open nrev comments); `review-select {path}` opens a file; `review-reviewed {path, reviewed?}` sets its reviewed mark to `reviewed` (idempotent, the module's `set_reviewed`) or toggles it when `reviewed` is omitted, and returns `{reviewed}`; `review-next {dir}` (`1` or `-1`, otherwise an error) opens the next or previous unreviewed file, wrapping, and returns `{path}` (empty when none); `review-excludes {excludes}` replaces the excluded globs and keeps reviewed marks of files that come back. Without nvim or a module review they return `[]`, `{reviewed: false}`, `{path: ""}` or do nothing. Every module notification is published as `review.changed {projectId, root, kind, path?}` with the nvim's root and the module's `kind`: `files_updated` (the file list updated), `file_open` (with the opened `path`), `reviewed` (a mark changed; with `path` when toggled through `review-reviewed`), `reviewed_restored` (nrev restored the marks), `comments` (comment counts changed) or `closed` (the user closed the review tab, e.g. `q` or `:DiffviewClose`; no `path`). An RPC to an nvim that does not answer within 2 s fails with `Neovim is waiting for input — press Enter in the editor` when nvim reports it is blocked (a hit-enter prompt), otherwise with `nvim rpc timed out`.

`editor-nvim.navigation` (hidden) takes args `{enabled, side}` and returns `{skipped}`. `side` is the Code sidebar's side, `left` or `right` (anything else is an error). It stores `{enabled, side}` in plugin storage under `navigation` (global, not per project; the `projectId` only routes the call) and applies it to every connected nvim; on every (re)connect editor-nvim applies the stored value right after registering the `clubmate` module, and does nothing when nothing is stored. Enabled: with `package.loaded["smart-splits"]` present it wraps smart-splits' `at_edge` (`config.move.at_edge` in v3, `config.at_edge` in v2) so that `ctx.direction` pointing at the sidebar (`left` for side `left`, `right` for side `right`) only calls `edge(ctx.direction)`, and every other direction runs the original `at_edge` (a function, or `wrap`/`split` through `ctx.wrap()`/`ctx.split()`); it maps no keys; otherwise it maps normal-mode `<C-h>`, `<C-j>`, `<C-k>`, `<C-l>` to `require("clubmate").navigate(dir)` with `desc = "clubmate navigate"`, taking over a global mapping that is nvim's built-in default (`desc` `:help …-default`) or a plain non-`expr` window move in the key's own direction (rhs keycodes equal to `<C-w>d`, `<C-w><C-d>`, `<Cmd>wincmd d<CR>` or `:wincmd d<CR>`), and skipping keys that have any other global mapping; `skipped` lists those keys (sorted, across all nvims). Disabled: removes the global mappings with that `desc`, restores the mappings it took over (exactly, from `maparg()`; unless the key was remapped meanwhile) and unwraps `at_edge` if it is still the wrapper. Applying is idempotent. The app stores the answer in `AppSettings.navigationKeys`, sends it with `AppSettings.sidebarSide` once per launch after the first project connects, and again whenever either changes; a non-empty `skipped` is shown as a banner (`Ctrl+J left alone: you already map it`).

`terminals.busy` (hidden) takes args `{sessionId}` and returns `{busy, process}`. `busy` is true when the session's process tree (`process.tree`) has a live descendant of the shell (the session's `childPid`); `process` is the `comm` of the newest such descendant (latest start time), `""` when not busy. An unknown or exited session is not busy. The app's ⌘W "Close Terminal" closes the Terminals section's selected terminal (the `selected` of the `terminals` list in `terminals.sidebar`): it always runs `terminals.busy` first and, when busy, asks `“<process>” is running. Close the terminal?` before `terminals.close`; an exited one is not busy, so it closes without asking. In a project window outside the Terminals section ⌘W does nothing and never closes the window (the red button does); in a window without a workspace (the welcome screen, Settings) it is "Close Window" and closes it. ghostty's `super+w` is unbound inside clubmate, so ⌘W reaching a surface does nothing. The item sits after "Close Session" in the File menu; SwiftUI keeps the system "Close" item (`performClose:`) and may hand ⌘W back to it when it rebuilds the menu, so the app moves ⌘W from it to its own item whenever the menu changes (the system item stays, without a shortcut).

The `search` plugin backs ⌘P and ⌘⇧F with hidden commands; the app calls them through `command.run` and never through the bus (search results are never published). `search.files {query, limit?=50 (max 200)}` (agent) ranks workspace-relative paths (prefixed with the folder name when the workspace has several folders; a file reachable through two folders, such as a worktree opened next to its repo, is listed once, under the first folder in order) from a per-workspace index of `git ls-files --cached --others --exclude-standard` (or a bounded walk outside git) capped at 200 000 paths, rebuilt in the background after `fs.changed`; it returns `{matches: [{path, absPath, positions, line?}], truncated, capped, indexing?}`, where `positions` are rune (Unicode scalar) indexes into `path`, a query ending in `:N` puts `line: N` on every match, and `indexing: true` (empty matches) means the first index is still building: retry. `search.start {query, regex?, case?, word?, glob?}` returns `{id}` and cancels the workspace's previous search; `search.poll {id, after}` waits up to 1 s and returns `{id, matches: [{path, absPath, line, col, text, ranges}], next, done, truncated?, indexing?, error?}` with at most 500 matches and under 512 KiB per reply; `search.cancel {id}` stops a search. `line` is 1-based, `col` the 1-based byte column of the first match in the full line (what `editor.open` takes), `text` the line cut to at most 512 characters around the first match, and `ranges` merged `[start, end)` rune offsets into `text`. A search keeps at most 10 000 matches (`truncated` when it stops there) and frees them once a poll has returned `done` at the end, so callers never re-poll an earlier `after`; an unknown, cancelled or other-workspace id polls as `done` with no matches. `search.preview {path, line, context?=8 (max 100)}` returns `{lines: [{n, text}]}` (each at most 512 characters) for a regular file inside the workspace folders, refusing symlinks and anything that resolves outside them. `search.grep {query, regex?, case?, word?, glob?, limit?=100 (max 500)}` (agent) is the synchronous variant: `{matches, truncated}` within 4 s and 448 KiB. Content search uses `$CLUBMATE_RESOURCES/tools/rg` first, then `rg` on the core's `PATH` (`--no-config --hidden --glob !.git`; user globs only narrow results) and a built-in RE2 engine when neither exists (files over 5 MiB, binaries and symlinks skipped). All of them refuse the home workspace with `search unavailable in the home workspace`. Walks never enter `~/Library` or another direct child of `~` when they start at `~` or above it; a workspace folder of `/` or a firmlink root such as `/System/Volumes/Data` is otherwise not guarded, since the user opened it.

The `git` plugin renders only `git.sidebar` (the Git tab of the Code sidebar) and `git.review`; `git.main` stays unrendered. `git.sidebar` is `empty` without repositories, else a `stack` of a failure badge and busy text (when set), the commit `form` (a repo `select` when there are several live repos, the message field and Commit; action `commit`, a new id after each commit) and a `scroll` around the `tree` `git`: one root per folder (branch as detail), `Staged`, `Changes` and `Untracked` groups, at most 1000 files per group and the tree within the node limit (menu entries count). Each file has a context menu: `unstage` for staged files, else `stage`, plus `discard` (with a confirm) for restorable unstaged changes; the event `value` is the file's id, and an id that is no longer listed fails with `the file is no longer listed`. `select` (click, ↩ or `o`) on a file opens it in nvim through `editor-nvim.diff` (`{base: "head", target: "index"}` when staged, else `{base: "index", target: "worktree"}`) without moving focus; an untracked folder only selects. `ga` / `gu` / `gr` send the file's `stage` / `unstage` / `discard` menu entry (with its confirm) and `gc` focuses the commit field. An untracked folder is collapsed by default and expands to its untracked files (`git ls-files --others --exclude-standard`, at most 1000, labelled relative to the folder, ids like other untracked files), which select, open and stage like files; their ids must be clean paths under a listed untracked folder. A folder's listing is cached until the next status refresh.

The `git` plugin manages the worktrees of each git workspace folder through hidden commands; `repo` (optional) is a workspace folder from `repos` and defaults to the first git folder. Worktrees always come from the folder's own `git worktree list`, compared with symlinks resolved, and map like editor-nvim's routing: a folder at `<checkout>/<rel>` maps to `<worktree as git prints it>/<rel>`, stored as empty when that is the folder itself. `git.worktrees {}` (agent) returns `[{repo, path, branch, head, main, current, defaultBase}]` for every git folder, main checkout first (`branch` empty when detached, `head` the short SHA, `defaultBase` the folder's default review base, omitted when it has none). `git.worktree-switch {repo?, path}` (agent) accepts only a listed worktree root (else `not a worktree of <repo>`) and calls `workspace.worktree.set`. `git.worktree-new {repo?, branch, from?, switch?}` (agent) and `git.worktree-remove {repo?, path, force?}` (agent, destructive) validate synchronously and return `{id}`, then run in the background behind the git section's busy gate (`another git operation is running` while one runs); `git.worktree-op-status {id}` (agent) waits up to 1 s and returns `{done, error?, path?, notice?}`, `path` being the new worktree after a create. New: the branch must pass `git check-ref-format --branch` unchanged, `<main>/.worktrees` and every existing component under it must not be a symlink (`worktrees folder must not be a symlink`), and `<main>/.worktrees/<branch>` must not exist; it runs `git worktree add <dir> <branch>` for an existing branch, else `git worktree add -b <branch> <dir> <sha>` from the HEAD of the worktree `from` (a listed worktree root, else `not a worktree of <repo>`; ignored when the branch exists) or, without it, of the current worktree, adds `.worktrees/` to `info/exclude` when the repo does not ignore it, then switches unless `switch` is `false` (`path` is returned either way). Remove refuses the main checkout (`cannot remove the main checkout`) and the checkout holding the folder itself (`cannot remove the checkout of the workspace folder`) synchronously; in the background it refuses a dirty worktree (`worktree has uncommitted changes`), re-reads the project, runs `editor-nvim.stop-root {root, force}` (its `unsaved buffers: …` error is the operation's error), `agents.stop-root {root: <worktree>}` (best effort: closes the worktree's agent sessions, stops their processes and deletes their checkpoint refs), `git worktree remove <path>` (never `--force`, never deleting the branch) and, when the folder's stored selection then points at the removed worktree, `workspace.worktree.set` back to the folder; it always ends with `editor-nvim.release-root {root}`, so a failed `git worktree remove` brings the current worktree's nvim back. `git.worktree-switch` also fails with `another git operation is running` while one runs. In the home workspace `git.worktrees` returns `[]` and switch, new and remove fail with `worktrees unavailable in the home workspace`. `git.worktree-sessions {path}` (not agent-visible) returns `[{id, title}]` of the project's running sessions whose cwd is inside `path`, except editor-nvim's own. `git.branches {}` (not agent-visible) returns `[{repo, name, remote?}]` per git folder: local branches no worktree has checked out, then remote-tracking branches whose local name does not exist (the remote is the longest `git remote` name prefixing the ref, so remotes with `/` work), each newest commit first (one `git for-each-ref --sort=-committerdate`), at most 1500 local and 500 remote-tracking per folder. `git.branch-switch {repo?, branch}` (not agent-visible, destructive) validates the name (git's ref-name rules, then `check-ref-format --branch`) and that it is `refs/heads/<branch>` or `refs/remotes/<branch>`, returns `{id}` behind the same busy gate and runs in the folder's current worktree: a branch some worktree has checked out switches the folder to that worktree; else, after `editor-nvim.unsaved {root}` returned no buffers (it fails at once with `Save or discard unsaved changes first: <names>`; a missing editor-nvim is skipped), `git switch --no-guess -- <local>` (a remote `origin/x` with a local `x`), or `git switch --track -- origin/x`; git's own refusal (local changes, conflicts) is the operation's error. When git warns that commits were left behind a detached `HEAD`, that warning is the status's `notice` (the app shows it in the banner). After a switch it runs `editor-nvim.checktime {root}` for the folder's root.

The `git` plugin's review compares a worktree's working state (the **head**, uncommitted and untracked files included) with the merge-base of a **base** and that worktree's `HEAD`. Reviews are kept per head worktree toplevel (symlinks resolved) and stored under `review/<projectId>` as `{reviews: {<head>: {base, head?, label?, filters}}, filters}`; a **branch head** (a local or remote branch no worktree has checked out) is reviewed read-only from git objects without a checkout: it is kept under the folder's current worktree with `head` = the branch, compares the merge-base of base and the branch's commit (or a `commit:<sha>` base itself) with that commit (`git diff <merge-base> <head sha>`, no untracked files), opens the editor with `base: <merge-base sha>..<head sha>` and opens files as `editor-nvim.diff {target: "rev:<head sha>"}`; once a folder's current worktree has that branch checked out (switched to it, or a worktree for it became current) the review becomes that worktree's working-tree review and is saved so; the top-level `filters` are the workspace default for new reviews and change with every filter change. The active review is the one whose head is a folder's current worktree (the last started one first): switching a folder to another worktree pauses it (the slot goes `empty`) and switching back resumes it with the same base and filters. Whenever the active review has not been opened in the editor by this plugin process, or its merge-base (or a branch head's commit) changed, it calls `editor-nvim.review-open {cwd: <head>, base: <merge-base sha>, excludes}`, so a review reopens after a restart; a failed open (an error from editor-nvim) is retried on the next refresh. A failed `review-open` or `review-entries` sets the header's `error` to editor-nvim's message (e.g. `Neovim is waiting for input — press Enter in the editor`) and keeps the last entries; the next refresh retries and clears it. `editor.started` for the workspace marks every review of the workspace unopened and refreshes, so the review tab comes back after nvim restarts. `review.changed` with kind `closed` (the user closed the module's review in nvim) marks the active review closed: refreshes (file saves, nvim events, `git.refresh`) neither reopen it nor ask for entries, and the list keeps its last entries; only the next `select`, `reviewed` or `next` event, or a new `git.review`, reopens it. Events are matched by workspace, not by root, because the nvim of a multi-folder workspace runs in its first folder.
- `git.review {base?, head?, baseLabel?}` (agent, hidden from the palette, which offers the client's Review… picker instead; `git.review-branch` is a hidden, non-agent alias): `head` is a worktree root, a branch checked out in one, or any other local or remote branch (a read-only branch head; `unknown branch <head>` otherwise), default the first git folder's current worktree; `base` is a branch, a remote branch or a worktree root (meaning its branch, or its `HEAD` when detached), default the repo's default base; `commit:<sha>` is that commit itself as the base side, with no merge-base (an unknown sha fails with `invalid ref`; with a branch head it is diffed against the branch's commit, still read-only), and `baseLabel` (at most 64 characters) is then the header's `base` label, default `commit:<sha>`. A `base` or `head` starting with `-` fails with `invalid ref`, unknown refs with `unknown branch <ref>`, unrelated histories with `no merge base with <base>`. It switches the folder to the head worktree when needed (never for a branch head) and focuses the editor. Starting the same base again keeps the review's filters, cursor and folds.
- `git.review-swap` (agent): the base becomes the head (its worktree, else a branch head) and the old head (its worktree root, or its branch) the base; the old review is dropped. It fails with `no review in progress`, or with `invalid ref` when the base is a `commit:<sha>`.
- `git.review-filter {tests?, generated?, glob?}` (agent): sets the active review's filters (or only the workspace default without one); omitted fields are kept. `tests` hides `*_test.go`, `**/testdata/**`, `*.spec.*`, `*.test.*`; `generated` hides `go.sum`, `**/go.sum`, `go.mod`, `**/go.mod`, `*-lock.json`, `*-lock.yaml`, `*.lock`, `*.pb.go`; `glob` is one more glob (trimmed; `""` clears; anything but letters, digits and `* ? [ ] { } , . _ - / !` fails with `glob may only contain …`, and a stored glob that does not pass is dropped on load). Globs match like git pathspecs: a glob without `*?[` matches the path or a directory prefix, otherwise it is matched against the whole toplevel-relative path with `*` crossing `/`. With a review it calls `editor-nvim.review-excludes` with the hidden globs.
- `git.review-refs {query}` (not agent-visible) returns `[{ref, kind, label}]` for the head's repo (at most 200): `worktree` (ref the worktree root, label its branch or folder name), then `branch` (local), then `remote` (`origin/…`, without `*/HEAD`). The head worktree (the active review's, else the first git folder's current one) and its branch are left out; for a branch head only that branch is left out, so its hosting worktree and branch are offered. An empty query keeps that order; otherwise each kind is filtered and ranked by the Go to File fuzzy scorer on `label`, kinds never mixed.
- `git.end-review` (agent) drops the active review and runs `editor-nvim.review-close`.

The slot `git.review` (declared by the `git` section) is `empty` without an active review. Otherwise it is a `scroll` around a `tree` with id `review` whose `review` header has `base` and `head` labels (branch names; the client adds "(working tree)" to the head), `baseRef` (as given to `git.review`), `headRef` (the head worktree root, or the branch of a branch head), `readOnly` (true for a branch head; the client then says "(read-only)" instead of "(working tree)"), `mode` (`module`, `diffview` or `native`), `progress` (`24 files · 6 hidden · 10/24 reviewed`; the hidden part only when non-zero, the reviewed part only in `module` mode), `warning` (`<A> has uncommitted changes that are not in the base` for a dirty base worktree), `error` (a refresh failure such as `unknown branch <ref>`) and `chips` (`tests` and `generated` with `on` = hidden, plus `glob` labelled with the glob while one is set). Items are the visible files grouped into folders (folders first, by name; a folder whose only child is one folder is merged into `a / b`, id the deepest path), file ids and folder ids being toplevel-relative paths. A file has `badge` = status (`M`, `A`, `D`, `?` for untracked, or diffview's letter), `additions` and `deletions`, and in `module` mode `reviewed` and `comments`. In `module` mode the set of files is `editor-nvim.review-entries`; otherwise it is `git diff <merge-base>` against the working tree plus untracked files (added lines counted from the first MiB of a regular file; an untracked symlink counts as one line and is never followed, other file types as none); the tree sorts them either way. Hidden files are counted from the latter in every mode and also filtered out of the module's entries. The tree holds at most 4900 rows (folders, files, chips and breadcrumb) and ends with a muted `… N more` row for the files left out. ui events on the slot: `select` (file or folder id; a file opens: `review-select` in `module` mode, otherwise `editor-nvim.diff {path, base: "rev:<merge-base>", target: "worktree"}`, or `target: "rev:<head sha>"` for a branch head), `expand` / `collapse`, `reviewed` (file id; in `module` mode it sets the mark to the opposite of the row's `reviewed` through `review-reviewed {path, reviewed}`, otherwise nothing), `next` (value `1` or `-1`; `review-next` in `module` mode, which follows diffview's order, otherwise the next or previous file in tree order, wrapping, opened like `select`), `collapse-others` (a file or folder id, `""` meaning the selected file: collapses every folder except that id's ancestors) and `focus` (folder id, a file focuses its folder, `"."` or `""` clears; while focused the tree shows that folder's children and a `breadcrumb` from `{id: ".", label: <head>}` down). The app shows the slot as the Review tab of the Code section's sidebar while it is not `empty` and switches to that tab when a review starts: the header's `started` is set by every `git.review` to the start time in Unix milliseconds (strictly increasing, also across plugin restarts; reviews restored after a restart carry none), and each workspace's store switches only when it sees a value greater than any it has seen, so the first value after launch, a paused review coming back on a worktree switch and a restored review never switch; otherwise the user's last chosen tab stays. It draws the `review` header above the tree, and sends `reviewed` (`r` on a file) and `next` (`n` / `N`) from the list's keys, and `collapse-others` with the cursor's id for `-`. `review.changed` events from the workspace's nvim move the cursor (`file_open`), mark the review closed until the next list action (`closed`) or refresh the slot after 300 ms (every other kind).

The app binds them as menu items, so they work with a terminal or nvim focused: View ▸ Go to File… (⌘P) and Find in Files… (⇧⌘F), next to Command Palette (⌘K); the three overlays are exclusive, and the shortcut of an open overlay whose field is not focused focuses the field instead of closing it. File ▸ Page Setup and Print are removed so ⌘P is not taken, and the embedded Ghostty config always gets `keybind = super+p=unbind` and `keybind = super+shift+f=unbind`. Opening a match calls `editor.open {path, line, col?}` and then focuses the Code section; ⌥↩ in Find in Files sends the results to `editor.quickfix` (at most 1000 files and 2 MiB, title `Search: <query>`, suffixed ` (first N)` when cut).

When nvim reaches its left or right edge through the `clubmate` Lua module (see `docs/nvim-integration.md`), editor-nvim calls `ui.focus` with slot `editor-nvim.sidebar` and `edge` `h` or `l`.

`ui.event` requires a non-empty `action`, a valid slot and a registered section. It is routed to the owning plugin.

`diagnostics.collect` `{projectId?, appVersion?, extra?}` writes `clubmate-diagnostics-<YYYYMMDD-HHMMSS>.zip` (local time; `-2`, `-3`, … appended when that name exists) into `<state>/diagnostics/`, keeps only the newest 3 archives there, and returns `{path, files: [{name, bytes}]}` (`bytes` uncompressed). The zip holds `info.json` (`version`, `commit`, `flavor`, `sessionProtocol`, `macOS`, `arch`, `collectedAt` in UTC, `coreVersion`, `coreUptimeSeconds`, `appVersion` when given), `logs/core.log` and `logs/plugins/<id>.log` (the last 2 MiB of each, starting after the first newline when cut; missing logs are skipped), `plugins.json` (`plugin.list`), `workspaces.json` (`[{id, name, repos, roots, missing}]`), `sessions.json` (`[{id, workspace, title, owner, cwd, state, exitCode, created}]`, never output), `ui/<projectId>.json` (the `ui.get` views of `projectId`, or of every workspace in `ui.presence` when absent; none without UI) and `README.txt` listing them (with the line `window.png may show terminal and editor contents.` when it is there). `extra` maps file names to base64 contents added as they are; only `settings.json` and `window.png` are accepted, each at most 10 MiB (otherwise invalid params). It never includes terminal output, environment variables, plugin storage or the databases. Plugin callers get invalid params.

`clubmate diagnostics [-o file.zip]` calls it without `extra` (60 s deadline) and copies the archive to `-o` (default `./<archive name>`), printing the path. When the call fails (no core, a dial error, the deadline, or an error reply) it neither starts the core nor reads any database: it writes the zip itself with `info.json` (the CLI's own build, `macOS`, `arch`, `collectedAt`, `"core": "unreachable"` and `coreError`), the same log tails and a README noting `core unreachable: no workspace/session/plugin/UI state`.

The app's Help ▸ Collect Diagnostics… first shows a sheet listing the files and `Terminal output, environment variables and plugin storage are not included.`, with an unchecked box "Include a screenshot of the window (may show terminal and editor contents)" and Cancel (default) / Save…. On Save… it passes its own settings (keys containing `token`, `secret`, `password` or `key`, case-insensitive, read `<redacted>`), the key window's workspace and its version, and `window.png` (its own drawing of the key window, never a Screen Recording prompt) only when the user opts in; then it asks where to save (default `~/Downloads`), moves the archive there and reveals it in Finder. Without a core connection it points to `cm diagnostics`.

## Notifications

- `ui.updated` `{subscription, view}`: `view` is a `SlotView`. On subscribe, the current views of the project are replayed first.
- `ui.focus` `{subscription, section, slot, edge}`: the client should show `section`, and `slot` when non-empty, for that subscription's project. `edge` is present only when the caller passed a non-empty one: the direction nvim navigation left in. The client ignores a focus whose `edge` does not lead to its sidebar (`h` with the sidebar on the left, `l` with it on the right; `j` and `k` never do). A focus to a hidden sidebar shows it first.
- `ui.closed` `{subscription, error}`: the subscription ended with an error (for example it fell behind); resubscribe and replace local state.

## File watching

`fs.watch` starts one FSEvents stream over the project's repos and roots (the union, deduplicated) as they are at call time (repos added or worktrees selected later are not covered; call `fs.watch` again). It ends on `fs.unwatch` or when the connection closes. Repos that cannot be resolved (missing or deleted) are skipped and the rest are watched; a project with no resolvable repos gets a watch that never emits. When a repo is a linked git worktree (`.git` is a file with `gitdir: <path>`), the watch also covers that worktree's gitdir and the main repository's common dir (from `<gitdir>/commondir`), so commits, checkouts and ref updates made in the worktree emit paths under `<main>/.git/` (only `HEAD`, `index`, `refs/heads/**` and `worktrees/<name>/{HEAD,index}` are reported from inside `.git`). Roots are symlink-resolved, so paths are real paths (`/private/var/...`, not `/var/...`).

- `fs.changed` `{watch, projectId, paths, overflow}`: sent to the watching connection with a 200ms coalescing window. `paths` is deduplicated. Under any `.git/`, and under a linked worktree's gitdir and the main repository's common dir, only `HEAD`, `index`, `refs/heads/**` and `worktrees/<name>/{HEAD,index}` are reported. A window with more than 1000 paths, or one in which FSEvents reports dropped or coalesced events (MustScanSubDirs, KernelDropped, UserDropped), is sent as `overflow: true` with `paths: []`; the receiver rescans.

Plugins receive it as `Plugin.FSChanged`, and use `Host.WatchFS` / `Host.UnwatchFS`.

The `agents` plugin hosts ACP v1 agents (Claude through `@agentclientprotocol/claude-agent-acp`), one process per (agent, workspace, worktree root) in the effective root of the workspace's first git folder (the first folder when none is git; the other folders go as `additionalDirectories` when the agent supports them). The process env and the `clubmate` MCP server passed at `session/new` and `session/resume` carry `CLUBMATE_PROJECT_ID=<workspace id>`, so Clubmate tools (also a `clubmate` server registered in Claude Code, which inherits the env) act on the session's workspace. `session/new` and `session/resume` also send `_meta.claudeCode.options.env` `{CLUBMATE_AGENT_SESSION: <agt_ id>}` (claude-agent-acp merges it into Claude's env), so hooks such as `cm notify` know which agent session they run in; `CLUBMATE_SESSION_ID` is never set on the adapter (it marks terminal sessions for the process tracker). Each process group is recorded with its start time in the plugin state dir; when the plugin starts it stops (TERM, then KILL after 2 s) recorded groups that are still alive, started at the recorded time and whose leader runs `claude-agent-acp` (or `$CLUBMATE_AGENTS_COMMAND`), then clears the record. Unavailable in the home workspace (`Agents aren't available in the home workspace`). Its commands are hidden; the agent-visible ones are `agents.new`, `agents.prompt`, `agents.cancel`, `agents.permission`, `agents.sessions`, `agents.wait`, `agents.transcript` (none destructive) and `agents.answer` (destructive). The calling agent session is the `command.run` `caller` (set by `clubmate mcp` from `CLUBMATE_AGENT_SESSION`); it counts only when it is a session of the workspace:
- `agents.new {agent?: "claude", branch?, prompt?, title?}` → `{session, worktree}` at once; the agent starts in the background. With a caller the session is its child (`parentSession`), runs in the caller's worktree, is not selected in `agents.main` (sessions without a parent are), and fails with `a session may run at most 8 child sessions at once` while 8 children of the caller are `running` or `waiting` (also an agent prompt that would start a turn on another, idle child); without one it runs in the effective root of the first git folder and is selected. `branch` (must be a valid branch name) makes the worktree `<main checkout>/.worktrees/<branch>` (plus the folder's subpath) the session's, returned at once; in the background (one creation at a time) it runs `git.worktree-new {repo, branch, from: <the caller's (or that root's) worktree>, switch: false}` and polls `git.worktree-op-status`, and the agent starts (and the prompt is sent) only once it is done; a failure is the session's `error` (`create worktree <branch>: <git's error>`); the next attach (Retry, `agents.resume`, a new prompt) creates the worktree again. `title` sets the title; `prompt` is submitted as by `agents.prompt` from the caller. After `session/new` a child gets its parent's current mode and `select` config values (instead of the worktree's remembered ones, and without storing them), and the parent's advisor is copied into the child's record (`advisor`) at creation and sent at `session/new`/`session/resume`; choosing an advisor in the child's own picker replaces it in the child's record only (the worktree's remembered advisor is untouched). When the agent cannot start, the session gets status `error` with the reason (e.g. `Node 22+ is required to run Claude (found <v>)`). The first start installs the adapter with npm into the plugin state dir; an install counts only once npm succeeded (a marker file), otherwise the next start reinstalls from scratch. While it runs, sessions without a running agent show `Installing Claude adapter…` under the header; a failed install is an `error` with `retry`.
- `agents.prompt {session, text, attachments?: [{kind: "file", path} | {kind: "selection", path, startLine, endLine, text}]}` checkpoints the worktree (`refs/clubmate/cp/<session>/<turn>`, a commit whose parent is `HEAD` and whose tree is the worktree with untracked files, built through a temporary index seeded from a copy of the worktree's index; the real index is never written) and sends `session/prompt`; it returns once the turn started and fails with `the session is closed`. While a turn runs the prompt is queued instead (in memory, not logged; closing or deleting the session drops the queue): when the turn ends without an error and was not cancelled, every queued prompt goes as the next turn, the texts joined in order with blank lines and the attachments concatenated. After a cancel or an error the queue stays until it is sent or removed (a prompt cancelled before it reached the agent goes back to the front of the queue); the next prompt sends the queue ahead of its own text. Files go as embedded resources when the agent supports them, else as resource links; selections as resources or a fenced text block. When a turn had an edit, delete or move tool call it ends with `editor-nvim.checktime {root}`. A prompt with a caller is logged with actor `agent:<caller id>` and `from: <caller id>` in the `session/prompt` payload, and its first text block goes to the agent prefixed with `[From Clubmate agent session "<caller title>" (<caller id>), not from the user]` and a blank line (the logged text has no prefix); an agent call (`agent: true`) without a caller is logged with actor `agent:unknown` (`from: "unknown"`) and prefixed with `[From another agent session, not from the user]` and a blank line; queued prompts are joined into one turn only while they share the same caller. The user's own prompts are logged with actor `user` (the agent's own events with `agent:<agent>`, e.g. `agent:claude`).
- Every turn ends its prompt with policy text blocks the transcript does not show. A top-level session gets its Finish text (`[Clubmate finish mode: ask]` or `[Clubmate finish mode: merge]`). A child gets `[Clubmate finish mode: child]` instead, whatever its Finish value: when it runs in its own linked worktree under `<main checkout>/.worktrees/` on a branch that is not the default base or `main`/`master`, and its parent is on a branch that is neither the default base (`origin/HEAD`, else `main`/`master`) nor `main`/`master`, it is told to run the tests, commit, and merge its branch into the parent's branch inside the parent's worktree (`git -C <parent worktree> merge --no-edit <branch>`, retried once after 5 s when another merge holds `index.lock`, never when that worktree has uncommitted changes; a conflicting merge is aborted with `git -C <parent worktree> merge --abort` and the conflicting files reported); otherwise (shared worktree, the child or its parent on the default branch or detached, parent gone) it is told to commit only. The composer has no Finish picker for a child. Both forbid merging into main and removing worktrees or branches. A session with at least one child also gets `[Clubmate orchestrator]`: write to the user only the children's questions that need the user, no echo of what was sent, no status recaps, answer children's permissions with `agents.permission`, pass the user's answers with `agents.answer`.
- When a child's turn ends `done` (no queued prompt, no pending permission, not `asks`), the plugin removes it if it is merged: it has its own worktree as above, its branch moved since the worktree was created (`fork` in the record, `HEAD` right after creation), `git merge-base --is-ancestor <branch> <parent branch>` holds, `git status --porcelain` is empty, `git.worktree-sessions` lists no terminal in it, no other open agent session runs inside it and the child has no open children of its own; the policies are computed within 10 s. It then closes the child (logged as `session/close` by `clubmate`, status `closed`; the child stays listed), runs `git.worktree-remove {repo, path}` (plugin-initiated, no approval; it calls `agents.stop-root` back), polls `git.worktree-op-status`, and deletes the branch with `git branch -d` in the parent's worktree. Failures are logged to stderr and as a `notice` entry (`Couldn't remove the merged worktree` with the error) in the child's transcript, and leave the child closed.
- `agents.answer {session, text}` (agent, destructive: the core asks the user first) sends `text` like `agents.prompt` with no caller: a user turn with actor `user` and no prefix.
- `agents.cancel {session}` sends `session/cancel` and answers every pending permission with `cancelled`; `agents.permission {session, request, option}` answers one (`request` is the permission entry's id, `option` one of its `optionId`s); only for a caller whose descendant (child, grandchild, …; never the caller itself) the session is, else and without a caller it fails with `the session was not started by this agent` (an unknown session fails with `unknown agent session` first). The app answers through the `permission` action instead.
- `agents.mode {session, mode}` sends `session/set_mode` (only advertised modes) and remembers the mode for new sessions in that worktree.
- `agents.config {session, id, value}` sends `session/set_config_option` for one of the agent's `select` config options (not the `mode` category, which `agents.mode` covers; only advertised values) and remembers the value for new sessions in that worktree, re-applied after `session/new` in the order the agent lists its options. `id: "advisor"` instead stores the Claude advisor model for the worktree (`fable`, `opus`, `sonnet`, or empty for the Claude Code default); it is passed as `_meta.claudeCode.options.settings.advisorModel` on the next `session/new` or `session/resume` and does not change a running session.
- `agents.stop-root {root}` (not agent-visible; `root` absolute) closes every session whose worktree is inside `root`, stops their processes (waiting up to 4 s) and deletes their checkpoint refs; `git.worktree-remove` calls it. `agents.close {session}` closes the session (`session/close` when supported); the process stops when no open session remains on it. `agents.delete {session}` (destructive, confirm) first closes the session, so it cannot start new children, then deletes every descendant session (each closed before its own children are collected, deleted children first, cancelling running turns; worktrees are untouched) and also calls `session/delete` when supported and removes the log and the checkpoint refs. `agents.resume {session}` reattaches through `session/resume` (fails with `the agent cannot resume this session` otherwise).
- `agents.sessions` → `[{id, workspace, worktree, agent, agentSessionId, parentSession?, advisor?, fork?, title, status, mode, finish?, createdAt, updatedAt, closed, error?, pending?, asks}]` (stored in plugin storage under `session/<id>`; `pending` is not stored: the ids of the permission entries awaiting an answer, sorted; `asks` as in `agents.wait`, computed when the status is set and stored, so listing sessions never loads a transcript); `status` is `running`, `waiting` (a permission is pending), `done`, `idle`, `error` (with `error`, e.g. the agent's stderr tail) or `closed`.
- `agents.wait {sessions: [id], timeout?}` (`timeout` in seconds, default 120, at most 300; the manifest gives it a 310 s command timeout) waits for any of the listed sessions of the workspace (not only the caller's children) to stop `running`: it returns at once when one of them is not `running`, else on the first status change of any of them, else when any of them starts a new turn (its `turn` grows, e.g. queued prompts went out), else when the timeout ends, and fails with `sessions is empty` or `unknown agent session: <id>`. It returns, in the order given, `[{session, status, turn, stopReason?, error?, asks, permission?: {request, title, kind, options: [{optionId, name, kind}]}}]`: `turn` is the latest turn and `stopReason` its stop reason; `permission` is the oldest pending permission (`request` the permission entry's id for `agents.permission`, `title` and `kind` from its tool call). `asks` is true when the status is `done` and the session's last agent message ends with `?` once trailing whitespace, `*`, `_` and `` ` `` are trimmed: the agent is asking a question. It is computed when the status is set and stored in the record.
- `agents.transcript {session, fromTurn?}` → `{session, modes, configOptions, commands, turns: [{turn, checkpointSha, stopReason?}], entries: [{kind, id, turn, ...}]}` with entries upserted by `(kind, id)`: `user` (`text`, `content` blocks, `from` the sending agent session id or `unknown` when an agent sent it), `agent` / `thought` (`text`), `tool` (the merged ACP tool call fields under `tool`; unfinished calls of a cancelled turn get status `cancelled`), `plan` (one per turn), `permission` (`toolCall`, `options`, `outcome` once answered) and `notice`.

The section `agents` ("Agents", icon `sparkles`, order 25, after Terminals) renders two slots per workspace. Both are `empty` with `Agents aren't available in the home workspace` in the home workspace.
- `agents.sidebar`: a `new` button (action `new`) and a `tree` `sessions`. On top, when any top-level session (no `parentSession`) is `waiting` or `done` with `asks` (as in `agents.wait`), a `Needs you · N` group (id `wt:needs`, expanded by default) lists them again with ids `needs:<id>`, as leaves. Then one row per worktree (id `wt:<root>`, label its folder name, expanded by default) with its open top-level sessions, newest first, and, when it has closed top-level sessions, a last `Closed · N` group (id `wt:closed:<root>`, folded by default) holding them. A session row has the title, `<agent> · <activity>` as detail (`Running · <elapsed> · <last tool>` where `<elapsed>` is the time since the current turn started: `<1 min`, `N min`, `N h M min`; `Waiting for permission · <tool>`, `Done · 12 min ago`, `Idle · …`, `Error · <first error line>`, `Closed · …`) and a status icon. Its menu has Close Session (`close`, open sessions only) and Delete Session (`delete`, with the confirm text; `Delete this agent session and its N child sessions, their transcripts and checkpoints?` when it has N > 0 descendants). A session with a parent that is in the list is not placed in its worktree's group: it is a child item of its parent's row (`hasChildren`, `expanded`, children newest first), recursively, and stays there when it is closed. A session with a `parentSession` never goes in `Needs you` (its orchestrator answers it) or in a `Closed` group. `select` with a session id or a `needs:<id>` opens that session (the `needs:` row stays selected while it is in the group); `close`/`delete` accept both ids. `expand`/`collapse` on a group row (`wt:<root>`, `wt:needs`, `wt:closed:<root>`) or on a session row (stored as `s:<id>`, expanded by default) folds it.
- `agents.main`: for the selected session (the newest when none is chosen; `empty` without sessions), a header (title; agent, worktree, mode and the current `model` config option; `review` "Review changes" when the worktree differs from the session's first checkpoint, rechecked after each turn and when the session is selected; `stop` while running; on `error` the first error line with `retry`, `signIn` when the agent needs a login, or `continue` when the agent cannot resume the session; a child session also has a `from <parent title>` button with action `selectParent` that selects the parent), then the `transcript`, the queued prompts (muted, each with `unqueue` "Remove"; when no turn runs a `sendQueued` "Send queued" button) and the `composer`. A closed session shows "Reopen" (`retry`) instead of the composer, or "Continue in a new session" (`continue`) when the agent cannot resume it (its agent advertises no `session/resume`, or resuming failed). `continue` creates a new session for the same agent and worktree and selects it; the old transcript stays readable. When the agent cannot start because Node is missing or too old, the main slot shows `empty` with `Node 22+ is required to run Claude (found <v>)` under the header.
- Node ids in `agents.main` start with `<session>/` (`<session>/tool/<toolCallId>`, `<session>/permission/<id>`, `<session>/composer/<n>`, `<session>/msg/<user|agent|thought>/<entry id>`, `<session>/plan/<turn>`), and events are applied to that session, not to the current selection. Message and plan ids stay the same when the window shifts, so the client keeps their state (e.g. an expanded "Thinking").
- The transcript shows the last 20 turns; the `showEarlier` button adds 20 more. A render is capped below the node limit: when the shown turns would exceed it, the oldest entries are dropped and the button stays. The open session renders at most 10 times a second while the agent streams; other sessions are not rendered, and a slot whose tree is unchanged since the last render is not sent again (a streaming background session re-renders only the sidebar).
- Tool cards: edits (`edit`, `delete`, `move`) show the ACP diff as a unified diff with `openLocation {path, line}` ("Open in nvim", → `editor.open`) and `review {turn}` ("Diff"); `execute` shows `$ command` and the output as `terminal`; `read` and `search` are one line with `openLocation` when the agent sent a location. Bodies over 200 lines or 64 KiB are cut to that with `truncated` and a `showAll` action; after `showAll` (node id names the card) the full body is sent, up to 1 MiB.
- Other actions: `send {text}` prompts with the pending composer attachments, `permission {request, option}` answers, `mode {mode}` switches, `config {id, value}` as `agents.config`, `attachFile {path}` adds a file chip, `attachSelection` adds the editor selection (`editor-nvim.selection`), `detach {id}` removes a chip, `unqueue` on `<session>/queue/<id>` drops a queued prompt, `sendQueued` sends the queue as a turn, `continue` starts a new session in the same worktree, `review {turn?}` runs `git.review {base: "commit:<checkpoint sha>", head: <worktree>, baseLabel: "before turn N"}` (default: the first turn with a checkpoint), `retry` reattaches (`agents.resume`), `close`/`delete` as the commands.
- Sign in: the client advertises `auth.terminal`. When `session/new` fails with `-32000` (auth required) and the agent offers a `terminal` auth method, the session errors with `sign in to continue` and the header offers `signIn`. It runs the agent's launch command plus the method's `args` (and `env`) in a terminal session owned by `agents` in the worktree, shown as a `surface` in `agents.main`; when it exits the terminal is removed and the session reattaches. A `-32000` from `session/resume` leads to the same Sign in. Closing or deleting the session kills and removes its sign-in terminal (its exit no longer reattaches); leftover sign-in terminals are removed when the plugin starts. The method's `env` never sets `ANTHROPIC_API_KEY`.

Every event is appended to `<state>/plugin-data/agents/sessions/<id>.jsonl` as `{workspace, worktree, session, parentSession, role, turn, seq, actor, ts, kind, payload}` with ACP payloads verbatim; text chunks are coalesced per message (flushed at turn end, after 2 s or at 64 KiB). Removing a workspace closes its sessions (`session/close` when supported, never `session/delete`: the agent's own history stays) and deletes their checkpoint refs, logs and records. Removing a worktree with sessions closes them and deletes their checkpoint refs.

## Bus topics

- `project.updated` `{project}`: published when a repo is added to a project (`project.addRepo`), it is renamed (`project.rename`) or a folder's worktree selection changes (`workspace.worktree.set`). Existing `fs.watch` streams do not follow; re-watch on this event.
- `editor.buffer` `{projectId, path}`: published by `editor-nvim` when nvim enters a file buffer (BufEnter). `path` is absolute, as nvim names the buffer.
- `editor.started` `{projectId, root}`: published by `editor-nvim` after it starts a new nvim for `root` (the first start and every restart) and connects to it; reconnecting to an nvim that is already running (e.g. after a plugin restart) publishes nothing.
- `editor.saved` `{projectId, path}`: published by `editor-nvim` after nvim writes a file buffer (BufWritePost).
- `agents.changed` `{workspace, session, kind}`: published by `agents` when a session is created, changes status or is deleted, coalesced per session and kind (`created`, `status`, `deleted`). Streamed transcript updates are not published.
- `agents.turn` `{workspace, session, status, asks}`: published by `agents` at every turn end (`status` after it: `done`, `error`, `closed`, `waiting` when a permission is still pending, or `running` when queued prompts start the next turn), when a session's agent fails (`error`), when a running session is closed (`closed`, once: the turn end that follows publishes nothing) and when a permission request starts waiting (`waiting`). `asks` is as in `agents.wait`. Not coalesced: one event per occurrence.
- `notify.posted` `{id, workspace, session?, owner?, title?, message, kind, agent?, ts}`: published by `notify.post` (`cm notify`, the `notify_post` MCP tool). `agent` is true (and the event source `agent`) when an agent called it through `command.run` with `agent: true`. `kind` is `needs-input`, `permission`, `done`, `stuck` or `info`; `message` is at most 1000 characters and `title` 120 (longer ones are cut with `…`); `owner` is the owner of a `ses_` session (e.g. `terminals`); `ts` is RFC 3339 UTC. `notify.post` checks that the workspace exists and that a `ses_` session belongs to it (other session ids pass as they are when shaped like `agt_<16 hex>`), and allows 5 calls per 10 s per workspace and 20 in all (error code -32015, "too many notifications", beyond that).
- `processes.killed` `{projectId, pids}`: published by `processes` when auto-kill terminates orphans of a project; never published with empty `pids`.

## Core notifications

- `project.open` `{id}`: sent to every connection that registered `"project.open"` (not to plugins, not to the caller of `project.open`, `workspace.open` or `workspace.home`); the client shows that project.
- `core.stopping` (no params): sent to every connected client (not to plugins) after `core.shutdown` has replied and right before the core stops. A client that sees the connection end after `core.stopping` treats the stop as intentional and does not restart the core; a connection that ends without it is an unexpected loss.

## Presence

The core publishes `ui.opened` `{projectId}` on the durable bus when a project's UI subscriber count goes from 0 to 1, and `ui.idle` `{projectId}` when it goes from 1 to 0.

## Visible section

Clients keep per-project UI state with `ui.state.get` / `ui.state.set` `{projectId, state}` (client callers only). Its `section` field is the section the project's window shows: the app has one window per project and writes `section` when it opens the project and on every switch. When a `ui.state.set` changes `section`, the core publishes `ui.section` `{projectId, section}` on the durable bus. Plugins read the current value with `ui.state.section` (`pluginsdk.Host.SelectedSection`).

`processes` uses it to skip work nobody sees: its 1 Hz refresh keeps recording history for every present project but renders only projects whose section is `processes` or unknown (`""`). On `ui.section` to `processes` it renders at once.

## Plugin runtime dir

The core creates `<runtime>/p/<pluginId>` (mode 0700) and passes its path to the plugin in `CLUBMATE_PLUGIN_RUNTIME_DIR` (`pluginsdk.RuntimeDir()`). It passes `<state>/plugin-data/<pluginId>` in `CLUBMATE_PLUGIN_STATE_DIR` (`pluginsdk.StateDir()`) for data that must survive restarts; the plugin creates it when needed. It also passes the build flavour in `CLUBMATE_FLAVOR` (`pluginsdk.Flavor()`): `release` for release builds, `dev` otherwise.

The core also passes the app's resources directory in `CLUBMATE_RESOURCES` (`pluginsdk.ResourcesDir()`), `Clubmate.app/Contents/Resources` when run from the app; bundled tools live under `tools/` and `nvim/` there.

A plugin's `session.create` (`pluginsdk.Host.CreateSession`) also takes `env`, entries added to the environment the session inherits, `unsetEnv`, names of variables removed from it first, and `pathAppend`, directories appended to the end of the session's `PATH` (entries already in it are skipped).

## ui.event contract

| node | trigger | `action` | `value` |
|---|---|---|---|
| button | click | `props.action ?? id` | `null` |
| list / tree | select item | `props.action ?? "select"` | item id |
| tree | expand / collapse | `"expand"` / `"collapse"` | item id |
| tree with `review` | `r` on a file / `n`, `N` | `"reviewed"` / `"next"` | item id / `1`, `-1` |
| table | select row | `props.action ?? "select"` | row id |
| table | expand / collapse | `"expand"` / `"collapse"` | row id |
| table | header click | `"sort"` | object `{column, desc}`: the clicked column id; `desc` flips when it is already the sort column, otherwise starts `true` for right-aligned columns and `false` for others |
| tabs | select tab | `props.action ?? "select"` | tab id |
| textField | submit | `props.action ?? "submit"` | text |
| toggle | change | `props.action ?? "toggle"` | bool |
| select | change | `props.action ?? "select"` | option value |
| folderField | pick folders | `props.action ?? "pick"` | string[] of absolute paths |
| form | submit | `props.action ?? "submit"` | object `{fieldNodeId: value}` |
| list / tree | choose a menu entry | entry `action` | item id |
| toolCard | click an action | entry `action` | entry `value` (`null` when absent) |
| permissionCard | click an option | `props.action ?? "permission"` | object `{request, option}`: `request` from props, `option` the option id |
| composer | send (⌘↩ or Send) | `"send"` | object `{text}` |
| composer | stop (Esc or Stop while `running`) | `"stop"` | `null` |
| composer | pick a mode | `"mode"` | object `{mode}` |
| composer | pick a `pickers` option | `"config"` | object `{id, value}` |
| composer | attach a file (picker or `@`) | `"attachFile"` | object `{path}`: absolute path |
| composer | attach the editor selection | `"attachSelection"` | `null` |
| composer | remove an attachment chip | `"detach"` | object `{id}` |

`nodeId` is the `id` of the node that fired the event.

## Forms

A `form` collects the values of the `textField`, `folderField`, `toggle` and `select` nodes among its descendants (nested forms collect their own fields), keyed by the field node `id`. The value is the field's current text, bool, option value or (`folderField`) string[] of chosen paths; fields that disappear from the tree are dropped.

- A `button` without an `action` prop inside a form submits the form: the form sends `props.action ?? "submit"` with the collected object as `value` and the form's `id` as `nodeId`.
- Return in a `textField` without an `action` prop submits the form the same way.
- Fields without an `action` prop inside a form are silent: they only update the collected values.
- A field or button with its own `action` prop sends its own event per the contract above (fields still update the collected values); it does not submit the form.
