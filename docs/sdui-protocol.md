# SDUI protocol

Plugins render trees of nodes into slots; clients draw them and send events back. Every tree is validated by `internal/sdui` (max 5000 nodes, depth 32). Violations fail with `ErrInvalidTree`.

## Node

```json
{"type": "button", "id": "new", "props": {"label": "New"}, "children": []}
```

- `type`: one of the types below.
- `id`: required for interactive types, unique within a tree.
- `props`: only the listed props are accepted; unknown props are rejected. `*` marks required props.
- `children`: count limited per type.

Interactive types (`tabs list tree table button textField folderField toggle select form toolCard permissionCard composer`) require an `id`. All but `toolCard` and `composer` accept an optional `action` prop: a string of 1-64 chars matching `^[a-z][a-zA-Z0-9.-]*$` (camelCase allowed, e.g. `showEarlier`). It overrides the default action name sent in `ui.event`. Action names inside props (`menu`, card `actions`) follow the same rule.

## Item shapes

`items` and `options` accept `null` as an empty list.

- item (`tabs`, `list`): `{id*, label*, detail, icon, badge, menu}`, strings except `menu`, ids unique and non-empty. `menu` is a list of menu entries (`list` and `tree` show them as the row's context menu).
- menu entry (item `menu`): `{action*, label*, confirm}`: choosing it sends `action` with the item id as value; with `confirm` the client asks first.
- tree item (`tree`): item fields plus `tone` (`neutral`, `accent`, `success`, `warning` or `danger`; colours the icon), `muted` (bool), `hasChildren` (bool), `expanded` (bool) and `children` (tree items).
- option (`select`): `{value*, label*}`.
- column (`table`): `{id*, title*, align, width}`: `align` is `left` (default) or `right`, `width` is a fixed width in points (`0` or absent = flexible, sharing the remaining space). Ids unique and non-empty.
- row (`table`): `{id*, depth, hasChildren, expanded, muted, cells*}`: `depth` is an integer 0-32 (indent 12pt per level, chevron when `hasChildren`), `muted` dims the row's text. Ids unique and non-empty. `cells` must have exactly one cell per column.
- cell (`table`): `{text, bar, tone, spark}`: `bar` is a number 0…1 drawn as a filled capsule behind the text, `tone` is `""`\|`ok`\|`warn`\|`danger` (colours the bar and sparkline, or the text when there is no bar), `spark` is a spark.
- spark (`table` cell): `{values*, max*}`: at most 900 numbers, `max` > 0. Values are clamped to 0…`max` and drawn as a 60×16pt line. The Go helpers `sdui.Sparkline`, `sdui.SparklineSized` and `sdui.NewSpark` clamp them before sending.
- attachment (`message`, `composer`): `{id, kind*, path*, startLine, endLine}`: `kind` is `file` or `selection` (with the 1-based line range); `path` is shown as given (relative to the worktree when inside it); `id` names a composer attachment for `detach` (non-empty and unique within the list when set).
- plan entry (`plan`): `{content*, status*}`, `status` `pending`\|`in_progress`\|`completed`.
- tool body (`toolCard` `body`): `{format*, text*}`: `format` `diff` (unified diff, drawn like `diff`), `text` (plain) or `terminal` (monospaced command and output).
- card action (`toolCard` `actions`): `{action*, label*, icon, value}`: `value` is a string, number, bool or an object of those.
- permission option (`permissionCard`): `{id*, label*, kind}`, ids unique, `kind` `allow_once`\|`allow_always`\|`reject_once`\|`reject_always` (tints the button; absent = neutral).
- command (`composer` `commands`): `{name*, description, hint}`: the agent's slash commands; `hint` describes the expected input.
- picker (`composer` `pickers`): `{id*, title, help, value*, options* (option[])}`: a session option menu; its label is the current option's label, prefixed by `title: ` when `title` is set; `help` is the tooltip.
- sort (`table`): `{column*, desc}`: the active sort column (arrow in its header) and direction. `column` must be one of the table's column ids.

A window shows at most one `surface` node at a time in v1. The client keeps every terminal it has shown mounted until the session's attach exits or the window closes, so switching between sessions is instant. A second `surface` visible in the same window at once renders a placeholder.

`list` and `tree` rows render lazily. Outside a `scroll` a `list` or `tree` scrolls itself and fills the height left by its siblings, so a long one never grows the window; a changed `selected` from the plugin scrolls to that row.

`table` rows render lazily; wrap the table in a `scroll` to scroll them under a pinned header. Each row counts toward the 5000-node limit; cells are bounded by the row and column caps (at most 1000 × 32), and spark values (cell sparks and `sparkline` nodes) are capped at 100000 per tree. The client does not page or truncate: a plugin with more rows renders the first 1000 or fewer and adds a final muted `… N more` row itself. `selected` works like `tree`'s: a changed value from the plugin sets, moves or clears the highlight (and scrolls to it); clicking a row highlights it locally and sends `select`. `sparkline` draws `values` as a 60×16pt line (e.g. in a header); with `height` it fills the available width at that height in points (e.g. a detail chart).

Agent chat nodes (the `agents` section):

- `transcript` is the chat column: a vertically scrolling list of its children (messages, plans, cards, `text`, a "Show earlier" `button`), anchored to the bottom while the user is at the bottom. Its `id` identifies the session, so the client keeps a scroll position per id. Adjacent `toolCard` children collapse into one summary row (`8 actions: read 3 files, 2 searches, …`, a spinner and the running card's title while one runs) that expands to one line per card; a lone card is shown as that line, and a line expands to the card's `body` and `actions`. Edit lines show the file name when the `title` holds a path (the path as a tooltip) and the `diff` body's `+added −removed`. Expanding the last item scrolls to the bottom. `failed` cards and `permissionCard`s stay full-size and split the run. Expansion is kept per card id until the app quits, so a group stays expanded as cards stream in or the run splits.
- `message` renders `text` as markdown (headings, lists, code blocks with copy, inline code, links). `user` messages are right-aligned bubbles with their `attachments` as chips (`@ path`, `path · lines 12–40`) and an optional muted `from` line ("from <from>") for prompts that another agent session sent; `agent` messages are plain; `thought` is collapsed behind "Thinking" and expands on click.
- `plan` is a checklist: `completed` checked, `in_progress` highlighted, `pending` empty.
- `toolCard` shows an icon for `kind`, the `title` and `status` (spinner while `pending`/`in_progress`, red for `failed`, muted for `cancelled`). `read` and `search` cards are one line. A `body` is shown under the title (`diff` and `terminal` in a monospaced box). `truncated` adds a muted "Output truncated" note; the plugin then also offers a `showAll` action. Each `actions` entry is a small button.
- `permissionCard` shows `text` and one button per option. With `outcome` set the card is answered: the chosen option (`outcome` = its id) is shown as chosen, `cancelled` as "Cancelled", and the buttons are disabled.
- `composer` is the prompt editor: a multi-line field (`placeholder`), the `attachments` as removable chips, an attach menu with the kinds in `attach`, the `agent` label, a mode picker over `modes` (current `mode`), one menu per `pickers` entry, and Send (with Stop beside it while `running`; labelled Queue while `running` unless `steers`, set when the agent takes prompts into a running turn). ⌘↩ sends (the plugin steers or queues it while a turn runs), Esc stops while `running`, `@` opens the client's fuzzy file picker (`search.files`) in attach mode, and `/` at the start lists `commands` filtered by the typed prefix; choosing one inserts `/name `. The field is uncontrolled; the plugin clears it after a send by rendering the composer with a new `id`.

`button.confirm`: when set, the client asks the user to confirm with that text before sending the event.

Input fields are uncontrolled: `value`/`values` on `textField`, `folderField`, `toggle` and `select` are initial values. The client keeps what the user entered while the node keeps its identity. A changed `value` in a later render replaces it, but re-rendering an unchanged one does not. To reset a form (e.g. after a successful submit), the plugin renders it with a new node `id`. The client then discards the form's field state and starts again from the props. Actions are routed by `action`, not by `id`, so rotating ids (e.g. `create-<n>`) does not change event handling.

## Slots

A slot is named `<section>.sidebar`, `<section>.main` or `<section>.status`, or `<section>.<name>` for a name the section declares in `slots`. A section is registered by a plugin, which owns all of its slots. Only the owning plugin may call `ui.render` for them. Slots are rendered per project, unless the section has `scope: "app"`. The client insets a `<section>.main` tree from the top edge, unless its root is a `surface`.

A manifest section may declare extra slots with `slots`: names matching `^[a-z][a-z0-9-]{0,31}$`, unique, and not `sidebar`, `main` or `status` (otherwise manifest load fails). `{"id": "alpha", "slots": ["extra"]}` adds the slot `alpha.extra`. Extra slots belong to the section like its own (owner, scope, `ui.event` routing); views cannot claim them, and the client decides where to show them. `ui.render` and `ui.event` on an undeclared `<section>.<name>` fail with invalid params. `ui.sections` lists them as `slots` (omitted when empty).

### Hosted sections

A manifest section may set `host` to another section's id; `ui.sections` returns it (omitted when empty). A `host` equal to the section's own id fails manifest load; a host that is not registered, is itself hosted or has another scope is dropped by the core, and the section stays a normal one. A hosted section has no rail icon, ⌘ number or palette "Go to …" entry, and the client shows none of its slots. Selecting it (a saved `section` in the UI state, `ui.focus` to it or any of its slots) selects the host. No bundled plugin sets `host`.

### Scope

A manifest section has `scope`: `"project"` (default) or `"app"`; any other value fails manifest load. `ui.sections` returns it. Slots of an app-scope section are not tied to a project and are rendered, read, subscribed and sent events with `projectId: ""`:

- `ui.get` and `ui.subscribe` with `""` cover only app-scope slots; with a project id, only project-scope slots.
- `ui.render` and `ui.event` with `""` on a project-scope slot, or with a project id on an app-scope slot, fail with invalid params.
- `ui.subscribe` with `""` does not count toward presence and publishes no `ui.opened`/`ui.idle`.
- App-scope slots of a stopped or crashed plugin are cleared like project slots (the `empty` view is delivered to live subscribers).

### Auto new

A manifest section may set `autoNew: true` (default `false`); `ui.sections` returns it. When the user selects such a section and its main slot, once rendered, is an `empty` node (the section has nothing to show, e.g. no terminals; an exited terminal's view is not `empty`), the client runs the section's `<section>.new` command once for that selection (`CommandInvocation.shouldAutoNew`). Terminals sets it, so a terminal appears on entering the section.

The `.status` slot is a compact status line for the section; clients show it in the status area while the section is active.

### Views

A plugin may claim a slot of another plugin's section with `contributes.views`:

```json
{"contributes": {"views": [{"slot": "alpha.sidebar"}]}}
```

The claiming plugin becomes the owner of that slot instead of the section owner: only it may `ui.render` the slot and `ui.event` for it is routed to it. Slot syntax is validated at manifest load. A view on a section that no plugin registers is ignored and logged. When two plugins claim one slot, the later manifest in discovery order loses its claim and the conflict is logged.

The agents plugin claims `editor-nvim.sidebar` for its chat panel: an agent session of the workspace's current worktree (the one picked there or with New, else the newest open one) with the same transcript and composer as the Agents section. The client shows that slot not as a tree sidebar but as a resizable panel on the right edge of Code, at most half the window wide; ⌘B and ⌃⌘S toggle it, and its visibility and width are kept per window. `ui.focus` to `editor-nvim.sidebar` opens the panel and focuses its composer.

## Revisions

Every slot (per project) has a revision counter that starts at 1 and increases by 1 on each render. When a plugin stops or crashes, its slots are cleared: the counter increments and the tree becomes `empty` with empty text. The cleared slot is removed from the store: the `empty` view (rev + 1) is delivered only to live subscribers, and later `ui.get` or subscribe replays omit the slot. Clients render that view like any other update (an empty pane) and do not get the slot back from `ui.get` after a reconnect.

`project.delete` clears every slot of the deleted project the same way (the `empty` view at rev + 1 to live subscribers; `ui.get` for that project then returns `[]`). Before deleting, the core kills the project's session processes (groups registered with `process.register` whose root is still running are left to their owner plugin, which handles `project.deleted`; leftovers of an ended registered group are killed with the sessions; once a group left running ends, the core kills whatever it left behind on the next process scan), waits for each of its sessions to stop and removes them, publishing `session.removed` `{id}` for each; then it deletes the project and publishes `project.deleted` `{id}`. If a session does not stop within the kill grace, the delete fails and the project is kept. Clients take a workspace out of its window when its project disappears from `project.list` after having been listed.

Revisions are in-memory and reset when the core restarts; clients must reset their rev map on reconnect.

Clients keep the highest `rev` per `(projectId, slot)` and ignore views with a lower or equal `rev`.

`SlotView` is `{projectId, slot, owner, rev, tree}`.

A command with `"hidden": true` in its manifest entry is still listed and runnable; clients leave it out of the command palette.

A command with a non-empty `"confirm"` string in its manifest entry is listed with that text (`""` when absent); the client asks for confirmation with it before running the command.

A manifest command entry may also declare, all optional and listed as declared:
- `description` (`""` when absent): what the command does, for agents and `command describe`;
- `args` and `result`: schemas for the command's args and its result (absent: any args, nothing declared);
- `agent` (default `false`): the command is meant for agents;
- `remote` (default `false`): paired companion devices may run it through the `remote` plugin (see [remote](remote.md));
- `scope` (`project`, the default, or `app`): an `app` command needs no workspace, so `command.run` skips the `projectId` check and passes whatever `projectId` it got (possibly `""`);
- `destructive` (default `false`): the command destroys state (closes, kills, discards);
- `provides`: generic capability names the command implements;
- `timeout` (1 to 600 seconds; listed only when set): how long the core waits for the plugin's `command.run` reply, instead of the 5 s every other plugin call gets (`routeTimeout`). For commands that block on purpose, such as `agents.wait`. Callers apply no shorter limit: `clubmate mcp`, `clubmate command run` and `clubmate agent` set no timeout on `command.run`.

A schema is a small JSON Schema subset: an object `{properties: {name: prop}, required: [name]}`, where a prop is `{type, items, enum, description, default}`, `type` is `string`, `integer`, `number`, `boolean` or `array`, and an `array` has scalar `items` or object `items`. Object items go one level deep: `{type: "object", properties, required}` whose properties are scalars or arrays of scalars (no further object items), and a value is validated item by item, so a bad field names its path (`args.items[0].line: want integer`). Only an `array` has `items`, only object items have `properties` and `required`, and only a scalar has `enum`; `enum` values and `default` must match the type (a `default` also the `enum`), and every `required` name must be a property; anything else fails manifest load. `default` is documentation only: the plugin applies it, the core never fills it in.

`command.run` validates `args` against the command's `args` schema before routing, so the plugin is never called with bad args. Absent or `null` args count as `{}`; properties not in the schema are allowed; a `null` property counts as absent. Errors are invalid params naming the field: `args: want object`, `args.path: required`, `args.line: want integer`, `args.side: want one of ["left","right"]`, `args.paths[1]: want string`. `integer` rejects fractions and exponents. A command without an `args` schema accepts any args.

`session.send` types `text` into a running session (a data frame on the session host's socket, chunked under the frame limit); with `enter: true` it sends `\r` as a separate frame 50 ms later, so a TUI sees a keypress rather than a paste. It then half-closes its connection and drains what the host sends until the host closes (2 s at most), so every input frame is consumed even when the host is still replaying a large ring to the new connection. `session.read` returns the last `bytes` (default 16384, 0 means default, more than 262144 is invalid params) of the session's output ring, cut from the raw bytes before processing. Without `raw` it renders the text the way a terminal shows each line: it drops OSC, DCS, SOS, PM and APC strings (up to BEL or `ESC \\`) and other escape sequences, but keeps a cursor on the current line: `\r` returns to column 0, `\b` and `CSI n D` move left, `CSI n C` moves right, `CSI n G` sets the column, `CSI K` (0, 1, 2) erases, and printable characters overwrite at the cursor (so a redraw by a line editor or zsh-syntax-highlighting reads back as the final line, and output ending in `50%\r` reads `50%`). Cursor moves stop at column 512 (an overflowing parameter counts as the maximum), lines are capped at 4096 characters, the rendered text is cut to its last `bytes` bytes, trailing spaces are trimmed, a control character right after `ESC` is kept, other control characters except tab and newline are dropped, and invalid UTF-8 is dropped (e.g. a character split by the cut); `raw: true` returns the tail as is. When the session's app is on the alternate screen it returns `altScreen: true` and no text. Both fail with not found (`-32004`) for a session that is not running. The core reads the ring with a new host frame: the client sends an empty `snapshot` frame (type 4), the host stops streaming to it and answers with one `snapshot` frame whose payload is `[1]` on the alternate screen, else `[0]` followed by the ring; data frames already queued may arrive first. The session protocol version is unchanged: hosts started by an older core ignore the frame, and `session.read` fails after 2 s with not found (`-32004`) `session host cannot be read; restart the session`.

Sessions get `PATH` with the core's own directory first (`Contents/Resources/bin` in the app, `bin/` in dev), so `clubmate` works in clubmate terminals. The core prepends it only when that directory has an executable `clubmate`, and not when it is already first. A login shell may reorder `PATH`: macOS `/etc/zprofile` runs `path_helper`, which puts the system directories first, so a `clubmate` installed in a system directory (e.g. a release symlink in `/usr/local/bin`) wins over the bundled one.

CLI over the registry:
- `clubmate command list [--agent]` (`--agent`: only agent commands), `clubmate command describe <id|capability>` (description, flags, `provides`, args and result schemas).
- `clubmate command run <id|capability> [key=value …] [--args JSON] [--project ID] [--agent]`: `--project` defaults to `$CLUBMATE_PROJECT_ID`; `key=value` pairs are coerced by the resolved command's schema (integer, number, boolean, string, array as comma-separated values) and an unknown key (or any key, for a command without an args schema) fails before calling the core, naming the key; pairs and `--args` are exclusive. The CLI never turns on `--agent` by itself, not even inside a clubmate session.
- `clubmate open <file>[:line]` runs `editor.open` with `{path (absolute, from the CLI's cwd), line}`; a trailing `:line` or `:line:column` is parsed (the column is dropped; line 0 means no line), and anything else stays part of the path (`a:b.go:3` is `a:b.go` line 3).
- `clubmate plugin list` and `clubmate plugin restart <id>` call `plugin.list` / `plugin.restart`.
- `clubmate session send <id> <text> [--enter]` and `clubmate session read <id> [--bytes N] [--raw]` run `session.send` / `session.read` through `command.run` (not as agent calls).
- `clubmate agent spawn [prompt] [--branch B] [--title T]`, `tell <session> <text>`, `wait <session>… [--timeout N]`, `output <session> [--from-turn N]`, `sessions`, `cancel <session>`, `blame <file|commit> [-L a,b]` run `agents.new` / `agents.prompt` / `agents.wait` / `agents.transcript` / `agents.sessions` / `agents.cancel` / `agents.blame` through `command.run`, always as agent calls with `caller` = `$CLUBMATE_AGENT_SESSION`; `--project` as for `command run`.
- `clubmate mcp` is a stdio MCP server (newline-delimited JSON-RPC 2.0, protocol `2025-06-18`; `initialize`, `ping`, `tools/list`, `tools/call`; other requests get `-32601`, notifications get no reply; stdout carries only protocol messages). Tools are the agent commands (core primitives included), named by id with `.` and `-` turned into `_`; a command that provides a capability is listed under the capability name instead. `inputSchema` is `{type: "object"}` with the command's args plus an optional `workspace`; annotations carry `destructiveHint` (the command's flag) and `readOnlyHint` (`workspace.list`, `session.list`, `session.read`, `process.tree`, `terminals.busy`). `tools/call` runs `command.run` with `agent: true` and `projectId` = `workspace`, else `$CLUBMATE_PROJECT_ID`, else the most recently opened workspace; the result is one text item with the JSON result, and failures (including approval refusals) are `isError: true` with the message. It never starts the core: without one, `tools/list` lists the core primitives and every call fails with `Clubmate isn't running`. There are no plugin-change events (manifests are read once per core start), so it re-checks the tool list every 5 s and sends `notifications/tools/list_changed` when it differs from the last list it served. See `docs/agents.md`.

`process.tree`'s `args` is the full argv (`[]` when it can't be read, e.g. for another user's process) and `startTime` is RFC 3339.

`process.register` makes a process the plugin started a root of its own group in `process.tree`, like a session: the root and its descendants get `sessionId` = the returned `id` (`prc_…`), and `sessionId` in `process.tree` and `process.kill` accepts that id. `owner` is the calling plugin. The pid must be a descendant of the plugin process (by parent chain), else invalid params; `label` is trimmed and 1..200 characters, and `projectId` must exist. Registering the same live process again keeps its `id`, `owner` and owning process and updates `projectId` and `label`; another plugin process registering it is refused. While a registration is active its processes are never orphans (`orphan: false`): their owner reaps them. It ends (`ended: true`) with `process.unregister` (by pid, the caller's own registrations only; another plugin's call does nothing), when the plugin's connection closes (later registers from that connection fail), or when the root process is gone: a root registered before a `process.tree` snapshot started that the snapshot misses is checked again by its start time, and only a dead or reused pid ends it, so a slow snapshot never drops a fresh registration; `process.roots` runs the same start-time check. An ended registration stays, labelled `<label> (exited)` once its root is gone, while any tracked process still carries its `id`: those leftovers stay in their project, are orphans when reparented to launchd, and `orphansOnly` kills (and the Processes section's auto-kill) reach them. It disappears from `process.roots` once no process carries it. The agents plugin registers each agent process it starts (`Claude · <worktree folder>`, in the background, best effort), and the Processes section lists registered groups next to sessions.

`process.kill` with `orphansOnly` kills only orphaned processes and needs `sessionId` or `projectId` (otherwise invalid params). With `projectId`, only that project's orphans are killed; with `sessionId`, only that session's. Without `orphansOnly`, `pids` must be tracked processes. Each target is signalled only if its start time still matches the tracked one, so a reused pid is skipped.

`project.open` fails with not found for an unknown project; otherwise it sends the `project.open` notification to every connection that registered `"project.open"` via `client.register`, except the caller, and returns how many were notified (`clients`). `clubmate workspace open --id <id>` calls it and, when `clients` is 0, runs `open -b com.clubmate.app --args --open-project <id>`.

Projects are shown to users as workspaces; `clubmate project …` is an alias of `clubmate workspace …`. A project is `{id, name, repos, roots, missing?, createdAt, home, lastOpenedAt}`; `lastOpenedAt` is `null` until the first `workspace.touch`; subscribing to a project's UI does not set it. `repos` are the workspace's folders. `roots` lists, in the same order, each folder's effective path: the directory selected for it with `workspace.worktree.set` (usually a git worktree of the folder), else the folder itself. A selection whose directory no longer exists falls back to the folder and is listed in `missing` (omitted when empty); it stays stored. Sessions created without `cwd` start in `roots[0]`. Clients that predate `roots` treat a missing one as `repos`. `project.list` orders by `lastOpenedAt` then `createdAt`, newest first.

`workspace.open` resolves each folder path (symlinks resolved, cleaned), drops duplicates and returns the project whose repos are exactly that set (order-insensitive, stored repos resolved the same way) with `created: false`; otherwise it creates a project with the resolved folders, named after the base name of the first one (`project.created`), with `created: true`. Folders must be absolute paths to existing directories (otherwise invalid params, as is an empty `folders`). `workspace.home` returns the single `home: true` project, named `~` and rooted at the user's home directory, creating it (`project.created`) on first use. Both then send the `project.open` notification exactly like `project.open` (not to the caller) and return how many were notified (`clients`); `clubmate workspace open <dir>…` and `clubmate workspace home` run the app like `open --id` when `clients` is 0. `workspace.touch` sets `lastOpenedAt` to now (not found for an unknown project); clients call it when they activate a workspace. `project.rename` fails with invalid params on a blank name and publishes `project.updated`.

`workspace.worktree.set` `{id, repo, path}` selects the directory a workspace folder points at. `repo` must equal an entry of `repos` exactly (otherwise invalid params `repo is not a folder of this workspace`). An empty `path`, or one equal to `repo`, clears the selection; any other `path` must be an absolute path to an existing directory (otherwise invalid params `path is not a directory`). It stores the selection, publishes `project.updated` with the full project and returns the project. Selections are deleted with the workspace and with the folder. Plugins call it as `pluginsdk.Host.SetWorktree`. It is not an agent command (an agent `command.run` of it fails with not found): it accepts any existing directory, so agents switch worktrees through a plugin command that validates the target instead.

`workspace.worktree.check` `{id}` re-reads the project and, when `missing` is not empty, publishes `project.updated` with it; it changes nothing and returns the project. The git plugin calls it (`pluginsdk.Host.CheckWorktrees`) when a refresh finds a `missing` list it has not reported yet, so a worktree removed outside Clubmate moves every plugin and the app back to the folder without waiting for another event; the app then shows the one-time banner and clears the selection by switching the folder to its own checkout.

`client.register` marks the calling connection for the listed handles: `"project.open"` and `"ui.confirm"`; anything else is invalid params. The app registers both. Registration lasts for the connection. Plugin callers get invalid params.

`ui.focus` is open to any caller. It is invalid params when the project does not exist, the section is not registered or is app-scope, or `slot` is not `""`, `<section>.sidebar` or `<section>.main`, or `field` is true with a `slot` other than `<section>.sidebar`. It sends the `ui.focus` notification to every `ui.subscribe` subscription of that project (app-scope subscriptions never receive it) and returns their count as `delivered`. Plugins call it as `Host.Focus`, or as `Host.FocusField` to focus the sidebar's text field.

`ui.render` is invalid params for a project that has been deleted.

`ui.approve` shows the app's approval dialog for a plugin's own action and waits up to 60 s. `command` must start with `<plugin id>.`, `title` is 1 to 200 characters, `args` is at most 10 string fields of at most 200 characters each, shown as detail lines; `body` is optional text of at most 65536 characters (`approvalMaxBody`) shown in full in a scrollable monospaced box, e.g. a script. A body line starting with `──── ` (four U+2500 and a space) is drawn as a bold, highlighted header and every other line is plain, with wrapped lines indented, so no other line can pass for a header; a plugin that puts untrusted text in `body` escapes U+2500 in it. The core forwards it as `ui.confirm` with `plugin: true` and the `body`, and the dialog asks "<title>?" instead of "Allow agent to <title>?", since the core can't tell whether a person or an agent started the plugin's action. Denial, timeout, a busy dialog or no running app fail with the same denied errors as approvals of agent commands.

`command.run` routes a plugin command with `via` set to the calling connection's plugin id (`""` for the app and the CLI); the core overwrites any `via` the caller sent, so a plugin can trust it.

`command.run` resolves `id` to a command: a listed command id wins; otherwise `id` is taken as a capability name (see below). It fails with unknown command when neither matches; it is routed to the plugin that registered the resolved command, which receives the resolved command id (not the capability name) in `id`.

A capability is a generic name a command declares in `provides`, so callers need not know which plugin implements it. A capability resolves to the first provider in plugin load (discovery) order whose plugin is running, else to the first provider (then `command.run` fails with plugin unavailable). When several commands provide one capability the core logs `capability X provided by A and B; using A` (command ids) once per distinct outcome. `command.capabilities` returns that resolution for every declared capability. Bundled capabilities: `editor.open` (`editor-nvim.open`), `editor.quickfix` (`editor-nvim.quickfix`), `editor.reveal` (`editor-nvim.reveal`), `terminal.new` (`terminals.new`) and `terminal.close` (`terminals.close`).

`command.list` also lists the core primitives, with `plugin: "core"`, `agent: true` (except `workspace.worktree.set` and `diagnostics.collect`, which are `agent: false`) and `hidden: true` (so the palette leaves them out). `command.run` resolves a primitive id before plugin commands and capabilities, and runs it with the existing method's handler. Plugin ids `core`, `session`, `workspace`, `process`, `ui` and `diagnostics` are reserved (manifest load fails), and `command.capabilities` maps a capability named like a primitive to that primitive, as `command.run` does:

|---|---|---|---|
| `workspace.list` | `project.list` | none | ignored |
| `workspace.open` | `workspace.open` | `{folders}` | ignored |
| `workspace.home` | `workspace.home` | none | ignored |
| `workspace.worktree.set` (not for agents) | `workspace.worktree.set` | `{id, repo, path}` | ignored |
| `diagnostics.collect` (not for agents) | `diagnostics.collect` | `{appVersion?, extra?}` | optional, the workspace whose UI is dumped |

Plugin commands keep requiring a valid `projectId`. An agent `session.send` always needs approval, also into the agent's own session. Approval shows the full `text`, so the 200-character limit applies: agents send long input in chunks. An agent call accepts only the keys the resolved command's args schema declares, matched exactly (primitives and plugin commands alike; a plugin command without a schema accepts any args unless it is destructive) (so `command`, `env` or a case variant like `Command` is invalid params: `args.Command: not allowed in agent calls`); keys inside object items are matched exactly too (`args.items[1].PATH: not allowed in agent calls`); the core rebuilds the args from those keys and dispatches that object.

An agent call is `command.run` with `agent: true` (the CLI's `command run --agent`; the MCP server always sets it). It resolves only core primitives and commands with `agent: true` (judged on the resolved command, never on the capability name); anything else fails with not found, as if unknown. Args are validated first. Then a `destructive` command needs the user's approval, and what the user approves is exactly what runs, so its args must be approvable or the call fails with invalid params before anyone is asked: an object (absent or `null` counts as `{}`); no args at all when the command declares no `args` schema; only keys its schema declares (`args.<key>: not declared`); at most 10 fields; each value at most 200 characters (a string's characters, otherwise its compact JSON); no number beyond ±2^53, anywhere in a value (`args.<key>: number outside ±2^53`), so the app shows it exactly. These limits live in the core (`approvalMaxFields`, `approvalMaxValue`, `approvalMaxInt`); the app checks the field and length limits itself and never truncates args. The core then sends the request `ui.confirm` `{title, workspace, command, args, timeoutMs, session?}` (`ui.approve` adds `body?` and `plugin`) (`title` is the command's title, `workspace` the affected workspace's name or `""`, `command` the resolved id, `args` the args exactly as they will run, or `{}`; once approved, exactly these bytes are dispatched; `timeoutMs` is 60000; `session` is `{id, title, workspace}` of the targeted session, when the args name one: `id` for `session.send`/`session.kill`, `sessionId` for plugin commands such as `terminals.close`) to one connection that registered `"ui.confirm"`: one that has a `ui.subscribe` subscription for the affected workspace if any, else the earliest connected. It waits up to 60 s for `{approved}`. The call fails with `-32014` (denied) and one of these messages, and the command does not run:
- `no app to approve`: no connection registered `"ui.confirm"`, or the request failed;
- `denied by user`: the answer was `approved: false` (when the answer carries a `reason`, that is the message instead);
- `approval timed out`: no answer within 60 s, or the app's own answer that it timed out;
- `approval busy`: that connection already has an approval pending (one per connection; the second is denied, not queued).

An approval outlives a dropped caller: if the caller disconnects while the alert is up, the request stays pending until it is answered or times out, and an approved command still runs. Non-agent calls (the app, plugins, the CLI without `--agent`) are unchanged: any listed command runs without approval. Agent mode is a cooperative guard, not a security boundary: any same-uid process can reach the core socket directly (and call without `agent`, or register `ui.confirm` itself).

The app answers `ui.confirm` with an alert "Allow agent to <title>?" whose text lists the workspace, the command, the targeted session (title, id and workspace) and each argument (shown in full; scalars of general category control, format, line separator or paragraph separator escaped as `\n`, `\r`, `\t` or `\u{…}`, so a value cannot fake extra lines or reorder text; the title, workspace and command are escaped the same way and cut at 200 characters with `…`). The alert has Allow and Deny (Deny is the default and holds focus; Allow never takes keyboard focus, so a space typed into the terminal as the alert appears can't approve; Esc denies). A `body` is shown below that text, long lines wrapped, with line breaks and tabs kept and every other such scalar escaped the same way; the box can't take focus, so it scrolls with the mouse or trackpad. If the args exceed the app's own limits (more than 10 fields, a value over 200 characters, or a body over 65536 characters) it shows no alert and answers `{approved: false, reason: "args too long to display"}`, so the alert never shows less than what runs. The alert closes itself 5 s before `timeoutMs` and the app answers `{approved: false, reason: "approval timed out"}`. It is a sheet on the key workspace window (else the first workspace window, else a modal alert) and asks for attention (dock bounce) until it closes.

editor-nvim keeps one nvim per project root, an entry of the project's `roots` (each folder's selected worktree, so every folder and every worktree of it has its own), else `$HOME`. Each runs in its root with its own socket (`<runtime>/<projectId>-<8 hex of sha256(root)>.sock`); a running session belongs to a root when its cwd is that root and it listens on that socket (or on the pre-worktree `<runtime>/<projectId>.sock`). The main and status slots show the nvim of the current root. The status slot's git branch is the one of the current buffer's repo (else the root's), read on `BufEnter`/`DirChanged` and again whenever the project's `fs.watch` reports a `HEAD` change (an in-place `git switch` in a checkout or a linked worktree) or an overflow. The current root starts as the first entry of `roots` that exists and stays until a path is routed to another folder (below) or exactly one folder's root changes (`project.updated` after a worktree switch of that folder), which makes that folder's root current; when the current root no longer exists or is no longer in `roots`, the first existing one is current again. When the current root changes, editor-nvim starts that root's nvim if needed and shows its surface, and the other nvims keep running. `editor-nvim.open` (absolute path), `quickfix` (first item's path) and `diffview` (`cwd`) first look, for each project folder, at that folder's own `git worktree list` (run in the folder's repo, never in the target path's repo): the worktree owning the path is the longest listed root containing it, compared with symlinks resolved. When the folder maps into that worktree (a folder at `<toplevel>/<rel>` maps to `<worktree>/<rel>`) and its current root differs, they call `workspace.worktree.set` for that folder with the worktree path as git prints it joined with `<rel>` (empty when it maps back to the folder itself), focus the editor and act on the new root's nvim. A path inside a folder that is already on the owning worktree, or inside a non-git folder's root (the longest such root), acts on that folder's nvim and makes it current; any other path acts on the current root's nvim.

`editor-nvim.restart` takes optional args `{force}` and restarts every running nvim of the project (and the current root's one if it is not running). Without `force: true` it first asks each of them for modified listed file buffers (`buftype` empty, `buflisted`; scratch buffers do not count) and fails with `unsaved buffers: <names>` (all of them, relative to the project repos and roots, `[No Name]` for unnamed buffers) if there are any; the sessions are left running. If an nvim does not answer within the RPC deadline it fails with `unsaved buffers: unknown (nvim not responding)`. If the session cannot be started its main slot shows the error and a Restart button, which restarts only the current root's nvim. `editor-nvim.stop-root` (hidden, not agent-visible) takes args `{root, force}` (`root` absolute): it stops the nvim of that root with the same unsaved check and errors, and is a no-op when there is none. After it succeeds (even as a no-op), no nvim starts in that root (opening a file there fails with `the worktree is being removed`) until `editor-nvim.release-root {root}` (hidden, not agent-visible), which starts it again when the root is still the project's current root. `editor-nvim.unsaved {root}` (hidden, not agent-visible) returns the names of the modified file buffers of every running nvim of the project whose files are inside the root, except files another nvim holds inside its own root (a worktree nested in the root, such as `.worktrees/<branch>`) (same names and `unknown` error as restart), `[]` when there are none; it never starts or stops nvim.

`editor-nvim.selection` (hidden, not agent-visible) takes no args and returns `{path, startLine, endLine, text}` for the current visual selection, else the last one (`'<` / `'>`), of the current root's running Neovim; `text` joins the selected lines with `\n`. It fails with `no selection` when there is none or Neovim is not running. `editor-nvim.checktime {root}` (hidden, not agent-visible; `root` absolute, else an error) runs `:checktime` in every running Neovim of the project, so unmodified buffers changed on disk under that root reload whichever folder's Neovim holds them; it is a no-op when none runs.

`editor-nvim.diffview {cwd, rev}` (hidden, not agent-visible) takes an absolute worktree root `cwd` and a commit sha `rev` (7 to 40 lowercase hex digits; anything else is an error), routes to that worktree's nvim like `editor-nvim.open`, runs `DiffviewOpen -C<cwd> <rev> --untracked-scoped` there and focuses the Code section, so the working tree (uncommitted and untracked files included) is compared with `rev`. Clubmate never installs or configures diffview; when `DiffviewOpen` fails (for example without diffview.nvim) nvim's error shows as the "open failed" badge. The agents' "Review changes" and tool-card "Diff" call it with the session's worktree and a turn's checkpoint sha.

`terminals.busy` (hidden) takes args `{sessionId}` and returns `{busy, process}`. `busy` is true when the session's process tree (`process.tree`) has a live descendant of the shell (the session's `childPid`); `process` is the `comm` of the newest such descendant (latest start time), `""` when not busy. An unknown or exited session is not busy. The app's ⌘W "Close Terminal" closes the Terminals section's selected terminal (the `selected` of the `terminals` list in `terminals.sidebar`): it always runs `terminals.busy` first and, when busy, asks `“<process>” is running. Close the terminal?` before `terminals.close`; an exited one is not busy, so it closes without asking. In a project window outside the Terminals section ⌘W does nothing and never closes the window (the red button does); in a window without a workspace (the welcome screen, Settings) it is "Close Window" and closes it. ghostty's `super+w` is unbound inside clubmate, so ⌘W reaching a surface does nothing. The item sits after "Close Session" in the File menu; SwiftUI keeps the system "Close" item (`performClose:`) and may hand ⌘W back to it when it rebuilds the menu, so the app moves ⌘W from it to its own item whenever the menu changes (the system item stays, without a shortcut).

The `cron` plugin renders `cron.sidebar` and `cron.main` for every workspace, again after every job change, every recorded run (scheduled or `cron.run`) and every owner or workspace cleanup. `cron.sidebar` is `empty` (`No cron jobs. Agents create them with cron.add.`) without jobs, else the `list` `jobs`, sorted by name: label the job name, detail `<schedule> · next <HH:MM>` (`Jan 2 15:04` when not today, in the job's timezone) or `paused · <last error>` (`paused` without one), icon `clock` or `pause.circle`, badge `failed` when the run with the latest `at` is an `error`, and a menu of `pause` or `resume`, `run` and `delete` (confirm `Delete cron job “<name>”?`). Events on `cron.sidebar` carry the job id as value and are the user's actions, so they skip the agent ownership check: `select` stores the selection under `selected/<workspace>` (a missing one falls back to the first job), `pause`/`resume`/`delete` act at once and `run` starts the run in the background (the history shows it when it ends). `cron.main` is `empty` (`Select a cron job`) without a selection, else a `stack` of the name, the command with its args (muted), schedule, next run or paused state, missed policy and owner (the session's title from `agents.sessions`, else its id, else `none`; a listed owner gets a `button` `<job id>/owner` "Show Session" with action `reveal`, which calls `agents.reveal`), then `No runs yet` or a `scroll` around the `table` `history` (columns `When`, `Status` and `Reason / Result`, the reason of a skip or error else the result; newest `at` first). See [cron](cron.md).

The `triggers` plugin renders `triggers.sidebar` and `triggers.main` for every workspace, again after every trigger change, every recorded run and every owner or workspace cleanup. `triggers.sidebar` is `empty` (`No triggers. Agents create them with triggers.add.`) without triggers, else the `list` `triggers`, sorted by name: label the trigger name, detail `on <topic> <match JSON>` or `paused · <last error>` (`paused` without one), icon `bolt` or `pause.circle`, badge `failed` when the run with the latest `at` is an `error`, and a menu of `pause` or `resume` and `delete` (confirm `Delete trigger “<name>”?`). Events on `triggers.sidebar` carry the trigger id as value and are the user's actions, so they skip the agent ownership check: `select` stores the selection under `selected/<workspace>` (a missing one falls back to the first trigger), `pause`/`resume`/`delete` act at once. `triggers.main` is `empty` (`Select a trigger`) without a selection, else a `stack` of the name, `On: <topic> <match>`, the command with its args (muted), `Active` or the paused state and owner (the session's title from `agents.sessions`, else its id, else `none`), then `No runs yet` or a `scroll` around the `table` `history` (columns `When`, `Event`, `Status` and `Reason / Result`; newest `at` first). See [triggers](triggers.md).

The `search` plugin has one hidden, non-agent command, which the app's file picker (the agents composer's attach list) calls through `command.run`; results are never published. `search.files {query, limit?=50 (max 200)}` ranks workspace-relative paths (prefixed with the folder name when the workspace has several folders; a file reachable through two folders, such as a worktree opened next to its repo, is listed once, under the first folder in order) from a per-workspace index of `git ls-files --cached --others --exclude-standard` (or a bounded walk outside git) capped at 200 000 paths, rebuilt in the background after `fs.changed`; it returns `{matches: [{path, absPath, positions, line?}], truncated, capped, indexing?}`, where `positions` are rune (Unicode scalar) indexes into `path`, a query ending in `:N` puts `line: N` on every match, and `indexing: true` (empty matches) means the first index is still building: retry. It refuses the home workspace with `search unavailable in the home workspace`. Walks never enter `~/Library` or another direct child of `~` when they start at `~` or above it; a workspace folder of `/` or a firmlink root such as `/System/Volumes/Data` is otherwise not guarded, since the user opened it.

The `git` plugin manages the worktrees of each git workspace folder through hidden commands; `repo` (optional) is a workspace folder from `repos` and defaults to the first git folder. Worktrees always come from the folder's own `git worktree list`, compared with symlinks resolved, and map like editor-nvim's routing: a folder at `<checkout>/<rel>` maps to `<worktree as git prints it>/<rel>`, stored as empty when that is the folder itself. `git.worktrees {}` (agent) returns `[{repo, path, branch, head, main, current}]` for every git folder, main checkout first (`branch` empty when detached, `head` the short SHA). `git.worktree-switch {repo?, path}` (agent) accepts only a listed worktree root (else `not a worktree of <repo>`) and calls `workspace.worktree.set`. `git.worktree-new {repo?, branch, from?, switch?}` (agent) and `git.worktree-remove {repo?, path, force?}` (agent, destructive) validate synchronously and return `{id}`, then run in the background behind a per-workspace busy gate (`another git operation is running` while one runs); `git.worktree-op-status {id}` (agent) waits up to 1 s and returns `{done, error?, path?, notice?}`, `path` being the new worktree after a create. New: the branch must pass `git check-ref-format --branch` unchanged, `<main>/.worktrees` and every existing component under it must not be a symlink (`worktrees folder must not be a symlink`), and `<main>/.worktrees/<branch>` must not exist; it runs `git worktree add <dir> <branch>` for an existing branch, else `git worktree add -b <branch> <dir> <sha>` from the HEAD of the worktree `from` (a listed worktree root, else `not a worktree of <repo>`; ignored when the branch exists) or, without it, of the current worktree, adds `.worktrees/` to `info/exclude` when the repo does not ignore it, then switches unless `switch` is `false` (`path` is returned either way). Remove refuses the main checkout (`cannot remove the main checkout`) and the checkout holding the folder itself (`cannot remove the checkout of the workspace folder`) synchronously; in the background it refuses a dirty worktree (`worktree has uncommitted changes`), re-reads the project, runs `editor-nvim.stop-root {root, force}` (its `unsaved buffers: …` error is the operation's error), `agents.stop-root {root: <worktree>}` (best effort: closes the worktree's agent sessions, stops their processes and deletes their checkpoint refs), `git worktree remove <path>` (never `--force`, never deleting the branch) and, when the folder's stored selection then points at the removed worktree, `workspace.worktree.set` back to the folder; it always ends with `editor-nvim.release-root {root}`, so a failed `git worktree remove` brings the current worktree's nvim back. `git.worktree-switch` also fails with `another git operation is running` while one runs. In the home workspace `git.worktrees` returns `[]` and switch, new and remove fail with `worktrees unavailable in the home workspace`. `git.worktree-sessions {path}` (not agent-visible) returns `[{id, title}]` of the project's running sessions whose cwd is inside `path`, except editor-nvim's own. `git.branches {}` (not agent-visible) returns `[{repo, name, remote?}]` per git folder: local branches no worktree has checked out, then remote-tracking branches whose local name does not exist (the remote is the longest `git remote` name prefixing the ref, so remotes with `/` work), each newest commit first (one `git for-each-ref --sort=-committerdate`), at most 1500 local and 500 remote-tracking per folder. `git.branch-switch {repo?, branch}` (not agent-visible, destructive) validates the name (git's ref-name rules, then `check-ref-format --branch`) and that it is `refs/heads/<branch>` or `refs/remotes/<branch>`, returns `{id}` behind the same busy gate and runs in the folder's current worktree: a branch some worktree has checked out switches the folder to that worktree; else, after `editor-nvim.unsaved {root}` returned no buffers (it fails at once with `Save or discard unsaved changes first: <names>`; a missing editor-nvim is skipped), `git switch --no-guess -- <local>` (a remote `origin/x` with a local `x`), or `git switch --track -- origin/x`; git's own refusal (local changes, conflicts) is the operation's error. When git warns that commits were left behind a detached `HEAD`, that warning is the status's `notice` (the app shows it in the banner). After a switch it runs `editor-nvim.checktime {root}` for the folder's root.


`ui.event` requires a non-empty `action`, a valid slot and a registered section. It is routed to the owning plugin.

`diagnostics.collect` `{projectId?, appVersion?, extra?}` writes `clubmate-diagnostics-<YYYYMMDD-HHMMSS>.zip` (local time; `-2`, `-3`, … appended when that name exists) into `<state>/diagnostics/`, keeps only the newest 3 archives there, and returns `{path, files: [{name, bytes}]}` (`bytes` uncompressed). The zip holds `info.json` (`version`, `commit`, `flavor`, `sessionProtocol`, `macOS`, `arch`, `collectedAt` in UTC, `coreVersion`, `coreUptimeSeconds`, `appVersion` when given), `logs/core.log` and `logs/plugins/<id>.log` (the last 2 MiB of each, starting after the first newline when cut; missing logs are skipped), `plugins.json` (`plugin.list`), `workspaces.json` (`[{id, name, repos, roots, missing}]`), `sessions.json` (`[{id, workspace, title, owner, cwd, state, exitCode, created}]`, never output), `ui/<projectId>.json` (the `ui.get` views of `projectId`, or of every workspace in `ui.presence` when absent; none without UI) and `README.txt` listing them (with the line `window.png may show terminal and editor contents.` when it is there). `extra` maps file names to base64 contents added as they are; only `settings.json` and `window.png` are accepted, each at most 10 MiB (otherwise invalid params). It never includes terminal output, environment variables, plugin storage or the databases. Plugin callers get invalid params.

When a plugin enters or leaves the `running` state the core publishes `plugin.changed` `{id, running}`.

`plugin.restart` `{id}` asks the supervisor to restart one plugin and returns at once; poll `plugin.list` for the outcome. A running plugin is stopped the way the core stops plugins (`plugin.shutdown`, then SIGTERM, then SIGKILL of its process group) and spawned again right away; a plugin in backoff is spawned now; a failed plugin is supervised again. A requested restart is not a crash: `restarts` does not grow, the crash window and backoff start over and `lastError` is cleared. As on a crash, the plugin's bus subscriptions, process roots and rendered slots go with the old connection, so the new process renders and subscribes again from `plugin.initialize`; the manifest (sections, commands) is the one read at core start. An unknown id fails with not found (`-32004`). The Plugins tab in Settings has a Restart button per plugin.

`clubmate diagnostics [-o file.zip]` calls it without `extra` (60 s deadline) and copies the archive to `-o` (default `./<archive name>`), printing the path. When the call fails (no core, a dial error, the deadline, or an error reply) it neither starts the core nor reads any database: it writes the zip itself with `info.json` (the CLI's own build, `macOS`, `arch`, `collectedAt`, `"core": "unreachable"` and `coreError`), the same log tails and a README noting `core unreachable: no workspace/session/plugin/UI state`.

The app's Help ▸ Collect Diagnostics… first shows a sheet listing the files and `Terminal output, environment variables and plugin storage are not included.`, with an unchecked box "Include a screenshot of the window (may show terminal and editor contents)" and Cancel (default) / Save…. On Save… it passes its own settings (keys containing `token`, `secret`, `password` or `key`, case-insensitive, read `<redacted>`), the key window's workspace and its version, and `window.png` (its own drawing of the key window, never a Screen Recording prompt) only when the user opts in; then it asks where to save (default `~/Downloads`), moves the archive there and reveals it in Finder. Without a core connection it points to `cm diagnostics`.

## File watching

`fs.watch` starts one FSEvents stream over the project's repos and roots (the union, deduplicated) as they are at call time (repos added or worktrees selected later are not covered; call `fs.watch` again). It ends on `fs.unwatch` or when the connection closes. Repos that cannot be resolved (missing or deleted) are skipped and the rest are watched; a project with no resolvable repos gets a watch that never emits. When a repo is a linked git worktree (`.git` is a file with `gitdir: <path>`), the watch also covers that worktree's gitdir and the main repository's common dir (from `<gitdir>/commondir`), so commits, checkouts and ref updates made in the worktree emit paths under `<main>/.git/` (only `HEAD`, `index`, `refs/heads/**` and `worktrees/<name>/{HEAD,index}` are reported from inside `.git`). Roots are symlink-resolved, so paths are real paths (`/private/var/...`, not `/var/...`).

- `fs.changed` `{watch, projectId, paths, overflow}`: sent to the watching connection with a 200ms coalescing window. `paths` is deduplicated. Under any `.git/`, and under a linked worktree's gitdir and the main repository's common dir, only `HEAD`, `index`, `refs/heads/**` and `worktrees/<name>/{HEAD,index}` are reported. A window with more than 1000 paths, or one in which FSEvents reports dropped or coalesced events (MustScanSubDirs, KernelDropped, UserDropped), is sent as `overflow: true` with `paths: []`; the receiver rescans.

Plugins receive it as `Plugin.FSChanged`, and use `Host.WatchFS` / `Host.UnwatchFS`.

The `agents` plugin hosts ACP v1 agents (Claude through `@agentclientprotocol/claude-agent-acp`), one process per (agent, workspace, worktree root) in the effective root of the workspace's first git folder (the first folder when none is git; the other folders go as `additionalDirectories` when the agent supports them). The process env and the `clubmate` MCP server passed at `session/new` and `session/resume` carry `CLUBMATE_PROJECT_ID=<workspace id>`, so Clubmate tools (also a `clubmate` server registered in Claude Code, which inherits the env) act on the session's workspace. `session/new` and `session/resume` also send `_meta.claudeCode.options.env` `{CLUBMATE_AGENT_SESSION: <agt_ id>}` (claude-agent-acp merges it into Claude's env), so hooks such as `cm notify` know which agent session they run in; `CLUBMATE_SESSION_ID` is never set on the adapter (it marks terminal sessions for the process tracker). Each process group is recorded with its start time in the plugin state dir; when the plugin starts it stops (TERM, then KILL after 2 s) recorded groups that are still alive, started at the recorded time and whose leader runs `claude-agent-acp` (or `$CLUBMATE_AGENTS_COMMAND`), then clears the record. Unavailable in the home workspace (`Agents aren't available in the home workspace`). Its commands are hidden; the agent-visible ones are `agents.new`, `agents.prompt`, `agents.cancel`, `agents.permission`, `agents.sessions`, `agents.wait`, `agents.transcript`, `agents.blame`, `agents.trace`, `agents.export`, `agents.import` (none destructive) and `agents.answer` (destructive). The calling agent session is the `command.run` `caller` (set by `clubmate mcp` from `CLUBMATE_AGENT_SESSION`); it counts only when it is a session of the workspace:
- `agents.new {agent?: "claude", branch?, prompt?, title?}` → `{session, worktree}` at once; the agent starts in the background. With a caller the session is its child (`parentSession`), runs in the caller's worktree, is not selected in `agents.main` (sessions without a parent are), and fails with `a session may run at most 8 child sessions at once` while 8 children of the caller are `running` or `waiting` (also an agent prompt that would start a turn on another, idle child); without one it runs in the effective root of the first git folder and is selected. `branch` (must be a valid branch name) makes the worktree `<main checkout>/.worktrees/<branch>` (plus the folder's subpath) the session's, returned at once; in the background (one creation at a time) it runs `git.worktree-new {repo, branch, from: <the caller's (or that root's) worktree>, switch: false}` and polls `git.worktree-op-status`, and the agent starts (and the prompt is sent) only once it is done; a failure is the session's `error` (`create worktree <branch>: <git's error>`); the next attach (Retry, `agents.resume`, a new prompt) creates the worktree again. `title` sets the title; `prompt` is submitted as by `agents.prompt` from the caller. After `session/new` a child gets its parent's current mode and `select` config values (instead of the worktree's remembered ones, and without storing them), and the parent's advisor is copied into the child's record (`advisor`) at creation and sent at `session/new`/`session/resume`; choosing an advisor in the child's own picker replaces it in the child's record only (the worktree's remembered advisor is untouched). When the agent cannot start, the session gets status `error` with the reason (e.g. `Node 22+ is required to run Claude (found <v>)`). The first start installs the adapter with npm into the plugin state dir; an install counts only once npm succeeded (a marker file), otherwise the next start reinstalls from scratch. While it runs, sessions without a running agent show `Installing Claude adapter…` under the header; a failed install is an `error` with `retry`.
- `agents.prompt {session, text, attachments?: [{kind: "file", path} | {kind: "selection", path, startLine, endLine, text}]}` checkpoints the worktree (`refs/clubmate/cp/<session>/<turn>`, a commit whose parent is `HEAD` and whose tree is the worktree with untracked files, built through a temporary index seeded from a copy of the worktree's index; the real index is never written) and sends `session/prompt`; it returns once the turn started and fails with `the session is closed`. While a turn runs and the agent advertised `_meta.steering.supported` in its `initialize` response, the prompt goes to the running turn as `_session/steering {sessionId, prompt, _meta: {steering: {idleBehavior: "promptRequired"}}}` (no checkpoint, no policies); on outcome `injected` it is logged as `session/prompt` with `steered: true` in the running turn, and on `promptRequired` (no turn in flight on the agent's side), an error, or without steering support it is handled as below: queued while the turn runs, else sent as a new turn. Otherwise, while a turn runs the prompt is queued instead (in memory, not logged; closing or deleting the session drops the queue): when the turn ends without an error and was not cancelled, every queued prompt goes as the next turn, the texts joined in order with blank lines and the attachments concatenated. After a cancel or an error the queue stays until it is sent or removed (a prompt cancelled before it reached the agent goes back to the front of the queue); the next prompt sends the queue ahead of its own text. Files go as embedded resources when the agent supports them, else as resource links; selections as resources or a fenced text block. When a turn had an edit, delete or move tool call it ends with `editor-nvim.checktime {root}`. A prompt with a caller is logged with actor `agent:<caller id>` and `from: <caller id>` in the `session/prompt` payload, and its first text block goes to the agent prefixed with `[From Clubmate agent session "<caller title>" (<caller id>), not from the user]` and a blank line (the logged text has no prefix); an agent call (`agent: true`) without a caller is logged with actor `agent:unknown` (`from: "unknown"`) and prefixed with `[From another agent session, not from the user]` and a blank line; queued prompts are joined into one turn only while they share the same caller. The user's own prompts are logged with actor `user` (the agent's own events with `agent:<agent>`, e.g. `agent:claude`).
- Every turn ends its prompt with policy text blocks the transcript does not show. A top-level session gets its Finish text (`[Clubmate finish mode: ask]` or `[Clubmate finish mode: merge]`). A child gets `[Clubmate finish mode: child]` instead, whatever its Finish value: when it runs in its own linked worktree under `<main checkout>/.worktrees/` on a branch that is not the default base or `main`/`master`, and its parent is on a branch that is neither the default base (`origin/HEAD`, else `main`/`master`) nor `main`/`master`, it is told to run the tests, commit, and merge its branch into the parent's branch inside the parent's worktree (`git -C <parent worktree> merge --no-edit <branch>`, retried once after 5 s when another merge holds `index.lock`, never when that worktree has uncommitted changes; a conflicting merge is aborted with `git -C <parent worktree> merge --abort` and the conflicting files reported); otherwise (shared worktree, the child or its parent on the default branch or detached, parent gone) it is told to commit only. The composer has no Finish picker for a child. Both forbid merging into main and removing worktrees or branches. A session with at least one child also gets `[Clubmate orchestrator]`: write to the user only the children's questions that need the user, no echo of what was sent, no status recaps, answer children's permissions with `agents.permission`, pass the user's answers with `agents.answer`.
- When a child's turn ends `done` (no queued prompt, no pending permission, not `asks`), the plugin removes it if it is merged: it has its own worktree as above, its branch moved since the worktree was created (`fork` in the record, `HEAD` right after creation), `git merge-base --is-ancestor <branch> <parent branch>` holds, `git status --porcelain` is empty, `git.worktree-sessions` lists no terminal in it, no other open agent session runs inside it and the child has no open children of its own; the policies are computed within 10 s. It then closes the child (logged as `session/close` by `clubmate`, status `closed`; the child stays listed), runs `git.worktree-remove {repo, path}` (plugin-initiated, no approval; it calls `agents.stop-root` back), polls `git.worktree-op-status`, and deletes the branch with `git branch -d` in the parent's worktree. Failures are logged to stderr and as a `notice` entry (`Couldn't remove the merged worktree` with the error) in the child's transcript, and leave the child closed.
- `agents.answer {session, text}` (agent, destructive: the core asks the user first) sends `text` like `agents.prompt` with no caller: a user turn with actor `user` and no prefix.
- `agents.cancel {session}` sends `session/cancel` and answers every pending permission with `cancelled`; `agents.permission {session, request, option}` answers one (`request` is the permission entry's id, `option` one of its `optionId`s). Called by an agent, both work only for a caller whose descendant (child, grandchild, …; never the caller itself) the session is, else and without a caller it fails with `the session was not started by this agent` (an unknown session fails with `unknown agent session` first); `agents.permission` refuses calls without a caller even from outside an agent, except a non-agent call routed from the `remote` plugin (`via: "remote"`, a paired companion acting as the user), which may answer any pending permission. The app answers through the `permission` action instead.
- `agents.mode {session, mode}` sends `session/set_mode` (only advertised modes) and remembers the mode for new sessions in that worktree.
- `agents.config {session, id, value}` sends `session/set_config_option` for one of the agent's `select` config options (not the `mode` category, which `agents.mode` covers; only advertised values) and remembers the value for new sessions in that worktree, re-applied after `session/new` in the order the agent lists its options. `id: "advisor"` instead stores the Claude advisor model for the worktree (`fable`, `opus`, `sonnet`, or empty for the Claude Code default); it is passed as `_meta.claudeCode.options.settings.advisorModel` on the next `session/new` or `session/resume` and does not change a running session.
- `agents.stop-root {root}` (not agent-visible; `root` absolute) closes every session whose worktree is inside `root`, stops their processes (waiting up to 4 s) and deletes their checkpoint refs; `git.worktree-remove` calls it. `agents.close {session}` closes the session (`session/close` when supported); the process stops when no open session remains on it. `agents.delete {session}` (destructive, confirm) first closes the session, so it cannot start new children, then deletes every descendant session (each closed before its own children are collected, deleted children first, cancelling running turns; worktrees are untouched) and also calls `session/delete` when supported and removes the log and the checkpoint refs. `agents.reveal {session}` (not agent-visible) selects the session in `agents.sidebar` (expanding its ancestors), re-renders and focuses `agents.main`; Cron and Backlog call it for an owner or claimer. `agents.resume {session}` reattaches through `session/resume` (fails with `the agent cannot resume this session` otherwise).
- `agents.sessions` → `[{id, workspace, worktree, agent, agentSessionId, parentSession?, advisor?, fork?, title, status, mode, finish?, createdAt, updatedAt, closed, error?, pending?, asks}]` (stored in plugin storage under `session/<id>`; `pending` is not stored: the ids of the permission entries awaiting an answer, sorted; `asks` as in `agents.wait`, computed when the status is set and stored, so listing sessions never loads a transcript); `status` is `running`, `waiting` (a permission is pending), `done`, `idle`, `error` (with `error`, e.g. the agent's stderr tail) or `closed`.
- `agents.wait {sessions: [id], timeout?}` (`timeout` in seconds, default 120, at most 300; the manifest gives it a 310 s command timeout) waits for any of the listed sessions of the workspace (not only the caller's children) to stop `running`: it returns at once when one of them is not `running`, else on the first status change of any of them, else when any of them starts a new turn (its `turn` grows, e.g. queued prompts went out), else when the calling session has queued prompts from the user (not from agents), else when the timeout ends, and fails with `sessions is empty` or `unknown agent session: <id>`. It returns `{sessions, message?}`: `message` `{text, attachments?}` holds the caller's queued user prompts (texts joined with blank lines, attachments concatenated), taken off the queue so they are not sent again; `sessions` is, in the order given, `[{session, status, turn, stopReason?, error?, asks, permission?: {request, title, kind, options: [{optionId, name, kind}]}}]`: `turn` is the latest turn and `stopReason` its stop reason; `permission` is the oldest pending permission (`request` the permission entry's id for `agents.permission`, `title` and `kind` from its tool call). `asks` is true when the status is `done` and the session's last agent message ends with `?` once trailing whitespace, `*`, `_` and `` ` `` are trimmed: the agent is asking a question. It is computed when the status is set and stored in the record.
- `agents.transcript {session, fromTurn?}` → `{session, modes, configOptions, commands, turns: [{turn, checkpointSha, stopReason?, commits?}], entries: [{kind, id, turn, ...}]}` with entries upserted by `(kind, id)`: `user` (`text`, `content` blocks, `from` the sending agent session id or `unknown` when an agent sent it), `agent` / `thought` (`text`), `tool` (the merged ACP tool call fields under `tool`; unfinished calls of a cancelled turn get status `cancelled`), `plan` (one per turn), `permission` (`toolCall`, `options`, `outcome` once answered) and `notice`.

The section `agents` ("Agents", icon `sparkles`, order 25, after Terminals) renders two slots per workspace. Both are `empty` with `Agents aren't available in the home workspace` in the home workspace.
- `agents.blame {path | commit, cwd?, startLine?, endLine?}` → `{attributions: [{commit, startLine?, endLine?, session, turn, agent, title, prompt, checkpoint}]}`. At each turn end (before `agents.turn`), the commits reachable from the worktree's `HEAD` but not from the checkpoint's parent nor from any other local or remote branch get a git note in `refs/notes/clubmate` (`Clubmate-Session`, `-Turn`, `-Agent`, `-Title`, `-Prompt` (first line, 80 characters), `-Checkpoint` lines, committed as `Clubmate <clubmate@localhost>`), unless they already have one; the turn's log then gets a `commits {turn, commits}` event. `path` (absolute, or relative to `cwd`, which defaults to the calling agent session's worktree) runs `git blame --porcelain` and returns the ranges of consecutive lines whose commit has a note; `commit` resolves any revision in `cwd` and returns its note, or no attributions.
- `agents.trace {rev?, cwd?}` → `{records}`: one Agent Trace 0.1 record `{version, id, timestamp, vcs: {type: "git", revision}, tool: {name: "clubmate", version}, files: [{path, conversations: [{url?, contributor: {type}, ranges: [{start_line, end_line}]}]}]}` per non-merge commit of `rev` (a commit, default `HEAD`, or a range with `..`: `rev-list --reverse --no-merges --max-count=200`), resolved in `cwd` (default the calling agent session's worktree). Each turn also pins `refs/clubmate/cp/<session>/<turn>.end` when it ends, and both checkpoints get a `Clubmate-Worktree: <git toplevel>` trailer. For commit C with parent P (an empty tree for a root commit), the snapshots are the checkpoints whose parent is P and whose worktree is the one of C's note's checkpoint (else the cwd's, else the only one; old checkpoints without the trailer match by C's note's session), plus the note's checkpoint itself, ordered per session by turn and across sessions by commit time. Clubmate writes the throwaway chain P's tree → snapshots → C's tree with `commit-tree` (no refs) and runs `git blame --porcelain -L` over the new-side hunks of `git diff -U0 P C` on its tip: a line from the step into `<turn>.end` is `ai` with `url` `clubmate://session/<id>#turn=<n>`; the step into a start checkpoint is `human` when no turn is open, that turn when exactly one is open and has an end checkpoint, else `unknown`; the last step is C's noted turn, else as a start step (`unknown` when no snapshot matched). Lines blamed to P's tree are left out, and so are files without changed lines. `id` is a UUID from the SHA-1 of the commit; `timestamp` is the committer date.
- `agents.export {session, dir}` → `{dir}`: fails with `stop the session's running turn before exporting it` while it runs, `dir must be an absolute path`, or when `dir` exists; creates it with `session.json` (the record), `log.jsonl` (a copy of the log, flushed first) and, in a git worktree with checkpoints, `refs.bundle` (`git bundle create` of `refs/clubmate/cp/<session>/*` and, when the session's turns noted commits (`turns[].commits`), `refs/notes/clubmate-export`, a temporary notes ref holding only those commits' notes, with `--not --branches --remotes --tags`).
- `agents.import {dir, branch?, note?}` → `{session, imported, worktree}`: reads `session.json` (`not a Clubmate session bundle` when it has no valid id, or when `session.json` or `log.jsonl` is not a regular file, e.g. a symlink), fetches `refs.bundle` into the repository of the caller's worktree (else the workspace's work root): `refs/clubmate/cp/<old id>/*` not forced (an existing ref with another value fails the import), `refs/notes/clubmate-export` into a temporary ref (deleted afterwards) whose notes are added to `refs/notes/clubmate` only when their `Clubmate-Session` is the imported session, their `Clubmate-Checkpoint` one of its checkpoint refs, the commit exists and has no note yet (a fetch that lacks prerequisite commits fails the import). Then it starts a session as `agents.new {agent, branch, title}` would, adds a closed copy under a new id that keeps only the old record's agent, title and times (workspace and worktree of the new session, no agent session id, parent, advisor, mode or notify, `importedFrom: <old id>`, `handoffTo: <new id>`, the log copied; reopening it starts a fresh agent session), sets `handoffFrom: <copy id>` on the new session and sends it the handoff brief of the copy followed by `note`, as `agents.handoff` does. Called by the user (not an agent), it selects the new session.
- `agents.handoff {session, note?}` returns `{session}` and fails with `stop the session's running turn before handing it off` while the session is `running` or `waiting`, with `the session was already handed off` once it has a `handoffTo`, and like `agents.new` when the session's parent is closed or already runs 8 children; an agent caller gets `the session was not started by this agent` unless the session descends from it. It closes the old session alone (its children stay open; logged as `session/close` by `user`), so its agent process may stop and the new session starts its own, then creates a session with the old one's workspace, worktree, agent, `parentSession`, advisor, `fork` and title and `handoffFrom: <old id>`, and sets `handoffTo: <new id>` on the old record. When the old transcript has a user prompt, the new session's first prompt (from the caller, as with `agents.prompt`) is the brief: `[Clubmate handoff] You continue agent session "<title>" (<id>) in <worktree>; it is closed now. Read its full transcript with agents.transcript session=<id> when this summary is not enough.`, then `Task (turn N):` with the first user prompt, `Last prompt (turn N):` with the last one when it differs, `Last reply (turn N):` with the last agent message, `Last turn N: <stop reason>, checkpoint <sha> taken before it.`, each text trimmed and cut at 2000 characters, and last the note or `Pick up where it left off.`, separated by blank lines; thoughts and tool calls are left out. Without a user prompt the note alone is sent, or nothing when it is empty. Called by the user (not an agent), it selects the new session.
- `agents.sidebar`: a row with a `new` button (action `new`) and a `branch` "New in worktree…" button (action `showBranch`), then a `tree` `sessions`. `showBranch` replaces that row with a `form` `newBranch` (action `newBranch`) holding a `textField` `branch`, a `start` "Start" button and a `cancel` "Cancel" button (action `hideBranch`, which restores the row), and focuses the field. `newBranch` with `{branch}` starts a top-level session in a new worktree `.worktrees/<branch>` (as `agents.new` with `branch`; an empty or invalid name is an error and keeps the form), restores the row, and selects and focuses the session. On top, when any top-level session (no `parentSession`) is `waiting` or `done` with `asks` (as in `agents.wait`), a `Needs you · N` group (id `wt:needs`, expanded by default) lists them again with ids `needs:<id>`, as leaves. Then one row per worktree (id `wt:<root>`, label its folder name, expanded by default) with its open top-level sessions, newest first, and, when it has closed top-level sessions, a last `Closed · N` group (id `wt:closed:<root>`, folded by default) holding them. A session row has the title, its activity as detail (`<elapsed> · <last tool>` while running, where `<elapsed>` is the time since the current turn started: `<1 min`, `N min`, `N h M min`; `Waiting for permission · <tool>`; `Error · <first error line>`; otherwise the last update, `12 min ago`) and a status icon whose `tone` carries the status (running `accent`, waiting `warning`, done `success`, error `danger`, idle and closed none). Its menu has Hand Off to New Session (`handoff`, sessions not running or waiting and not handed off yet), Close Session (`close`, open sessions only) and Delete Session (`delete`, with the confirm text; `Delete this agent session and its N child sessions, their transcripts and checkpoints?` when it has N > 0 descendants). A session with a parent that is in the list is not placed in its worktree's group: it is a child item of its parent's row (`hasChildren`, `expanded`, children newest first), recursively, and stays there when it is closed. A session with a `parentSession` never goes in `Needs you` (its orchestrator answers it) or in a `Closed` group. `select` with a session id or a `needs:<id>` opens that session (the `needs:` row stays selected while it is in the group); `handoff`/`close`/`delete` accept both ids; `handoff` selects the new session. `expand`/`collapse` on a group row (`wt:<root>`, `wt:needs`, `wt:closed:<root>`) or on a session row (stored as `s:<id>`, expanded by default) folds it.
- `agents.main`: for the selected session (the newest when none is chosen; `empty` without sessions), a header (title; agent, worktree, mode, the current `model` config option and the current `thought_level` one as `<value> <option name, lower case>`, e.g. `High effort`; `review` "Review changes" when the worktree differs from the session's first checkpoint, rechecked after each turn and when the session is selected; `merge` "Merge to main" (with a confirm) next to it for a top-level session that is `done`, has Finish `ask` and changes, and runs in a worktree under `.worktrees/`: the click refuses unless the worktree is a linked one on a branch other than the default base or `main`/`master`, no other open session works in it and the main checkout is clean, then prompts the agent, as the user, to commit and do the Finish `merge` steps now; `stop` while running; on `error` the first error line with `retry`, `signIn` when the agent needs a login, or `continue` when the agent cannot resume the session; a child session also has a `from <parent title>` button with action `selectParent` that selects the parent; a session started by a handoff has an "Earlier session" button (id `<id>/handoffFrom`, action `openHandoff`) that selects the old one while it exists), then the `transcript`, the queued prompts (muted, each with `unqueue` "Remove"; when no turn runs a `sendQueued` "Send queued" button) and the `composer`. A closed session shows "Reopen" (`retry`) instead of the composer, or "Hand off to a new session" (`continue`) when the agent cannot resume it (its agent advertises no `session/resume`, or resuming failed); a handed-off one shows "Open new session" (id `<id>/handoffTo`, action `openHandoff`) instead, while the new session exists. `continue` hands the session off as `agents.handoff` without a note and selects the new session; the old transcript stays readable. When the agent cannot start because Node is missing or too old, the main slot shows `empty` with `Node 22+ is required to run Claude (found <v>)` under the header.
- Node ids in `agents.main` start with `<session>/` (`<session>/tool/<toolCallId>`, `<session>/permission/<id>`, `<session>/composer/<n>`, `<session>/msg/<user|agent|thought>/<entry id>`, `<session>/plan/<turn>`), and events are applied to that session, not to the current selection. Message and plan ids stay the same when the window shifts, so the client keeps their state (e.g. an expanded "Thinking").
- The transcript shows the last 20 turns; the `showEarlier` button adds 20 more. A render is capped below the node limit: when the shown turns would exceed it, the oldest entries are dropped and the button stays. The open session renders at most 10 times a second while the agent streams; other sessions are not rendered, and a slot whose tree is unchanged since the last render is not sent again (a streaming background session re-renders only the sidebar).
- Tool cards: paths under the session's worktree are shown relative to it in titles, diff headers and permission text (`openLocation` keeps the absolute path). Edits (`edit`, `delete`, `move`) show the ACP diff as a unified diff with `openLocation {path, line}` ("Open in nvim", → `editor.open`) and `review {turn}` ("Diff", as `review` below); `execute` shows `$ command` and the output as `terminal`; `read` and `search` are one line with `openLocation` when the agent sent a location. Bodies over 200 lines or 64 KiB are cut to that with `truncated` and a `showAll` action; after `showAll` (node id names the card) the full body is sent, up to 1 MiB.
- Other actions: `send {text}` prompts with the pending composer attachments, `permission {request, option}` answers, `mode {mode}` switches, `config {id, value}` as `agents.config`, `attachFile {path}` adds a file chip, `attachSelection` adds the editor selection (`editor-nvim.selection`), `detach {id}` removes a chip, `unqueue` on `<session>/queue/<id>` drops a queued prompt, `sendQueued` sends the queue as a turn, `continue` starts a new session in the same worktree, `review {turn?}` runs `editor-nvim.diffview {cwd: <worktree>, rev: <checkpoint sha>}` for that turn (default: the first turn with a checkpoint; `no checkpoint to review yet` without one), `retry` reattaches (`agents.resume`), `close`/`delete` as the commands.
- Sign in: the client advertises `auth.terminal`. When `session/new` fails with `-32000` (auth required) and the agent offers a `terminal` auth method, the session errors with `sign in to continue` and the header offers `signIn`. It runs the agent's launch command plus the method's `args` (and `env`) in a terminal session owned by `agents` in the worktree, shown as a `surface` in `agents.main`; when it exits the terminal is removed and the session reattaches. A `-32000` from `session/resume` leads to the same Sign in. Closing or deleting the session kills and removes its sign-in terminal (its exit no longer reattaches); leftover sign-in terminals are removed when the plugin starts. The method's `env` never sets `ANTHROPIC_API_KEY`.

Every event is appended to `<state>/plugin-data/agents/sessions/<id>.jsonl` as `{workspace, worktree, session, parentSession, role, turn, seq, actor, ts, kind, payload}` with ACP payloads verbatim; text chunks are coalesced per message (flushed at turn end, after 2 s or at 64 KiB). Removing a workspace closes its sessions (`session/close` when supported, never `session/delete`: the agent's own history stays) and deletes their checkpoint refs, logs and records. Removing a worktree with sessions closes them and deletes their checkpoint refs.

## Bus topics

- `project.updated` `{project}`: published when a repo is added to a project (`project.addRepo`), it is renamed (`project.rename`) or a folder's worktree selection changes (`workspace.worktree.set`). Existing `fs.watch` streams do not follow; re-watch on this event.
- `agents.changed` `{workspace, session, kind}`: published by `agents` when a session is created, changes status or is deleted, coalesced per session and kind (`created`, `status`, `deleted`). Streamed transcript updates are not published.
- `agents.turn` `{workspace, session, status, asks, reply}`: published by `agents` at every turn end (`status` after it: `done`, `error`, `closed`, `waiting` when a permission is still pending, or `running` when queued prompts start the next turn), when a session's agent fails (`error`), when a running session is closed (`closed`, once: the turn end that follows publishes nothing) and when a permission request starts waiting (`waiting`). `asks` is as in `agents.wait`; `reply` is the turn's last agent message, trimmed and cut at 4000 characters (`…` appended), or empty when the turn has none. Not coalesced: one event per occurrence.
- `notify.posted` `{id, workspace, session?, owner?, title?, message, kind, agent?, ts}`: published by `notify.post` (`cm notify`, the `notify_post` MCP tool). `agent` is true (and the event source `agent`) when an agent called it through `command.run` with `agent: true`. `kind` is `needs-input`, `permission`, `done`, `stuck` or `info`; `message` is at most 1000 characters and `title` 120 (longer ones are cut with `…`); `owner` is the owner of a `ses_` session (e.g. `terminals`); `ts` is RFC 3339 UTC. `notify.post` checks that the workspace exists and that a `ses_` session belongs to it (other session ids pass as they are when shaped like `agt_<16 hex>`), and allows 5 calls per 10 s per workspace and 20 in all (error code -32015, "too many notifications", beyond that).
- `git.changed` `{workspace}`: published by `git` (debounced 300 ms) when a `HEAD` file in a git dir of an open workspace's folder changes (an in-place `git switch` in a checkout or a linked worktree) or its `fs.watch` overflows; the app reloads `git.worktrees` for that workspace, so the titlebar pill follows the branch.
- `processes.killed` `{projectId, pids}`: published by `processes` when auto-kill terminates orphans of a project; never published with empty `pids`.

## Core notifications

- `project.open` `{id}`: sent to every connection that registered `"project.open"` (not to plugins, not to the caller of `project.open`, `workspace.open` or `workspace.home`); the client shows that project.
- `core.stopping` (no params): sent to every connected client (not to plugins) after `core.shutdown` has replied and right before the core stops. A client that sees the connection end after `core.stopping` treats the stop as intentional and does not restart the core; a connection that ends without it is an unexpected loss.

## Presence

The core publishes `ui.opened` `{projectId}` on the durable bus when a project's UI subscriber count goes from 0 to 1, and `ui.idle` `{projectId}` when it goes from 1 to 0.

## Visible section

Clients keep per-project UI state with `ui.state.get` / `ui.state.set` `{projectId, state}` (client callers only). Its `section` field is the section the project's window shows: the app has one window per project and writes `section` when it opens the project and on every switch. When a `ui.state.set` changes `section`, the core publishes `ui.section` `{projectId, section}` on the durable bus. Plugins read the current value with `ui.state.section` (`pluginsdk.Host.SelectedSection`).

`processes` uses it to skip work nobody sees: its 1 Hz refresh keeps recording history for every present project but renders only projects whose section is `processes` or unknown (`""`). On `ui.section` to `processes` it renders at once.

## Plugin runtime dir

The core creates `<runtime>/p/<pluginId>` (mode 0700) and passes its path to the plugin in `CLUBMATE_PLUGIN_RUNTIME_DIR` (`pluginsdk.RuntimeDir()`). It passes `<state>/plugin-data/<pluginId>` in `CLUBMATE_PLUGIN_STATE_DIR` (`pluginsdk.StateDir()`) for data that must survive restarts; the plugin creates it when needed. It also passes the build flavour in `CLUBMATE_FLAVOR` (`pluginsdk.Flavor()`): `release` for release builds, `dev` otherwise.

The core also passes the app's resources directory in `CLUBMATE_RESOURCES` (`pluginsdk.ResourcesDir()`), `Clubmate.app/Contents/Resources` when run from the app; bundled tools live under `tools/` and `nvim/` there.

A plugin's `session.create` (`pluginsdk.Host.CreateSession`) also takes `env`, entries added to the environment the session inherits, `unsetEnv`, names of variables removed from it first, and `pathAppend`, directories appended to the end of the session's `PATH` (entries already in it are skipped).

## ui.event contract

| node | trigger | `action` | `value` |
|---|---|---|---|
| button | click | `props.action ?? id` | `null` |
| list / tree | select item | `props.action ?? "select"` | item id |
| tree | expand / collapse | `"expand"` / `"collapse"` | item id |
| table | select row | `props.action ?? "select"` | row id |
| table | expand / collapse | `"expand"` / `"collapse"` | row id |
| table | header click | `"sort"` | object `{column, desc}`: the clicked column id; `desc` flips when it is already the sort column, otherwise starts `true` for right-aligned columns and `false` for others |
| tabs | select tab | `props.action ?? "select"` | tab id |
| textField | submit | `props.action ?? "submit"` | text |
| toggle | change | `props.action ?? "toggle"` | bool |
| select | change | `props.action ?? "select"` | option value |
| folderField | pick folders | `props.action ?? "pick"` | string[] of absolute paths |
| form | submit | `props.action ?? "submit"` | object `{fieldNodeId: value}` |
| list / tree | choose a menu entry | entry `action` | item id |
| toolCard | click an action | entry `action` | entry `value` (`null` when absent) |
| permissionCard | click an option | `props.action ?? "permission"` | object `{request, option}`: `request` from props, `option` the option id |
| composer | send (⌘↩ or Send) | `"send"` | object `{text}` |
| composer | stop (Esc or Stop while `running`) | `"stop"` | `null` |
| composer | pick a mode | `"mode"` | object `{mode}` |
| composer | pick a `pickers` option | `"config"` | object `{id, value}` |
| composer | attach a file (picker or `@`) | `"attachFile"` | object `{path}`: absolute path |
| composer | attach the editor selection | `"attachSelection"` | `null` |
| composer | remove an attachment chip | `"detach"` | object `{id}` |

`nodeId` is the `id` of the node that fired the event.

## Forms

A `form` collects the values of the `textField`, `folderField`, `toggle` and `select` nodes among its descendants (nested forms collect their own fields), keyed by the field node `id`. The value is the field's current text, bool, option value or (`folderField`) string[] of chosen paths; fields that disappear from the tree are dropped.

- A `button` without an `action` prop inside a form submits the form: the form sends `props.action ?? "submit"` with the collected object as `value` and the form's `id` as `nodeId`.
- Return in a `textField` without an `action` prop submits the form the same way.
- Fields without an `action` prop inside a form are silent: they only update the collected values.
- A field or button with its own `action` prop sends its own event per the contract above (fields still update the collected values); it does not submit the form.
