# Agents

Agents running in Clubmate terminals (Claude Code, Codex, scripts) can drive Clubmate through one registry of commands: core primitives (workspaces, sessions, processes, focus) and actions that plugins declare (open a file, switch a worktree, close a terminal, ...).

## What agents can do

`clubmate command list --agent` shows everything an agent may run, and `clubmate command describe <id>` shows one command's arguments.

- Workspaces: list, open folders, open the home workspace.
- Sessions: list, start a login shell, type into one (`session.send`), read its recent output (`session.read`), kill one.
- Processes: the process tree of every session and of processes plugins register (agent processes).
- UI: show a section, focus one of its slots or a node in it (`ui.focus`).
- Notifications: `notify.post` shows a macOS notification (needs input, permission, question, done, stuck, info), skipped while the user looks at the session; see [notifications](notifications.md).
- Backlog: `backlog_list`, `backlog_claim`, `backlog_update`, `backlog_done` and friends share a per-workspace task list with the user; see [backlog](backlog.md).
- Plugin actions marked for agents. Some are generic capabilities, so an agent need not know which plugin provides them: `editor.open`, `editor.quickfix`, `editor.reveal`, `terminal.new`, `terminal.close`.
- Git worktrees: `git.worktrees` lists every git folder's worktrees, `git.worktree-switch` switches a folder to one of them, `git.worktree-new` creates `.worktrees/<branch>` and switches to it (unless `switch` is false), and `git.worktree-remove` removes a linked worktree (never the main checkout or one with uncommitted changes). Both run the repo's [worktree hooks](worktree-hooks.md). Create and remove return `{id}` at once; `git.worktree-op-status id=…` waits up to 1 s for the outcome (the app instead gets the `git.outcome` event).
- Agent sessions: `agents.sessions` lists the workspace's agent sessions with their status, `parentSession`, `childStatus` (a done or idle orchestrator whose child sessions still run or wait), `needsYou` and `needsYouSince` (see [Needs you](#needs-you)), `activity` (`{title, at}` only for a `done` session waiting for its own reminder, see below; a running session's tool calls are never named outside its transcript), `turns` (the turns it has started so far, absent while its transcript is not in memory; Backlog's Owner row says "running · turn 3" from it) `repo` (the short name of a repo child's repo, its full path in `repoPath`), `task` and `taskSummary` (see [Needs you](#needs-you) § Landing), `connectRequests` (§ Connect requests) and notification policy (`notify`, `notifyEffective`); `agents.sessions session=…` lists only that session (empty when the workspace has none), with `childStatus` and `notifyEffective` still worked out from the whole workspace, and is what the Mac and the phone fetch to check a notification's policy and what the phone fetches to check a permission is still pending before it answers it, so neither client pulls the whole list for those; `agents.sessions since=…` returns `{sessions, removed, cursor, delta}` instead of the list: `since=""` gives every session and a `cursor`, and an earlier `cursor` gives only the sessions whose row changed since then, any field, `childStatus` and `notifyEffective` included (`delta: true`), with the ids `removed` since then; a cursor from before the plugin restarted, or one older than the oldest removal the plugin still remembers (it keeps the last 64 removed ids per workspace), gives every session again without `delta`. The phone's session list and the Mac's agent counts and notifications load the whole list once per workspace and then only what changed on each `agents.changed`; `agents.notify session=… policy=all|needs-input|muted` sets the policy of the caller's own session or one it started (see [notifications](notifications.md#per-session-policy)), and `agents.transcript session=…` reads one session's transcript from Clubmate's own log (`last=true` keeps only the last turn and leaves out the modes, config options and commands catalogs; `compact=true` drops the images in tool calls' content, the image data in user prompts and the commands catalog; tool calls never carry `rawOutput` or `_meta`, which stay only in the log; `since=<cursor>` returns only what changed after an earlier result's `cursor`).
- Child agent sessions (no approval): `agents.new` starts a session, optionally in a new worktree `.worktrees/<branch>` made from the caller's worktree without switching the workspace, and sends it a first `prompt` (`notify` sets its notification policy); `agents.prompt` sends any session a follow-up (added to the running turn when the agent supports steering, else queued) and returns `{turn}` when it started a turn, `null` otherwise; `agents.cancel` stops a running turn; `agents.permission` answers a permission request and `agents.elicitation` a question (AskUserQuestion, an MCP form or sign-in link), but only of sessions the calling agent session started (directly or through its children); the paired phone (through the `remote` plugin) and the voice plugin answer any session's permission requests and questions as the user; `agents.wait` waits without polling until one of the listed sessions stops running (done, waiting for permission, asking a question, error or closed), up to 300 s per call, and returns their status with the pending permission's options; it also returns early with the user's queued messages to the calling session, which then leave the queue and show in its transcript as your message in the running turn.
- Failed turns: a turn the agent ends with an internal error (`-32603`, e.g. Claude Code's "ended the turn without returning results for tool calls" when the advisor tool is rate-limited) is retried once, 3 s later, within the same turn: the transcript shows a notice and a Clubmate message asking the agent to continue. When every tool call that error lists was still open when a message was steered into the turn (yours or Clubmate's; it interrupts a server tool such as the advisor, which then never returns), the turn is not failed and not retried: it ends `done`. A second failure leaves the session in error, as any other error does. Network errors ("No response from API", "Connection refused", `ECONNREFUSED`) are not retried within the turn, since Claude Code has already waited and retried; see the network error paragraph under orchestration.
- Handoffs: `agents.handoff session=… note=…` continues a session that is not running in a fresh one (same worktree, agent, parent, advisor, title, graph run, notification policy, AFK mode and starting cron job or trigger), seeded with a brief from Clubmate's log (the task, the last prompt and reply, the last turn's stop reason and checkpoint, and how to read the full transcript) followed by `note`; the old session is closed but can be reopened, and each links to the other. The sessions the old one started move to the new one (`parentSession`), so their wake-ups, permissions and questions reach it. Agents may hand off only sessions they started. In the app, a session's menu has "Hand Off to New Session", and a session whose agent cannot resume offers "Hand off to a new session". A closed session that was not handed off carries `reopen` in `agents.sessions`, the action its closed footer offers as `{id, label, icon, command, args}`: "Reopen" (`agents.resume`) for that one session, "Restore" (`agents.restore`) on a task's parent, or "Hand off to a new session" (`agents.handoff`) when its agent cannot resume; the Mac builds its button from the same action and the phone shows it in the closed session's footer, so neither client decides which one applies.
- Attribution: `agents.blame path=…` (or `commit=…`) tells which agent session, turn and prompt made a file's lines or a commit; `agents.trace rev=…` exports a commit's or a range's changed lines as [Agent Trace](https://agent-trace.dev/) records; see [History and attribution](#history-and-attribution).
- Moving a session: `agents.export session=… dir=…` writes a session bundle, `agents.import dir=…` continues it in another worktree or workspace; see [Resuming elsewhere](#resuming-elsewhere).
- Reminders and schedules: `cron.add` calls a command later or repeatedly, e.g. `agents.prompt` to your own session tomorrow morning; the job is deleted with your session unless `owner: "none"`. Watching your children needs no cron job: Clubmate wakes you when their turns end (see below). See [cron](cron.md).
- Reacting to events: `triggers.add` calls a command when a bus event arrives, e.g. `agents.prompt` to a reviewer session when another session's `agents.turn` ends; `triggers.emit` publishes your own `event.<name>`, which `cron.add` can schedule. See [triggers](triggers.md).
- Unattended runs: a session a cron job or trigger starts with `agents.new` remembers it (`cronJob: cj_…` or `trigger: tr_…` in `agents.sessions`, set by those plugins; anyone else passing them gets `invalid_params`), and each `agents.turn` of it carries the id. `agents.turn` says `finished: true` when the session is done with its work: the turn ended `done` and no child session (any depth) is running, waiting for permission or asking its parent. A parent waiting for its children ends many turns with `finished: false`; Clubmate wakes it when the last child ends, and the turn after that is `finished: true`. So a trigger on `agents.turn` with match `{"cronJob":"cj_…","finished":true}` follows every run of a recurring job without knowing its session id. `agents.turn` doesn't say what the run changed; the triggered session checks that itself (e.g. commits since the last tag).
- Agent graphs: `graphs.run graph=… input=…` starts a team of child sessions from `.clubmate/graphs/<graph>.json` (one session per role, one trigger per edge) and the Graphs section shows the run; `graphs.list`, `graphs.show`, `graphs.stop`, `graphs.delete`. See [agent graphs](agent-graphs.md).
- Tasks across repos: `agents.connect-repo` asks the user for repos, `agents.task` declares a change across them in landing order, `agents.new` with `repo` and `slug` starts a child per repo (from an agent session only for a repo its task lists, so every repo child has a task to report to) and `agents.task-report` reports how its repo landed; see [Needs you](#needs-you), [Task tree](#task-tree) and [Repos card](#repos-card). Answering a connect or Land request, leaving a repo unlanded, asking its child to fix it and removing a folder stay the user's own.
- Open items: `agents.open-items` leaves the decisions and offers still open at the end of a turn for the user, as a quiet card that needs no answer; see [Open items](#open-items).
- Problem reports: `report.send` sends a report about Clubmate itself to its developers, after the user checked it in a sheet; see [problem reports](reports.md).
- Answers on your behalf (asks you first): `agents.answer session=… text=…` shows you the text and, once you allow it, sends it to the session as your own message.
- Web research: `browser.open`, `browser.snapshot`, `browser.click` and the other `browser.*` tools drive a hidden WebKit browser in the app, one set of tabs per agent session, and `browser.handoff` asks the user to solve a captcha or sign in; see [agent browser](browser.md).
- Showing a doc: after writing a spec, plan or report the user should read, `docs.open {path}` (MCP `docs_open`) shows it rendered in a popup with mermaid diagrams drawn; see [docs viewer](docs-viewer.md).
- Testing the app: `testapp.list` lists running test instances and `testapp.call instance=… method=…` calls one of them (see below).

Hidden helpers and commands not marked for agents stay out of reach.

## Import your nvim config

**Import my nvim config** in the command palette starts an agent session in the Agents section that reads `~/.config/nvim` and moves your own keymaps, options, autocmds and plugins into Clubmate's Neovim user layer (`~/.config/clubmate`, or `~/.config/clubmate-dev` for development builds), following the guide bundled at `nvim-distro/skill/SKILL.md`. It skips what Clubmate's defaults already cover and asks you before adding destructive or machine-specific mappings. It needs an open folder workspace and never changes `~/.config/nvim`. The first time Neovim starts in a workspace while `~/.config/nvim` exists, it offers the same import once.

## Testing the app

Agents test Clubmate in their own invisible instances instead of taking over the user's screen. `scripts/test-app.sh start [name]` (name defaults to the branch) launches the Debug build with scratch state, runtime and `XDG_*` dirs under `/tmp/clubmate-test-<name>`, its own core and its own defaults suite, in test mode (`CLUBMATE_TEST_MODE=1`): it never activates, its windows are transparent and ignore the mouse, app-modal dialogs are skipped and every approval is denied (with the launch arg `--test-approvals` the real approval alert shows instead; it can still only be denied, by ⎋ or its timeout, and the pointer is refused while it is up). Inside the app it still acts as the active app with a key window, so focus, focus rings, menu keys and SwiftUI's focused values work as on screen: `NSApp.isActive` answers true, `NSApp.keyWindow` is the workspace window, its attached sheet or a popover or panel that asked for key, `activate` does nothing, and the first key or pointer input to a window announces it as key again (SwiftUI misses the first announcement while its window is still opening). `relaunch [name] [app] [-- app args]` restarts only its app with new launch args (core, state and seed data stay; e.g. after writing `theme = …` to its `state/ghostty.conf`), `stop [name]` quits it and removes the dirs, `list` shows running ones, `cm [name] -- <args>` runs the CLI against one, with that instance's workspace as `CLUBMATE_WORKSPACE_ID`. `start [name] -- --sdui-gallery` shows the SDUI gallery with a core but no workspace. `make gallery-smoke` starts the gallery, takes one snapshot into `build/gallery-smoke` and stops it; it fails when any fixture node crashes the app.

- `ui.snapshot {out, png?, width?, height?}` (CLI `cm ui snapshot --out <dir> [--size 640x800] [--no-png]`): the app draws each of its windows itself (main window with titlebar, popovers, sheets, settings) to `w<window id>.png`, terminals included, and writes `w<window id>.json`: every rendered SDUI node with its frame in window points, its parent, its menu entries, plus every terminal's visible text and native menus listed as text. Rows of SDUI lists and trees and the option rows of a `choice` are listed too (source `row`, id `<list id>#<item id>`, role `row` plus `selected`, `focused`, `hovered`), and never flagged. The result names the key window (`key`), its first responder's class (`responder`) and the smallest node around it (`focus`), e.g. `<session>/composer/0` when the caret is in a prompt. Flags: `outside-window`, `wider-than-parent`, `overlaps-sibling`, `zero-size`, `truncated` (text nodes, measured). The result's `summary` lists only flagged elements, or `0 problems`. `--size` resizes the main window first.
- `ui.present {target, shown}` (CLI `cm ui present <target> [--hide]`): opens `inbox`, `worktree`, `switcher`, `settings`, `palette`, `onboarding`, `onboarding-vscode`, the problem report sheet fixtures `report` and `report-over`, or the `approval` and `approval-paths` (long hyphenated paths, a Session line and a From line) fixture alerts without a click; an alert lists `alert.detail`, `alert.facts` (role `text clipped` when the arguments need more lines than the alert gives them) and `alert.accessory`, the problem report sheet `report.text` and `report.summary`; menus are never opened, they appear as text in the layout. `card:<node id>` expands a transcript tool card (`--hide` collapses it), and with it the summary row of its group; card ids (`<session>/tool/<tool call id>`) are listed by `cm ui dump` and not checked, so a wrong id changes nothing. `message:<node id>` expands a long message the same way, and `image:<message node id>#<path>` opens the image viewer.
- `ui.key {keys, focus?, caller?}` (CLI `cm ui key [--focus <node id>] <combo>...`): `focus` first makes the view under that SDUI node (an id from the snapshot layout; with duplicate ids any match, so prefer a unique one) first responder, e.g. a text field. Each combo then goes, in the key window, to the active key monitors (sidebar trees, the composer, a sheet's ⎋), else, when it has ⌘, to the window's key equivalents (view shortcuts), else, with ⌘ or ⌃, to the app menu (after letting SwiftUI fill its items, as opening the menu bar does), else as a key down and up to the first responder; the result lists the route each combo took (`voice` when the voice key took it, `monitor`, `monitor over terminal`, `shortcut`, `menu <item>`, `menu <item> over terminal`, `menu <item> (enabled, not sent)` or `(disabled, not sent)`, `responder <class>`, or `alert`: an alert's keys go through the app's event queue, so its own ⎋ monitor sees them). A combo is `[cmd+][ctrl+][opt+][shift+]<key>`, `<key>` a US-layout letter, digit or punctuation, `return`, `tab`, `space`, `delete`, `esc`, `up`, `down`, `left` or `right`; `cm ui key --focus description o n e opt+return t w o` types two lines. ⌘N and ⌃⌘↓ reach the menu like a real key press; with an SDUI `sheet`, a form sheet or a popover up, keys go to it. Only ⎋ is sent while an alert (approvals), the problem report sheet or any app-modal window is up, so keys can't answer an approval or send a report. While a terminal has focus a combo goes only to the key monitors that pass terminals (a button's ⌘↩) and, with ⌘ or ⌃, to app menu items with their own target (the app's commands, not Edit's Paste or Select All, which act on the first responder), and is refused when none takes it, so keys never run shell commands. Tab moves AppKit focus, but SwiftUI's `.focusable` controls (buttons, choice rows) never join the Tab loop in the test app, even with `-NSTreatUnknownArgumentsAsOpen NO -AppleKeyboardUIMode 2`.
- `ui.pointer {action, node, at?, count?, to?, keys?, context?, item?, file?, dy?, caller?}` (CLI `cm ui click|hover|drag|menu|scroll|drop`): pointer input at a node of the snapshot layout (its centre, or `--at x,y` points from its top left; refused when the id is on screen more than once, or the point is outside its window or under an alert). `cm ui click <node> [--count 2]` posts mouse down and up into the app's event queue, so local event monitors and tracking loops see them as real clicks; `cm ui hover <node>` sends mouse entered, moved and exited to the tracking areas under and no longer under the point (posted mouse moves never reach SwiftUI's `onHover`); `cm ui drag <from> <to>` presses, moves in ten steps and releases inside one window (no test uses `--count 2` yet); `--keys cmd` (or `shift+opt`…) holds modifiers. `cm ui scroll <node> --dy N` turns the wheel N lines (negative: up) with `--keys` held: the event is built from a CGEvent tagged in its `eventSourceUserData` and posted into the queue, and while it is pending `NSEvent.window` and `locationInWindow` answer the node's window and point for that tag (the queue rebuilds the NSEvent from its CGEvent, so nothing attached to the NSEvent survives), so local monitors (the graph's ⌘/⌃+wheel zoom) and the view under the point see it like a real wheel; no momentum or precise deltas. A menu a click opens (a SwiftUI `Menu`, a `Picker`, a context menu with `cm ui menu <node> --context`) is read when it starts tracking, picked when `cm ui menu <node> '<item> > <sub item>'` names an enabled item, and closed at once, so no menu shows; the result's `menu` lists its items with `enabled`, `checked` (✓) and `children`. `cm ui drop <node> <file>` hands the file to the drop view under the point (SwiftUI's sits beside the hit-test chain) as a drag from Finder would, through a private pasteboard; a real drag session, the menu's look, Quick Look, trackpad scrolling phases and gestures (pinch) are not covered. Clicks carry `caller` like `ui.key`.
- Over MCP: `testapp.call` proxies `ui.snapshot`, `ui.present`, `ui.key`, `ui.pointer`, `ui.get`, `ui.event` and `command.run` (both always as an agent call), `command.list`, `workspace.list` and `workspace.open` to `/tmp/clubmate-test-<instance>`; `ui.snapshot`'s `out` defaults to and must stay inside `/tmp/clubmate-test-<instance>/snapshots`, and a `ui.pointer` drop's `file` must be inside `/tmp/clubmate-test-<instance>`.
- `make mac-ui-test [RUN=<regexp>]` builds the fake agent and runs `internal/macui` against the Debug app (`CLUBMATE_TEST_APP`; without it the tests skip): each test starts its own instance on a scratch repo under `build/mac-ui/<name>`, drives it with `ui key` and `ui pointer` and asserts on the snapshot (focused node, row state, windows, menus) and on plugin commands. It covers menu keys in Agents, Triggers and Cron, the graph Trust sheet's keys, question card clicks and ⌘↩ (in Agents and in the Code chat with a review open), the Open items card and queue, an image link in a transcript, the inbox's graph pin arriving while the inbox is open, the Start agent popover, a file drop and the tag chips in Backlog, the title picker, worktree and folder sheets, the Connect card, Archive task, the approval alert (with its From line) over the problem report sheet, the drawn views (trigger flow edges, lanes and runstrip keys, the Runs fold per cron job, a graph History move, ⌘-wheel zoom), row hover, a drag on the sidebar divider (`<slot>/resize`) and the Settings font menus. `RUN` goes through make, so a `$` in it is eaten: write `RUN='TestA|TestB'`, not `TestA$|TestB`.

Multi-repo landing check: `scripts/mr-landing-check.sh run` builds two scratch repos under `build/mr-landing/repos`, `pr-flow` (its CLAUDE.md: land through a pull request, push to its bare `origin`, never merge locally) and `plain` (no instructions), starts the test instance `mr-landing` with a workspace of both, starts an orchestrator with finish mode merge and asks it to add a README line in both repos as a task across repos. It waits until both repos settle and the orchestrator's turn ends, so a merge the orchestrator makes after its children landed counts, and checks: `pr-flow` reads `prOpen` or `onBranch` with its rule corrected to `pr`, its `main` has no merge and `origin` has `feat/mrcheck` when a pull request is claimed; `plain` reads `onBranch` with `main` untouched; both `feat/mrcheck` branches hold the line. It writes `task.json`, `sessions.jsonl` and a snapshot of the orchestrator (`shots/`) next to the repos and exits non-zero on a failed check. `MR_AGENT=fake` (the default) drives every session with fakeagent's `run` steps, which run a shell line in the session's folder with its `CLUBMATE_AGENT_SESSION` so `clubmate command run` calls come from that session; `MR_AGENT=haiku` (or another model name) runs real Claude on that model, picked with `agents.config` before the first prompt. `MR_KEEP=1` leaves the instance running, `MR_APP` names another `Clubmate Dev.app`, `MR_TIMEOUT` the seconds to wait (120 fake, 1500 real), `stop` stops it. Each scratch repo's `.claude/settings.json` lists every CLAUDE.md above `build/` in `claudeMdExcludes`, so a real agent reads only the repo's own rules and not Clubmate's "squash into main".

A test instance stays offline: in test mode (outside release builds) the plugins never start `claude -p`, so graph step and turn summaries and the voice cleanup are skipped as when the CLI is missing (`plugins/internal/claudecli`).

The user's own app never answers `ui.snapshot`, `ui.present`, `ui.key` or `ui.pointer`: only a test-mode app registers them, and test mode needs a dev build with non-default state and runtime dirs.

## Approvals

Destructive actions (closing or killing sessions, typing into a session, answering an agent session as you, restarting the editor, killing orphan processes, removing a worktree) ask you first. Clubmate shows an alert naming the action, the workspace, the targeted session, the agent session that asked (a "From:" line with its title and id, e.g. `git.worktree-remove` from a child session; just the id when Clubmate can't find it in that workspace) and every argument in full, with Allow and Deny. Deny is the default. If nobody answers within 60 seconds, or the app isn't open, the action is refused.

An agent session calling these tools is the parent of the sessions it starts with `agents.new` (Clubmate knows the caller from `CLUBMATE_AGENT_SESSION`, which every agent session has). A child starts with the parent's mode, model, effort and advisor, not the worktree's remembered ones (the model is the one `model` on `agents.new` names when given, the effort the one `effort` names), and at most 8 children of one parent run or wait for permission at once. A model or effort level the agent doesn't offer leaves a notice in the transcript with the offered values and the same text in the session's `startNotice` (`agents.sessions`), so the parent sees it; the real Claude adapter offers `default`, `opus`, `fable` (Fable 5.2), `sonnet`, `haiku` and full ids such as `claude-fable-5-1`, and effort `default`, `low`, `medium`, `high`, `xhigh`, `max` for models that have it. A session an agent starts where it is not the parent (in another workspace, or through a cron job or trigger with `owner: "none"` that agent made) is top-level but not yours: it records that agent in `startedBy`, takes no AFK default, and one agent keeps at most 8 such sessions open at once (closing one frees its place). Agents without an agent session (Claude in a plain terminal, `cm --agent`) count as one such agent, `startedBy: "unknown"`; a graph run or another plugin starting a session is not one. A prompt an agent sends through `agents.prompt` or `agents.new` is logged as coming from that agent (`agent:<session id>`) and reaches the target with `[From Clubmate agent session "<title>" (<id>), not from the user]` in front, so it never passes for your approval; from an agent without an agent session it is logged as `agent:unknown` and starts with `[From another agent session, not from the user]`. Prompting an idle child also counts against the limit of 8. Agents without an agent session (Claude in a terminal, `clubmate command run --agent`) start top-level sessions that aren't yours (above) and cannot answer permission requests.

A child in its own worktree merges its finished, tested work into its parent's branch in the parent's worktree, never into `main`; a child sharing its parent's worktree, or whose parent is on the default branch, only commits and the parent merges. Children never remove worktrees or branches: once a child's turn ends with its branch merged into the parent's branch and its worktree clean and unused, Clubmate closes the child (it stays listed as Closed) and removes its worktree and branch itself, without asking. It doesn't when removing would lose something git can't bring back: an ignored secret file no other worktree holds identically, a commit on no branch, or an unsaved buffer of it in any Neovim of the workspace (or a Neovim that doesn't answer). Then the worktree stays, the child shows `Couldn't remove the merged worktree: …` with the reason, nothing retries it, and you remove it from the title picker, which lists what would go. A session that has children is told to write to you only the children's questions that need your answer, to answer their permission requests itself with `agents.permission`, and to pass your answers on with `agents.answer` rather than paraphrasing them.

Clubmate wakes an orchestrator when a child's turn ends: once a child is done, ends in an error or waits for permission, and the parent is not in a turn of its own, the parent gets `[Clubmate] Child "<title>" (<id>) is <status>.` (the title's first line, quoted), one line per child in one message when several finish together (within a second, `CLUBMATE_AGENTS_WAKE_DELAY` overrides it, or while the parent's turn was still running). A child the parent already saw through `agents.wait` is not reported again, so an orchestrator that waits on its children is not woken twice. A suspended parent is resumed for the message like for any prompt. Pending wake-ups live in memory and are lost if the plugin restarts. A hand-off passes the old session's pending wake-ups to the new one, including a child's report that lands while the hand-off runs or after it (the closed session forwards it to the session it handed off to), and an `agents.wait` the old session still has open counts as the new session's wait.

When Clubmate restarts (an update, a core handover) while a turn is running, the turn is cut off. On start, the agents plugin sends `[Clubmate] Your turn was cut off by a restart; continue from where you stopped.` to every cut-off session that is not closed, including one that was waiting for a permission or an answer (it asks again), so every session picks up its work without you. Messages you queued while the turn ran are stored with the session and survive the restart (a queued image is kept as a file in the plugin's state, under `uploads/<session>`, and read back when it is sent): a cut-off session gets them in the same continue prompt, after the restart line, and any other session keeps them queued as before. A queue too long to store with the session (over 64 KiB as JSON) is written to `uploads/<session>/queue.json` instead and read back on start. A prompt taken off the queue stays stored with the session until it goes to the agent; the transcript line of a prompt is written right before it is sent and marks it sent. A turn cut off before that point gets its prompt back: an agent that exits or a cancel puts it back at the front of the queue instead of sending it (a close drops it with the queue), a turn that reaches the send while the plugin shuts down does not send, and after a restart the session sends it as it was, without the restart line, since nothing was cut. A prompt whose transcript line was written counts as sent, so a restart never sends it twice; a restart in the instant between that line and the send loses it. `CLUBMATE_AGENTS_SEND_HOLD` holds a turn before that point in tests.

When a turn ends with a network error ("No response from API", "Connection refused", `ECONNREFUSED`, "Can't reach the API server", "No internet route", "Unable to connect to API ("), an overload or a rate limit in a session that is in AFK mode or belongs to a live orchestration (never a night session), Clubmate sends it `[Clubmate] Your turn ended with an error (<reason>). Continue the task from where you stopped.` 1 min later (`CLUBMATE_AGENTS_NET_RETRY_AFTER` overrides the minute), then after 2, 4 and 8 min and every 10 min after that, up to 8 times; the transcript shows a notice with the attempt ("Network error; retrying in …", "Claude is temporarily overloaded; retrying in …"). A turn that ends without an error resets the count. While a retry is pending, the parent is not woken for the child's error; once the retries run out, the session stays in error with a "…; stopped retrying" notice and the parent is woken as for any error. Any other session stays in error; send it a message to continue. Pending retries live in memory and are lost if the plugin restarts.

AFK mode is for when you step away. Turn it on with the AFK item in the composer options menu of a top-level session, or tell the agent you are away ("я афк") and it turns it on itself with `agents.afk on=true`; "я вернулся" turns it off. The record keeps who turned it on in `afkBy`: empty when you did (the composer menu, the phone, `cm` outside an agent session, `agents.afk-default`, `agents.new afk:true` from you, a cron job or a trigger), the session id when an agent did (`agents.afk` or `agents.new afk:true` from a session); you turning it on clears it, an agent turning it on again leaves yours. Both read the same everywhere except [connect requests](#needs-you): only AFK you turned on connects a path without asking. While it is on, each prompt of that session and of all its child sessions tells the agent to work without asking you, make and note its own decisions, hand large work to child sessions and subagents, and finish with one short report of commits, decisions and open questions. Turning it on while a turn runs also adds the instruction to that turn and to the running turns of the session's child sessions (steering), so they don't wait for the next prompt. The instruction is not shown in the transcript. `agents.afk-default on=true|false` sets whether new top-level sessions you start start in AFK mode: yours from the app, the phone, `cm`, another plugin, a graph run, or a cron job or trigger you made (or a plugin made), not one an agent starts outside its own tree (`startedBy`, above), which starts without AFK unless its `agents.new` says `afk: true`, and then `afkBy` names that agent. `agents.new` takes `afk: true|false` (from any caller, e.g. a cron job's or trigger's args) to start that session in or out of AFK mode from its first prompt, so an unattended session doesn't depend on the agent turning AFK mode on for itself; `finish: ask|merge` sets a top-level session's finish mode instead of the default, but only from you (the app, the phone, the CLI without `--agent` outside an agent session): agents, a plain `cm` from an agent's shell, cron jobs, triggers and other plugins get `invalid_params`, since merging into main without asking stays your call.

From the Agents sidebar you can run a task in its own worktree end to end: press "New in worktree…", type a branch name and press Start (or Return) to start a session in a new `.worktrees/<branch>` made from the workspace's worktree (as `agents.new` with `branch`). When its turn is done, "Review changes" in the session header opens the diff; with Finish set to "Merge to main" the agent squashes its branch into `main` itself once the tests pass.

Claude in Chrome: Claude Code started through the SDK, as Clubmate starts it, ignores its "enabled by default" setting, so a Claude session gets the `claude-in-chrome` tools only because Clubmate passes `--chrome` (`_meta.claudeCode.options.extraArgs` on `session/new` and `session/resume`). It does so while `claudeInChromeDefaultEnabled` is true in `$CLAUDE_CONFIG_DIR/.claude.json` (or `~/.claude.json`), the setting `/chrome` → "Enabled by default" writes, and only for a session you started yourself or a child of one: never for a service session, nor for one a cron job, a trigger, a graph run or another agent (`startedBy`) started, nor their children, since those run unattended in your signed-in browser.

"Context" (⌘I) in a Claude session's header shows what the session sees instead of its transcript, to find out why it did not do something you expected: the CLAUDE.md files it loaded (user, project, memory and nested ones, with their current text), the skills, MCP servers (and the ones that need a sign-in or failed), hook context, subagent types, tools and deferred tools it was offered, each with how often it used it; unused ones are muted. It reads the session's own Claude log (`$CLAUDE_CONFIG_DIR` or `~/.claude`, `projects/*/<agent session id>.jsonl`) and follows it as it grows; it shows the current state, not its history. "Transcript" (⌘I) goes back.

The status bar shows how much of the Claude subscription is used: `5h 42% ↻19:03 · 7d 81% ↻Wed`, the 5-hour and weekly limits with their reset times, in the warning colour once Claude warns about a limit and in the danger colour once it is reached. The numbers come from the rate-limit reports Claude attaches to agent replies, so they appear after the first reply of an agent session, are kept across restarts, and miss usage from Claude outside Clubmate until the next reply; a limit disappears once its reset time passes. The tooltip names when they were last updated; `agents.usage` returns them.

Agent mode is a cooperative guard for well-behaved agents, not a security boundary: any program running as your user can reach Clubmate directly.

Inside an agent session `cm` sends `CLUBMATE_AGENT_SESSION` as the `caller` of every `command.run`, `ui.event` and `ui.key`, with or without `--agent`, so a plain `cm` from the agent's shell reads as that session and not as you. A test-mode app sends a key press's caller on the `ui.event` and `command.run` its buttons send while it handles that press, so `cm ui key opt+1` on a Connect or Land card is refused like the button. A caller counts only when it is a session of the core it reached; Backlog and Graphs treat a caller they cannot check, because the session list failed, as a session. Then `agents.connect-answer`, `agents.land-answer`, `agents.land-commits`, `agents.repo-leave`, `agents.repo-fix`, `agents.folder-remove`, `agents.folder-sheet`, `agents.repos-sheet`, archiving and cleaning up (`agents.archive-plan`, `agents.archive`, `agents.archive-sheet`, `agents.restore`, `agents.cleanup-plan`, `agents.cleanup-sheet`), `agents.mode`, `agents.config`, setting `agents.finish-default` or `agents.afk-default`, answering open items (`agents.open-answer`, `agents.open-no`, `agents.open-later`, `agents.open-backlog`, `agents.open-convert`) and `graphs.approve`, `graphs.continue` and `graphs.trust` refuse it, and so do the buttons that are yours: in Agents sending a message, answering a permission or a question, the open items card, mode, config, delete and settings; adding or changing a backlog task; approving or trusting in Graphs. `agents.afk`, `agents.notify`, `agents.cancel` and `agents.handoff` reach only the session itself and the ones it started, as with `--agent`. Backlog changes are the session's and a prompt carries its "not from the user" line. It turns on no agent gating: hidden commands such as `agents.close` still run, and so does any other button. Test instances stay open: `scripts/test-app.sh` runs `cm` with the variable unset, and a `cm` aimed at an instance with its state dir sends a session id that core doesn't know, so both are you there, while an agent session of that instance is refused like any other. Pairing and companion access (`remote.pair`, `remote.cancel-pair`, `remote.enable`, `remote.set-port`, `remote.revoke`, `remote.set-push-relay`, `remote.set-report-inbox`, `remote.report-upload`) have no workspace to check a session in, so they refuse any caller and `--agent`, also the unknown id of a `cm` aimed at a test instance: run them there through `scripts/test-app.sh`. This is a guard against an agent answering in your place by accident, not a boundary, for `cm ui key` as for the other two: a process with your uid can unset the variable, make up an id or talk to the socket itself.

## Status

One map for both clients: the glyph (SF Symbol), the word and the tone of each state a session shows. The agents plugin decides the state once: `status` in `agents.sessions` and in the session header (`header.status`), with the parent states `childrenRunning`/`childrenWaiting` (`childStatus` in `agents.sessions`) and `asks` (a top-level `done` session with `needsYou`), `asksParent` (a `waiting` child with `asksParent` in `agents.sessions`), `review` (a `done` session with `review` in `agents.sessions`), and `open` (a `done` session with `openCount`, see [Open items](#open-items)). The Mac (sidebar, header, Graphs) and the phone copy this table and never pick a glyph or tone on their own.

| State | Glyph | Word | Tone |
|---|---|---|---|
| `running` (a turn runs, a command the agent sent to the background still runs after its turn, the agent works on its own when that command ends, or a `done` session waits for its own reminder) | `play.circle` | elapsed ("4 min"), for a reminder "next check 19:12", else "Running" | accent |
| `waiting` (permission or question pending) | `exclamationmark.circle` | "waiting" ("asking" for a question) | warning |
| `asks` (done, its last message asks you) | `exclamationmark.circle` | "asking" | warning |
| `asksParent` (a child's question waits for the session that started it, see [Needs you](#needs-you)) | `arrow.up.circle` (the phone draws `arrow.up` in its glyph circle) | "asking parent" (the phone "Asks parent: <question>", header "Asking parent") | accent |
| `review` (a top-level session whose Finish is not "Merge to main" ended its turn `done` with changes, not marked reviewed yet) | `eye.circle` (the phone draws `eye` in its glyph circle) | "review" (the phone "Review") | accent |
| `open` (done, with open items left; `status` stays `done` and `needsYou` false) | `checkmark.circle` | outlined "3 open" | none, the count in warning ink |
| `done` | `checkmark.circle` | age ("2 h ago") | none (secondary ink) |
| `idle` (no turn yet) | `circle` | "idle" | none |
| `error` (the turn failed) | `xmark.circle` | "exit 1" when the error carries the agent's exit status, else "Stopped"; the session header badge reads "Stopped · exit 1" or "Stopped · error" | danger |
| `closed` | `archivebox`; on the Mac row the glyph of the status it closed from when that was `done` (`checkmark.circle`) or `error` (`xmark.circle`), kept as `closedStatus` (sessions closed before it was kept have none) | "Closed"; when Clubmate closed it (`autoClosed`) "auto" on the Mac row, "Auto-closed" on the phone | none |
| `childrenRunning` (done or idle, a child runs) | `play.circle` | "Waiting for child sessions" | accent |
| `childrenWaiting` (done or idle, a child waits) | `exclamationmark.circle` | "Child session waiting" | warning |

One agent process serves every session of a worktree. When it exits, only the sessions with a turn, a background task or a request open turn `error`; the others keep their status, question and review mark, get no second `agents.turn`, and start a new process with their next prompt.

A failed session's header shows the error in words under the title: "Claude exited with status 1." for an exit status, "Claude stopped: <message>" for an untyped agent error (the `acp error <code>` prefix dropped), a typed failure's own sentence ("Claude is temporarily overloaded."); `error` in `agents.sessions` keeps the raw text. The plugin builds these words once: the Mac gets them in its sidebar and header nodes, the phone as `failure` `{word, badge, line}` in `agents.sessions` (row "exit 1" or "Stopped", header "Stopped · exit 1" or "Stopped · error", the sentence above, shown under the transcript), present only on an `error` session; a phone talking to a Mac that sends no `failure` shows "Stopped" and "Stopped · error".

Under the error both clients offer the same way out, built once by the plugin (`failureActions`): "Sign in" when the agent needs a login, else "Hand off to a new session" when the agent cannot resume the session, else "Retry". The Mac draws them as buttons; the phone gets them as `failure.actions` `[{id, label, icon, command?, args?}]` and shows a button for each action with a `command` the Mac lets it run (Retry → `agents.resume`, Hand off → `agents.handoff`, which opens the new session). An action without a `command` happens only on the Mac: the phone shows it as a line, "Sign in on Mac Studio". While the Mac is offline the buttons are disabled with the same reason as a permission ("Can't answer — Mac Studio is offline").

Clubmate closes a top-level session an hour after its turn ended `done` (`CLUBMATE_AGENTS_CLOSE_AFTER` overrides the hour), together with its child sessions, when nothing in that tree runs, waits or has queued messages, the session itself doesn't ask a question, nothing has open items, a waiting connect request or an open task, or stopped with an error, owns a cron job or trigger (they would be deleted with it), and nothing was logged in any of them for that hour. A node session of a graph run that is top-level (the run was not started by an agent session: cron, a trigger, the Graphs section, `cm`) closes this way only once its run is `stopped` in `graphs.list` or gone from it (`graphs.delete`), since a running run's edges may prompt it again, and then also when it is still `idle` because the run never reached it; the hour still counts from the node's own last activity, and while the graphs plugin can't be asked the node stays open. A node of a run started by an agent session sits under that session and closes with its tree. A child whose parent is already closed counts as top-level here and closes on its own. Sessions started with their own system prompt or tool limits (the voice session, a night session) are never closed this way. Nor is a session in `review`: when a top-level session whose Finish is not "Merge to main" ends a turn `done` and its worktree differs from its first checkpoint (what "Review changes" shows), the plugin sets `review` on it (in `agents.sessions` and the record) and keeps it until you press "Reviewed" in its header on the Mac or the phone (`agents.reviewed session=…`, remote); the hour then counts from the press. Its next turn, a close or an error clears `review`, and the turn after decides again. A top-level session whose last message asks stays `asks`; a child's `asks` holds nothing back, since it was for the session that started it (see [Needs you](#needs-you)), which got it when the child's turn ended and has since finished. A session with open items stays too, since an hour would send them all to the backlog; once they are answered or aged out the hour counts as usual. `review` is not Needs you and sends no push. A child Clubmate closes after its branch was merged is marked the same way. Such a session carries `autoClosed` in `agents.sessions` until it is reopened; the Mac sidebar row reads "auto" and its header "Closed automatically an hour after it finished", the phone "Auto-closed" and "Closed automatically". The transcript logs the close with actor `clubmate`.

Clubmate deletes a closed top-level session 30 days after anything last happened in it (`CLUBMATE_AGENTS_DELETE_AFTER` overrides the 30 days; `0` turns it off), together with its child sessions, exactly as Delete does: transcripts, checkpoint refs, uploaded files and the search index entries go. It waits while any session of that tree is open, any of them was active in those 30 days, or one holds a task that hasn't landed; night sessions go with their next night instead. A session whose parent is still kept goes with that parent.

A turn of Claude Code can end while a command it sent to the background runs on (`run_in_background`, e.g. `gh run watch`); Claude Code wakes the agent when the command ends, without a prompt. The plugin keeps such a session `running` from the end of its turn through the agent's own follow-up: a background task starts with the `backgroundTaskId` in a tool result's `_meta.claudeCode.toolResponse`, agent output (a message, thought or new tool call) with no turn running starts the follow-up, and the follow-up ends at its result (the `usage_update` with a `cost`). At a turn's end the plugin checks the session's `claude` process: when no shell runs under it any more, the task ended during the turn and the session is `done`. Stop (`agents.cancel`) on such a session stops waiting: the session turns `done`, and a follow-up in progress is cancelled. The phone and the Mac show it as any running session; nothing on the clients changes.

A session whose turn ended `done` but that owns an enabled one-shot cron job (`in`, `at`) prompting itself (`agents.prompt` with its own id, "check the CI again in 5 minutes") is shown as `running` too: in `agents.sessions` (`status`, `group`, `active`, no `needsYou` even when its last message ends with `?`), in its header and on its sidebar row ("next check 19:12", the earliest such job; `activity` in `agents.sessions` carries the same title with `at` when its turn ended, and there is no `turnStartedAt`). `reminding: true` in `agents.sessions` marks it: no turn runs, so cron and triggers do not count it as busy and its reminder fires. Its turn still ended `done` for the agent (`agents.turn`, `agents.wait`), so a prompt starts a new turn rather than steering one; but its `done` or `asks` notification is not posted, and a parent counts it as a running child. The cron plugin sends the workspace's reminders whenever its jobs change, and again after the agents plugin restarts (`agents.reminders {reminders: [{session, at}]}`, only from the cron plugin); when the job fires, is deleted or paused the session shows `done` again. A recurring job (`every`, `cron`) never makes a session look running.

The session header's meta line repeats the sidebar row's detail, which the row often cuts: AFK, the notify policy ("Input only", "Muted"), and the activity (`15 min` while running, the parent states' words, the last change's age otherwise), leaving out a state the header already shows as a badge (waiting for you, asking, Stopped, a review's progress), then the context fill. The plugin builds both from one `sessionRow`. The phone's session header shows the same activity after the state from `agents.sessions` (`Running · 15 min` from `turnStartedAt`, or a reminder's `activity` title).

Waiting is amber (warning) everywhere: sidebar, Graphs, header badge ("waiting for you"), phone. A failed turn is `error`, never `done`. An internal error (`-32603`: untyped, or typed `incomplete_tool_call` or `no_result`; never in a night session) is retried once in the same turn ("The turn failed; retrying once"); only when the retry fails too does the session end in `error`, so a turn that recovers on the retry is `done`.

## Repos card

An orchestrator with a task shows the Repos card as the last thing in its transcript, under its latest report: a `repos` node ([SDUI](sdui-protocol.md#node-types)) the plugin renders from `task` on every change, not written by the agent. It isn't in the Code chat panel. The plugin decides everything in it and the client draws the fields.

- Header: "3 repos", the counts ("1 merged · 1 failed · 1 waits"; several open pull requests read "2 PRs open, in order"), `feat/<slug>` "in each" while open. "1 failed" is danger, "1 ready to land" warning while a Land request is out, the rest muted.
- A row: its place in the order (equal `order` shares a number), repo name, how it lands with its `source` as written by the agent, its state. An AFK-connected repo reads "pull request · connected while you were away", whatever its rule. Words: `merged · PR #87`, `on its branch`, `PR #412 open`, `ready to land`, `failed`, `landing`, `running`, `asking`, `left unlanded`, `waits`, and `waits for 2` (a place in the order), `waits for its report` or `waits for task pause, landing there`; a repo that finished and waits reads `on its branch · waits for 2`. PR numbers come from the child's report (git is the only source of pull request state), so "PR #412 open" can be stale. Amber only for what needs you: `ready to land` with a Land request, and `asking` when the child itself needs you.
- A failed row opens by itself: the failing `tail`, Ask it to fix ↩ (`agents.repo-fix`), Open its session, Open in Code, Leave it unlanded… (`agents.repo-leave`, after a confirmation), and "Leaving it unlanded holds ads-management too." when repos after it haven't landed. Any other row with something to show opens on a click, with the actions that apply. A closed orchestrator offers none. Open in Code runs `git.worktree-switch` on the child's worktree, moves Code to its folder with `editor.code-root` and goes to Code; the title pill follows.
- The card is folded to its header unless a repo failed or a Land request waits. Folding or opening it holds until those change: a new failure or a new request opens the card again, even one folded by hand. Folding or opening a row holds until its state or the time it entered that state changes. The plugin decides this once and sends `collapsed`, `open` and the keys that hold a choice (`foldKey` on the card and on each row), so the Mac and the phone keep the same rule; the Mac's choice is kept per session until the plugin restarts, the phone's while the app runs.
- The header pill "3 repos · 1 failed ▾" opens the card, scrolls to it and gives it the keys, from anywhere in the transcript. The card's keys are in [shortcuts](shortcuts.md#repos-card-agents-section).
- Footer: "Lands in order 1 → 2 → 3 · a repo waits until the ones before it landed", with no order line while every repo shares one place. Once every child is done it reads "All children done · 3 worktrees left behind" with Archive task… at its end.

## Open items

A decision or an offer an agent leaves at the end of a turn is an open item, not a question: the turn ends `done`, nothing waits, and the items sit under the report until you get to them. A question the agent cannot go on without stays AskUserQuestion, amber and `waiting`. An agent always ends a turn with some text, often after the tool call, so the Mac draws the card after the turn's last message, not where the call was; the phone docks it above the composer.

- Posting. An agent posts with `agents_open_items` (`agents.open-items`) for its own session; a user or a test instance may name any `session` with `cm command run agents.open-items --args '…'`. Each item is `{kind: "decision", header, question, quote, multiSelect?, options: [labels], descriptions: [lines]}` or `{kind: "offer", label, description?, quote}`: `header` of up to 12 characters, 2 to 4 options, a description for each (Other is always offered), and `quote`, the report's sentence. The manifest schema allows no objects inside array items, so the tool takes labels and descriptions as two parallel lists; stored and sent to clients an option is `{label, description}`. A bad item fails the whole call with a message that says what to fix.
- Limits. The open set holds 3 decisions and 4 offers across the session's turns. Anything beyond that is filed in the backlog at once, one task per item with the quote and the session's id, and its task id is in the entry's `overflow`, so the agent doesn't have to count.
- Record. Items live in the session log (`open-items`, with `open-items/changed` for what happens to them), so they survive restarts. Ids are `oi-N`, unique in the session. State is `open`, `answered`, `no`, `backlog` (with `task`, the backlog id) or `handed`. Clients get one transcript entry per turn: `{kind: "openItems", items: [{id, kind, header, question, label, description, quote, options, multiSelect, state, answer, task, number, at}], overflow: [taskIds], later}`.
- Report markers. In the text it sends (`agents.transcript` and the Mac's message nodes, not the log), the plugin puts a circled digit after the sentence that holds each item's `quote`, in the last agent message of that turn that has it: the card's item 1 is ①. An agent often writes a line after the tool call, so earlier messages of the turn count too. No match, no marker. The digit stays plain text; the Mac's prose draws ① to ⑳ over it as the digit in warning ink in a ring, in any message, keeping the line height and what a copy gives.
- `agents.sessions`: `openCount` (each unanswered item is 1, omitted at 0), `openDecisions` and `openOffers` (how many of them are decisions and offers, omitted at 0), `openSince` (the oldest one's time) and `group: "open"`. `status` stays `done` and `needsYou` false. With a pending permission or question the session is `waiting`; its items stay and show again afterwards. For edges and `agents.turn` an open session is `done`. A prompt you type leaves the items open. A posted item you already closed in a way the agent hasn't heard yet (its answer waits in the queue, or you said no and no turn has started since) is not posted again and its old id comes back, so an agent that re-offers something during the turn your queued answer waits on leaves no card behind; the same text is compared, ignoring case. Once the agent has the answer, the same item is a new one.
- Answering (user only, also from the phone). `agents.open-answer {session, answers: [{item, option?, options?, other?}], offers: [ids], note?}` closes those items and starts one turn, queued when a turn runs: `Answers: Lists → Add an SDUI prop; Grouping → Its own group; do: ⌘/ screen`, then the note. `agents.open-later {session}` keeps them open and sets `later` on the entry, which folds the card; ignoring the card is the same. `agents.open-backlog {session, items?}` files one task per item, all when `items` is empty. `agents.open-no {session, items?}` closes them and starts no turn; the session's next turn begins with `None of these: …`. `agents.open-queue {workspace?}` lists `[{session, title, worktree, updatedAt, items}]`, oldest first. `agents.open-convert {session}` prompts the session to post what it left in prose.
- Aging. An item still open 7 days after posting (`CLUBMATE_AGENTS_OPEN_AFTER` overrides the 7 days) or when its session closes, by hand or any other way, becomes a backlog task, with a line in the session. A deleted session takes its items along. While the backlog can't be reached the items stay open and the plugin tries again.
- Closed sessions. Closing normally empties the set, so this is for an item that could not be filed: an offer answered with `agents.open-answer` starts a new session in the closed session's worktree (the main checkout when that is gone) and returns `{session}`, a decision goes to the backlog with its answer.
- Children. A child's items never reach you while its parent exists and is open: they close as `handed` and the parent is prompted with `[Clubmate] Child "…" (agt_…) left open items: …`, the items in the text. It answers the child with `agents_prompt` or carries them into its own `agents_open_items`. With the parent gone they stay on the child as yours. Graph nodes and cron or trigger sessions behave as top-level sessions.
- On the Mac. One card holds the open set, at the entry of the newest turn that has open items, under its report: `Open after this turn`, the outlined count (`openCount`), `2 decisions · 3 offers · answer any time; nothing waits`, each decision numbered with its header chip, quote line and radio or check rows, the offers as one `Next — tick what you want me to do` item, what was already answered or filed as a muted line, `+N more went to the backlog: #a, #b`, then Send answers, Later, To backlog and No to all, which closes the items with no turn, so a card nobody wants to act on goes away in one click. Older entries show one line once all their items are closed. Later folds the card to one line with Show; a waiting session hides it until it stops waiting. In a form of at most 560 pt the items are an accordion, as in the question card. The plugin keeps the picks, the keyboard cursor and the folded state per session in memory (`sessionUI.open`), the form autosaves into them, so the card, the queue and the composer see the same picks: a message typed while something is picked goes out as `open-answer` with the text as its note, and the composer's placeholder says so (`Message Claude… — your answers go with it`). Keys are in [shortcuts](shortcuts.md#open-items-agents-section-card-or-open-queue).
- Report numbers. The card's numbers and the report's circled digits come from one function (`openNumbers`): decisions in posting order across the entries that still have an open item, every offer the one number after them, since the offers are one item on the card. An entry with nothing open has no digits. The same numbers go out as `number` on the items of the `openItems` entries and of `agents.open-queue`, omitted where there is none. They are worked out when sent, not stored, and an entry whose numbers changed counts as changed, so a phone that fetches only what changed gets the new ones. The phone draws the field on its card, its queue and the Next row; for a Mac that doesn't send it the phone numbers a turn's items itself, each by its place in the turn.
- Open filter. The chip `Open N` in Agents (⌥O; `N` sums `openCount` over the workspace's open sessions, children included) turns the sidebar into the sessions with open items or `mayAsk` and the main pane into the queue, oldest first: `Open · 7 items in 3 sessions`, Send N answers (⌘↩, answers are sent per session, one turn each), one card per session with Open session (↩), an accordion across all of them. A `mayAsk` session gets a card with Turn into items (`agents.open-convert`). Picking a row moves the cursor to that session. The row shows the outlined count in place of its age; `mayAsk` shows `may have left a question` in the faint ink. The status bar reads `· 5 open`, the sum of `openCount`.
- Phone. The Mac lists groups in `groupOrder`; the phone shows its Open section above Running, oldest `openSince` first, and folds a card whose entry has `later` or whose session has a turn running. Its row reads "Done · 2 decisions, 3 offers" from `openDecisions` and `openOffers`, and it fetches `agents.open-queue` only while its Open screen is shown; and a message typed while picks are unsent goes as `note` of `agents.open-answer`. Its card's footer reads No to All, Later, Send answers; No to All asks nothing: the card turns into "Closed 5 items · Claude hears “none of these” next turn" with Undo, and `agents.open-no` goes 5 s later, or at once when a message is sent first; To Backlog stays in the session header's •••.
- Safety net. A turn that posted no items, is not `waiting` or `asks`, and whose last paragraph matches `your call|up to you|should it|should I|if you want|let me know if|want me to|если хочешь|решать тебе|на твоё усмотрение|могу сделать|скажи, если` gets `mayAsk` in `agents.sessions` until its next turn. It will fire falsely, so it is only a faint hint.

## Needs you

A session needs you when a permission or a question is pending (status `waiting`), when a top-level session's turn is done and its last message asks a question (`asks`), when a connect request waits on a session whose turn has ended, or at any time while a `Land ‹repo›?` request or a failed repo of its task waits (see Connect requests and Landing below). A child session's `asks` is for the session that started it, not for you, so it never needs you on its own. So is a child's pending question (AskUserQuestion, a form `elicitation/create`; a URL one such as a sign-in stays yours) while the session that started it exists and is not closed: the child shows `asksParent` (`asksParent: true` in `agents.sessions`), sends no push and no Mac notification, counts as running for its parent's `childStatus`, and the parent is woken with `[Clubmate] Child "…" (agt_…) asks you, not the user: "<question>" (agents_elicitation request elicitation-N). Answer it yourself; ask the user only when the decision is theirs.` The parent answers with `agents_elicitation` or asks you itself. With the parent gone the question needs you. A child's pending permissions always need you. A session that stopped with an error does not need you unless a connect request or a landing waits on it; it shows as Stopped. A child that stopped with an error doesn't need you on its own either, but a repo child's failure makes its orchestrator need you. Nor do [open items](#open-items): they have their own count and group. Nor does a night session (`night` in `agents.sessions`, a service session of the nightly self-improvement run): its permission requests are rejected and its questions declined at once, and a last message ending with `?` doesn't count. Nor does a session that is `running` because its background task runs on, even when its last message ends with `?` (see § Status). The ending `?` is a fallback: a top-level Claude session is told, through its system prompt (`_meta.systemPrompt.append` on `session/new` and `session/resume`), to ask questions that need your answer with AskUserQuestion, which arrives as a pending question (`elicitation/create`) and needs no guessing, and to post what stays open at the end of a turn as open items (§ Open items). Child sessions are told only the second part; their questions go to the session that started them. Nor is a session the voice plugin started with its own `systemPrompt`: it gets that text instead. The agents plugin computes this once and sends it as `needsYou` in `agents.sessions`; a top-level turn that ends with `asks` is also posted once as a `needs-input` notification (see [notifications](notifications.md#in-the-app)). The Mac sidebar's "Needs you" filter (a top-level session that needs you, or whose child waits for permission), the Mac status bar's "N need you" and the phone (its "Needs you" list, waiting counts, session groups and glyphs) show exactly these sessions; neither client derives it on its own. The phone falls back to the same rule only for a Mac whose Clubmate does not send `needsYou` yet.

Connect requests. A session asks to connect repos to the workspace with `agents.connect-repo {repos: [{path | url, reason, landsBy, source}]}`. The call returns at once with `{request, status: "pending", next}`, since a tool call times out and a request has no limit; the session ends its turn and Clubmate prompts it with the answer. The request is stored on the session's record as `connectRequests` (`[{id, from?, fromTitle?, at, repos: [{path?, url?, name, reason, landsBy, source, facts, state, folder?, note?}]}]`, `facts` being what `git.repo-facts` returned), so it survives a restart and never times out; a pending one also keeps the session from auto-closing. A child's request lands on its top-level ancestor, the orchestrator, skipping closed ones, with the child in `from` and `raisedOn` in the child's result; the answer goes to the orchestrator only. The orchestrator needs you once its turn has ended (`done`, `idle` or `error`): its `pending` carries the request ids, `pendingSummary` has `kind: "connect"` ("Connect ads?", "Connect 3 repos?") and the turn end posts `needs-input`, as does a child's request landing on a session that is not running. The user answers with `agents.connect-answer {request, answers: [{path, action: connect | skip | other, otherPath?}]}`, `path` being the repo's path or, without one, its url. Only the user's answer counts: a call with `agent`, with a `caller` that is a session of this core, or through a plugin other than remote or voice, is refused, and no parent's word stands in for it, in `agents.permission`, in a prompt or by turning AFK on for a child. A repo left out of the answer is skipped, not pending, so one answer closes its request; an answer to a closed request is refused with `this connect request was already answered`. One connect answers every pending request for that repo in the workspace, whichever task asked: the repos reached this way read `connected`, and a request with nothing left to decide closes. A closed request prompts its session with one line per repo (`connected`, `skipped`, `failed` with why). A connected repo becomes a folder of the workspace with `addedBy` the orchestrator's title. A `url` connects by cloning (a remote helper url such as `ext::…` is refused when the request is raised; `git.clone`, next to the workspace's first folder under the repo's name, or into `otherPath`): the repo reads `cloning` meanwhile, no longer needs you, and the prompt comes when the clone ends; several urls clone one after another, without holding up the workspace's worktree work, and a clone in flight is followed again after a plugin restart. While the orchestrator itself is AFK (its own `afk`, not a child's) and you turned that on (`afkBy` empty), a path on disk connects at once with `addedAfk`, a notice in its transcript and `status: "connected"`, and needs no answer; a `url` still waits, since AFK never clones. AFK an agent turned on for itself connects nothing: "я афк" in a prompt reads the same as text another session wrote, so the request waits for you like any other. Turning AFK on for a session whose path requests wait connects them the same way, and the request's prompt goes out once nothing in it is left to decide. A session that stopped with an error while a request waits posts `needs-input`, not `stuck`. Otherwise a path that already is one of the workspace's folders reads `connected` at once; a path inside one still gets the card ([Repos in a folder](#repos-in-a-folder)).

On the Mac a waiting request is a card docked above the composer, in the permission family: `request.connectRepo` for the oldest open connect request, else `request.land` for the first repo with a Land request. It answers through the same code as `agents.connect-answer` and `agents.land-answer`. A connect card shows up to 3 repos and folds the rest; each row has name, path, remote, branch and clean state, the agent's reason as a quote, how it lands with its source, and what it brings, neutral. The card has the keys until the composer is clicked ([shortcuts](shortcuts.md#repo-requests-agents-section-or-code-chat-panel)); ticks and other folders are kept per request until the answer. Reason and source come from agents, so they render as text, never as links or controls. A repo not on disk reads "Clone … into …?" and the button "Clone and connect"; other folder there picks the parent of the clone. On a Land card Review… opens the child's review in Code, or its diff when it has none, and leaves the request open, Merge prompts the child, and Leave it unlanded… confirms first and says what it holds. The header badge reads "1 to land". The phone gets the same nodes as `request` and `repos` on `agents.transcript` (left out for agent callers, with no task or no request), and calls the same commands, so its words can't drift; see [Multi-repo tasks on the phone](#multi-repo-tasks-on-the-phone). `pendingSummary.onMac` stays true on `connect`, `land` and `failed` for a phone built before these cards, which shows the summary with "Answer on the Mac"; a phone that has the cards uses it only when the Mac sends no `request`. A question the orchestrator asks wins over a failed repo: `pendingSummary` is then the question, or nothing when its text is unknown, so the phone can answer it.

Landing. A task is declared with `agents.task` on the orchestrator and its `task.repos[]` are in landing order, each with `name`, `order`, `landsBy`, `source`, `state`, `for`, `session`, `pr`, `tail`, `request`, `capped`, `into`, its default branch, `fixAsked` and, once a Land request is out, `branch` and `commits`; the plugin decides all of it and clients render it. `state` is `waits` (not started or held, `for` says what for: a repo's name, "ads, which failed", "ads, left unlanded", "task pause, landing there", "its report"), `running`, `asking` (the child waits for an answer), `failed` (the child's session stopped with an error or it reported `failed`, with `tail`), `ready` (the work is done, and in ask mode a `Land ‹repo›?` request is out), `onBranch`, `prOpen`, `merged` or `left`. A child that is done reports with `agents.task-report {state, pr?, tail?}`: `ready`, `failed`, `onBranch`, `prOpen` or `merged`. Nothing lands before its `ready`, and a session of its that ends a turn without one reads `waits` for "its report". The landed states count only in their turn: `onBranch`, `prOpen` and `merged` are refused before Clubmate's land prompt, so `prOpen` can't clear a Land card, while a settled repo ignores any report, `ready` after `merged` included, and the result's `note` says so. A repo lands only after every repo with a lower `order` has landed, which means `merged` or `onBranch`; repos with the same `order` don't wait for each other, and a failure, `left` or an open pull request holds the rest. One task lands per folder at a time, across the app: a repo holds its folder from `ready` until it is `merged`, `onBranch`, `prOpen`, `failed` or `left`, and the holder is stored on the task, so it survives a restart, and `agents.task` declared again without a repo that holds its folder is refused, so the hold can't go with it; a second task reads `waits` for "task ‹slug›, landing there" and goes on by itself. A closed child reads `left` and gives the folder up, and so does a closed orchestrator. With `landsBy: branch` the repo goes to `onBranch` when its turn comes, with no prompt. Otherwise the orchestrator's finish mode decides. Merge: the plugin prompts the child to land by its repo's own rules, once; the prompt is stored as sent before it goes, so a restart never sends it twice, one lost in that moment shows as `waits` for "its report", and a landing cut off by a restart is continued like any turn. A queued land prompt is not stored with the session's queue: at plugin start a repo whose child hasn't begun its land turn gets it again, unless git shows it landed, which also goes for any prompt about to be sent. A land turn that ends with no report and nothing in git makes the repo `failed`, with a `tail` saying so, and it keeps the folder until the child reports or the user leaves the repo. A check git couldn't finish (git was killed or ran out of time) decides nothing: the repo stays as it is and is checked again at the next pull request check. Ask: a request with `kind: "land"` in `pendingSummary` ("Land ads?") and its id in `pending`, with no timeout, answered by `agents.land-answer {request, action: review | merge | leave}`, the user's word only, as for a connect request. `review` returns `{session, worktree}` for the client to open and changes nothing, `merge` prompts the child saying the user agreed, `leave` records `left`, which frees the folder and holds what depends on the repo. In any mode `agents.repo-leave {session, repo}`, the user's word only, does the same for a repo that failed or is held, and `agents.repo-fix {session, repo}`, also the user's word only, prompts the child of a failed repo with its `tail`, once per failure (`fixAsked`; a second press does nothing, and the row drops the button until the repo fails again); the repo leaves `failed` when that turn starts, also for a child that stopped with an error. The child is what lands, since only it has its repo's rules: if they say nothing it commits on the branch, stops and reports `onBranch`. Its first prompt names the rule the orchestrator declared for its repo and asks it to correct that rule with `agents.task` before it starts when the repo's instructions say otherwise or nothing (then `branch`), so the Land card says what it will do. After the orchestrator declares it, a repo's rule changes only through `agents.task` again: from the orchestrator, which declares the whole task anew, or from that repo's child, which names only its own repo and changes its `landsBy` and `source`, never the order; a child naming another repo, or any other session, is refused, and neither a land prompt nor a report rewrites the rule. The orchestrator's prompts carry the task's rules once it has a task: change no repo itself, and its finish mode is not for the task's repos, so it never merges, squashes, pushes or deletes a child's branch or worktree. Declaring the first task while a turn runs also adds those rules to that turn (steering), since an orchestrator usually declares and runs the whole task in its first turn, which started with only its finish mode. An agent session that starts a repo child for a repo its task doesn't list is refused with "declare it with agents_task first", since a repo child without a task has nothing to report its landing to. A repo connected by AFK for this orchestrator reads `capped`, and its land prompt asks for a pull request at most in this task, even if its rule is merge. The cap is advisory: it holds per orchestrator and lives in the prompt, so another orchestrator's task on that folder isn't capped, and a capped child's `merged` counts when git shows it. A folder with `addedAfk` that the user hasn't `seen` is never fetched, by `base: "default"` or by these checks: the user hasn't looked at its config yet, so a child starts from the local default branch with a notice, and a pull request there moves on once the folder was seen. `merged` holds only if git shows the change in the default branch, `origin/<default>` or the local one: the branch tip is an ancestor, or `git merge-tree --write-tree <default> <branch>` gives exactly the default branch's tree, which is exact to the byte and covers merges and squash merges, and the branch has a net change from its fork, so a commit and its revert or an empty commit prove nothing; a conflict or a failure is not proof, and no merge driver, merge attribute, merge setting or replace ref of the repo takes part; a branch with no commits of its own never counts, measured from the merge base recorded at `ready`, so a deleted child doesn't blank it. A claim git denies stays not merged and the result's `note` says so. Git is the only source of pull request state, no `gh`: a `prOpen` repo moves to `merged` when git sees it. Its repo is fetched every 5 minutes while a task has one (`CLUBMATE_AGENTS_PR_CHECK` overrides that) and stops when none is left, on any child's report for every `prOpen` repo of its task, and at plugin start. A closed orchestrator's task is neither fetched nor checked; if the session is reopened the next check picks it up. A Land request or a failed repo makes its orchestrator need you at once, running or not, since nothing in its turn answers it: a wake from a child doesn't take the card out of Needs you. The child shows its failure as usual, the parent's `pendingSummary` has `kind: "failed"` ("ads failed") and `taskSummary` reads as in [Task tree](#task-tree), which the sidebar shows instead of a child count. An orchestrator with an open task and its children aren't auto-closed until every repo is `merged`, `onBranch` or `left`, and a repo child is never cleaned up after a merge. A hand-off carries the task, its finish mode and its children along: after an orchestrator's, the old session holds neither the task nor a request and its children's `parentSession` names the new one, so the tree, `taskSummary`, wakes and the counts follow the live owner, and after a repo child's, the new child takes over the repo with its state, `ready` and folder. A folder holding a repo of an open task can't be removed.

Graph runs. A graph run needs you while one of its steps waits for your approval or one of its edges holds a firing past its round cap (see [agent graphs § Needs you](agent-graphs.md#needs-you)). The graphs plugin decides it and hands it over (`agents.run-needs`, only from the graphs plugin); `agents.sessions` lists such a run as its own entry next to the sessions: `kind: "run"`, `id` the run id (`gr_…`), `title` the run title, `run: {id, title, number}` (`number` the run's place among the workspace's runs of its graph; the phone titles the row "Review gate · #4"), `status: "waiting"`, `needsYou`, `needsYouSince` (when the step began to wait or the firing was held), `group: "needsYou"`, `pending: ["step-<node>"]` with `pendingSummary {kind: permission, tool: execute, text: <command>, role: <the step's role>}` for a step (the phone's row reads "Squash into main wants to run `git merge…`"), or `pending: ["cap-<edge>"]` with `pendingSummary {kind: question, text: "<From> → <To> ran N of N rounds"}` for a cap. Its appearing publishes `agents.changed` (`status`), its going away (answered, continued, stopped, removed) `agents.changed` `resolved` with that request and `requestKind` `permission` (both post a `permission` notification, so the phone drops it), and it is in `removed` of the next delta. A run counts once: the Mac sidebar's run row reads the text ("Tests wants to run make test") in warning ink, opens and counts once under Needs you whether its node sessions are top-level or under the session that started the run; the status bar's "N need you" (which reads "N runs need you", "1 run needs you", while everything that needs you is a run), the bell's pinned items ("Permission · Run make test" or "Question · Tests → Coder ran 2 of 2 rounds", the run title under it; it opens the run in Graphs, as does its macOS notification, and the graphs plugin's own `notify.post` for the run is folded into it) and the phone's Needs you list (a run row opening the run) count the entry like a session. A run's node session that waits for permission itself still counts on its own. The entry is answered with `graphs.approve` or `graphs.continue`, never `agents.permission`; the voice assistant leaves run entries out.

A [night session](#self-improvement) never needs you: its permission requests are rejected at once and its offers wait without asking.

Groups. The plugin also sends each session's `group` in `agents.sessions`, the section the phone lists it in: `closed` for a closed session, else `needsYou` when it needs you, else `service` for a service session, else `running` while its status is `running`, else `open` while it is `done` with open items, else `done`. A parent is lifted to its most urgent child's group (any depth, after lifting the child): to `needsYou` always, to `running` or `open` unless the parent is a service session; the order is `needsYou`, `running`, `open`, `done`, `closed`, `service`, so a closed parent with a running child lists under Running and a done parent whose child waits for permission under Needs you. The phone puts each top-level session (with its children nested under it) in its `group`'s section; it never works out the group itself, and falls back to the session's own group without lifting only for a Mac that does not send `group` yet. Each section's count and its workspace row ("N running · N closed") count these top-level sessions per `group` (children count with their parent, not on their own, as in the Mac sidebar's groups) and "N waiting" from every session that needs you. `active` in `agents.sessions` is true for a session that is `running` or `waiting` and not a service session; the Mac status bar's "N agents" counts these.

Oldest first. A session that needs you also carries `needsYouSince` in `agents.sessions`: when its pending request was made, or when its turn ended with the question. Every list of sessions that need you is ordered by it, oldest first, ties by session id: the Mac sidebar's "Needs you" filter (a top-level session counts with the oldest request in its subtree, and its worktree group, when shown, with its oldest session), the bell's pinned items and the phone's "Needs you" list across workspaces and Macs.

A session that needs you is never folded. In the Mac sidebar the worktree group, the Service group, the graph run and every parent above it are expanded while it needs you, whatever the user folded. The exception is a parent with repos, which folds and keeps that row pinned under it (see [Task tree](#task-tree)). On the phone a subagent or child that asks is a nested row under its parent, one step in (24pt) with no separator between them, never hidden in a folded group.

### Needs an answer

A question card whose fields are all AskUserQuestion's questions (`choice` or `multi`, each with its `<key>_custom` Other, none `required`) needs an answer before Send: a picked option, a ticked option, or text in an open Other row. Text in a closed Other row isn't sent, so it doesn't count. The plugin decides it and sends `needsAnswer` on the entry's `elicitation`; on the Mac the form's `needsAny` carries it. Any other form (`text`, `number` or `boolean` fields, an MCP form with its own `required`) sends as it did. Skip stays enabled on every card and means "none of these, go on"; on the Mac the footer says so next to it ("Skip answers “none of these” and ends the turn", "Skip ends the turn" when that doesn't fit). A single question a pick answers has no Send.

## Task tree

A session with a task (`task` in `agents.sessions`) or with a pending connect request has its repos as children in the Mac sidebar, in landing order, each named by its repo with a folder glyph. The plugin builds these rows; single sessions and ordinary children keep their rows. A repo's row is its child session when it has one, otherwise an item with no session behind it that selects the orchestrator (`repo:<orchestrator>:<path>`, skipped by ⌃⌘↓/⌃⌘↑). Other children of the session follow the repos.

| Row | Word | Glyph | Tone |
|---|---|---|---|
| `merged` | merged | `checkmark.circle` | success |
| `onBranch` | on branch | `checkmark.circle` | none |
| `prOpen` | PR open | `arrow.triangle.pull` | none |
| `left` | left | `minus.circle` | none |
| `failed` | failed | `xmark.circle` | danger |
| `asking` for you, or a `Land ‹repo›?` request | asking | `exclamationmark.circle` | warning |
| `asking` for its orchestrator | asking | `arrow.up.circle` | accent |
| `running` | elapsed ("4 min", "2 h"), else running | `play.circle` | accent |
| `ready` with no request | queued | `circle` | none |
| `waits` | waits | `circle` | none |
| a repo with a pending connect request, once the session's turn ended | connect? | `exclamationmark.circle` | warning |
| the same while the turn runs | connect? | `circle` | none |

Every word fits in 9 characters. The parent's detail is its summary, also `taskSummary` in `agents.sessions` (a pending connect alone shows it on the Mac row only): "2 need you" counts child sessions that need you, Land requests, repos asking to connect, the parent's own permission or question and, once any of those is there, failed repos; failed repos alone read "1 failed"; with nothing to do it reads "8 repos". A summary that wants you is amber on the parent's detail and glyph, unless the parent itself stopped with an error; the failed child stays red.

The parent is open by default while its session is open. It folds the first time you open it after its task is finished (every repo landed or left, no turn running, nothing waiting); unfolding it by hand holds. A folded parent keeps the rows that need you, failed or are asking pinned under it (`pinned` on a tree item), which is the only case where a session that needs you sits under a folded row.

A repo child of a task with two or more repos shows a crumb above its header: Agents / ‹task› / ‹repo›, "2 of 8", and ⌃ ⌄ buttons with ⌥↑ ⌥↓ moving to the repo before and after it that has a session. There is no wrap-around: at the end the button is disabled. While the repo waits, its header carries a badge with what for ("waits for internal-auth").

The title pill reads "ads +1" in the accent ink while a folder an agent added was not seen (`seen` on the folder); opening the title picker marks them seen (`workspace.folder.seen`). Until then `git.worktree-new` on a folder AFK added and nobody has seen runs none of the repo's hooks or filters while it checks out, included config too, so LFS files stay pointers; if it cannot list them, or the checkout fails, it removes the worktree and the branch it made for it and reports the error. That covers the checkout only: later git commands in that worktree, an agent's or a plugin's, read the repo's config as usual and can run them. Two plugin commands that would run them are refused in such a folder until it is seen, with "it was connected while you were away and you haven't seen it yet: open the title picker to look at it first": `git.branch-switch`, and `git.worktree-remove` without `discard` (its `git status` and `git worktree remove` can run clean filters), so a child in such a folder isn't checked for a merge at all: it stays open and done with `cleanupOnSeen` on its record, and the cleanup runs again when the folder is marked seen (`workspace.folder.seen`), closing the child if it is still open and removing its worktree and branch if it was merged; a child closed in between is cleaned up too. A connect that AFK did is a system row in the orchestrator's transcript (`repo` and `path` on the notice): neutral, an AFK badge, its time and what happened (opened a PR, or a PR at most), and one action, Remove from ‹workspace›…, which opens the Remove folder sheet. Once the folder is gone the row says so and the action goes. On the phone the notice stays a plain line.

**Archive task.** Archive Task… on the parent row menu and Archive task… in the Repos card footer show once every repo merged, stays on its branch, has a PR open or was left, and no session of the task runs; the sheet (`agents.archive-sheet`, slot `agents.sheet`) is never automatic. It comes from `agents.archive-plan {session}`, read now, and says per repo what happens to the worktree and the local branch and why. A worktree goes when it is clean; ignored files don't count, except secret files (below). One with uncommitted files, a secret file or detached commits, or that an open session outside the task works in, stays, with what it would lose (`.env.local would be lost`) or the session it closes and a Remove it anyway box; ticking one turns Archive red with the Remove button's words (`Archive · lose 3 files, .env.local and 1 commit`, `Archive · closes ‹session›`), plain until then. One that holds a submodule or a repo, is locked (it says why), one a running session of any workspace works in, one open in Code in any workspace or one that couldn't be read stays with no box. A local branch goes under `git branch -d` rules: it must be proven in the default branch (by ancestry, or for a squash by `git merge-tree`, `landed` on `git.worktree-state`; `git branch -d` decides, and only that exact proof, read again right before, deletes a branch it calls not fully merged, and only while it still points at the tip seen; no repo hook runs), and an open PR from the child's last report, a remote branch of that name, the repo's stay rule or a worktree that stays keep it. Since git can't delete a branch a worktree holds, the sheet says "it stays with its worktree" where the board says Delete branch. Remote branches are never touched. Cron jobs that run in a worktree that goes are named, and pause; a worktree that then stays resumes them. "Also remove ‹folder› from ‹workspace›" is offered, unticked, for a folder this task added that no other open session or task uses, except the first folder; it goes through the Remove folder path. Close sessions only moves the sessions to Closed and touches nothing else. `agents.archive {session, choices}` runs it: a worktree goes only when `choices` name it with the `seen` of the plan, and each is read once more right before it goes (tip, merged, cost), checked for holders, sessions and tasks as well as terminals of every workspace (`git.worktree-sessions`, which also sees a shell that `cd`ed in, the editor's own Neovim aside), and passed to `git.worktree-remove` with what you saw; anything that changed or failed is kept and listed on a sheet titled `“‹task›” is archived`, with Close. Refused while a session of the task runs, waits or is queued, and while a repo hasn't finished. Everything here is the user's only: the commands and the sheet's actions refuse an agent, and `git.branch-delete` takes the agents plugin's word alone.

**Clean up worktrees.** "Clean up worktrees…" in the title picker's footer and folder actions, and "Clean up 163…" on a folder's Stale row, open one sheet (`agents.cleanup-sheet`, `agents.cleanup-plan {folder?}`), never automatic. It lists every worktree that is stale or made by hand, once even when two folders share a repo, except a live one, the main or default checkout (in a bare layout, the worktree on the default branch), one open in Code in any workspace and a child's in an open task that hasn't settled, which Archive task deals with, in groups by what removing them costs, each row in one group, so the groups add up: `191 · 182 stale, 9 by hand`.

| Group | Goes | Ticks |
|---|---|---|
| Merged and clean | worktree and local branch | ticked, group box |
| PR merged, remote branch deleted | worktree and local branch | ticked with proof, group box |
| Remote branch deleted, not found in main | worktree; branch stays | none |
| No commits for 30 d, all pushed | worktree; branch stays | one at a time |
| Unpushed commits or uncommitted files | worktree; branch stays | one at a time |
| Made by hand | worktree | one at a time |

Proof for the second group is the child's merged report, which git checked, or the change in the default branch, by ancestry or `git merge-tree`; unpushed commits beat the report, and only that exact proof beats them, as a squash leaves its branch unpushed by definition. There is no "PR closed without merging" group, since git can't tell it. A branch still on the remote, an open PR or a stay rule keeps the branch in any group, and the row says so. Ignored files (node_modules, build output, caches) are regenerable: they cost nothing, so a row with only those is ticked like a clean one. A secret file is the exception: a row holding one stays in its group unticked and says so (`keeps .env.local`), the group says how many (`2 worktrees with secret files, not ticked`), and its group box or its own box ticks it; nothing else that costs anything is ever ticked for you. A secret file is an ignored file named `.env`, `.env.*`, `*.pem`, `*.key`, `.npmrc` or `.netrc` that isn't inside an ignored folder (`node_modules/` counts as a whole, so a package's test key doesn't hold its worktree); the list lives in `secretNames` in `plugins/git/index.go` and `secrets` on `git.worktree-state` ([SDUI protocol](sdui-protocol.md)). Clean up, Archive and Remove folder share it. Rows that can't be read, hold a repo or are locked have no box, and a locked one says why. A row with an open session that isn't running isn't pre-ticked, stays out of the group box and names the session its own box would close, like a child just restored; a session that opened after the sheet read the row keeps it. The row and the button turn red with what is lost, in the Remove words (`Remove 138 · lose 3 files, .env.local and 1 commit`; two or more secret files read `2 secret files`); the button is plain while nothing is lost and waits for every ticked row to be read. A filter or a folder narrows the list, and only what shows counts: a tick on a hidden row removes nothing.

The plan comes from the cached index and one `git.worktree-unpushed` per folder, so 400 worktrees open at once. Cost is read only for what is shown or pre-ticked, 24 at a time, at most 8 at once in git, and a row moves group when its numbers say so. Rows go one by one through the Archive path: re-read right before it goes, holders of every workspace, terminals and Code checked, a change or failure kept and listed on a sheet with Close. Cron jobs that run in a listed worktree are named, and pause when it goes; one whose worktree stays resumes. The sheet and its actions are yours only.

**Restore.** `agents.restore {session}` (Restore on a closed task's row menu and footer, `reopen` in `agents.sessions`) brings a closed session and its closed children back, read-write, and returns `{restored, stayed: [{session, title, why}]}`. It is refused, with the reason under the footer, when the session's own worktree is gone, its folder left the workspace or the worktree was recreated on another branch than the one it closed on (`closedBranch`). A child that can't return stays closed and is named under the footer, so a task with one removed worktree still comes back. Any other closed session keeps Reopen, which brings back only that session, under the same refusals. The board's "recreates a worktree from its branch" isn't built.

**Remove folder sheet.** Remove from ‹workspace›… (the AFK row, and the title picker through `agents.folder-sheet`) opens one sheet over the window in any section, drawn by the plugin in the slot `agents.sheet` (`docs/sdui-protocol.md`). It says what removing changes, from `agents.folder-impact`: sessions, worktrees, graphs, hooks, instructions, the trust that is kept per repo, the Cron jobs that run in the folder, each by name, and that Backlog and triggers are untouched. A row with nothing to say stays away, except Sessions, Cron jobs and Untouched. Removing never deletes files, except the worktree whose box you tick, through `git.worktree-remove`. A worktree shows what its box costs: files that are lost, secret files (a single one by name; other ignored files cost nothing), detached commits on no ref, or commits that stay on its branch. Only the first 5 worktrees, those with open sessions first, have a box, and one holding an initialised submodule or a repo inside has none and says why, since what's in there can't be counted. Remove (⌘↩) is plain until a ticked worktree would lose something, then it is red and names it (`Remove · lose 1 file, .env and 1 commit`, without the workspace's name or the sheet's note, so the cost is never cut); ⎋ cancels. It is disabled while a session of this workspace runs, waits or is queued in the folder, a session of any workspace does so in a ticked worktree, while a task of this workspace still lands there or an unsettled task of any workspace has its child in a ticked worktree, or when it is the workspace's last folder, and the sheet says what holds it and follows it live. If a ticked worktree changed since the sheet read it, nothing is removed and the sheet shows the new cost. The check marks the folder and the ticked worktrees as leaving under a short lock, then the folder goes and the worktrees after it, so a refusal or a failed folder loses no files, and until it ends a new session, a handoff or a prompt there is refused while everything else carries on. A worktree is read once more before its teardown: if it would lose more than you saw, a terminal of any workspace is open in it, or git fails, it stays on disk and the sheet, now titled `internal-auth left ads`, gives its path and why, with Close. What teardown itself writes doesn't count. If Cron stops answering after the sheet read it, nothing happens and the sheet says so; pressing Remove again on the sheet that now says Cron couldn't be read goes on without pausing. Removing pauses the Cron jobs with a reason (`internal-auth left ads`); if the folder can't be removed they resume. Triggers stay as they are. The sheet and its buttons are yours only: `agents.folder-sheet` and its actions refuse an agent.

With two or more git folders the pill names the folder Code shows, "ads / internal-auth ▸ main". ## Repos in a folder

A workspace folder that isn't a git repo but holds repos, like `~/develop/kufar` with 79 repos one level down, has no worktrees, branches or repo children of its own. The git plugin finds the repos in it (`git.repos-in`, [SDUI](sdui-protocol.md)): two levels down, skipping hidden directories and `node_modules`, never looking inside a repo it found, and stopping after 3 s with what it has. The Add repos sheet lists them with boxes, newest commit first, nothing ticked, with a filter field, a box that ticks every row the filter shows and the age of each repo's last commit; a repo that is already a folder has no box and reads "in ‹workspace›". Ticks stay while the filter changes. Add N to ‹workspace› (⌘↩) adds the ticked repos as folders in the sheet's order, after the folders the workspace has, so the parent stays first; they are yours (`addedBy` empty) and seen, so no "+N" and no AFK rules. ⎋ cancels. A walk that ran out of time says so under the list.

The sheet opens by itself once per folder, the first time the workspace's window opens with that folder, or when the folder is added while it is open, and only while no other sheet is up; the plugin remembers it (`reposOffered/<workspace>/<folder>` in its storage), so cancelling ends the offer. After that "Add repos from ‹folder›…" stays in the title picker's footer next to "Add a folder to ‹workspace›…" (`picker.addRepos`), as long as the folder holds a repo that isn't a folder yet. A folder whose repos are all added is offered nothing.

A file shows once, under the deepest folder that holds it: with `kufar` and `kufar/ads-management` both folders, search and the docs list read `ads-management/main.go`, not `kufar/ads-management/main.go`. Code's file tree is Neovim's, of the one folder Code shows, so with `kufar` shown it still lists `ads-management/` as a directory.

An agent connecting a repo inside one of the workspace's folders (`agents.connect-repo` with a path under `kufar`) still gets the card, like any repo the workspace doesn't have: the agent can write inside that folder, so a `.git` it made there could carry config that runs commands, and only your yes or the Add repos sheet adds it. While the orchestrator is AFK the AFK rule applies instead.

## Review progress

A session that opened or received an open review (see [nvim integration § Review changes](nvim-integration.md#review-changes)) shows its progress. The agents plugin follows the bus topic `editor-nvim.review`, keeps every open review and its comment states until its `closed` event, stores them with the last event's seq in its storage (`reviews`) and on start resumes the topic from that seq, so progress and card states survive a restart of the plugin. When a review closes, its last comment states are written into the log of every session that holds its Review card, looked for among its opener, its recipient and the sessions in its worktree (`review/closed {id, states}`), and leave the storage, so a closed review's card keeps its final states for good; on start, states stored by an older version for a review that is not open are moved into the logs the same way. `editor-nvim.ready` (editor-nvim started again and holds no review) closes every open review the same way and gives each session the newest review whose `opener` or `recipient` it is: `reviewProgress {id, reviewed, total, open, sent, text, short}` in `agents.sessions`, `text` reading `review N/M · K` (K open comments) and `short` reading `N/M · K` (`N/M` without open comments). The phone row shows `text` in place of the age of a done, idle or review session ("review 5/15 · 1" instead of "2 h ago"). The Mac sidebar row shows `short` there under the review glyph (`eye.circle`) instead of the status glyph, so it fits the 6 em a list keeps for a detail; a running, waiting or failed row keeps its own words and glyph. The Mac session header adds the badge `Review N/M · K issue(s)`, after Send `Review M/M · N comments sent`, success once every file is reviewed, and the button "Open review" ⌘R, which shows that review in the Code section: its nvim tab current, nvim focused (`editor-nvim.review-show {id}`). Closing the review drops the field, the row text and the header. Each review payload also publishes `agents.changed` kind `review` for its opener and recipient, which is how the phone learns the text changed. Neither client works the text out itself; the phone has no review panel. "Review changes" in the header and "Full diff" on an edit card pass the session and the turn, so the review reads `Before turn N` and the session is its opener. On the Mac "Review changes" opens a popover whose "Compare with" picks session start (the first checkpoint) or a local branch (its merge-base with the worktree, the default branch listed first); the session remembers the pick until the plugin restarts, and the phone's button uses it.

## Search

`agents.search query=<text>` (remote, agent) finds the workspace's sessions, closed ones included, by title and by what was said in them: your prompts and the agent's replies, not thoughts or tool output. It is a case-insensitive substring match of the whole query. Up to 50 sessions come back, the ones whose title matches first, then the most recently updated, each with up to 3 hits `{kind: title|prompt|reply, turn, snippet}`; a snippet is up to 120 characters from about 12 characters before the match (from the line start when that is nearer, else cut at a word), whitespace collapsed, as plain text (markdown marks and link targets dropped). The plugin reads the text from its own session logs (`sessions/<id>.jsonl`) once, in the background after it starts, and then only the lines appended since the last search, so typing stays fast with hundreds of sessions. The Mac and the phone render this result and never match or rank on their own.

On the Mac the Agents sidebar has a "Search sessions" field above the filter chips. While it holds text the chips and the tree give way to the results: a row per session (status glyph, title, when it was last updated) with its prompt and reply hits under it; clicking either opens the session. Cleared, the tree comes back. On the phone the session list is searchable the same way. Not done: jumping to the matched turn, and a key that focuses the field.

## Service sessions

A session started with its own system prompt or tool limits is a service session: the voice session (`systemPrompt`, `disallowedTools` or `mode` on `agents.new`, accepted only from the voice plugin) and the night sessions of [self-improvement](#self-improvement), which the agents plugin starts itself. Such a session has `service: true` in `agents.sessions`. The Mac sidebar lists it in one "Service" group (its count at the right) at the bottom of the tree, outside the worktree groups and after Closed, folded by default; the phone in a "Service · N" section after Closed, folded too. It is not counted in "All" or "Running", nor in the Mac status bar's "N agents" (`active` is false), and its `group` is `service` (see [Needs you](#needs-you) § Groups). While it needs you it counts under "Needs you" and is never folded: on the Mac its group opens and its count turns warning, on the phone it moves to "Needs you". A session a service session starts with `agents.new` is not its child: it is a top-level session of yours, in the workspace's root, with your defaults, and it is selected like one you started. `model` on `agents.new`, from any caller (an agent through MCP, the user, `cm`), does not make a service session either: the session, a child included, keeps its parent, the user's settings, its group, advisor and worktree, and switches to that model right after `session/new`. A resume restores the model the session last ran on, so a later pick in the model menu sticks. When the agent offers no such model (or no model choice), the transcript gets a notice "Model <name> is not available" listing the offered ones, and the session runs on its current model. `firstMode` on `agents.new` (from the user or Backlog's Start agent only, which refuses anyone but the user and passes the caller on, so a session of any workspace is refused here too; an agent, a plain `cm` from an agent's shell or another plugin gets `invalid_params`) does not make a service session: it is the mode the session starts in instead of the worktree's remembered one, applied once on `session/new`; a resume takes the worktree's mode like any session.

## Self-improvement

Once a day Claude reviews its own day, changes how it works and tidies each project's memory. In the morning you get a short report and can undo any change. It is off by default: Settings → Agents → Self-improvement (`self.enabled` in the plugin's storage). While it is off no session gets the self and no night runs. Turning it off during a night cancels the running session and ends the night; what already landed stays. The repository stays too, so turning it back on continues. Once there is a prompt or a skill, a second row appears with Reset (confirmed), which empties the prompt and removes the skills. Reset keeps `lessons.md`, the reports and the memory patches, and does not touch memory.

**The self** is a git repository in the plugin's state dir (`self/`): `prompt.md` (at most 6 KB, appended to the system prompt after the plugin's own text), `skills/<name>/SKILL.md` (at most 5, delivered as the local plugin `self`, so a skill reads `self:<name>`), `lessons.md` (hypotheses and rejected changes, never sent to sessions), `memory-patches/<date>/<workspace>.patch` and `reports/<date>.md`. Every ordinary session gets it, children and graph nodes too; service sessions don't, and it does not make a session a service session. It holds no scripts, hooks or settings. A blank `prompt.md` counts as no prompt. A running session keeps what it has; a change reaches a resumed session the next time it attaches.

**The night** starts at 04:00 local time, on the plugin's own timer. If the Mac slept through it, it runs on the next core start or wake, but only before 08:00; later the night is skipped. The next digest reaches back to the last night that finished without stopping early (`self.digestedUntil`; `self.lastRun` only keeps a night from running twice), so a skipped or failed night loses nothing. `cm command run agents.night-run` starts one now, in the background (`self-improvement is off` while the setting is off, `a night is already running` during one). Each night:

1. Digest. Go collects, per non-home workspace, the sessions updated since then: your prompts, the agent's final replies, and facts from the log (cancelled turns, denied permissions, failed tools by name, repeated Bash commands). Tool output, thoughts and fetched pages are left out. Capped at 8 KB per session and 64 KB per workspace. All digests empty: nothing runs, no session and no report.
2. Sleep. One session per project with a digest and a memory dir, one after another, titled "Sleep: <workspace>". Its sandbox holds that project's digest, memory and undone cleanups and nothing else, and it may read the project's folders. It merges, removes what is stale, checks facts against the code and shrinks. Night sessions have no tool that deletes, so it removes a file by writing it empty: `agents.self-declare` drops empty memory files before it commits, except `MEMORY.md`, since an empty index more likely means a mistake than a cleanup. Memory means `~/.claude/projects/<escaped folder>/memory/` of your workspace folders, or `autoMemoryDirectory` when set. Applying is all or nothing per project: if a memory file changed since the sandbox was made, that project's sleep is dropped and comes back the next night.
3. Improve. One session, titled "Night review", in the most recently opened non-home workspace, after every Sleep. Its sandbox holds a copy of the self and all digests, and no memory. It checks whether a recent change's problem repeated, and reverts that change if so; then it picks at most two patterns that cost you the most and edits `prompt.md` or a skill, with a hypothesis in `lessons.md`. No clear pattern, no edit.
4. Apply. A night session calls `agents.self-declare` after each change, which commits its sandbox. Only declared changes count, and only once the session has ended; a crash or a timeout applies nothing from that session.
5. Report. See below.

**Limits.** While applying, whatever the agent did, on each commit and again on what it landed as, since a merge can change it (renames are off, so an edit can't follow a file): only `prompt.md`, `lessons.md`, `skills/*/SKILL.md` and, for Sleep, memory `.md` files may change; `prompt.md` over 6 KB or more than 5 skills is dropped; a skill is read from the commit and again as it landed, reverts and undo included, and its frontmatter may hold only `name` and `description` (it can have none), and one with shell syntax (`` !` ``, a code fence with `!` in its info string), a substitution (`$` directly before a letter, digit, `_` or `{`, since Claude Code substitutes `$ARGUMENTS` first and the parts then join into shell syntax) or a control or invisible character anywhere (a bare `\r`, any Unicode space but the plain one, a BOM, zero-width characters, invalid UTF-8; `\t` and `\r\n` are fine) is dropped, because Claude Code honours `allowed-tools` and `hooks` there and runs that syntax; a commit that removes a `Rejected by the user:` or `Undone from session` line from `lessons.md` is dropped; at most two commits touch the prompt and skills per night (a revert doesn't count and is applied first). What is dropped is listed in the report. While running, a night session is confined by the plugin: it starts in `auto` and is set to `default` before the first prompt, and it refuses the turn if that fails. It has only Read, Grep, Glob, Edit and Write, Sonnet, 60 turns and no Claude Code settings. Its allowlist covers edits in the sandbox, reads in the sandbox and (Sleep) the project's folders, and `agents.self-declare`; every other permission request is rejected at once, so nothing waits for you, and a form or URL question is declined too. Rejected requests aren't logged, but the report counts them as `Refused: N`, so an escape attempt, or a rule that stopped matching, can't pass for a quiet night. A sandbox holds no `.git`: the git dir sits beside it and Go names it explicitly, so a session can't plant a hook or a config. Each session has 30 minutes (`CLUBMATE_AGENTS_NIGHT_SESSION_LIMIT`) and the night 60 (`CLUBMATE_AGENTS_NIGHT_LIMIT`). A session at its limit ends only that session; a failure, the night's limit or turning the setting off ends the night, which then notifies you, with a report when something landed. A restart mid-night does the same on the next start: it lists what landed since the night began and saves the report, with undo from any chat, since the Improve session is gone. `prompt.md` must hold behaviour only, never a project name, path, code or secret: the Improve session sees all digests, so this rule is a prompt instruction plus the diff in the report.

**Report.** The plugin writes it after Apply, since only it knows what landed: "Night review" in the Improve session, at most 10 lines plus the diffs of `prompt.md` and skills, saved as `reports/<date>.md`. What was refused, dropped or skipped comes first, at most 3 lines so it can't push out what changed, and a diff over 4 KB ends with how much was cut. A night with nothing to change says so in one line. The notification (`Night review`, with "2 changes", "Nothing to change", or "Nothing landed, see the report" when something was dropped or skipped and nothing landed) reaches the phone like any other. Each change is an open offer labelled "Undo: …", at most 4: one per self edit, one for a revert, one for all of the night's memory cleanup. The card differs from other open items: picks are undone at once with no agent turn (it says "Undo happens at once, with no turn"), and it has no To backlog, since a night session's offers never go to the backlog.

**Undo** has no deadline. `agents.self-changes` lists the changes, newest first, and `agents.self-undo {change}` reverts one (a git revert, or the reverse patch for memory). Both work from any session, so "undo yesterday's change about X" works in any chat; only a night session is refused. An undo that no longer applies says so and changes nothing, and so does one that would leave an unsafe skill; undoing the newer change first gets past that. Every undo records in `lessons.md` who undid it, `Rejected by the user: <summary>` or, when an agent called it, `Undone from session <id>: <summary>`, so Improve doesn't redo it. Sleep never sees `lessons.md`: a project's undone memory changes (the newest 10, each with its summary and patch) reach that project's Sleep sandbox, and only that one, as `rejected.md`, which stays out of what it can declare.

**Night sessions.** Each is a [service session](#service-sessions) that counts as `done` and never under Needs you, even with open offers. Sleep is closed once it is applied, so it moves from Service to Closed; the Improve session stays with its sandbox until the next night that isn't skipped, so you can ask it why it did something. It resumes in `default` or not at all, its mode and settings can't be changed, and it can't be handed off: a hand-off would be an ordinary session in a sandbox that holds every digest. That next night deletes the previous night's sessions and sandboxes, with any unanswered offers; undo still works through chat and `reports/` keeps the report. A night session is hidden from `agents.search`, `agents.sessions`, `agents.transcript`, `agents.wait` and `agents.export` for agent callers other than the night session itself, so an ordinary session can't read a digest; you see them in the sidebar as usual. Claude Code's own logs of a night session hold the digests, so `~/.claude/projects/<escaped sandbox>` goes with that sandbox, for its path as is and with symlinks resolved, and nothing else under `projects` is touched.

## Permission card

A pending permission request shows the same content on the Mac and the phone; the agents plugin builds it once: the Mac gets it as the `permissionCard` node ([SDUI](sdui-protocol.md#node-types)), the phone as `card` `{text, title, command?, caption?, options}` on each permission entry of `agents.transcript` (left out for agent callers), with the same option fields:

- Title by tool kind: "Run a command?" for a command; other kinds keep the sentence "Claude wants to edit notify.go".
- The command itself (`command`), in a monospaced box.
- The request's description as the caption, always attributed: "Claude says: Run the notify tests".
- Options in this order: Allow once ⌥1 · Always allow… ⌥2 · Reject ⌥3; "Always reject" (Claude's `reject_always`) sits in the card's ••• menu without a key. These labels replace Claude's own ("Yes", "Yes, and don't ask again for go test commands", "No") only when the request has the usual one option per kind; anything else (plan-mode exits, several allow options) keeps Claude's labels and gets ⌥1–3 in order.
- Always allow… asks first and stores nothing until confirmed: the option carries the `rule` Claude would store and its `scope` ("in shop on this Mac", rules go to the project's local Claude settings on this Mac). The Mac shows them in a popover anchored to the button ("Claude will run matching commands in **shop** without asking, on this Mac, until you remove the rule from the allow list.", the name from the option's `workspace`, bold and never broken at a hyphen; Cancel ⎋ is the default and ↩ cancels too, ⌥2 again confirms) and the phone in its confirm sheet; only the confirm sends the option. Claude does not send the rule over ACP, only its label, so the plugin rebuilds it from that label for commands (`Bash(go test:*)`, one rule per command prefix Claude names); when the label names no command (paths, "similar" commands, other tools) there is no `rule` and the confirm shows the option's label instead.

## Names in the UI

What the agents plugin renders uses names, not ids or command names: a session is its title, a graph run its graph's title; prompts Clubmate sends an agent ("[Clubmate] Child "Fix tests" (agt_…) is done.", the handoff summary) keep the ids for the agent but show without them in the transcript. A detached worktree is labelled "detached · 03a9ff5f". Themed UI is in sentence case ("New in worktree…"); Title Case only in context menus.

## Multi-repo tasks on the phone

The phone draws a task from what the plugin sends and decides nothing about it.

- `agents.sessions` adds, on a session with a task or a connect request: `requests` (the ids waiting for an answer, also while the turn runs, when `pending` doesn't list them yet), `taskRows` `[{name, path, session?, word?, tone?, connect?}]` in landing order, `taskBadge` ("1 to land", "1 PR open"), `archivable` and `taskFinished`. As in the Mac's tree, an open task's children show until you fold it, children that need you or failed and a repo waiting to connect stay pinned, and a finished task folds the first time you open it; this also holds for a session with no task while a connect request waits. A row's `word` is the repo's state; it is left out while its session runs, so the phone shows that session's own line, and a repo with no folder yet reads "not connected yet". `pendingSummary` of kind `connect` adds `lead` and `subject`: "Wants to connect" and the repo or "3 repos". With neither a task nor a request none of these fields is sent.
- `agents.transcript` adds `request`, the `request.connectRepo` or `request.land` node, and `repos`, the `repos` node. It is the Mac's card built with no choices of the Mac's: nothing is under the cursor, the failed rows are open, and it is unfolded while a Land request waits. Rows carry `path` and `session`, and every row that has buttons sends them, open or not, as the node's stack children, read by their `action`, since the phone folds and opens a row itself.
- An AFK notice entry adds `afk` `{detail, remove?}`: the line under the title and "Remove from ads…", which is left out once the folder is gone.
- `agents.land-commits {request}` lists what a Land request would land, up to the branch's live tip: `{commits: [{sha, title}], more, tip, detail}`, at most 50, `detail` the card's line with the live count. Merge stays off until the list has loaded. The phone sends `tip` to `agents.land-answer`, which refuses a merge when the branch moved; the Mac sends none.
- `agents.connect-answer` takes `seen` from the card and `agents.archive` takes `seen` from the plan. Each refuses, changing nothing, when what the user saw changed: the repos still waiting, or a repo's worktree or branch step, what would be lost, the sessions, the holds and the Cron jobs. A client with no `seen` isn't checked; the Mac sends none, since its sheet re-reads the plan itself. The archive plan adds `cronLines`, one line per job that pauses, `cronWarn` when Cron couldn't be read, and `held`. Both commands take `key`: a resend with the same key returns the first success for 7 days, also after a plugin restart, and a run a restart cut off answers that its outcome is unknown. A failure isn't kept. `anyway` and `folder` on `agents.archive` are refused through a plugin: those choices stay on the Mac.

An offline Mac: Connect and Archive queue on the phone, persisted, each with the request or plan's `seen` and a key, and are tried on reconnect and on every later event, so a plugin that comes back or a Mac that gains the command sends them; Undo works until the send starts, and they are listed on the Macs screen too, which needs no session list. A send whose answer is lost goes back in the queue and resends with the same key. A refusal is read from its machine code, never its words: the plugin marks `reason` `stale` (the request or plan moved on, or the workspace or session is gone), `answered` or `unknown` on the error, and the `remote` plugin sends it as the error's `code`. A `stale` or `answered` one drops the item with a note, and one already answered is never sent. Any other error keeps it and backs off, 30 seconds and doubling up to 30 minutes; after 8 tries the item stops and stays listed with the error until dismissed. Once a send has started the item offers no Undo and reads "may have run" (unless no address of the Mac could be reached at all, so the request never left the phone: then it goes back undoable), and queueing the same answer can't replace it, so its key survives. When an earlier try got no answer and the resend is refused, or the code is `unknown`, the note says the outcome is unknown, not that it wasn't sent. A Mac too old for the command gets one note, and the item waits. One archive runs at a time per task; a second is refused while the first runs. Merge, Ask it to fix, Leave it unlanded… and Remove from ads… are disabled offline and never queue.

## Transcript folding

Tool calls are folded on the Mac and the phone: consecutive calls are one actions row, and a call's output opens only when you click or tap it. A completed `agents_open_items` call is not drawn on either client, since the card says the same: the plugin leaves it out of the `transcript` node and sends `hidden: true` on the entry in `agents.transcript`, where the phone skips it. It isn't counted in an actions row and a row left with no calls isn't drawn. An agent reading `agents.transcript` still gets the call. Running, failed and cancelled ones show like any other call. On an iPad or Fold wider than a phone the actions row is a card that names its first three calls ("Show all N" for the rest), as the iPad board draws it; each call's output still opens only on tap. A failed call is folded too: on the Mac its card says Failed and the actions row "N failed", on the phone its title is in the danger colour and its card or group gets a danger border. A user message longer than 40 lines or 4000 characters shows its first 12 lines, at most 1200 characters, with "Show all N lines" ("Show all" when it has no more than 12 lines; "Show less" folds it again); opened, it scrolls inside a capped box, since one row that tall leaves the transcript scrolled past its end, blank. A prompt the voice plugin sent (an entry with `voice {heard, utterance}` in `agents.transcript`) is one right-aligned capsule "🎙 <heard>" (one line, tail-cut) with a chevron; clicking or tapping it opens the prompt JSON, pretty-printed with sorted keys, in a scroll box at most 480 pt tall. A Review prompt (an entry with `review` in `agents.transcript`, sent by the review's Send) is a Review card on the Mac: `Review`, `you · N/M files · K comments`, "Open review" while the review is open, one row per comment (type glyph, `file:line`, the first line of the text, `open` or `resolved` as nrev has it now, or had it when the review closed) and the note; on the phone it stays a plain user message with the prompt text, folded like any long one. A plan card is headed "Plan · n of m" (n steps done); while steps remain its done steps are folded behind "Show done" ("Hide done" folds them again), and a finished plan lists every step. Nothing in the transcript opens itself. The design boards say failures expand; that is overruled. The one exception is the [Repos card](#repos-card), which is no transcript entry but a live card the plugin owns: its failed row opens by itself, the card itself opens for a failure or a waiting Land request on both clients, which overrules `MR-Merge-*`, where it is drawn folded, and the plugin decides both and sends `open`, `collapsed` and `foldKey`, so the phone renders those fields and works nothing out. A closed ```` ```mermaid ```` fence in an agent message is drawn as a diagram (one hidden web view per app renders it to an image, cached by source, theme and width); it keeps its aspect and is at most 480 pt tall on the Mac and 420 pt on the phone, shows its source as a code block while it renders, and stays a code block when mermaid cannot parse it, when it would be over 16384 px on a side or 24 million pixels even at 1×, or while the fence is still open. Clicking it on the Mac opens a sheet with the diagram fitted to the window (pinch, zoom buttons, Esc closes); tapping it on the phone opens it full screen (pinch, double tap to zoom). A Markdown link or code span in an agent message that names a doc (see § Docs in the transcript, `docLinks`) is drawn as a link in the accent colour (a code span keeps its code background) on the Mac and the phone; clicking or tapping it opens the doc, whether or not the doc also has a card. Under the message text each of its `docCards` with `presented` is a card (the same on both clients): a kind icon on an accent-tinted tile, the title on one line (tail-cut), "Document · <rel>", "Diagram · <rel>" or "Artifact · <rel>" under it (middle-cut) and a trailing open glyph; the whole card opens the doc. On the Mac the cards are at most 27 em wide (324 pt at the default 12 pt interface font) and sit side by side while each gets 20 em, else one per row at the full width; the kind word stays and the path is cut in the middle; on the phone they are one per row at the full width. The message's other `docCards` (docs it only mentions) are folded under the presented cards into one muted plate: a docs icon, "N docs mentioned" (the file name when there is one) and a chevron; clicking or tapping it opens the same cards under it, laid out like the presented ones, and folds them again. Folded is the default; on the Mac the state is kept per message until the app quits, on the phone while the transcript is open, and never saved. A change to this rule lands in both clients in the same commit.

## Jumping to a turn

`agents.reveal {session, turn}` opens the session in Agents and scrolls its transcript on the Mac so that turn's prompt is at the top (`anchor` on the `transcript` node, see [SDUI protocol](sdui-protocol.md)); it stays there until you scroll, another turn is revealed or the session starts a new turn; revealing the same turn again scrolls back to it. Every `agents.turn` event carries its `turn` number, so a caller can jump to the turn an event was about. The phone ignores `anchor` for now.

## Docs in the transcript

A tool call is a doc when its status is `completed` and either its kind is `edit` (Write, Edit, MultiEdit) and one of its `locations` or `diff` paths ends in `.md`, `.markdown`, `.mmd`, `.html` or `.htm` (case-insensitive, `pkg/docext`), or it has a `resource_link` whose `file://` URI does. The agents plugin decides this once and sends the first such path, absolute against the session's worktree, as the entry's `doc` field in `agents.transcript`; a failed, cancelled or still running call, a delete or move, and a call on other files have none. The Mac card gets an Open action (before Open in nvim) and the phone's tool row an Open button; both show the doc in the [docs viewer](docs-viewer.md) — the Mac through `openDoc` on `agents.main`, which runs `docs.open {path, session}`, the phone with `docs.read`. Like the rest of a call, Open is inside the folded actions row until you open it. Neither client checks the path itself.

An agent message links the docs it names. When a turn ends, the plugin reads each of that turn's `agent` messages as Markdown and takes every link target that has no URL scheme (`http(s)`, `mailto`, `file:` … are skipped) and every inline code span without whitespace; fenced code is not read. A candidate's `#anchor` is set aside and the rest is percent-decoded, `~/` expanded and joined to the session's worktree when relative; it is kept when that is an existing regular file ending in a doc extension (`pkg/docext`). The entry gets `docLinks: {"<target or code span as written>": "<absolute path>[#anchor]"}` in `agents.transcript` and as the `message` node's `docLinks` prop in `agents.main` (omitted when empty); a message still streaming has none, a replayed transcript resolves them again on load, and thoughts and subagent messages have none. On the Mac a click sends `openDoc` with the value on the message node, which runs `docs.open {path, session}`; the phone's native transcript opens the doc sheet with `docs.read`, and its SDUI transcript sends `openDoc` like the Mac. The same pass gives the entry `docCards: [{path, kind, title, rel, presented?}]` (in `agents.transcript` and as the `message` node's prop, omitted when empty): one per distinct doc, the presented ones first, each group in order of first mention, at most 8, `path` absolute without the `#anchor` (two mentions that differ only in the anchor are one card), `kind` `markdown`, `mermaid` (`.mmd`) or `artifact` (`.html`, `.htm`), `title` the first `# ` heading of a Markdown file or the `<title>` of an artifact, read from the file's first 64 KiB (`pkg/docext`, the docs viewer's title too), else the file name without its extension, and `rel` the path relative to the session's worktree (absolute when outside it). Clicking or tapping a card opens its doc like a link. A doc is presented when the agent called `docs_present` or `docs_open` on it during that turn: the plugin listens to `docs.presented` and `docs.opened` (see [docs viewer](docs-viewer.md#bus)) and writes each as a `doc_presented {path, title?}` event in the session's log at the session's current turn, so a replayed transcript keeps it; one that arrives after the turn ended links that turn again. A presented doc's card gets `presented: true` and the `title` passed to `docs_present` when there is one; a presented doc that none of the turn's messages names is added as a card to the turn's last agent message (a turn without an agent message shows none). Only presented cards are drawn open (§ Transcript folding). These links do not add the doc to `agents.docs`. Clubmate's agent instructions and the `docs_open`/`docs_present` tools ask agents to mention docs freely as a link or `path` and to present only the few the user should look at. Any other link in agent Markdown stays a link on the Mac and the phone only for `http`, `https` and `mailto` (`MarkdownLinkPolicy` in `ClubmateProtocol`, applied by `Markdown.inline`); other schemes (`shortcuts:`, `tel:`, app deep links, a hand-written `clubmate-doc:`) show as plain text, and the phone's URL elicitation Open opens only those schemes too.

An agent message shows the images it names. The same pass over a finished turn's `agent` messages keeps every candidate (link target or code span, resolved the same way) without an `#anchor` that is an existing regular file ending in `.png`, `.jpg`, `.jpeg`, `.gif` or `.webp` (case-insensitive) after symlinks are resolved, and gives the entry `images: [{path, rel, width, height}]` (in `agents.transcript` and as the `message` node's prop, omitted when empty): one per distinct path in order of first mention, at most 4, `path` absolute, `rel` as for `docCards`, `width`/`height` the pixel size when the file's header says it (png, jpeg, gif; omitted otherwise). An image is never a doc link or card; the entry's `imageLinks` maps each target written in the message that names one of its `images` (exactly as written) to that image's `path`, and the client draws it as a link in the accent colour, like a doc link. On the Mac and the phone the images are thumbnails under the message, side by side and wrapping (Mac 4 rows tall, phone 112 pt): the image cropped to the tile from its top, the tile as wide as the image's aspect wants between square and twice its height, a hairline border, a spinner while it loads, the file name under it (one line, middle-cut) and `rel` as its tooltip on the Mac. A click or tap on a thumbnail or on an image link opens the image in a viewer: on the Mac a sheet sized to the window with the file name and `rel`, zoom out / Fit / zoom in and Close (Esc), on the phone full screen (pinch, double tap to zoom, a close button). Nothing folds and nothing opens itself; the thumbnail is the folded state. The Mac reads the file and reads it again once it changed; the phone fetches it once per message when the thumbnail appears, so a later message naming a rewritten file shows the new one, and asks for it with `agents.image {session, path}` (not an agent tool, remote), which returns `{mimeType, data}` (base64) only for a path an `images` entry of that session names, and fails for files over 8 MiB, for a path that no longer resolves to an image file name and for bytes that do not sniff as `image/*`. A file that is gone shows a photo glyph and "Image not found" in its thumbnail and in the viewer.

`agents.docs {session?}` (not an agent tool, remote) lists those docs as `{docs: [{path, session, at}]}`: one per path at its latest `at` (when that call began), newest first, from that session and its subagents' calls, or without `session` from every session of the workspace. It reads each session's transcript, so a dropped one is read back first. `docs.list` builds the docs lists on it (see [docs viewer](docs-viewer.md#docs-list)).

When an agent opens a doc with `docs_open`, the phone shows "Opened <file name>" with an Open button above the composer of that session's screen, for 8 s or until tapped; on any other screen it shows nothing.

## CLI

Inside a Clubmate terminal, `clubmate` is on `PATH` and `$CLUBMATE_WORKSPACE_ID` names the current workspace.

```sh
clubmate open src/main.go:42                       # open in the editor
clubmate command run terminal.new                  # any command or capability
clubmate command run session.read id=ses_123 bytes=4000
clubmate command run terminals.close --agent sessionId=ses_123
clubmate session send ses_123 "make test" --enter
clubmate session read ses_123
```

`key=value` arguments are typed by the command's schema (arrays are comma-separated); `--args '{"…": …}'` takes JSON instead. `--agent` runs the command as an agent would, with the same limits and approvals. The CLI never turns it on by itself.

`clubmate agent` wraps the agent-session commands and always runs them as an agent call, so a session started from an agent session's shell is its child:

```sh
clubmate agent spawn "fix the flaky test" --branch fix/flaky   # agents.new; without --branch it shares your worktree
clubmate agent tell agt_123 "also update the docs"             # agents.prompt
clubmate agent wait agt_123 agt_456 --timeout 300              # agents.wait
clubmate agent output agt_123 --from-turn 2                    # agents.transcript
clubmate agent sessions                                        # agents.sessions
clubmate agent cancel agt_123                                  # agents.cancel
clubmate agent blame src/main.go -L 10,40                       # agents.blame; or a commit: clubmate agent blame HEAD~2
clubmate agent trace main..HEAD                                # agents.trace; default HEAD
clubmate agent export agt_123                                  # agents.export into ./agt_123.clubmate-session
clubmate agent import agt_123.clubmate-session --branch more   # agents.import; without --branch it continues in your worktree
```

A reviewer is a child in your own worktree: `clubmate agent spawn "Review git diff main..HEAD read-only: report bugs, change nothing"` (or `agents_new` without `branch` over MCP), `wait` for it, `tell` it one round of follow-ups, then fix what it found yourself.

## History and attribution

A turn is the unit of history. Before each prompt Clubmate pins a checkpoint of the worktree at `refs/clubmate/cp/<session>/<turn>` (its parent is `HEAD` at turn start), and when the turn ends another one at `refs/clubmate/cp/<session>/<turn>.end`; both carry a `Clubmate-Worktree: <path>` trailer. When the turn ends, the commits it added to the current branch get a git note in `refs/notes/clubmate`:

```
Clubmate-Session: agt_4c67f4de54b9ae47
Clubmate-Turn: 3
Clubmate-Agent: claude
Clubmate-Title: Fix the flaky test
Clubmate-Prompt: <first line of the turn's prompt>
Clubmate-Checkpoint: <checkpoint sha>
```

The turn's commits are those reachable from `HEAD` but not from its start or from any other branch (local or remote), so rebasing onto `main`, merging `main` or fast-forwarding a child's branch claims nothing that is already elsewhere; a squash or merge commit belongs to the turn that made it. A commit keeps its first note. The transcript lists them per turn (`turns[].commits`).

Read them with `git log --notes=clubmate`, `agents.blame` or `clubmate agent blame <file|commit> [-L a,b]` (git blame of the file, only line ranges whose commit has a note).

Limits:
- `git merge --squash` into `main` makes a new commit, noted with the session that ran the squash (the orchestrator), not the child whose branch it was; the child's notes stay on its branch commits.
- Commits the user makes in the same worktree during an agent's turn, or pulls into its branch from that branch's remote, are noted with that turn.
- Rebase and amend drop the notes unless the repo sets `git config notes.rewriteRef refs/notes/clubmate`; Clubmate doesn't set it.
- Notes are local; push `refs/notes/clubmate` to share them, but they carry each session's title and the first line of its prompts, so check them before pushing.

### Agent Trace

`agents.trace rev=<commit|a..b>` (`clubmate agent trace`) returns one [Agent Trace](https://agent-trace.dev/) record (version `0.1`; the spec's own example says `0.1.0`, its schema allows only `major.minor`) per non-merge commit, oldest first, at most 200. Each changed file lists its changed lines grouped by contributor:

- `ai`, with `url` `clubmate://session/<id>#turn=<n>`: written during that agent turn;
- `human`: changed while no agent turn ran in the worktree;
- `unknown`: Clubmate can't tell (a turn still running, or one from before end-of-turn checkpoints existed, two turns running at once, or a commit with no Clubmate history at all).

How: Clubmate replays the commit's parent, the checkpoints of the commit's worktree whose parent is that commit (plus the checkpoint named in the commit's note), and the commit itself as a throwaway chain of commits, then runs `git blame` on the changed lines. A line is credited to the step that introduced it: the step into `<turn>.end` is the turn, the step into a turn's start checkpoint happened between turns, and the last step belongs to the commit's noted turn (when the commit has no note it is `unknown` if the commit has no checkpoints at all, else human with no turn open, the turn when the one open turn has ended, and `unknown` otherwise). The record `id` is derived from the commit, so exporting twice gives the same record.

Limits: edits the user makes in nvim while a turn runs count as the turn's; two sessions working in one worktree at once make their overlap `unknown`; a squash commit is credited to the session that ran the squash; `model_id` and `content_hash` are not filled.

### Resuming elsewhere

Built (one machine): `agents.export session=… dir=…` (`clubmate agent export <session> [dir]`) writes a bundle directory: `session.json` (the record), `log.jsonl` (Clubmate's log) and `refs.bundle` (a git bundle of the session's checkpoint refs and the notes of the commits its turns made, without commits already on a branch, remote or tag; other sessions' notes stay out). It refuses a running session and an existing `dir`. `agents.import dir=… [branch=…] [note=…]` (`clubmate agent import <dir>`) fetches the checkpoint refs into the repository (never overwriting existing ones) and adds the bundle's notes that name the imported session and one of its checkpoints, on commits the repository has and that have no note yet, adds a closed copy of the session with the original transcript (`importedFrom`), and starts a new session in the caller's worktree (or a new `.worktrees/<branch>`) whose first prompt is the handoff brief of the copy. The copy and the new session link like a handoff. This works across worktrees, workspaces and clones on the same Mac; the bundle's checkpoints need their parent commits in the target repository (fetch the session's branch first).

Design (not built): continuing the agent's own conversation instead of a brief. Claude Code keeps it in `~/.claude/projects/<encoded cwd>/<agentSessionId>.jsonl`; the bundle would carry that file (found by globbing for the id), import would place it under the target cwd's project directory and `session/resume` with the old `agentSessionId`, falling back to the brief when resume fails. On another machine the same bundle works once the branch is pushed and fetched; a relay or shared store for bundles belongs with the mobile companion work.

## MCP (Claude Code and other MCP clients)

`clubmate mcp` is a stdio MCP server over the same registry. Every call it makes is an agent call.

Its `initialize` instructions end with "Working in Clubmate" (`internal/mcp/clubmate.md`) and "Tasks across repos" (`internal/mcp/clubmate_repos.md`), both embedded in the binary: split a task, run independent parts as child sessions with `agents_new` and a branch, collect them with `agents_wait`, and use `cron_add` and `triggers_add` instead of polling. Every MCP client that connects gets it, in any project.

- Tools are named after the command or capability with `.` and `-` replaced by `_` (`editor_open`, `workspace_list`, `terminal_close`). A plugin command that provides a capability appears under the capability's name only.
- Every tool takes an optional `workspace` id. It defaults to `$CLUBMATE_WORKSPACE_ID`, then the most recently opened workspace. With `$CLUBMATE_WORKSPACE_ID` set, any other workspace is refused ("workspace … is not this session's workspace (…); agents act only in their own workspace"): an agent acts only in its own workspace.
- If Clubmate isn't running, the tools still list the core primitives, and calls fail with "Clubmate isn't running". The server never starts Clubmate itself.

To connect Claude Code, use **Settings → Agents → Connect Claude Code**. It runs:

```sh
claude mcp add --scope user clubmate -- "/Applications/Clubmate.app/Contents/Resources/bin/clubmate" mcp
```

Development builds register the server as `clubmate-dev` instead, so both can be connected at once. The button is shown only when `claude` is on your login shell's `PATH`; Clubmate looks once per launch, so restart Clubmate after installing `claude`. It says "Connected" only when the registered server runs this copy of Clubmate; if it runs another one, it shows that command and offers "Reconnect" (remove, then add; if the remove fails, nothing is added). Clubmate never edits Claude's config files itself.
