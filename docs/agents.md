# Agents

Agents running in Clubmate terminals (Claude Code, Codex, scripts) can drive Clubmate through one registry of commands: core primitives (workspaces, sessions, processes, focus) and actions that plugins declare (open a file, switch a worktree, close a terminal, ...).

## What agents can do

`clubmate command list --agent` shows everything an agent may run, and `clubmate command describe <id>` shows one command's arguments.

- Workspaces: list, open folders, open the home workspace.
- Sessions: list, start a login shell, type into one (`session.send`), read its recent output (`session.read`), kill one.
- Processes: the process tree of every session and of processes plugins register (agent processes).
- UI: show a section, focus one of its slots or a node in it (`ui.focus`).
- Notifications: `notify.post` shows a macOS notification (needs input, permission, done, stuck, info), skipped while the user looks at the session; see [notifications](notifications.md).
- Backlog: `backlog_list`, `backlog_claim`, `backlog_update`, `backlog_done` and friends share a per-workspace task list with the user; see [backlog](backlog.md).
- Plugin actions marked for agents. Some are generic capabilities, so an agent need not know which plugin provides them: `editor.open`, `editor.quickfix`, `editor.reveal`, `terminal.new`, `terminal.close`.
- Git worktrees: `git.worktrees` lists every git folder's worktrees, `git.worktree-switch` switches a folder to one of them, `git.worktree-new` creates `.worktrees/<branch>` and switches to it (unless `switch` is false), and `git.worktree-remove` removes a linked worktree (never the main checkout or one with uncommitted changes). Both run the repo's [worktree hooks](worktree-hooks.md). Create and remove return `{id}` at once; `git.worktree-op-status id=…` waits up to 1 s for the outcome (the app instead gets the `git.outcome` event).
- Agent sessions: `agents.sessions` lists the workspace's agent sessions with their status, `parentSession`, `childStatus` (a done or idle orchestrator whose child sessions still run or wait), `needsYou` and `needsYouSince` (see [Needs you](#needs-you)), `activity` (`{title, at}` only for a `done` session waiting for its own reminder, see below; a running session's tool calls are never named outside its transcript), `turns` (the turns it has started so far, absent while its transcript is not in memory; Backlog's Owner row says "running · turn 3" from it) and notification policy (`notify`, `notifyEffective`); `agents.sessions session=…` lists only that session (empty when the workspace has none), with `childStatus` and `notifyEffective` still worked out from the whole workspace, and is what the Mac and the phone fetch to check a notification's policy and what the phone fetches to check a permission is still pending before it answers it, so neither client pulls the whole list for those; `agents.sessions since=…` returns `{sessions, removed, cursor, delta}` instead of the list: `since=""` gives every session and a `cursor`, and an earlier `cursor` gives only the sessions whose row changed since then, any field, `childStatus` and `notifyEffective` included (`delta: true`), with the ids `removed` since then; a cursor from before the plugin restarted, or one older than the oldest removal the plugin still remembers (it keeps the last 64 removed ids per workspace), gives every session again without `delta`. The phone's session list and the Mac's agent counts and notifications load the whole list once per workspace and then only what changed on each `agents.changed`; `agents.notify session=… policy=all|needs-input|muted` sets the policy of the caller's own session or one it started (see [notifications](notifications.md#per-session-policy)), and `agents.transcript session=…` reads one session's transcript from Clubmate's own log (`last=true` keeps only the last turn and leaves out the modes, config options and commands catalogs; `compact=true` drops the images in tool calls' content, the image data in user prompts and the commands catalog; tool calls never carry `rawOutput` or `_meta`, which stay only in the log; `since=<cursor>` returns only what changed after an earlier result's `cursor`).
- Child agent sessions (no approval): `agents.new` starts a session, optionally in a new worktree `.worktrees/<branch>` made from the caller's worktree without switching the workspace, and sends it a first `prompt` (`notify` sets its notification policy); `agents.prompt` sends any session a follow-up (added to the running turn when the agent supports steering, else queued) and returns `{turn}` when it started a turn, `null` otherwise; `agents.cancel` stops a running turn; `agents.permission` answers a permission request and `agents.elicitation` a question (AskUserQuestion, an MCP form or sign-in link), but only of sessions the calling agent session started (directly or through its children); the paired phone (through the `remote` plugin) and the voice plugin answer any session's permission requests and questions as the user; `agents.wait` waits without polling until one of the listed sessions stops running (done, waiting for permission, asking a question, error or closed), up to 300 s per call, and returns their status with the pending permission's options; it also returns early with the user's queued messages to the calling session.
- Failed turns: a turn the agent ends with an internal error (`-32603`, e.g. Claude Code's "ended the turn without returning results for tool calls" when the advisor tool is rate-limited) is retried once, 3 s later, within the same turn: the transcript shows a notice and a Clubmate message asking the agent to continue. When every tool call that error lists was still open when a message was steered into the turn (yours or Clubmate's; it interrupts a server tool such as the advisor, which then never returns), the turn is not failed and not retried: it ends `done`. A second failure leaves the session in error, as any other error does. Network errors ("No response from API", "Connection refused", `ECONNREFUSED`) are not retried within the turn, since Claude Code has already waited and retried; see the network error paragraph under orchestration.
- Handoffs: `agents.handoff session=… note=…` continues a session that is not running in a fresh one (same worktree, agent, parent, advisor, notification policy, AFK mode and starting cron job or trigger), seeded with a brief from Clubmate's log (the task, the last prompt and reply, the last turn's stop reason and checkpoint, and how to read the full transcript) followed by `note`; the old session is closed but can be reopened, and each links to the other. Agents may hand off only sessions they started. In the app, a session's menu has "Hand Off to New Session", and a session whose agent cannot resume offers "Hand off to a new session". A closed session that was not handed off carries `reopen` in `agents.sessions`, the action its closed footer offers as `{id, label, icon, command, args}`: "Reopen" (`agents.resume`), or "Hand off to a new session" (`agents.handoff`) when its agent cannot resume; the Mac builds its button from the same action and the phone shows it in the closed session's footer, so neither client decides which one applies.
- Attribution: `agents.blame path=…` (or `commit=…`) tells which agent session, turn and prompt made a file's lines or a commit; `agents.trace rev=…` exports a commit's or a range's changed lines as [Agent Trace](https://agent-trace.dev/) records; see [History and attribution](#history-and-attribution).
- Moving a session: `agents.export session=… dir=…` writes a session bundle, `agents.import dir=…` continues it in another worktree or workspace; see [Resuming elsewhere](#resuming-elsewhere).
- Reminders and schedules: `cron.add` calls a command later or repeatedly, e.g. `agents.prompt` to your own session tomorrow morning; the job is deleted with your session unless `owner: "none"`. Watching your children needs no cron job: Clubmate wakes you when their turns end (see below). See [cron](cron.md).
- Reacting to events: `triggers.add` calls a command when a bus event arrives, e.g. `agents.prompt` to a reviewer session when another session's `agents.turn` ends; `triggers.emit` publishes your own `event.<name>`, which `cron.add` can schedule. See [triggers](triggers.md).
- Unattended runs: a session a cron job or trigger starts with `agents.new` remembers it (`cronJob: cj_…` or `trigger: tr_…` in `agents.sessions`, set by those plugins; anyone else passing them gets `invalid_params`), and each `agents.turn` of it carries the id. `agents.turn` says `finished: true` when the session is done with its work: the turn ended `done` and no child session (any depth) is running, waiting for permission or asking its parent. A parent waiting for its children ends many turns with `finished: false`; Clubmate wakes it when the last child ends, and the turn after that is `finished: true`. So a trigger on `agents.turn` with match `{"cronJob":"cj_…","finished":true}` follows every run of a recurring job without knowing its session id. `agents.turn` doesn't say what the run changed; the triggered session checks that itself (e.g. commits since the last tag).
- Agent graphs: `graphs.run graph=… input=…` starts a team of child sessions from `.clubmate/graphs/<graph>.json` (one session per role, one trigger per edge) and the Graphs section shows the run; `graphs.list`, `graphs.show`, `graphs.stop`. See [agent graphs](agent-graphs.md).
- Open items: `agents.open-items` leaves the decisions and offers still open at the end of a turn for the user, as a quiet card that needs no answer; see [Open items](#open-items).
- Problem reports: `report.send` sends a report about Clubmate itself to its developers, after the user checked it in a sheet; see [problem reports](reports.md).
- Answers on your behalf (asks you first): `agents.answer session=… text=…` shows you the text and, once you allow it, sends it to the session as your own message.
- Web research: `browser.open`, `browser.snapshot`, `browser.click` and the other `browser.*` tools drive a hidden WebKit browser in the app, one set of tabs per agent session, and `browser.handoff` asks the user to solve a captcha or sign in; see [agent browser](browser.md).
- Showing a doc: after writing a spec, plan or report the user should read, `docs.open {path}` (MCP `docs_open`) shows it rendered in a popup with mermaid diagrams drawn; see [docs viewer](docs-viewer.md).
- Testing the app: `testapp.list` lists running test instances and `testapp.call instance=… method=…` calls one of them (see below).

Hidden helpers and commands not marked for agents stay out of reach.

## Import your nvim config

**Import my nvim config** in the command palette starts an agent session in the Agents section that reads `~/.config/nvim` and moves your own keymaps, options, autocmds and plugins into Clubmate's Neovim user layer (`~/.config/clubmate`, or `~/.config/clubmate-dev` for development builds), following the guide bundled at `nvim-distro/skill/SKILL.md`. It skips what Clubmate's defaults already cover and asks you before adding destructive or machine-specific mappings. It needs an open folder workspace and never changes `~/.config/nvim`. The first time Neovim starts in a workspace while `~/.config/nvim` exists, it offers the same import once.

## Testing the app

Agents test Clubmate in their own invisible instances instead of taking over the user's screen. `scripts/test-app.sh start [name]` (name defaults to the branch) launches the Debug build with scratch state, runtime and `XDG_*` dirs under `/tmp/clubmate-test-<name>`, its own core and its own defaults suite, in test mode (`CLUBMATE_TEST_MODE=1`): it never activates, its windows are transparent and ignore the mouse, app-modal dialogs are skipped and every approval is denied. `relaunch [name] [app] [-- app args]` restarts only its app with new launch args (core, state and seed data stay; e.g. after writing `theme = …` to its `state/ghostty.conf`), `stop [name]` quits it and removes the dirs, `list` shows running ones, `cm [name] -- <args>` runs the CLI against one, with that instance's workspace as `CLUBMATE_WORKSPACE_ID`. `start [name] -- --sdui-gallery` shows the SDUI gallery with a core but no workspace. `make gallery-smoke` starts the gallery, takes one snapshot into `build/gallery-smoke` and stops it; it fails when any fixture node crashes the app.

- `ui.snapshot {out, png?, width?, height?}` (CLI `cm ui snapshot --out <dir> [--size 640x800] [--no-png]`): the app draws each of its windows itself (main window with titlebar, popovers, sheets, settings) to `w<window id>.png`, terminals included, and writes `w<window id>.json`: every rendered SDUI node with its frame in window points, its parent, its menu entries, plus every terminal's visible text and native menus listed as text. Flags: `outside-window`, `wider-than-parent`, `overlaps-sibling`, `zero-size`, `truncated` (text nodes, measured). The result's `summary` lists only flagged elements, or `0 problems`. `--size` resizes the main window first.
- `ui.present {target, shown}` (CLI `cm ui present <target> [--hide]`): opens `inbox`, `worktree`, `switcher`, `settings` or the `approval` fixture sheet without a click; menus are never opened, they appear as text in the layout. `card:<node id>` expands a transcript tool card (`--hide` collapses it), and with it the summary row of its group; card ids (`<session>/tool/<tool call id>`) are listed by `cm ui dump` and not checked, so a wrong id changes nothing.
- `ui.key {keys, focus?}` (CLI `cm ui key [--focus <node id>] <combo>...`): `focus` first makes the view under that SDUI node (an id from the snapshot layout; with duplicate ids any match, so prefer a unique one) first responder, e.g. a text field. Each combo then goes to the active key monitors (sidebar trees, the composer), else, when it has ⌘, to the window's key equivalents (view shortcuts; never the app menu), else as a key down and up to the first responder of the workspace window; the result lists the route each combo took (`monitor`, `monitor over terminal`, `shortcut`, `responder <class>`). A combo is `[cmd+][ctrl+][opt+][shift+]<key>`, `<key>` a US-layout letter, digit or punctuation, `return`, `tab`, `space`, `delete`, `esc`, `up`, `down`, `left` or `right`; `cm ui key --focus description o n e opt+return t w o` types two lines. Keys are refused while an alert or any sheet but a plugin's form sheet (`form` with `sheet: true`, e.g. Send review) is open, so they can't answer an approval; with a form sheet up they go to it. While a terminal has focus a combo goes only to the key monitors that pass terminals (a button's ⌘↩) and is refused when none takes it, so keys never run shell commands. The test app never becomes active, so it has no key window: menu shortcuts (⌘N New, ⌘W) are not sent and Tab does not move focus. Run their commands instead (`cm command run backlog.new` focuses the new task field), and focus a sidebar with `cm command run ui.focus section=<section> slot=<section>.sidebar`.
- Over MCP: `testapp.call` proxies `ui.snapshot`, `ui.present`, `ui.key`, `ui.get`, `ui.event`, `command.list`, `command.run` (always as an agent call), `workspace.list` and `workspace.open` to `/tmp/clubmate-test-<instance>`; `ui.snapshot`'s `out` defaults to and must stay inside `/tmp/clubmate-test-<instance>/snapshots`.

The user's own app never answers `ui.snapshot`, `ui.present` or `ui.key`: only a test-mode app registers them, and test mode needs a dev build with non-default state and runtime dirs.

## Approvals

Destructive actions (closing or killing sessions, typing into a session, answering an agent session as you, restarting the editor, killing orphan processes, removing a worktree) ask you first. Clubmate shows an alert naming the action, the workspace, the targeted session and every argument in full, with Allow and Deny. Deny is the default. If nobody answers within 60 seconds, or the app isn't open, the action is refused.

An agent session calling these tools is the parent of the sessions it starts with `agents.new` (Clubmate knows the caller from `CLUBMATE_AGENT_SESSION`, which every agent session has). A child starts with the parent's mode, model, effort and advisor, not the worktree's remembered ones, and at most 8 children of one parent run or wait for permission at once. A prompt an agent sends through `agents.prompt` or `agents.new` is logged as coming from that agent (`agent:<session id>`) and reaches the target with `[From Clubmate agent session "<title>" (<id>), not from the user]` in front, so it never passes for your approval; from an agent without an agent session it is logged as `agent:unknown` and starts with `[From another agent session, not from the user]`. Prompting an idle child also counts against the limit of 8. Agents without an agent session (Claude in a terminal, `clubmate command run --agent`) start top-level sessions and cannot answer permission requests.

A child in its own worktree merges its finished, tested work into its parent's branch in the parent's worktree, never into `main`; a child sharing its parent's worktree, or whose parent is on the default branch, only commits and the parent merges. Children never remove worktrees or branches: once a child's turn ends with its branch merged into the parent's branch and its worktree clean and unused, Clubmate closes the child (it stays listed as Closed) and removes its worktree and branch itself, without asking. A session that has children is told to write to you only the children's questions that need your answer, to answer their permission requests itself with `agents.permission`, and to pass your answers on with `agents.answer` rather than paraphrasing them.

Clubmate wakes an orchestrator when a child's turn ends: once a child is done, ends in an error or waits for permission, and the parent is not in a turn of its own, the parent gets `[Clubmate] Child "<title>" (<id>) is <status>.` (the title's first line, quoted), one line per child in one message when several finish together (within a second, or while the parent's turn was still running). A child the parent already saw through `agents.wait` is not reported again, so an orchestrator that waits on its children is not woken twice. A suspended parent is resumed for the message like for any prompt. Pending wake-ups live in memory and are lost if the plugin restarts.

When Clubmate restarts (an update, a core handover) while a turn is running, the turn is cut off. On start, the agents plugin sends `[Clubmate] Your turn was cut off by a restart; continue from where you stopped.` to every cut-off session that is not closed, including one that was waiting for a permission or an answer (it asks again), so every session picks up its work without you.

When a turn ends with a network error ("No response from API", "Connection refused", `ECONNREFUSED`, "Can't reach the API server", "No internet route", "Unable to connect to API ("), an overload or a rate limit in a session that is in AFK mode or belongs to a live orchestration, Clubmate sends it `[Clubmate] Your turn ended with an error (<reason>). Continue the task from where you stopped.` 1 min later (`CLUBMATE_AGENTS_NET_RETRY_AFTER` overrides the minute), then after 2, 4 and 8 min and every 10 min after that, up to 8 times; the transcript shows a notice with the attempt ("Network error; retrying in …", "Claude is temporarily overloaded; retrying in …"). A turn that ends without an error resets the count. While a retry is pending, the parent is not woken for the child's error; once the retries run out, the session stays in error with a "…; stopped retrying" notice and the parent is woken as for any error. Any other session stays in error; send it a message to continue. Pending retries live in memory and are lost if the plugin restarts.

AFK mode is for when you step away. Turn it on with the AFK item in the composer options menu of a top-level session, or tell the agent you are away ("я афк") and it turns it on itself with `agents.afk on=true`; "я вернулся" turns it off. While it is on, each prompt of that session and of all its child sessions tells the agent to work without asking you, make and note its own decisions, hand large work to child sessions and subagents, and finish with one short report of commits, decisions and open questions. Turning it on while a turn runs also adds the instruction to that turn and to the running turns of the session's child sessions (steering), so they don't wait for the next prompt. The instruction is not shown in the transcript. `agents.afk-default on=true|false` sets whether new top-level sessions start in AFK mode. `agents.new` takes `afk: true|false` (from any caller, e.g. a cron job's or trigger's args) to start that session in or out of AFK mode from its first prompt, so an unattended session doesn't depend on the agent turning AFK mode on for itself; `finish: ask|merge` sets a top-level session's finish mode instead of the default, but only from you (the app, the phone, the CLI without `--agent`): agents, cron jobs and triggers get `invalid_params`, since merging into main without asking stays your call.

From the Agents sidebar you can run a task in its own worktree end to end: press "New in worktree…", type a branch name and press Start (or Return) to start a session in a new `.worktrees/<branch>` made from the workspace's worktree (as `agents.new` with `branch`). When its turn is done, "Review changes" in the session header opens the diff; with Finish set to "Merge to main" the agent squashes its branch into `main` itself once the tests pass.

"Context" (⌘I) in a Claude session's header shows what the session sees instead of its transcript, to find out why it did not do something you expected: the CLAUDE.md files it loaded (user, project, memory and nested ones, with their current text), the skills, MCP servers (and the ones that need a sign-in or failed), hook context, subagent types, tools and deferred tools it was offered, each with how often it used it; unused ones are muted. It reads the session's own Claude log (`$CLAUDE_CONFIG_DIR` or `~/.claude`, `projects/*/<agent session id>.jsonl`) and follows it as it grows; it shows the current state, not its history. "Transcript" (⌘I) goes back.

The status bar shows how much of the Claude subscription is used: `5h 42% ↻19:03 · 7d 81% ↻Wed`, the 5-hour and weekly limits with their reset times, in the warning colour once Claude warns about a limit and in the danger colour once it is reached. The numbers come from the rate-limit reports Claude attaches to agent replies, so they appear after the first reply of an agent session, are kept across restarts, and miss usage from Claude outside Clubmate until the next reply; a limit disappears once its reset time passes. The tooltip names when they were last updated; `agents.usage` returns them.

Agent mode is a cooperative guard for well-behaved agents, not a security boundary: any program running as your user can reach Clubmate directly.

## Status

One map for both clients: the glyph (SF Symbol), the word and the tone of each state a session shows. The agents plugin decides the state once: `status` in `agents.sessions` and in the session header (`header.status`), with the parent states `childrenRunning`/`childrenWaiting` (`childStatus` in `agents.sessions`) and `asks` (a top-level `done` session with `needsYou`), `asksParent` (a `waiting` child with `asksParent` in `agents.sessions`), `review` (a `done` session with `review` in `agents.sessions`), and `open` (a `done` session with `openCount`, see [Open items](#open-items)). The Mac (sidebar, header, Graphs) and the phone copy this table and never pick a glyph or tone on their own.

| State | Glyph | Word | Tone |
|---|---|---|---|
| `running` (a turn runs, a command the agent sent to the background still runs after its turn, the agent works on its own when that command ends, or a `done` session waits for its own reminder) | `play.circle` | elapsed ("4 min"), for a reminder "next check 19:12", else "Running" | accent |
| `waiting` (permission or question pending) | `exclamationmark.circle` | "waiting" ("asking" for a question) | warning |
| `asks` (done, its last message asks you) | `exclamationmark.circle` | "asking" | warning |
| `asksParent` (a child's question waits for the session that started it, see [Needs you](#needs-you)) | `arrow.up.circle` (the phone draws `arrow.up` in its glyph circle) | "asking parent" (the phone "Asks parent: <question>", header "Asking parent") | accent |
| `review` (a top-level session whose Finish is not "Merge to main" ended its turn `done` with changes, not marked reviewed yet) | `eye.circle` (the phone draws `eye` in its glyph circle) | "review" (the phone "Review") | accent |
| `open` (done, with open items left; `status` stays `done` and `needsYou` false) | `checkmark.circle` | outlined "3 open" | none, the count in warning ink |
| `done` | `checkmark.circle` | age ("2 h ago") | none (secondary ink) |
| `idle` (no turn yet) | `circle` | "idle" | none |
| `error` (the turn failed) | `xmark.circle` | "exit 1" when the error carries the agent's exit status, else "Stopped"; the session header badge reads "Stopped · exit 1" or "Stopped · error" | danger |
| `closed` | `archivebox`; on the Mac row the glyph of the status it closed from when that was `done` (`checkmark.circle`) or `error` (`xmark.circle`), kept as `closedStatus` (sessions closed before it was kept have none) | "Closed"; when Clubmate closed it (`autoClosed`) "auto" on the Mac row, "Auto-closed" on the phone | none |
| `childrenRunning` (done or idle, a child runs) | `play.circle` | "Waiting for child sessions" | accent |
| `childrenWaiting` (done or idle, a child waits) | `exclamationmark.circle` | "Child session waiting" | warning |

A failed session's header shows the error in words under the title: "Claude exited with status 1." for an exit status, "Claude stopped: <message>" for an untyped agent error (the `acp error <code>` prefix dropped), a typed failure's own sentence ("Claude is temporarily overloaded."); `error` in `agents.sessions` keeps the raw text. The plugin builds these words once: the Mac gets them in its sidebar and header nodes, the phone as `failure` `{word, badge, line}` in `agents.sessions` (row "exit 1" or "Stopped", header "Stopped · exit 1" or "Stopped · error", the sentence above, shown under the transcript), present only on an `error` session; a phone talking to a Mac that sends no `failure` shows "Stopped" and "Stopped · error".

Under the error both clients offer the same way out, built once by the plugin (`failureActions`): "Sign in" when the agent needs a login, else "Hand off to a new session" when the agent cannot resume the session, else "Retry". The Mac draws them as buttons; the phone gets them as `failure.actions` `[{id, label, icon, command?, args?}]` and shows a button for each action with a `command` the Mac lets it run (Retry → `agents.resume`, Hand off → `agents.handoff`, which opens the new session). An action without a `command` happens only on the Mac: the phone shows it as a line, "Sign in on Mac Studio". While the Mac is offline the buttons are disabled with the same reason as a permission ("Can't answer — Mac Studio is offline").

Clubmate closes a top-level session an hour after its turn ended `done` (`CLUBMATE_AGENTS_CLOSE_AFTER` overrides the hour), together with its child sessions, when nothing in that tree runs, waits or has queued messages, the session itself doesn't ask a question, nothing has open items or stopped with an error, owns a cron job or trigger (they would be deleted with it), and nothing was logged in any of them for that hour. A node session of a graph run that is top-level (the run was not started by an agent session: cron, a trigger, the Graphs section, `cm`) closes this way only once its run is `stopped` in `graphs.list`, since a running run's edges may prompt it again; the hour still counts from the node's own last activity, and while the graphs plugin can't be asked the node stays open. A node of a run started by an agent session sits under that session and closes with its tree. Sessions started with their own system prompt or tool limits (the voice session, a night session) are never closed this way. Nor is a session in `review`: when a top-level session whose Finish is not "Merge to main" ends a turn `done` and its worktree differs from its first checkpoint (what "Review changes" shows), the plugin sets `review` on it (in `agents.sessions` and the record) and keeps it until you press "Reviewed" in its header on the Mac or the phone (`agents.reviewed session=…`, remote); the hour then counts from the press. Its next turn, a close or an error clears `review`, and the turn after decides again. A top-level session whose last message asks stays `asks`; a child's `asks` holds nothing back, since it was for the session that started it (see [Needs you](#needs-you)), which got it when the child's turn ended and has since finished. A session with open items stays too, since an hour would send them all to the backlog; once they are answered or aged out the hour counts as usual. `review` is not Needs you and sends no push. A child Clubmate closes after its branch was merged is marked the same way. Such a session carries `autoClosed` in `agents.sessions` until it is reopened; the Mac sidebar row reads "auto" and its header "Closed automatically an hour after it finished", the phone "Auto-closed" and "Closed automatically". The transcript logs the close with actor `clubmate`.

A turn of Claude Code can end while a command it sent to the background runs on (`run_in_background`, e.g. `gh run watch`); Claude Code wakes the agent when the command ends, without a prompt. The plugin keeps such a session `running` from the end of its turn through the agent's own follow-up: a background task starts with the `backgroundTaskId` in a tool result's `_meta.claudeCode.toolResponse`, agent output (a message, thought or new tool call) with no turn running starts the follow-up, and the follow-up ends at its result (the `usage_update` with a `cost`). At a turn's end the plugin checks the session's `claude` process: when no shell runs under it any more, the task ended during the turn and the session is `done`. Stop (`agents.cancel`) on such a session stops waiting: the session turns `done`, and a follow-up in progress is cancelled. The phone and the Mac show it as any running session; nothing on the clients changes.

A session whose turn ended `done` but that owns an enabled one-shot cron job (`in`, `at`) prompting itself (`agents.prompt` with its own id, "check the CI again in 5 minutes") is shown as `running` too: in `agents.sessions` (`status`, `group`, `active`, no `needsYou` even when its last message ends with `?`), in its header and on its sidebar row ("next check 19:12", the earliest such job; `activity` in `agents.sessions` carries the same title with `at` when its turn ended, and there is no `turnStartedAt`). `reminding: true` in `agents.sessions` marks it: no turn runs, so cron and triggers do not count it as busy and its reminder fires. Its turn still ended `done` for the agent (`agents.turn`, `agents.wait`), so a prompt starts a new turn rather than steering one; but its `done` or `asks` notification is not posted, and a parent counts it as a running child. The cron plugin sends the workspace's reminders whenever its jobs change, and again after the agents plugin restarts (`agents.reminders {reminders: [{session, at}]}`, only from the cron plugin); when the job fires, is deleted or paused the session shows `done` again. A recurring job (`every`, `cron`) never makes a session look running.

The session header's meta line repeats the sidebar row's detail, which the row often cuts: AFK, the notify policy ("Input only", "Muted"), and the activity (`15 min` while running, the parent states' words, the last change's age otherwise), leaving out a state the header already shows as a badge (waiting for you, asking, Stopped, a review's progress), then the context fill. The plugin builds both from one `sessionRow`.

Waiting is amber (warning) everywhere: sidebar, Graphs, header badge ("waiting for you"), phone. A failed turn is `error`, never `done`. An untyped internal error is retried once in the same turn ("The turn failed; retrying once"); only when the retry fails too does the session end in `error`, so a turn that recovers on the retry is `done`.

## Open items

A decision or an offer an agent leaves at the end of a turn is an open item, not a question: the turn ends `done`, nothing waits, and the items sit under the report until you get to them. A question the agent cannot go on without stays AskUserQuestion, amber and `waiting`. An agent always ends a turn with some text, often after the tool call, so the Mac draws the card after the turn's last message, not where the call was; the phone docks it above the composer.

- Posting. An agent posts with `agents_open_items` (`agents.open-items`) for its own session; a user or a test instance may name any `session` with `cm command run agents.open-items --args '…'`. Each item is `{kind: "decision", header, question, quote, multiSelect?, options: [labels], descriptions: [lines]}` or `{kind: "offer", label, description?, quote}`: `header` of up to 12 characters, 2 to 4 options, a description for each (Other is always offered), and `quote`, the report's sentence. The manifest schema allows no objects inside array items, so the tool takes labels and descriptions as two parallel lists; stored and sent to clients an option is `{label, description}`. A bad item fails the whole call with a message that says what to fix.
- Limits. The open set holds 3 decisions and 4 offers across the session's turns. Anything beyond that is filed in the backlog at once, one task per item with the quote and the session's id, and its task id is in the entry's `overflow`, so the agent doesn't have to count.
- Record. Items live in the session log (`open-items`, with `open-items/changed` for what happens to them), so they survive restarts. Ids are `oi-N`, unique in the session. State is `open`, `answered`, `no`, `backlog` (with `task`, the backlog id) or `handed`. Clients get one transcript entry per turn: `{kind: "openItems", items: [{id, kind, header, question, label, description, quote, options, multiSelect, state, answer, task, number, at}], overflow: [taskIds], later}`.
- Report markers. In the text it sends (`agents.transcript` and the Mac's message nodes, not the log), the plugin puts a circled digit after the sentence that holds each item's `quote`, in the last agent message of that turn that has it: the card's item 1 is ①. An agent often writes a line after the tool call, so earlier messages of the turn count too. No match, no marker. The digit stays plain text; the Mac's prose draws ① to ⑳ over it as the digit in warning ink in a ring, in any message, keeping the line height and what a copy gives.
- `agents.sessions`: `openCount` (each unanswered item is 1, omitted at 0), `openSince` (the oldest one's time) and `group: "open"`. `status` stays `done` and `needsYou` false. With a pending permission or question the session is `waiting`; its items stay and show again afterwards. For edges and `agents.turn` an open session is `done`. A prompt you type leaves the items open.
- Answering (user only, also from the phone). `agents.open-answer {session, answers: [{item, option?, options?, other?}], offers: [ids], note?}` closes those items and starts one turn, queued when a turn runs: `Answers: Lists → Add an SDUI prop; Grouping → Its own group; do: ⌘/ screen`, then the note. `agents.open-later {session}` keeps them open and sets `later` on the entry, which folds the card; ignoring the card is the same. `agents.open-backlog {session, items?}` files one task per item, all when `items` is empty. `agents.open-no {session, items?}` closes them and starts no turn; the session's next turn begins with `None of these: …`. `agents.open-queue {workspace?}` lists `[{session, title, worktree, updatedAt, items}]`, oldest first. `agents.open-convert {session}` prompts the session to post what it left in prose.
- Aging. An item still open 7 days after posting (`CLUBMATE_AGENTS_OPEN_AFTER` overrides the 7 days) or when its session closes, by hand or any other way, becomes a backlog task, with a line in the session. A deleted session takes its items along. While the backlog can't be reached the items stay open and the plugin tries again.
- Closed sessions. Closing normally empties the set, so this is for an item that could not be filed: an offer answered with `agents.open-answer` starts a new session in the closed session's worktree (the main checkout when that is gone) and returns `{session}`, a decision goes to the backlog with its answer.
- Children. A child's items never reach you while its parent exists and is open: they close as `handed` and the parent is prompted with `[Clubmate] Child "…" (agt_…) left open items: …`, the items in the text. It answers the child with `agents_prompt` or carries them into its own `agents_open_items`. With the parent gone they stay on the child as yours. Graph nodes and cron or trigger sessions behave as top-level sessions.
- On the Mac. One card holds the open set, at the entry of the newest turn that has open items, under its report: `Open after this turn`, the outlined count (`openCount`), `2 decisions · 3 offers · answer any time; nothing waits`, each decision numbered with its header chip, quote line and radio or check rows, the offers as one `Next — tick what you want me to do` item, what was already answered or filed as a muted line, `+N more went to the backlog: #a, #b`, then Send answers, Later, To backlog and ••• with No to all. Older entries show one line once all their items are closed. Later folds the card to one line with Show; a waiting session hides it until it stops waiting. In a form of at most 560 pt the items are an accordion, as in the question card. The plugin keeps the picks, the keyboard cursor and the folded state per session in memory (`sessionUI.open`), the form autosaves into them, so the card, the queue and the composer see the same picks: a message typed while something is picked goes out as `open-answer` with the text as its note, and the composer's placeholder says so (`Message Claude… — your answers go with it`). Keys are in [shortcuts](shortcuts.md#open-items-agents-section-card-or-open-queue).
- Report numbers. The card's numbers and the report's circled digits come from one function (`openNumbers`): decisions in posting order across the entries that still have an open item, every offer the one number after them, since the offers are one item on the card. An entry with nothing open has no digits. The same numbers go out as `number` on the items of the `openItems` entries and of `agents.open-queue`, omitted where there is none. They are worked out when sent, not stored, and an entry whose numbers changed counts as changed, so a phone that fetches only what changed gets the new ones. The phone draws the field on its card, its queue and the Next row; for a Mac that doesn't send it the phone numbers a turn's items itself, each by its place in the turn.
- Open filter. The chip `Open N` in Agents (⌥O; `N` sums `openCount` over the workspace's open sessions, children included) turns the sidebar into the sessions with open items or `mayAsk` and the main pane into the queue, oldest first: `Open · 7 items in 3 sessions`, Send N answers (⌘↩, answers are sent per session, one turn each), one card per session with Open session (↩), an accordion across all of them. A `mayAsk` session gets a card with Turn into items (`agents.open-convert`). Picking a row moves the cursor to that session. The row shows the outlined count in place of its age; `mayAsk` shows `may have left a question` in the faint ink. The status bar reads `· 5 open`, the sum of `openCount`.
- Phone. The Mac lists groups in `groupOrder`; the phone shows its Open section above Running, oldest `openSince` first, and folds a card whose entry has `later` or whose session has a turn running. It counts kinds for "2 decisions, 3 offers" from `agents.open-queue`, and a message typed while picks are unsent goes as `note` of `agents.open-answer`.
- Safety net. A turn that posted no items, is not `waiting` or `asks`, and whose last paragraph matches `your call|up to you|should it|should I|if you want|let me know if|want me to|если хочешь|решать тебе|на твоё усмотрение|могу сделать|скажи, если` gets `mayAsk` in `agents.sessions` until its next turn. It will fire falsely, so it is only a faint hint.

## Needs you

A session needs you when a permission or a question is pending (status `waiting`), or when a top-level session's turn is done and its last message asks a question (`asks`). A child session's `asks` is for the session that started it, not for you, so it never needs you on its own. So is a child's pending question (AskUserQuestion, a form `elicitation/create`; a URL one such as a sign-in stays yours) while the session that started it exists and is not closed: the child shows `asksParent` (`asksParent: true` in `agents.sessions`), sends no push and no Mac notification, counts as running for its parent's `childStatus`, and the parent is woken with `[Clubmate] Child "…" (agt_…) asks you, not the user: "<question>" (agents_elicitation request elicitation-N). Answer it yourself; ask the user only when the decision is theirs.` The parent answers with `agents_elicitation` or asks you itself. With the parent gone the question needs you. A child's pending permissions always need you. A session that stopped with an error does not need you; it shows as Stopped. Nor do [open items](#open-items): they have their own count and group. Nor does a night session (`night` in `agents.sessions`, a service session of the nightly self-improvement run): its permission requests are rejected and its questions declined at once, and a last message ending with `?` doesn't count. Nor does a session that is `running` because its background task runs on, even when its last message ends with `?` (see § Status). The ending `?` is a fallback: a top-level Claude session is told, through its system prompt (`_meta.systemPrompt.append` on `session/new` and `session/resume`), to ask questions that need your answer with AskUserQuestion, which arrives as a pending question (`elicitation/create`) and needs no guessing, and to post what stays open at the end of a turn as open items (§ Open items). Child sessions are told only the second part; their questions go to the session that started them. Nor is a session the voice plugin started with its own `systemPrompt`: it gets that text instead. The agents plugin computes this once and sends it as `needsYou` in `agents.sessions`; a top-level turn that ends with `asks` is also posted once as a `needs-input` notification (see [notifications](notifications.md#in-the-app)). The Mac sidebar's "Needs you" filter (a top-level session that needs you, or whose child waits for permission), the Mac status bar's "N need you" and the phone (its "Needs you" list, waiting counts, session groups and glyphs) show exactly these sessions; neither client derives it on its own. The phone falls back to the same rule only for a Mac whose Clubmate does not send `needsYou` yet.

Graph runs. A graph run needs you while one of its steps waits for your approval or one of its edges holds a firing past its round cap (see [agent graphs § Needs you](agent-graphs.md#needs-you)). The graphs plugin decides it and hands it over (`agents.run-needs`, only from the graphs plugin); `agents.sessions` lists such a run as its own entry next to the sessions: `kind: "run"`, `id` the run id (`gr_…`), `title` the run title, `run: {id, title, number}` (`number` the run's place among the workspace's runs of its graph; the phone titles the row "Review gate · #4"), `status: "waiting"`, `needsYou`, `needsYouSince` (when the step began to wait or the firing was held), `group: "needsYou"`, `pending: ["step-<node>"]` with `pendingSummary {kind: permission, tool: execute, text: <command>, role: <the step's role>}` for a step (the phone's row reads "Squash into main wants to run `git merge…`"), or `pending: ["cap-<edge>"]` with `pendingSummary {kind: question, text: "<From> → <To> ran N of N rounds"}` for a cap. Its appearing publishes `agents.changed` (`status`), its going away (answered, continued, stopped, removed) `agents.changed` `resolved` with that request and `requestKind` `permission` (both post a `permission` notification, so the phone drops it), and it is in `removed` of the next delta. A run counts once: the Mac sidebar's run row reads the text ("Tests wants to run make test") in warning ink, opens and counts once under Needs you whether its node sessions are top-level or under the session that started the run; the status bar's "N need you" (which reads "N runs need you", "1 run needs you", while everything that needs you is a run), the bell's pinned items ("Permission · Run make test" or "Question · Tests → Coder ran 2 of 2 rounds", the run title under it; it opens the run in Graphs, as does its macOS notification, and the graphs plugin's own `notify.post` for the run is folded into it) and the phone's Needs you list (a run row opening the run) count the entry like a session. A run's node session that waits for permission itself still counts on its own. The entry is answered with `graphs.approve` or `graphs.continue`, never `agents.permission`; the voice assistant leaves run entries out.

A [night session](#self-improvement) never needs you: its permission requests are rejected at once and its offers wait without asking.

Groups. The plugin also sends each session's `group` in `agents.sessions`, the section the phone lists it in: `closed` for a closed session, else `needsYou` when it needs you, else `service` for a service session, else `running` while its status is `running`, else `open` while it is `done` with open items, else `done`. A parent is lifted to its most urgent child's group (any depth, after lifting the child): to `needsYou` always, to `running` or `open` unless the parent is a service session; the order is `needsYou`, `running`, `open`, `done`, `closed`, `service`, so a closed parent with a running child lists under Running and a done parent whose child waits for permission under Needs you. The phone puts each top-level session (with its children nested under it) in its `group`'s section; it never works out the group itself, and falls back to the session's own group without lifting only for a Mac that does not send `group` yet. Each section's count and its workspace row ("N running · N closed") count these top-level sessions per `group` (children count with their parent, not on their own, as in the Mac sidebar's groups) and "N waiting" from every session that needs you. `active` in `agents.sessions` is true for a session that is `running` or `waiting` and not a service session; the Mac status bar's "N agents" counts these.

Oldest first. A session that needs you also carries `needsYouSince` in `agents.sessions`: when its pending request was made, or when its turn ended with the question. Every list of sessions that need you is ordered by it, oldest first, ties by session id: the Mac sidebar's "Needs you" filter (a top-level session counts with the oldest request in its subtree, and its worktree group, when shown, with its oldest session), the bell's pinned items and the phone's "Needs you" list across workspaces and Macs.

A session that needs you is never folded. In the Mac sidebar the worktree group, the Service group, the graph run and every parent above it are expanded while it needs you, whatever the user folded. On the phone a subagent or child that asks is a nested row under its parent, one step in (24pt) with no separator between them, never hidden in a folded group.

### Needs an answer

A question card whose fields are all AskUserQuestion's questions (`choice` or `multi`, each with its `<key>_custom` Other, none `required`) needs an answer before Send: a picked option, a ticked option, or text in an open Other row. Text in a closed Other row isn't sent, so it doesn't count. The plugin decides it and sends `needsAnswer` on the entry's `elicitation`; on the Mac the form's `needsAny` carries it. Any other form (`text`, `number` or `boolean` fields, an MCP form with its own `required`) sends as it did. Skip stays enabled on every card and means "none of these, go on". A single question a pick answers has no Send.

## Review progress

A session that opened or received an open review (see [nvim integration § Review changes](nvim-integration.md#review-changes)) shows its progress. The agents plugin follows the bus topic `editor-nvim.review`, keeps every open review until its `closed` event (and each review's comment states after it), stores them with the last event's seq in its storage (`reviews`) and on start resumes the topic from that seq, so progress and card states survive a restart of the plugin; `editor-nvim.ready` (editor-nvim started again and holds no review) closes every open review, keeping the states, and gives each session the newest review whose `opener` or `recipient` it is: `reviewProgress {id, reviewed, total, open, sent, text}` in `agents.sessions`, `text` reading `review N/M · K` (K open comments) and `short` reading `N/M · K` (`N/M` without open comments). The phone row shows `text` in place of the age of a done, idle or review session ("review 5/15 · 1" instead of "2 h ago"). The Mac sidebar row shows `short` there under the review glyph (`eye.circle`) instead of the status glyph, so it fits the 6 em a list keeps for a detail; a running, waiting or failed row keeps its own words and glyph. The Mac session header adds the badge `Review N/M · K issue(s)`, after Send `Review M/M · N comments sent`, success once every file is reviewed, and the button "Open review" ⌘R, which shows that review in the Code section: its nvim tab current, nvim focused (`editor-nvim.review-show {id}`). Closing the review drops the field, the row text and the header. Each review payload also publishes `agents.changed` kind `review` for its opener and recipient, which is how the phone learns the text changed. Neither client works the text out itself; the phone has no review panel. "Review changes" in the header and "Full diff" on an edit card pass the session and the turn, so the review reads `Before turn N` and the session is its opener.

## Search

`agents.search query=<text>` (remote, agent) finds the workspace's sessions, closed ones included, by title and by what was said in them: your prompts and the agent's replies, not thoughts or tool output. It is a case-insensitive substring match of the whole query. Up to 50 sessions come back, the ones whose title matches first, then the most recently updated, each with up to 3 hits `{kind: title|prompt|reply, turn, snippet}`; a snippet is the start of the line the match is on, from about 12 characters before it, cut at a word, as plain text (markdown marks and link targets dropped). The plugin reads the text from its own session logs (`sessions/<id>.jsonl`) once, in the background after it starts, and then only the lines appended since the last search, so typing stays fast with hundreds of sessions. The Mac and the phone render this result and never match or rank on their own.

On the Mac the Agents sidebar has a "Search sessions" field above the filter chips. While it holds text the chips and the tree give way to the results: a row per session (status glyph, title, when it was last updated) with its prompt and reply hits under it; clicking either opens the session. Cleared, the tree comes back. On the phone the session list is searchable the same way. Not done: jumping to the matched turn, and a key that focuses the field.

## Service sessions

A session started with its own system prompt or tool limits is a service session: the voice session (`systemPrompt`, `disallowedTools`, `mode` or `model` on `agents.new`, accepted only from the voice plugin) and the night sessions of [self-improvement](#self-improvement), which the agents plugin starts itself. Such a session has `service: true` in `agents.sessions`. The Mac sidebar lists it in one "Service" group (its count at the right) at the bottom of the tree, outside the worktree groups and after Closed, folded by default; the phone in a "Service · N" section after Closed, folded too. It is not counted in "All" or "Running", nor in the Mac status bar's "N agents" (`active` is false), and its `group` is `service` (see [Needs you](#needs-you) § Groups). While it needs you it counts under "Needs you" and is never folded: on the Mac its group opens and its count turns warning, on the phone it moves to "Needs you". A session a service session starts with `agents.new` is not its child: it is a top-level session of yours, in the workspace's root, with your defaults, and it is selected like one you started. `firstMode` on `agents.new` (from the user only, an agent gets `invalid_params`; Backlog's Start agent sets it) does not make a service session: it is the mode the session starts in instead of the worktree's remembered one, applied once on `session/new`; a resume takes the worktree's mode like any session.

## Self-improvement

Once a day Claude reviews its own day, changes how it works and tidies each project's memory. In the morning you get a short report and can undo any change. It is off by default: Settings → Agents → Self-improvement (`self.enabled` in the plugin's storage). While it is off no session gets the self and no night runs; the repository stays, so turning it back on continues. Once there is a prompt or a skill, a second row appears with Reset (confirmed), which empties the prompt and removes the skills. Reset keeps `lessons.md`, the reports and the memory patches, and does not touch memory.

**The self** is a git repository in the plugin's state dir (`self/`): `prompt.md` (at most 6 KB, appended to the system prompt after the plugin's own text), `skills/<name>/SKILL.md` (at most 5, delivered as the local plugin `self`, so a skill reads `self:<name>`), `lessons.md` (hypotheses and rejected changes, never sent to sessions), `memory-patches/<date>/<workspace>.patch` and `reports/<date>.md`. Every ordinary session gets it, children and graph nodes too; service sessions don't, and it does not make a session a service session. It holds no scripts, hooks or settings. A blank `prompt.md` counts as no prompt. A running session keeps what it has; a change reaches a resumed session the next time it attaches.

**The night** starts at 04:00 local time, on the plugin's own timer. If the Mac slept through it, it runs on the next core start or wake, but only before 08:00; later the night is skipped. The next digest reaches back to the last night that finished without stopping early (`self.digestedUntil`; `self.lastRun` only keeps a night from running twice), so a skipped or failed night loses nothing. `cm command run agents.night-run` starts one now, in the background (`self-improvement is off` while the setting is off, `a night is already running` during one). Each night:

1. Digest. Go collects, per non-home workspace, the sessions updated since then: your prompts, the agent's final replies, and facts from the log (cancelled turns, denied permissions, failed tools by name, repeated Bash commands). Tool output, thoughts and fetched pages are left out. Capped at 8 KB per session and 64 KB per workspace. All digests empty: nothing runs, no session and no report.
2. Sleep. One session per project with a digest and a memory dir, one after another, titled "Sleep: <workspace>". Its sandbox holds that project's digest, memory and undone cleanups and nothing else, and it may read the project's folders. It merges, removes what is stale, checks facts against the code and shrinks. Night sessions have no tool that deletes, so it removes a file by writing it empty: `agents.self-declare` drops empty memory files before it commits, except `MEMORY.md`, since an empty index more likely means a mistake than a cleanup. Memory means `~/.claude/projects/<escaped folder>/memory/` of your workspace folders, or `autoMemoryDirectory` when set. Applying is all or nothing per project: if a memory file changed since the sandbox was made, that project's sleep is dropped and comes back the next night.
3. Improve. One session, titled "Night review", in the most recently opened non-home workspace, after every Sleep. Its sandbox holds a copy of the self and all digests, and no memory. It checks whether a recent change's problem repeated, and reverts that change if so; then it picks at most two patterns that cost you the most and edits `prompt.md` or a skill, with a hypothesis in `lessons.md`. No clear pattern, no edit.
4. Apply. A night session calls `agents.self-declare` after each change, which commits its sandbox. Only declared changes count, and only once the session has ended; a crash or a timeout applies nothing from that session.
5. Report. See below.

**Limits.** While applying, whatever the agent did, on each commit and again on what it landed as, since a merge can change it (renames are off, so an edit can't follow a file): only `prompt.md`, `lessons.md`, `skills/*/SKILL.md` and, for Sleep, memory `.md` files may change; `prompt.md` over 6 KB or more than 5 skills is dropped; a skill is read from the commit and again as it landed, reverts and undo included, and its frontmatter may hold only `name` and `description` (it can have none), and one with shell syntax (`` !` ``, a code fence with `!` in its info string), a substitution (`$` directly before a letter, digit, `_` or `{`, since Claude Code substitutes `$ARGUMENTS` first and the parts then join into shell syntax) or a control or invisible character anywhere (a bare `\r`, any Unicode space but the plain one, a BOM, zero-width characters, invalid UTF-8; `\t` and `\r\n` are fine) is dropped, because Claude Code honours `allowed-tools` and `hooks` there and runs that syntax; a commit that removes a `Rejected by the user:` or `Undone from session` line from `lessons.md` is dropped; at most two commits touch the prompt and skills per night (a revert doesn't count and is applied first). What is dropped is listed in the report. While running, a night session is confined by the plugin: it starts in `auto` and is set to `default` before the first prompt, and it refuses the turn if that fails. It has only Read, Grep, Glob, Edit and Write, Sonnet, 60 turns and no Claude Code settings. Its allowlist covers edits in the sandbox, reads in the sandbox and (Sleep) the project's folders, and `agents.self-declare`; every other permission request is rejected at once, so nothing waits for you, and a form or URL question is declined too. Rejected requests aren't logged, but the report counts them as `Refused: N`, so an escape attempt, or a rule that stopped matching, can't pass for a quiet night. A sandbox holds no `.git`: the git dir sits beside it and Go names it explicitly, so a session can't plant a hook or a config. Each session has 30 minutes (`CLUBMATE_AGENTS_NIGHT_SESSION_LIMIT`) and the night 60 (`CLUBMATE_AGENTS_NIGHT_LIMIT`). A session at its limit ends only that session; a failure or the night's limit ends the night, which then notifies you, with a report when something landed. A restart mid-night does the same on the next start: it lists what landed since the night began and saves the report, with undo from any chat, since the Improve session is gone. `prompt.md` must hold behaviour only, never a project name, path, code or secret: the Improve session sees all digests, so this rule is a prompt instruction plus the diff in the report.

**Report.** The plugin writes it after Apply, since only it knows what landed: "Night review" in the Improve session, at most 10 lines plus the diffs of `prompt.md` and skills, saved as `reports/<date>.md`. What was refused, dropped or skipped comes first, at most 3 lines so it can't push out what changed, and a diff over 4 KB ends with how much was cut. A night with nothing to change says so in one line. The notification (`Night review`, with "2 changes", "Nothing to change", or "Nothing landed, see the report" when something was dropped or skipped and nothing landed) reaches the phone like any other. Each change is an open offer labelled "Undo: …", at most 4: one per self edit, one for a revert, one for all of the night's memory cleanup. The card differs from other open items: picks are undone at once with no agent turn (it says "Undo happens at once, with no turn"), and it has no To backlog, since a night session's offers never go to the backlog.

**Undo** has no deadline. `agents.self-changes` lists the changes, newest first, and `agents.self-undo {change}` reverts one (a git revert, or the reverse patch for memory). Both work from any session, so "undo yesterday's change about X" works in any chat; only a night session is refused. An undo that no longer applies says so and changes nothing, and so does one that would leave an unsafe skill; undoing the newer change first gets past that. Every undo records in `lessons.md` who undid it, `Rejected by the user: <summary>` or, when an agent called it, `Undone from session <id>: <summary>`, so Improve doesn't redo it. Sleep never sees `lessons.md`: a project's undone memory changes (the newest 10, each with its summary and patch) reach that project's Sleep sandbox, and only that one, as `rejected.md`, which stays out of what it can declare.

**Night sessions.** Each is a [service session](#service-sessions) that counts as `done` and never under Needs you, even with open offers. Sleep is closed once it is applied, so it moves from Service to Closed; the Improve session stays with its sandbox until the next night that isn't skipped, so you can ask it why it did something. It resumes in `default` or not at all, its mode and settings can't be changed, and it can't be handed off: a hand-off would be an ordinary session in a sandbox that holds every digest. That next night deletes the previous night's sessions and sandboxes, with any unanswered offers; undo still works through chat and `reports/` keeps the report. A night session is hidden from `agents.search`, `agents.sessions` and `agents.transcript` for agent callers, so an ordinary session can't read a digest; you see them in the sidebar as usual. Claude Code's own logs of a night session hold the digests, so `~/.claude/projects/<escaped sandbox>` goes with that sandbox, for its path as is and with symlinks resolved, and nothing else under `projects` is touched.

## Permission card

A pending permission request shows the same content on the Mac and the phone; the agents plugin builds it once: the Mac gets it as the `permissionCard` node ([SDUI](sdui-protocol.md#node-types)), the phone as `card` `{text, title, command?, caption?, options}` on each permission entry of `agents.transcript` (left out for agent callers), with the same option fields:

- Title by tool kind: "Run a command?" for a command; other kinds keep the sentence "Claude wants to edit notify.go".
- The command itself (`command`), in a monospaced box.
- The request's description as the caption, always attributed: "Claude says: Run the notify tests".
- Options in this order: Allow once ⌥1 · Always allow… ⌥2 · Reject ⌥3; "Always reject" (Claude's `reject_always`) sits in the card's ••• menu without a key. These labels replace Claude's own ("Yes", "Yes, and don't ask again for go test commands", "No") only when the request has the usual one option per kind; anything else (plan-mode exits, several allow options) keeps Claude's labels and gets ⌥1–3 in order.
- Always allow… asks first and stores nothing until confirmed: the option carries the `rule` Claude would store and its `scope` ("in shop on this Mac", rules go to the project's local Claude settings on this Mac). The Mac shows them in a popover anchored to the button ("Claude will run matching commands in **shop** without asking, on this Mac, until you remove the rule from the allow list.", the name from the option's `workspace`, bold and never broken at a hyphen; Cancel ⎋ is the default and ↩ cancels too, ⌥2 again confirms) and the phone in its confirm sheet; only the confirm sends the option. Claude does not send the rule over ACP, only its label, so the plugin rebuilds it from that label for commands (`Bash(go test:*)`, one rule per command prefix Claude names); when the label names no command (paths, "similar" commands, other tools) there is no `rule` and the confirm shows the option's label instead.

## Names in the UI

What the agents plugin renders uses names, not ids or command names: a session is its title, a graph run its graph's title; prompts Clubmate sends an agent ("[Clubmate] Child "Fix tests" (agt_…) is done.", the handoff summary) keep the ids for the agent but show without them in the transcript. A detached worktree is labelled "detached · 03a9ff5f". Themed UI is in sentence case ("New in worktree…"); Title Case only in context menus.

## Transcript folding

Tool calls are folded on the Mac and the phone: consecutive calls are one actions row, and a call's output opens only when you click or tap it. A completed `agents_open_items` call is not drawn on either client, since the card says the same: the plugin leaves it out of the `transcript` node and sends `hidden: true` on the entry in `agents.transcript`, where the phone skips it. It isn't counted in an actions row and a row left with no calls isn't drawn. An agent reading `agents.transcript` still gets the call. Running, failed and cancelled ones show like any other call. On an iPad or Fold wider than a phone the actions row is a card that names its first three calls ("Show all N" for the rest), as the iPad board draws it; each call's output still opens only on tap. A failed call is folded too: on the Mac its card says Failed and the actions row "N failed", on the phone its title is in the danger colour and its card or group gets a danger border. A user message longer than 40 lines or 4000 characters shows its first 12 lines with "Show all N lines"; opened, it scrolls inside a capped box, since one row that tall leaves the transcript scrolled past its end, blank. A prompt the voice plugin sent (an entry with `voice {heard, utterance}` in `agents.transcript`) is one right-aligned capsule "🎙 <heard>" (one line, tail-cut) with a chevron; clicking or tapping it opens the prompt JSON, pretty-printed with sorted keys, in a scroll box at most 480 pt tall. A Review prompt (an entry with `review` in `agents.transcript`, sent by the review's Send) is a Review card on the Mac: `Review`, `you · N/M files · K comments`, "Open review" while the review is open, one row per comment (type glyph, `file:line`, the first line of the text, `open` or `resolved` as nrev has it now) and the note; on the phone it stays a plain user message with the prompt text, folded like any long one. A plan card is headed "Plan · n of m" (n steps done); while steps remain its done steps are folded behind "Show done" ("Hide done" folds them again), and a finished plan lists every step. Nothing in the transcript opens itself. The design boards say failures expand; that is overruled. A closed ```` ```mermaid ```` fence in an agent message is drawn as a diagram (one hidden web view per app renders it to an image, cached by source, theme and width); it keeps its aspect and is at most 480 pt tall on the Mac and 420 pt on the phone, shows its source as a code block while it renders, and stays a code block when mermaid cannot parse it, when it would be over 16384 px on a side or 24 million pixels even at 1×, or while the fence is still open. Clicking it on the Mac opens a sheet with the diagram fitted to the window (pinch, zoom buttons, Esc closes); tapping it on the phone opens it full screen (pinch, double tap to zoom). A Markdown link or code span in an agent message that names a doc (see § Docs in the transcript, `docLinks`) is drawn as a link in the accent colour (a code span keeps its code background) on the Mac and the phone; clicking or tapping it opens the doc, whether or not the doc also has a card. Under the message text each of its `docCards` with `presented` is a card (the same on both clients): a kind icon on an accent-tinted tile, the title on one line (tail-cut), "Document · <rel>", "Diagram · <rel>" or "Artifact · <rel>" under it (middle-cut) and a trailing open glyph; the whole card opens the doc. On the Mac the cards are at most 27 em wide (324 pt at the default 12 pt interface font) and sit side by side while each gets 20 em, else one per row at the full width; the kind word stays and the path is cut in the middle; on the phone they are one per row at the full width. The message's other `docCards` (docs it only mentions) are folded under the presented cards into one muted plate: a docs icon, "N docs mentioned" (the file name when there is one) and a chevron; clicking or tapping it opens the same cards under it, laid out like the presented ones, and folds them again. Folded is the default; on the Mac the state is kept per message until the app quits, on the phone while the transcript is open, and never saved. A change to this rule lands in both clients in the same commit.

## Jumping to a turn

`agents.reveal {session, turn}` opens the session in Agents and scrolls its transcript on the Mac so that turn's prompt is at the top (`anchor` on the `transcript` node, see [SDUI protocol](sdui-protocol.md)); it stays there until you scroll, another turn is revealed or the session starts a new turn; revealing the same turn again scrolls back to it. Every `agents.turn` event carries its `turn` number, so a caller can jump to the turn an event was about. The phone ignores `anchor` for now.

## Docs in the transcript

A tool call is a doc when its status is `completed` and either its kind is `edit` (Write, Edit, MultiEdit) and one of its `locations` or `diff` paths ends in `.md`, `.markdown`, `.mmd`, `.html` or `.htm` (case-insensitive, `pkg/docext`), or it has a `resource_link` whose `file://` URI does. The agents plugin decides this once and sends the first such path, absolute against the session's worktree, as the entry's `doc` field in `agents.transcript`; a failed, cancelled or still running call, a delete or move, and a call on other files have none. The Mac card gets an Open action (before Open in nvim) and the phone's tool row an Open button; both show the doc in the [docs viewer](docs-viewer.md) — the Mac through `openDoc` on `agents.main`, which runs `docs.open {path, session}`, the phone with `docs.read`. Like the rest of a call, Open is inside the folded actions row until you open it. Neither client checks the path itself.

An agent message links the docs it names. When a turn ends, the plugin reads each of that turn's `agent` messages as Markdown and takes every link target that has no URL scheme (`http(s)`, `mailto`, `file:` … are skipped) and every inline code span without whitespace; fenced code is not read. A candidate's `#anchor` is set aside and the rest is percent-decoded, `~/` expanded and joined to the session's worktree when relative; it is kept when that is an existing regular file ending in a doc extension (`pkg/docext`). The entry gets `docLinks: {"<target or code span as written>": "<absolute path>[#anchor]"}` in `agents.transcript` and as the `message` node's `docLinks` prop in `agents.main` (omitted when empty); a message still streaming has none, a replayed transcript resolves them again on load, and thoughts and subagent messages have none. On the Mac a click sends `openDoc` with the value on the message node, which runs `docs.open {path, session}`; the phone's native transcript opens the doc sheet with `docs.read`, and its SDUI transcript sends `openDoc` like the Mac. The same pass gives the entry `docCards: [{path, kind, title, rel, presented?}]` (in `agents.transcript` and as the `message` node's prop, omitted when empty): one per distinct doc, the presented ones first, each group in order of first mention, at most 8, `path` absolute without the `#anchor` (two mentions that differ only in the anchor are one card), `kind` `markdown`, `mermaid` (`.mmd`) or `artifact` (`.html`, `.htm`), `title` the first `# ` heading of a Markdown file or the `<title>` of an artifact, read from the file's first 64 KiB (`pkg/docext`, the docs viewer's title too), else the file name without its extension, and `rel` the path relative to the session's worktree (absolute when outside it). Clicking or tapping a card opens its doc like a link. A doc is presented when the agent called `docs_present` or `docs_open` on it during that turn: the plugin listens to `docs.presented` and `docs.opened` (see [docs viewer](docs-viewer.md#bus)) and writes each as a `doc_presented {path, title?}` event in the session's log at the session's current turn, so a replayed transcript keeps it; one that arrives after the turn ended links that turn again. A presented doc's card gets `presented: true` and the `title` passed to `docs_present` when there is one; a presented doc that none of the turn's messages names is added as a card to the turn's last agent message (a turn without an agent message shows none). Only presented cards are drawn open (§ Transcript folding). These links do not add the doc to `agents.docs`. Clubmate's agent instructions and the `docs_open`/`docs_present` tools ask agents to mention docs freely as a link or `path` and to present only the few the user should look at. Any other link in agent Markdown stays a link on the Mac and the phone only for `http`, `https` and `mailto` (`MarkdownLinkPolicy` in `ClubmateProtocol`, applied by `Markdown.inline`); other schemes (`shortcuts:`, `tel:`, app deep links, a hand-written `clubmate-doc:`) show as plain text, and the phone's URL elicitation Open opens only those schemes too.

An agent message shows the images it names. The same pass over a finished turn's `agent` messages keeps every candidate (link target or code span, resolved the same way) without an `#anchor` that is an existing regular file ending in `.png`, `.jpg`, `.jpeg`, `.gif` or `.webp` (case-insensitive) after symlinks are resolved, and gives the entry `images: [{path, rel, width, height}]` (in `agents.transcript` and as the `message` node's prop, omitted when empty): one per distinct path in order of first mention, at most 4, `path` absolute, `rel` as for `docCards`, `width`/`height` the pixel size when the file's header says it (png, jpeg, gif; omitted otherwise). An image is never a doc link or card; the entry's `imageLinks` maps each target written in the message that names one of its `images` (exactly as written) to that image's `path`, and the client draws it as a link in the accent colour, like a doc link. On the Mac and the phone the images are thumbnails under the message, side by side and wrapping (Mac 4 rows tall, phone 112 pt): the image cropped to the tile from its top, the tile as wide as the image's aspect wants between square and twice its height, a hairline border, a spinner while it loads, the file name under it (one line, middle-cut) and `rel` as its tooltip on the Mac. A click or tap on a thumbnail or on an image link opens the image in a viewer: on the Mac a sheet sized to the window with the file name and `rel`, zoom out / Fit / zoom in and Close (Esc), on the phone full screen (pinch, double tap to zoom, a close button). Nothing folds and nothing opens itself; the thumbnail is the folded state. The Mac reads the file and reads it again once it changed; the phone fetches it once per message when the thumbnail appears, so a later message naming a rewritten file shows the new one, and asks for it with `agents.image {session, path}` (not an agent tool, remote), which returns `{mimeType, data}` (base64) only for a path an `images` entry of that session names, and fails for files over 8 MiB, for a path that no longer resolves to an image file name and for bytes that do not sniff as `image/*`. A file that is gone shows a photo glyph and "Image not found" in its thumbnail and in the viewer.

`agents.docs {session?}` (not an agent tool, remote) lists those docs as `{docs: [{path, session, at}]}`: one per path at its latest `at` (when that call began), newest first, from that session and its subagents' calls, or without `session` from every session of the workspace. It reads each session's transcript, so a dropped one is read back first. `docs.list` builds the docs lists on it (see [docs viewer](docs-viewer.md#docs-list)).

When an agent opens a doc with `docs_open`, the phone shows "Opened <file name>" with an Open button above the composer of that session's screen, for 8 s or until tapped; on any other screen it shows nothing.

## CLI

Inside a Clubmate terminal, `clubmate` is on `PATH` and `$CLUBMATE_WORKSPACE_ID` names the current workspace.

```sh
clubmate open src/main.go:42                       # open in the editor
clubmate command run terminal.new                  # any command or capability
clubmate command run session.read id=ses_123 bytes=4000
clubmate command run terminals.close --agent sessionId=ses_123
clubmate session send ses_123 "make test" --enter
clubmate session read ses_123
```

`key=value` arguments are typed by the command's schema (arrays are comma-separated); `--args '{"…": …}'` takes JSON instead. `--agent` runs the command as an agent would, with the same limits and approvals. The CLI never turns it on by itself.

`clubmate agent` wraps the agent-session commands and always runs them as an agent call, so a session started from an agent session's shell is its child:

```sh
clubmate agent spawn "fix the flaky test" --branch fix/flaky   # agents.new; without --branch it shares your worktree
clubmate agent tell agt_123 "also update the docs"             # agents.prompt
clubmate agent wait agt_123 agt_456 --timeout 300              # agents.wait
clubmate agent output agt_123 --from-turn 2                    # agents.transcript
clubmate agent sessions                                        # agents.sessions
clubmate agent cancel agt_123                                  # agents.cancel
clubmate agent blame src/main.go -L 10,40                       # agents.blame; or a commit: clubmate agent blame HEAD~2
clubmate agent trace main..HEAD                                # agents.trace; default HEAD
clubmate agent export agt_123                                  # agents.export into ./agt_123.clubmate-session
clubmate agent import agt_123.clubmate-session --branch more   # agents.import; without --branch it continues in your worktree
```

A reviewer is a child in your own worktree: `clubmate agent spawn "Review git diff main..HEAD read-only: report bugs, change nothing"` (or `agents_new` without `branch` over MCP), `wait` for it, `tell` it one round of follow-ups, then fix what it found yourself.

## History and attribution

A turn is the unit of history. Before each prompt Clubmate pins a checkpoint of the worktree at `refs/clubmate/cp/<session>/<turn>` (its parent is `HEAD` at turn start), and when the turn ends another one at `refs/clubmate/cp/<session>/<turn>.end`; both carry a `Clubmate-Worktree: <path>` trailer. When the turn ends, the commits it added to the current branch get a git note in `refs/notes/clubmate`:

```
Clubmate-Session: agt_4c67f4de54b9ae47
Clubmate-Turn: 3
Clubmate-Agent: claude
Clubmate-Title: Fix the flaky test
Clubmate-Prompt: <first line of the turn's prompt>
Clubmate-Checkpoint: <checkpoint sha>
```

The turn's commits are those reachable from `HEAD` but not from its start or from any other branch (local or remote), so rebasing onto `main`, merging `main` or fast-forwarding a child's branch claims nothing that is already elsewhere; a squash or merge commit belongs to the turn that made it. A commit keeps its first note. The transcript lists them per turn (`turns[].commits`).

Read them with `git log --notes=clubmate`, `agents.blame` or `clubmate agent blame <file|commit> [-L a,b]` (git blame of the file, only line ranges whose commit has a note).

Limits:
- `git merge --squash` into `main` makes a new commit, noted with the session that ran the squash (the orchestrator), not the child whose branch it was; the child's notes stay on its branch commits.
- Commits the user makes in the same worktree during an agent's turn, or pulls into its branch from that branch's remote, are noted with that turn.
- Rebase and amend drop the notes unless the repo sets `git config notes.rewriteRef refs/notes/clubmate`; Clubmate doesn't set it.
- Notes are local; push `refs/notes/clubmate` to share them, but they carry each session's title and the first line of its prompts, so check them before pushing.

### Agent Trace

`agents.trace rev=<commit|a..b>` (`clubmate agent trace`) returns one [Agent Trace](https://agent-trace.dev/) record (version `0.1`; the spec's own example says `0.1.0`, its schema allows only `major.minor`) per non-merge commit, oldest first, at most 200. Each changed file lists its changed lines grouped by contributor:

- `ai`, with `url` `clubmate://session/<id>#turn=<n>`: written during that agent turn;
- `human`: changed while no agent turn ran in the worktree;
- `unknown`: Clubmate can't tell (a turn still running, or one from before end-of-turn checkpoints existed, two turns running at once, or a commit with no Clubmate history at all).

How: Clubmate replays the commit's parent, the checkpoints of the commit's worktree whose parent is that commit (plus the checkpoint named in the commit's note), and the commit itself as a throwaway chain of commits, then runs `git blame` on the changed lines. A line is credited to the step that introduced it: the step into `<turn>.end` is the turn, the step into a turn's start checkpoint happened between turns, and the last step belongs to the commit's noted turn (or is human when the commit has no note). The record `id` is derived from the commit, so exporting twice gives the same record.

Limits: edits the user makes in nvim while a turn runs count as the turn's; two sessions working in one worktree at once make their overlap `unknown`; a squash commit is credited to the session that ran the squash; `model_id` and `content_hash` are not filled.

### Resuming elsewhere

Built (one machine): `agents.export session=… dir=…` (`clubmate agent export <session> [dir]`) writes a bundle directory: `session.json` (the record), `log.jsonl` (Clubmate's log) and `refs.bundle` (a git bundle of the session's checkpoint refs and the notes of the commits its turns made, without commits already on a branch, remote or tag; other sessions' notes stay out). It refuses a running session and an existing `dir`. `agents.import dir=… [branch=…] [note=…]` (`clubmate agent import <dir>`) fetches the checkpoint refs into the repository (never overwriting existing ones) and adds the bundle's notes that name the imported session and one of its checkpoints, on commits the repository has and that have no note yet, adds a closed copy of the session with the original transcript (`importedFrom`), and starts a new session in the caller's worktree (or a new `.worktrees/<branch>`) whose first prompt is the handoff brief of the copy. The copy and the new session link like a handoff. This works across worktrees, workspaces and clones on the same Mac; the bundle's checkpoints need their parent commits in the target repository (fetch the session's branch first).

Design (not built): continuing the agent's own conversation instead of a brief. Claude Code keeps it in `~/.claude/projects/<encoded cwd>/<agentSessionId>.jsonl`; the bundle would carry that file (found by globbing for the id), import would place it under the target cwd's project directory and `session/resume` with the old `agentSessionId`, falling back to the brief when resume fails. On another machine the same bundle works once the branch is pushed and fetched; a relay or shared store for bundles belongs with the mobile companion work.

## MCP (Claude Code and other MCP clients)

`clubmate mcp` is a stdio MCP server over the same registry. Every call it makes is an agent call.

Its `initialize` instructions end with "Working in Clubmate" (`internal/mcp/clubmate.md`, embedded in the binary): split a task, run independent parts as child sessions with `agents_new` and a branch, collect them with `agents_wait`, and use `cron_add` and `triggers_add` instead of polling. Every MCP client that connects gets it, in any project.

- Tools are named after the command or capability with `.` and `-` replaced by `_` (`editor_open`, `workspace_list`, `terminal_close`). A plugin command that provides a capability appears under the capability's name only.
- Every tool takes an optional `workspace` id. It defaults to `$CLUBMATE_WORKSPACE_ID`, then the most recently opened workspace.
- If Clubmate isn't running, the tools still list the core primitives, and calls fail with "Clubmate isn't running". The server never starts Clubmate itself.

To connect Claude Code, use **Settings → Agents → Connect Claude Code**. It runs:

```sh
claude mcp add --scope user clubmate -- "/Applications/Clubmate.app/Contents/Resources/bin/clubmate" mcp
```

Development builds register the server as `clubmate-dev` instead, so both can be connected at once. The button is shown only when `claude` is on your login shell's `PATH`; Clubmate looks once per launch, so restart Clubmate after installing `claude`. It says "Connected" only when the registered server runs this copy of Clubmate; if it runs another one, it shows that command and offers "Reconnect" (remove, then add; if the remove fails, nothing is added). Clubmate never edits Claude's config files itself.
