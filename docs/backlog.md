# Backlog

The **Backlog** section is a per-workspace task list shared by you and your agents.

## What it shows

- Sidebar (direction A of `design/features/backlog-cleanup/`): a header row "Backlog · 70 open" (the tasks that aren't done or won't do) with a ghost `+` (`newTask`, action `newOpen`) at its right; + or ⌘N opens a "New task…" field (form `new`, field `title`, with an × `newClose`) under the tag chips, Return adds a `todo` task, selects it and keeps the field open with the cursor in it, × closes it (it stays open in memory per workspace until then). Then a "Search, or a #number" field (`textField` `search`, `live`, action `search`) that keeps only the tasks whose title, description, note or tags contain the text (any case) or whose number it is (`12`, `#12`), together with the tag chip; while it holds text every group is open (Done too) and its header doesn't fold, and no match reads "No tasks match"; the text is kept in memory per workspace; a query that is only a number of an existing task (`601`, `#601`) pins that task under its own section label "Task #601" (`group:pinned`, no count, doesn't fold) above the status groups, whatever its status or the tag chip, with its status glyph, title and `#601`, and leaves it out of its status group (the row keeps its id, so it is the same row the group would show); a number with no task reads one muted row "No task #999 · last is #83" (`missing`, the highest task number in the workspace) instead; and when the typed text changes to such a number the task is selected and opens on the right while the caret stays in the field (typing `6` → `60` → `601` opens #6, #60, then #601; leaving a field of the open task first saves its edit); the text matches stay below in their groups; once any task that isn't done has a tag, a row of tag chips on one line (`tabs` `tags`, action `filter`: `all` "All" with the count of tasks that aren't done, then `tag:<tag>` for the most used tag of the tasks that aren't done and the selected one, with their counts; the other tags, most used first, ties A–Z, are in a `select` `tagMenu` (action `filter`) that reads "+N" and opens a menu of "tag count" items, and picking one makes it the selected chip; the chips and the field stay put above the scrolling tree) that keeps only the tasks with that tag until the plugin restarts or the tag is gone; then the tasks under section labels In progress, Todo, Idea, Not now, Done, Won't do with their count at the right (tree parents with `action` and no `icon`, see [SDUI § tree item](sdui-protocol.md#item-shapes); a click or ↩ folds one, a folded one shows › after its label; Done and Won't do start folded). An open group shows its first 100 tasks (plus the selected one when it is further down), then a `faint` `action` row `Show 100 more · N left` (`Show N more` once 100 or fewer are left; id `more:<status>`) whose `select` shows the next 100, kept per workspace in memory until the group is folded; the count at the right is always the whole group. The tree also stays below the [SDUI node limit](sdui-protocol.md) (each row counts with its menu entries): when the open groups would pass it, as with a search that opens every group, the later rows wait behind the same more row. Rows sit on fixed columns: the priority mark (‼ high, ↓ low, the column kept blank for normal), the title, `#12` as the detail; the pinned row shows its status glyph in the mark column.
- Main: the task as an autosaving form. Its `header` is the title, edited in place (click it or ↩ on it; ↩ or leaving saves, Esc cancels; a bad title shows its error under it), the status glyph, "#12 · saved" as the muted meta ("#12 · not saved" while a field shows an error), then the actions. The primary one follows the owner (the plugin decides it, the client only draws it):
  - you own it (Todo or Idea, or In progress by you, or by a closed session): **Start agent** (⌘↩), which opens the Start popover (see Start agent below); In progress by you adds Release, by a closed session Take back;
  - an open agent session owns it: **Open ‹session›** (⌘↩) selects it in Agents; a session that is a node of a graph run reads **Open ‹run title›** and selects the run in Graphs (`agents.graph-reveal`); Take back next to it;
  - an external agent (an `owner` name) owns it: Take back only.

  Done (D), Won't do (W, a ghost button with the ⃠ glyph, not on a done or won't do task: opens a "Won't do #n" row under the form with a "Why it won't be done — ↩ closes the task" field (`reasonText`, focused) and Cancel; ↩ calls `backlog.close` with the text for the task the row belongs to (not the current selection), an empty one shows "Reason must not be empty" under the field, and a reason sent with no Won't do row open is ignored; the row menu's "Won't Do…" selects the task and opens the same field), Edit (E, only with a description: shows it as the multi-line field, then "Done editing" back) and Delete (⌘⌫, confirmed; a ghost button, red only in its confirm) follow. Five property rows follow: Status (S opens its menu), Priority (P), Tags (one field, comma- or space-separated; a bad tag shows its error under it), Owner and Note (a multi-line field: agents write it with `backlog_update note`, you here; the form's action `save.<id>.<version>` names the note version it was drawn with; the version goes up only when the note changes outside this form (an agent, the phone), never on your own saves; a save from an older version that still holds that version's text leaves the stored note alone, for a save already on its way when the agent's note arrived; any other note text is yours and is saved, clearing an agent's note too. A Note field you clicked into but didn't type in takes the agent's note at once (the `textField` rule in [SDUI § Forms](sdui-protocol.md#forms)), so changing Priority then keeps it; if you had typed, your text wins), then Last owner while there is one, then a rule and the description; the form autosaves. Owner and Last owner are chips when they are agent sessions (the session's title, `‹run title› · ‹session›` for a graph run's node, `(closed)` once closed) that open the session or the run like Open ‹owner›; you and external agents are plain text. Owner adds the live session's state from `agents.sessions` (`running · turn 3` from its `turns`, `waiting`, `idle`, `turn done`, `failed · exit 1` from its `failure`, `needs you`), when the current owner got the task and how (`since Nov 16 18:46 · created it`, `created by ‹session›` for a task an agent added, `claimed it`, `started`, `released`, `taken back`, `stopped`; `running · turn 3 · since Nov 3 15:03 · claimed it`), Last owner how it ended (`stopped · Nov 2 17:20`; a session that stopped from a failure: `stopped · exit 1` in red, no time (the chip opens the session), and the ⊗ glyph on its chip and on its dot in Owners).
- Links, under the description: "Links · N" with a ghost "+ Link" at its right that opens the link field (`linkText`; it closes again once a link is added, and stays open on an error), then Attachments with its drop field. Owners, last and only from 2 owner moves: a `lanes` node with one lane per owner in order of first appearance (you, each session, a graph run as `‹run title› · run`; at most 8, the most recent kept) and one move per entry of the owner history, each joined to the one before and labelled how it moved (`Start agent`, `claimed`, `released`, `done`, `taken back`, `stopped`; a session that stopped from a failure gets the ⊗ glyph in red on its lane, its dot in red and `failed → back` on the hop); a time axis under the lanes gives each move's time (`Nov 2 14:10` on the first and on a new day, `16:02` otherwise); the current owner's move is drawn as its glyph and the last hop in accent; the tooltip says who, how and when. A session or run move opens it (click, or ←/→ then ↩). It folds under `Owners · N moves` (h).
- Links and Attachments sit under the form, each a muted `Links · N` / `Attachments · N` row, a `list` of the entries and an add field. A link row reads `#8 Record missed runs` with `blocked by · done` and the other task's status glyph; clicking it selects that task, its menu has Remove link. The add field takes `blocks #3`, `blocked by #5`, `relates #7` (or `relates to`, `blocked_by`; a bare `#7` relates) and shows a bad one as its error. An attachment row shows its title or ref with `worktree`, `image`, `artifact` or `link` and Remove attachment in its menu; clicking it opens it as `backlog.get`'s `opens` says: a web link (any `http(s)` ref) in the Mac's browser, a Markdown, Mermaid or `.html` path in the docs viewer (`docs.open`), an image path in the Mac's default app (`open`, since the docs viewer shows no images), any other path in the editor (`editor.open`); a path is resolved against the workspace's first folder (its current worktree); the add field takes a worktree path or a URL (a claude.ai `/artifact/` URL or an `.html` path is an artifact, an image extension an image, other URLs a link, other paths a file). It is a drop zone (`textField` `drop`, dashed): files dropped on it become attachments with their path relative to the workspace's first folder, once their symlinks are resolved; a file outside that folder, or a folder, is refused with the field's error and nothing is added. A dropped web link fills the field; a pasted one is added with ↩ like a typed one. `@` in the empty field opens the workspace's file picker and attaches the picked file the same way.
- Take back makes you the owner and keeps the task In progress; the session (or agent) that had it becomes the last owner.
- A non-empty description shows rendered under the header (a `document` node, `size: fit`, rendered by `pkg/docrender`: tables, highlighted code, mermaid diagrams; `http(s)` links open outside the app; `#n` of an existing task, outside code and links, is a task link `clubmate-doc:/task/<n>` with the task's title as tooltip, and clicking it selects that task) after the property rows; Edit (E) in the header swaps it for the multi-line field and "Done editing" back. The flag is per workspace and holds only for the selected task. An empty description is the field. A change from anywhere (an agent, the phone) re-renders it on `backlog.changed`.
- Without tasks the main pane is a centred `empty` (`center`) "Nothing in the backlog" with one sentence on what tasks and Start agent are, a New task field with Add under it, and the lifecycle as disabled status chips, each row centred (a `stack` with `align: center`): Idea → Todo → In progress → Done, "or parks in Not now · In progress is owned by you or a session".
- Companion (iPhone/iPad): a Backlog item under each Mac with the same groups (Not now, Done and Won't do folded), a search field under the large title that hides as the list scrolls (stock `.searchable`; it asks the Mac `backlog.list {query}` and shows the tasks it returns in place: a number the Mac puts first is pinned in its own group "Task #n" with "Return opens #n", ↩ opens it; text matches stay in their status groups; "No task #n" when the number has no task), New Task (title, description, priority, status), and a task screen with the plugin's `primary` from `backlog.get` as its prominent button (Start agent with "Passes the description, 2 links, …" under it, calling `backlog.start`; Open ‹owner›, which opens that session in Agents; Take back, calling `backlog.takeback`), then Release (yours) or Take back (someone else's), Done, Won't do… (asks for the reason, then `backlog.close`; only when the Mac offers `backlog.close`), Move to and Edit; swipe and the context menu start an agent too. A Mac without `backlog.start` gets the old buttons (Start claims the task for you). The description comes from `descriptionHtml` with the shared document web view and its `#n` links open that task; a Mac that sends none gets it as plain Markdown. Links show as two-line rows (`#8 Record missed runs`, `blocked by · done`) that open the task; attachments as rows that open a web link in the browser and a `doc` in the docs sheet, while `editor` and `system` ones read "on the Mac". Above the buttons "In progress by ‹owner›" adds the plugin's `ownerState` ("· running · turn 3"), and a "Last owner: ‹who› · ‹what› · ‹time›" line (what in danger ink when `tone` is `danger`) shows `lastOwner` unless that owner still holds the task; after the attachments an "Owners · N" section lists `history` oldest first as who / what · time, and a row with a `session`, like the Last owner line, opens that session in Agents. It acts as you (owner `user`) and refreshes on `backlog.changed`. For the phone `backlog.get` (from the user, not an agent) also returns the words the Mac shows, decided in the plugin: `ownerState` (`running · turn 3`), `lastOwner` and `history` as `{who, what, at, tone?, session?}` lines (`Fix the flaky… · Start agent`, `you · stopped · exit 1` with `tone: danger`; a failed `lastOwner` has no `at`, like the Mac's line), and, when `primary` is Start agent, `primary.start` `{agents, modes, where, prompt, owns}`: the Start popover's options as `{value, label}`, the generated prompt and the ownership line.
- `backlog.reveal {id}` (hidden, not for agents or the phone) shows a task in the section: selects it, clears the tag chip when the task lacks that tag and the search when it doesn't match, unfolds its status group, renders and focuses the task tree with the cursor on it. An unknown number fails with `task not found: #<id>` and changes nothing. The agents plugin calls it when a `#n` task link in a transcript is clicked.
- ⌘N inside the section, the header's +, or "New backlog task" in the palette opens and focuses the New task field (`backlog.new` opens it, renders, then names its node, `title`, so the search field never takes it); `gc` in the task tree focuses the search field, the sidebar's first text field, also while the New task field is open. Delete is UI-only (row menu, confirmed).

Statuses: `idea`, `todo`, `in_progress`, `done`, `not_now`, `wont_do`. `wont_do` (Won't do, ⃠ `nosign`) closes a task that is no longer needed (obsolete, superseded, a duplicate, ruled out) without calling it done: like `done` it is not open (not in `status: open`, not in the "N open" and tag counts) and sorts with the done tasks, newest first. Only `backlog.close {id, reason}` sets it: the reason is required and is added to the note as `Won't do: <reason>` (after a blank line when the note has text); on a task already Won't do it changes nothing (the first reason stays, no `backlog.changed`); `backlog.update status=wont_do` is refused ("use backlog.close"), so no task is closed without a reason. Moving it back is a plain `backlog_update status` (or `backlog_done`); it can't be claimed or started. Priorities: `high`, `normal`, `low`. Tags: up to 10 per task, each one word of letters, digits, `-`, `_`, `.` or `/` and up to 32 characters, stored lowercase without a leading `#`, duplicates dropped; `backlog_update` with `tags` replaces them (`[]` clears). The phone shows tags only on the pinned row of a number search and searches them. Order is priority, then oldest first (done: newest first).

Links: `links` `[{kind, task}]` with kind `blocked_by` (this task waits for the other), `blocks` or `relates`, at most 20, one per other task, never to itself or to a task that doesn't exist. Links stay symmetric: setting `A blocks B` gives B `blocked_by A`, `relates` gives `relates` back, removing one removes the other, and deleting a task removes the links to it. Attachments: `attachments` `[{kind, ref, title?}]` with kind `file` (a path relative to the worktree, no `..`), `image` or `artifact` (a worktree path or an `http(s)` URL) or `url` (`http(s)`), at most 20. `backlog_update` with `links` or `attachments` replaces the list (`[]` clears).

## Start agent

Start agent (⌘↩) calls `agents.new` with the task title as the session title and a first prompt of `Backlog task #n: <title>`, the description, the links (`- blocked by #8 Record missed runs (done)`), the attachments (`- file design/check/fix-list.md`) and a closing line telling the session it owns the task and finishes with `backlog_done` or `backlog_release`. The new session (top level, in the workspace's first git folder) then owns the task: In progress, claimed by it, owner move `started`. It works on Todo and Idea, and on In progress while you or a closed session own it. The task is reserved while its session starts, so a second Start meanwhile (a double ↩, the Mac and the phone at once) fails `task #n is already getting an agent` instead of starting a second session.

On the Mac the button opens the Start popover (a `button` with a `form` child) before anything starts: Agent (Claude), Mode (Last used, the worktree's remembered mode, which is what Start did before; or Ask before edits, Accept edits, Plan, Bypass permissions, passed as `agents.new` `firstMode`; it holds until the session resumes, which takes the worktree's mode, so a mode to keep is set in the composer), Where (this worktree, or a new worktree on branch `backlog/<id>-<title slug>`, passed as `agents.new` `branch`; the existing branch is checked out when it is there), Prompt (what it passes, `description, 1 link, 1 file`, with Edit, which turns it into a field holding the generated prompt), the line "The session owns #n until it ends or you take it back." and Cancel ⎋ / Start ↩. Start sends the form to the plugin, which calls `agents.new`; an edited prompt replaces the title, description, links and attachments part, and the closing ownership line is always added. ⌘↩ on the task opens the popover, ↩ in it starts. On the phone Start agent on the task screen opens the same choices as a sheet ("Start agent on #n": Agent, Mode, Where from `primary.start`, Prompt with Edit, the ownership line as footer, Cancel / Start) and sends `backlog.start` with only what is set (an unedited prompt is left out); a Mac that sends no `primary.start` gets `backlog.start {id}`, and the list's swipe and context menu start with the defaults. A `ui.event` with `agent: true` that changes a task (start, takeback, release, done, status, priority, delete, the edit form's save, add, link/unlink, attach/detach, drop) is refused: the plugin runs those as you, so an agent could start a session in a mode it picks or skip the ownership checks; agents use the `backlog.*` commands, which act as them. Selecting, filtering, searching, folding and opening still work.

## Agent workflow

Agents use the MCP tools `backlog_list`, `backlog_get`, `backlog_add`, `backlog_update`, `backlog_claim`, `backlog_release`, `backlog_done`, `backlog_close`.

1. `backlog_list` with `status: todo`, take the first task (`backlog_get` for the full text).
2. `backlog_claim` it. If another owner holds it, the error says who; pick the next task.
3. Work. Record progress with `backlog_update` and a `note`.
4. Finish with `backlog_done` and a note naming the commit, or `backlog_release` (with a note) if you give up.

Agent calls get short replies, so a write doesn't echo the whole task back into the agent's context. An agent call is one with `agent: true` or a caller that is a session here (a plain `cm` from an agent's shell counts too, the same rule that keeps it from `backlog.start`). `backlog_add`, `backlog_update`, `backlog_claim`, `backlog_release`, `backlog_done` and `backlog_close` return `{id, title, status, priority, tags, claimedBy, cursor}` (`tags` and `claimedBy` left out when empty), and `backlog_list` returns rows `{id, title, status, priority, tags, claimedBy, updatedAt}`; `full: true` returns whole tasks, and `backlog_get` always returns the whole task. A failed write returns its error as before. `backlog.list` with `since` (the phone's sync) is the same for every caller, and the Mac, the phone and other plugins (`host.RunCommand` without the agent flag) keep getting whole tasks.

`backlog_list` defaults to `status: open` (idea + todo + in progress); `tag` keeps only tasks with that tag; `query` keeps the tasks the sidebar's search would (title, description, note, tags, or the number) and, without `status`, searches every status, done, not now and won't do included; a `query` that is only a number lists that task first (before `limit` cuts); `slim: true` leaves out `description` (the phone lists with it and fetches the open task with `backlog.get`). `backlog.list since=…` returns `{tasks, removed, order, cursor, delta}` over every status (done included; `status`, `tag`, `query` and `limit` are ignored, `slim` still applies): `since=""` gives every task and a `cursor`, an earlier `cursor` gives only the tasks that changed after it (`delta: true`) and the numbers `removed` since then; `order` is every task number in list order, so the phone never sorts: always in a full reply, in a delta only when the order changed after the cursor (the plugin keeps the order's hash as one more entry). Every write to a task bumps the workspace's counter inside the store, under its lock, so silent writes (a session's failure badge, the other side of a link, a task handed back when its session closed) count too. The counter, its epoch and one entry per task live in the plugin's storage (`delta/tasks/<workspace>/…`) and survive restarts; a save first marks the head dirty and clears it last, so a save cut off half way (or an entry that can't be read) starts a new epoch on the next load and every phone resyncs in full, never from a wrong delta. A failed counter save never fails the task write: it is logged and the counter moves to a new epoch at once. A delete removes the task before it records the removal; a cursor from another epoch (the counter was wiped with its workspace), above the head or older than the 256 removals kept gives everything again without `delta`. Writes to one task (`backlog.update`, `claim`, `release`, `done`, `start`, `takeback`) take an optional `seen`, the cursor of the list the write was made on: when that task changed after it the write is refused with reason `stale` and nothing changes; a change to another task never refuses it; a `seen` from another epoch, or one the plugin can't read, is refused too, since nothing proves the task is unchanged. Without `seen` (the Mac, agents) there is no check, and `backlog.add` is never refused. Each write's reply carries `cursor`, taken right after the write, so the phone's next write to the same task passes it as `seen` and is not refused by its own change; the phone never uses it as its list's `since`, which would skip other tasks' changes in between (see [remote § Phone outbox](remote.md#phone-outbox)). A resend of the same write (the link dropped before the reply) is not checked against `seen` here: the phone sends it with the same `requestId`, and [remote](remote.md) answers it with the stored outcome before the command reaches the plugin. `backlog.get` from the app or the phone also returns `descriptionHtml`, the description rendered (with `#n` task links `clubmate-doc:/task/<n>`), and `primary`, the primary action as the Mac draws it: `{action: start|reveal|takeback, label, summary?, session?, run?}` (absent for Done, Not now and Won't do); agents get neither. Every caller gets each attachment's `path` (the ref resolved against the workspace's first folder, for path refs) and `opens` (`url`, `doc`, `editor` or `system`). The user-only commands `backlog.start {id, agent?, mode?, where?, prompt?}` (Start agent with the popover's choices, each optional; returns `{session}`) and `backlog.takeback {id}` (returns the task) are what the phone calls; agents can't run them, and neither can a plain `cm` from an agent's shell (a caller that is a session here, or one the session list cannot check), like the buttons.

A task an agent finds goes in with `backlog_add` as `idea` by default; an agent may add or move a task to `todo` (e.g. when the user asks it to). Nobody sets `in_progress` through update (claim does that). To park a task use `not_now`; to close one that won't be done use `backlog_close` with a reason.

## Owners

Every task keeps its owner history, `owners` in `backlog_get`: moves `{owner, title?, run?, runTitle?, at, why, failure?}`, oldest first, at most 100 (the first kept). A new task starts with you (`created`); `started` (Start agent), `claimed` (backlog_claim, also a stale take-over) move it to the claimer; `released`, `done`, `won't do` (backlog_close of an In progress task), `taken back` and `stopped` move it back to you. A move to the owner the task already has is not recorded. A session owner stores its title and, when it is a graph run's node, the run's id and title. Tasks from before the history have none stored and read as you since creation, then the last owner and the current one (no migration). `backlog_list` leaves `owners` out.

- Hosted agent session (`agt_…`), also through `cm` in its shell, which sends `CLUBMATE_AGENT_SESSION`: the owner is that session; any `owner` argument is ignored.
- External agent (for example Claude Code connected with `clubmate mcp` in a terminal): pass `owner`, a name unique to you such as your session id; `user`, `agent` and names starting with `agt_` are rejected. Its claims never go stale.
- You (UI, palette, `cm command run` without `--agent` outside an agent session): the owner is `user`.

Release is allowed to the owner, an ancestor agent session of the owner (an orchestrator closing its children's tasks) and the user. Done and close (won't do) are allowed to them too, and to anyone when the task is unclaimed or its claim is stale. A stale claim is taken over with claim. A task claimed by someone else can only get a new title, description, priority, tags, links, attachments or note from other agents, not a new status.

## Stale claims

When an agent session that owns an In progress task is closed or deleted (`agents.changed`), the task goes back to the status it was claimed from and to you (owner move `stopped`, the session as `lastClaimedBy`). The session's failure is kept on that move as `failure` (`exit 1`, or `error` for one without an exit status): while an owner session's status is `error` (`agents.changed` kind `status`) the plugin notes its `failure` badge from `agents.sessions` on the session's own move, clears it when the session runs again, and copies it to the `stopped` move, since a closed session no longer carries its error. Nothing else changes status on its own. A claim by an `agt_…` session is stale when that session is closed or no longer listed (for instance when the backlog plugin missed the close). The UI shows it as "<title> (closed)" so you can mark the task done or move it back. Claiming a task with a stale claim takes it over, and the previous owner is kept as `lastClaimedBy`. If the agents plugin can't be asked, claims are treated as live.

## Examples

```sh
cm command run backlog.list --agent status=todo
cm command run backlog.get --agent id=12
cm command run backlog.claim --agent id=12 owner=my-session
cm command run backlog.update --agent id=12 note="parser done, tests next"
cm command run backlog.done --agent id=12 owner=my-session note="abc1234 fix parser"
cm command run backlog.add --agent title="Flaky bus test" status=idea
cm command run backlog.update --agent id=12 tags=voice,phone
cm command run backlog.list --agent tag=voice
cm command run backlog.list --agent query="flaky bus"
cm command run backlog.update --agent id=12 'links=[{"kind":"blocked_by","task":8}]'
cm command run backlog.update --agent id=12 'attachments=[{"kind":"file","ref":"design/check/fix-list.md"}]'
```

An array of objects goes to `cm command run` as one JSON array.

Prefer the MCP tools inside an agent session: `cm command run` without `--agent` counts as the user.
